Chapter 3 · Part I · Landscape and Mental Models

Assembling a Runtime: boot, profiles, bundles, patch layers

You type dsh web, press Enter, the browser opens — and in those few seconds a plugin tree grew from nothing. This chapter traces that growth: the profile decides which layers stack, a bundle is each layer's distribution format, and patches rewrite rows layer by layer by id. After this chapter you can explain every plugin row running inside any dsh process on your machine.

Learning objectives
  • Break one dsh launch into: pick a profile → stack bundle layers per dsh.profile → apply patch layers → Loader mounts
  • State the role of each file in a profile directory ($DSH_HOME/profiles/<name>/)
  • Explain what a bundle is and why dsh-base is the first layer of every profile
  • Predict a row's final config from the correct layer order (bundle → profile patch → home patch → --patch)
  • Inspect the composed result with your own eyes via --dump-config and write your first cordis.patch.yml

3.1 Boot is assembly

First, correct an assumption you might carry in: dsh is not 「one compiled big program that loads all its features at startup」. The accurate statement is the architecture document's first sentence: a running dsh is a plugin tree assembled at boot from ordered layers. Each row in the tree is a plugin — the kind from Chapter 2, with inject, a key in ctx, and events for communication.

Break dsh web into steps:

  1. Pick the profile: the launcher (apps/cli) parses its own flags and determines it will start the web profile;
  2. Resolve the layer list: read the profile's dsh.profile to get an ordered bundle list;
  3. Compose the entry list: start from an empty list, each bundle contributes a batch of plugin rows, then your patch layers go on top;
  4. Mount: the Cordis Loader mounts these rows according to inject dependencies (Chapter 2's mechanism);
  5. Assert: boot glue (packages/boot/app-boot) verifies that every enabled row actually activated — anything that failed to mount is named in the error.

This chapter's protagonists are steps 2 and 3: where layers come from, in what order they stack, and who overrides whom. Steps 4 and 5 are covered in Chapter 18 (CLI and boot).

3.2 Profiles: named compositions in the Harness home

A profile is a named composition stored in the Harness home. The Harness home is set by the environment variable $DSH_HOME, defaulting to ~/.dsh. Each profile occupies one directory: 

~/.dsh/                       # Harness home ($DSH_HOME, default ~/.dsh)
├── cordis.patch.yml         # home-level patch layer (above all profiles, global to your machine)
└── profiles/
    └── web/                 # one profile = one directory
        ├── package.json     # dsh.profile (the bundle order list) + out-of-tree plugin dependencies
        └── cordis.patch.yml # this profile's own patch layer

The package.json in a profile directory serves two purposes:

  • The dsh.profile field: an ordered bundle list whose order is the layer order;
  • dependencies: where your own (out-of-tree) plugins get installed, managed for you by the dsh plugin command.

web and headless ship with the product as templates and initialize automatically on first use; other names do not exist out of thin air — you must first create one and install plugins with dsh plugin --profile <name> <pnpm args>. Launching a nonexistent profile fails on the spot (fails loud, see 3.6).

Both 「one-shot」 and 「long-lived」 start here

Chapter 1's two forms line up here: dsh web starts the web profile (a long-lived browser app); dsh --profile headless "task" starts the headless profile (a one-shot runner that exits when done). They are not two programs but two different layer stacks.

3.3 Bundles: installable layers

A bundle is a distribution format: an npm package carrying a batch of Cordis configuration rows plus the code those rows mount. The key is 「distribution format」 — rows a bundle inserts hold no privilege; like any other row they can be rewritten by id from the layers above it. That is exactly the property the architecture document stresses: everything a bundle inserts stays modifiable by patches from higher layers.

How does a package declare itself a bundle? Point at a patch file under the dsh field in package.json:

// packages/bundle/base/package.json (illustrative)
{
  "name": "@deepseek-ai/dsh-base",
  "dsh": {
    "bundle": { "patch": "./cordis.patch.yml" }
  }
}

The product ships three bundles, each with a distinct role:

bundleRole
@deepseek-ai/dsh-base The first layer of every profile (about 78 rows): model adapters (llm-deepseek), default model selection (agent-default-model), tools (including tool-bash), persistence (session-persistence-jsonl), sandbox and approval policy (bash-sandbox and friends), settings, credentials, telemetry. However customized a profile is, it stacks upward from this layer.
@deepseek-ai/dsh-web-app Adds the browser app on top of base: the web server, API gateway, workspace, the full set of browser plugins, and the coding persona (system-prompt's persona is set in this layer, not in base).
@deepseek-ai/dsh-headless Adds the one-shot runner on top of base: HMR disabled, the Code Mode worker mounted, and no Host, HTTP server, or browser plugin at all.

Why does persona live in web-app rather than base? Because base's rows are shared by every mode while persona is a mode-specific value — dsh's layering discipline: mode-specific values live in the mode's bundle, and base stays neutral. The cost and payoff of that discipline show up immediately in patch semantics.

3.4 Layer order: from the empty list to the final tree

All layers stack onto the same empty entry list, in a fixed order:

  1. The bundles the profile lists, in the order written in dsh.profile.bundles (e.g. base → web-app);
  2. The profile's own cordis.patch.yml;
  3. The home-level $DSH_HOME/cordis.patch.yml;
  4. The command-line --patch overlay (if any).

A 「patch」 can do two things, and only two things:

  • Replace a row's entire config by id — note this is whole-row replacement, no deep merge. Fields you want to keep must be restated verbatim; omitted fields are gone. This is not laziness but intent: whole-row replacement means a row's final form is determined solely by 「the last layer that touched it」, with no multi-layer merge arithmetic in your head.
  • insert adds new rows — new plugins (your own or third-party installed) enter the tree here.

A real example (packages/bundle/web-app/cordis.patch.yml, excerpt) — as the later layer, web-app rewrites rows already present in base and inserts its own new rows: 

# packages/bundle/web-app/cordis.patch.yml (excerpt)
- id: system-prompt          # replaces the entire config of this row from base
  config:
    persona: >-
      You are a coding agent powered by the {{model}} model.
      Your working directory is {{cwd}}.

- id: hmr                     # or simply disable this row
  disabled: true

- insert:                        # insert new rows only web needs
  - id: storage
    name: '@deepseek-ai/dsh-storage'
  …

How to predict a row's final config

Scan the layer order bottom-up and find the last layer that touches this id: if it replaced the config, the final config is exactly what it wrote (any field it did not restate falls back to the plugin code's default, not to a lower layer's value); if nobody touched it, the original value from the bundle's insert applies. 「Last write wins」 operates per row — different rows can come from different layers.

3.5 See it yourself: dump your tree

No need to simulate in your head. This command prints the composed result verbatim and starts nothing:

dsh --profile web --dump-config

It composes offline with exactly the same resolution and patch algorithms as a real boot (so what it prints necessarily matches what you would start), and !!js expressions are preserved verbatim. The architecture document's next sentence is this chapter's key: any row it prints can be replaced by your own patch.

Write your first patch. In ~/.dsh/profiles/web/cordis.patch.yml (illustrative):

# ~/.dsh/profiles/web/cordis.patch.yml (illustrative)
- id: agent-default-model     # this row in base was originally deepseek-v4-flash
  config:
    provider: deepseek-official
    model: deepseek-v4-pro       # whole-row replace: both fields restated

- insert:                        # mount one more plugin of your own
  - id: my-weather
    name: '@your-scope/dsh-my-weather'

Save it and run --dump-config again, then diff the outputs: the agent-default-model row changed and my-weather appeared. Changing the running product required forking no code — this is what Chapter 2's 「no privileged core to patch」 feels like in your hands.

3.6 Fails loud; takes effect on save

The assembly mechanism is this flexible — what happens on error? dsh's position is a principle that runs through the repository: misconfiguration fails loud. Errors provable at load time are reported at load time; boot's startup glue tears down the half-mounted tree and refuses to start rather than limping along crippled. Applied to this chapter's mechanisms:

  • The profile list names a package with no bundle declaration → resolution fails, naming it;
  • cordis.patch.yml is an empty file or comments only → it throws outright (it parses as nothing-at-all rather than an empty list; to disable this layer, write []);
  • A patch points at an id not in the tree → an stderr warning (hinting you may have mistyped the id);
  • A row is declared but never activates (a dependency service stays absent) → the startup assertion names every plugin that failed to mount.

One more, crucial for the development experience: every profile startup watches your patch files for changes (HMR watch). Save cordis.patch.yml and the tree re-assembles in place under the same layer order; if the new content is unreadable or unparseable, the last good tree keeps running and the failure is broadcast — one slip of the hand cannot crash the running session.

A real case that shows the value of failing loud: base's patch gates two shell sets with a platform expression — tool-bash/bash-sandbox carry disabled: !!js process.platform === 'win32' (bash has no Windows runner), and their twin rows tool-pwsh/pwsh-sandbox the reverse. To restore bash on your machine you must complete the whole recipe (disable both pwsh rows and enable both bash rows); do only half and the two executor families register the same bash service — loading fails on the spot and tells you why. Succeeding halfway silently, leaving a half-crippled tree, is the worst outcome a system like this can have.

3.7 Chapter recap

  • A running dsh = a plugin tree assembled at boot from ordered layers: pick profile → stack bundles per dsh.profile → apply patches → the Loader mounts per inject dependencies → startup assertion.
  • A profile is a named composition in the Harness home ($DSH_HOME, default ~/.dsh): under profiles/<name>/, a package.json (dsh.profile bundle order list + plugin dependencies) and a cordis.patch.yml. web and headless ship as product templates and initialize automatically on first use; other profiles are created with dsh plugin.
  • A bundle = a distribution format of Cordis config rows plus mounted code; package.json's dsh.bundle field points at the patch file; the rows it inserts remain rewritable from layers above.
  • dsh-base is the first layer of every profile: model adapters, default model, tools, persistence, sandbox and approval policy, settings, credentials, telemetry. dsh-web-app adds the browser app; dsh-headless adds the one-shot runner with no server.
  • Layer order: empty entry list → bundles (in the profile's listed order) → profile patch → home-level patch → --patch overlay. Patches locate by id and either whole-row replace (no deep merge; kept fields must be restated) or insert new rows; for the same row, the later layer wins.
  • dsh --profile web --dump-config prints the composed result offline with the same algorithms as boot; any printed row can be replaced by your patch. HMR watches patch files: save to re-assemble; broken content keeps the last good tree.
  • Fails loud: no bundle declaration, empty or comments-only patch files, a half-finished shell-restore recipe… all error at load time, never leaving silent damage.
Common pitfalls
  • Assuming patches deep-merge — an id patch replaces the entire row's config; fields you keep must be restated verbatim.
  • Editing packages/bundle/base/cordis.patch.yml to change product behavior — that is a released artifact; your rewrites belong in profile / home patch layers, which win by layer order.
  • Launching a profile name that was never created — only web and headless auto-initialize; everything else needs dsh plugin first.
  • Assuming --dump-config starts services — it purely composes and prints offline, starting not one process.
  • Mistyping a patch id and ignoring stderr — a patch matching no row is a warning, not an error; the tree starts as usual and silently lacks the rewrite you thought you made.
  • Emptying cordis.patch.yml to disable a patch layer — an empty or comments-only file throws; writing [] is the explicit disable.
