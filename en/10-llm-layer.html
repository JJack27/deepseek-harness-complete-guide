Chapter 10 · Part II · The Core Spine

The LLM Capability Layer: The Adapter Seam and Streaming Vocabulary

The last two chapters both ended at the same call: ctx.llm.stream(request). This chapter covers the world behind it — how packages/llm/ defines a vendor-neutral message and streaming vocabulary, how adapters swap in and out like plugs, how streaming chunks become assistant/message in the log, and how much code it really takes to switch model vendors (the answer: one new adapter plugin).

Learning objectives
  • State the dual identity of ctx.llm: adapter registry + unified streaming call API
  • Recite the message vocabulary: Message, content blocks, the StreamChunk protocol, and BlockAssembler
  • Describe how a streaming reply enters the log via llm/stream → assistant/chunk* → assistant/message
  • State the division of labor among the llm group's five packages: llm / llm-deepseek / llm-pi-ai / llm-retry / token-meter
  • Explain how ctx.agentDefaultModel relates to prepareCall() / request/header

10.1 ctx.llm: an adapter seam

The LlmRuntime service from packages/llm/llm hangs on ctx.llm. It is the LLM-domain instance of the capability seam that Chapter 11 will formally name: a vendor-neutral message and streaming vocabulary (the language all packages speak) plus an adapter registry (replaceable implementations).

There is exactly one core registration API: 

const handle = ctx.llm.registerAdapter(['deepseek-official'], adapter)
// all-or-nothing: one provider route has at most one adapter at a time (a duplicate name throws DUPLICATE_ADAPTER)
// handle.dispose() unregisters; handle.replace(providers) swaps the route atomically, with no gap

Requests select the adapter via GenerateOptions.provider; model is interpreted by the adapter itself (the catalog is advisory — unlisted model ids pass through as-is). The companion query surface: listProviders() / listModels(provider) / resolveModelInfo(provider, model) (to get an exact model's context window, output defaults, and reasoning tiers) — these are discovery surfaces for picker UIs, not routing whitelists.

Switching model vendors = writing one new adapter plugin (extend LlmAdapter, implement stream(), optionally implement the metadata methods), registering a few provider routes, done. Not one line of the loop, session, tools, or UI changes — this is precisely where Chapter 3's assembly and Chapter 11's seam pay off.

10.2 The message and streaming vocabulary

docs/subsystems/llm-streaming.md is this layer's dictionary. Three levels of vocabulary, coarse to fine:

  • Message: an immutable value with a stable MessageId, a role (system/user/assistant), and an array of content blocks. A model-produced assistant message carries provider, model, and the optional adapter-private replayState in its source. The constructors (createUserMessage / createAssistantMessage / createToolResultMessage) produce deep-frozen values — messages are immutable from birth.
  • content blocks: message content is an array of typed blocks — text, reasoning (thinking, distinct from visible text), tool-call (carrying a CallId, a name, and the raw JSON argument string), tool-result (nested content + isError). The block union comes from the merge-extensible ContentBlockMap — a new modality (images and the like) enters the core map only when the adapter/UI/compaction/replay paths all support it.
  • The StreamChunk raw stream protocol: adapters emit not messages but seven raw block kinds — block-start / text-delta / reasoning-delta / tool-call-delta / block-end / usage / finish (usage precedes finish). Each stream has exactly one terminal finish; operational failures end with a finish of {kind:'error'|'aborted', failure} and never throw across the stream API — the consistent convention at service boundaries.

BlockAssembler is what assembles chunks back into messages — the repository's single assembly implementation, shared with the agent loop. This design of 'raw chunk protocol + shared assembler' means: any new adapter that can speak the chunk language gets UI token-by-token rendering, chunk-faithful logging, and message finalization all working automatically.

10.3 How streaming enters the log

Zoom the Chapter 7 call chain into the LLM layer (step() in agent.ts):

Three key points:

  • Dual-track consumption: the loop logs each chunk as assistant/chunk (preserving streaming fidelity and UI replay) while feeding BlockAssembler to accumulate blocks. Only when the stream reaches finish normally is one assistant/message event assembled — it is the only assistant surface that participates in deriveMessages().
  • Failure produces no message: when the terminal finish is error/aborted, the agent/request-error waterfall comes first (Chapter 7: keep the original error by default; returning {kind:'retry'} re-issues within the same step). The failed attempt's chunks stay in the log but are never assembled into a message, so the model history is unpolluted. Even a max-tokens-truncated reply with empty content still gets a message event (recording usage and an empty chunk-reference list).
  • llm/stream is a waterfall: cache, logging, and routing plugins wrap here; listeners must call next(). The request object is deep-frozen and marked with sessionId by the loop (markAgentLoopRequest()); Chapter 7's invariant validates 'request ⟺ log-derived' consistency at exactly this gate.

10.4 ReplayEnvelope: adapter-private replay state

A practical problem: when a historical assistant message again faces the adapter that originally produced it, that adapter holds private facts it could reuse — native response ids, the native stop reason, per-block provider-side metadata. The harness cannot read those fields, and should not. dsh's answer (docs/subsystems/llm-streaming.md) is: replay state is adapter-private; only its split is shared vocabulary:

  • A successful terminal finish chunk may carry a replayState (a ReplayEnvelope): response-level private metadata plus an optional array of per-block entries, aligned one-to-one with the emitted blocks in first-seen order. Both halves stay opaque to the harness.
  • What is shared is only the split itself: when BlockAssembler drops a block, the per-block entry at the same position is dropped too; if the entry count does not match the emitted block count, the whole envelope is discarded; an adapter whose metadata is independent of block structure may simply omit the blocks field. The result: stored metadata always describes stored content. The loop stores the pruned envelope alongside the assembled assistant/message in the log.
  • On a later request, LlmRuntime passes the state back only when the historical provider and the target provider are currently registered to the same adapter instance; that adapter validates it and owns any cross-model or cross-provider conversion. Other adapters receive the provider-neutral content plus provider/model fields, without the private state.
  • Durable content stays authoritative: an adapter that cannot use the state stored under its name degrades that one message to provider-neutral conversion with a diagnostic — the request itself does not fail.

The most instructive rule here is that one keep/drop decision covers content and metadata together: a max-tokens finish drops every tool call (a truncated call is unsafe to execute), and the same decision prunes the replay envelope's per-block entry at each dropped position — blocks() and replayState can never disagree, whatever assembly removes.

10.5 The llm group's five packages

PackageRoleKey points
dsh-llm vocabulary + service the Message / StreamChunk / BlockAssembler / HarnessError families; the ctx.llm registry and streaming API
dsh-llm-deepseek the official DeepSeek adapter exclusively owns the deepseek-official route; direct fetch + SSE (eventsource-parser frame decoding); credentials read apiKeyEnv via ctx.credentials (default DEEPSEEK_API_KEY), baseURL defaults to DEEPSEEK_BASE_URL then falls back to the public endpoint; thinking/reasoningEffort, maxTokens (default 256000), idle read timeout, and more are all config
dsh-llm-pi-ai the multi-provider adapter turns any provider/profile (including OpenAI-compatible gateways and self-hosted endpoints) into a configuration declaration via @earendil-works/pi-ai — route names deliberately differ from the official ones (e.g. pi-ai's deepseek) so both adapters can coexist
dsh-llm-retry the retry executor does not wrap ctx.llm.stream(); hangs on agent/request-error and retries with backoff per each provider's retryPolicy, landing llm/retry / llm/retry-started durable events around the wait
dsh-token-meter token metering ctx.tokenMeter folds usage per session from the log (a fixed 4-chars/token heuristic), shared by pressure-sensitive plugins like compaction; optionally exposes tokenUsage / contextPressure / contextBreakdown projections

The two designs — 'retry does not wrap stream' and 'metering folds from the log' — embody the same principle: every cross-boundary observable fact takes the log as its source of truth; in-process wrapping only does policy. Note also the pairings: llm-retry consumes the retryPolicy carried by the adapter registration; token-meter reuses the provider-reported usage (the usage field in assistant/message), falling back to heuristic estimation only when they cannot be aligned.

10.6 Request configuration: from default model to request/header

Where does an agent's provider/model come from? Entry points (such as dsh --profile headless, or the Host-side ApiProxy), when creating an Agent with no session-local selection, read ctx.agentDefaultModel provided by packages/core/agent-default-model: the plugin config requires {provider, model}; currentSelection() returns the current selection (a settings provider may layer user choice on top of it); saveSelection() persists the full user selection. It does not validate catalog membership — 'is this model available' is diagnosed by whichever party actually opens the request.

Once chosen, how does the configuration become a request? Chapter 7 already showed the buildRequest() skeleton; here are the LLM-side details:

  1. The agent/request waterfall proposes an LlmCallConfig (provider/model/reasoningEffort/temperature/maxTokens/stop — session-level state, not knobs to tweak casually).
  2. ctx.llm.prepareCall(config) performs an exact-model lookup: validates explicit effort, materializes adapter defaults (which fields came from defaults is recorded in the adapterDefaults marker), and binds the current adapter registration and immutable retryPolicy into a one-shot PreparedLlmCall — afterwards, even an HMR adapter swap cannot splice vendor A's capability query with vendor B's request.
  3. The loop lands the effective configuration in the log as a request/header event (the first entry's reason is initial/resume; afterwards change lands only on actual change); provider/model/context-window changes additionally land a request/context event. The next proposal omits fields marked as adapter defaults — after a route switch, each field is resolved fresh, unpolluted by stale defaults.

So 'how the model was called at the time', like 'what the model saw at the time', is fully reconstructible from the log. A side note on the test channel: real-API e2e tests read DEEPSEEK_API_KEY (optionally DEEPSEEK_BASE_URL) and self-skip without a key — credentials never enter configuration files; they resolve by reference through ctx.credentials.

The key intuition of this chapter

The LLM layer compresses 'vendor differences' into the single point of the adapter, 'streaming facts' into the two events chunk and message, and 'call configuration' into the single log line request/header. With those three done, the rest of the system can be completely oblivious to 'which model, which vendor'.

10.7 Chapter recap

  • ctx.llm = vendor-neutral vocabulary + adapter registry; registerAdapter(providers, adapter) allows one adapter per provider route — switching vendors is switching plugins.
  • Three vocabulary levels: Message (immutable, with id/role/source) → content blocks (text/reasoning/tool-call/tool-result, merge-extensible) → the StreamChunk raw stream protocol (seven block kinds, exactly one terminal finish; failures also go through finish instead of throwing).
  • BlockAssembler is the single assembler; chunks are consumed on two tracks: landing assistant/chunk for fidelity + accumulating blocks; only on stream termination does one assistant/message land, and deriveMessages recognizes only message.
  • A successful finish may carry a ReplayEnvelope (adapter-private replay state): assembly prunes per-block entries as it drops blocks; only the same adapter instance gets it back, and an unreadable state degrades to provider-neutral conversion instead of failing.
  • llm group division of labor: llm (vocabulary/service), llm-deepseek (the deepseek-official route), llm-pi-ai (multi-provider), llm-retry (hangs on agent/request-error, lands llm/retry events), token-meter (folds usage from the log).
  • ctx.agentDefaultModel gives entry points the deployment default; prepareCall() binds exact-model defaults and the retryPolicy; effective configuration lands in the log as request/header, with adapter-default fields marked and re-resolved on route switches.
  • e2e tests read DEEPSEEK_API_KEY / DEEPSEEK_BASE_URL and self-skip without a key; credentials resolve by reference via ctx.credentials.
Common pitfalls
  • Assuming an adapter failure throws across the boundary — it does not: all failures are normalized into the stream's terminal finish (error/aborted), and consumers discard the unfinished blocks.
  • Treating listModels() as a routing whitelist — the catalog is an advisory discovery surface; unlisted model ids pass through as-is.
  • Mutating the request inside an llm/stream listener or forgetting next() — requests are deep-frozen (loop requests are additionally invariant-checked), and forgetting next() short-circuits the whole chain.
  • Assuming retry is a resend loop wrapped around stream — llm-retry hangs on agent/request-error; every adapter call is exactly one vendor attempt.
  • Assuming request/header lands every step — it lands only on the first entry (initial/resume) and on actual change (change); sampling configuration is session-level state, not a per-step knob.
