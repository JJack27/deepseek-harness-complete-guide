Chapter 5 · Part II · The Core Spine

Persistence: JSONL/SQLite Backends and Versioning

The previous chapter's SessionEvent log is the live truth, alive in process memory. This chapter covers how it becomes durable (crash-surviving): an abstract persistence seam (ctx.sessionPersistence), two interchangeable backends (JSONL and SQLite), two-layer versioning with a reject-on-mismatch loading policy, crash recovery, and the projections, titles, and telemetry derived from the same log. After this chapter you can answer where dsh stores your sessions, in what format, and what happens when versions change.

What you'll be able to do
  • Describe the persistence seam's responsibility boundary: write-behind batching, the revision token, and what prepare/load/inspect/readFrom each solve
  • State the two backends' physical forms: one transcript file per session for JSONL; SQLite's three tables with one row per event
  • Distinguish the two versioning layers: SessionHeader.version (currently 0) covers the event vocabulary, SQLite SCHEMA_VERSION (currently 15) covers the table layout — both reject rather than migrate
  • Explain why crash recovery 「closes out orphan turns」 instead of truncating the log
  • List where log-derived state goes (the projection cache's cold-read ladder, titles, telemetry) and where non-session data goes (the ctx.storage hub)

5.1 The in-memory log is the live truth; persistence is a seam

Pin down last chapter's division once more: SessionStore (ctx.sessions) deliberately implements no persistence. Disk is a plugin's business — the persistence plugin subscribes to session/event (a synchronous notification; the plugin copies events into its own buffer without blocking the producer) and drains at session/flush checkpoints. The abstract service is ctx.sessionPersistence (package packages/session/session-persistence), a standard capability seam: a Service Definition declares the interface, two Service Providers implement it, several Consumers use it — the same SessionEvent vocabulary, with no second persistence event type to keep in sync.

The interface surface (all in session-persistence/src/index.ts), remembered by use case:

  • locate(meta): synchronously resolves where a session's artifact lives — no reading, creating, or flushing. JSONL returns the transcript's absolute path; SQLite returns undefined (all sessions share one database).
  • create(meta) / append(id, events): register header metadata / persist a batch of contiguous events. append resolves only after durability completes.
  • prepare(id): for resume — takes out an unpublished SessionPreparation (the one from 4.8 last chapter), commits repair, and reserves exclusivity.
  • load(id) / inspect(id): load the balanced logical view (committing cold recovery) / inspect read-only without writing recovery.
  • readFrom(id, fromSeq): read the stored suffix from a seq — for read models that continue from a watermark.
  • list() / listSnapshots(): lightweight enumeration reading only header metadata, without parsing full logs.

The coordinator and write-behind batching

The two backends do not each invent buffering: session-persistence/src/coordinator.ts provides shared buffering, serialization, repair, and disposal orchestration (a third-party backend may also implement the seam directly). The batching policy lives in write-behind.ts:

  • The first pending event starts a fixed batch window (200ms by default, configurable via writeBatchMaxDelayMs); later events within the window join the same batch without resetting the deadline.
  • When the window expires it triggers one durable batch write; events arriving during the write get their own new window, forming subsequent batches.
  • session/flush cancels the wait and drains to quiescence — which is why the loop treats it as an ordering and error-observation checkpoint before claiming the next ordinary turn.
  • On a background write failure, events are retained and automatic retry pauses; a new event restarts the window, and an explicit flush retries immediately and reports the failure through agent/error and the log — it is never written into an already-closed turn as a session event.

revision (revision.ts, SessionPersistenceRevision) is an opaque token of the backend's own representation: it identifies both which storage source and which version of that source, changing transactionally with each append or repairing load. Consumers of derived state compare this cheap token before loading the full log — if equal, no re-read is needed. Callers only test equality; they never interpret its internals.

5.2 The JSONL backend: one transcript file per session

packages/session/session-persistence-jsonl stores each session as one append-only logical JSONL log. On-disk layout: 

<root>/
  --<normalized-cwd>--/        # human-readable project directory (_no-cwd/ when no cwd)
    <encoded-session-id>/      # the session's own directory
      session.jsonl.zstd       # default: a sequence of checksummed zstd frames
      session.jsonl            # only when compression: 'none'

Three things about the logical content are worth remembering:

  • The first line is the SessionHeader (tagged { type: 'session', ... }); after it, one stored record per line, with seq contiguous across the entire decoded log (events[i].seq === i). assistant/chunk loses not one entry.
  • packed chunk row: with the default on (packChunks: true), runs of ≥3 assistant/chunk deltas for the same block pack into one row (text-chunks / reasoning-chunks / tool-call-chunks — slash-free bare tags that cannot be confused with event types), using seq0/time0 + per-member dt to reconstruct each member's seq/time exactly — measured to shrink the logical log by roughly 60%. Reads are layout-blind: packed, unpacked, and mixed files load to identical results. This is a working instance of last chapter's contract — the persistence layer may choose its encoding, but load must return the exact events.
  • Physical encoding: the default is a concatenation of checksummed Zstandard frames — one frame for the header line, then one frame per durable batch. compression: 'none' keeps raw newline-delimited text. A root belongs to exactly one encoding; mixed suffixes are rejected, not ignored.

One deliberate 「no default」 in configuration: root is required. Defaulting it to process.cwd() would let files drift with the process's cwd (bash calls and subprocesses both change it), scattering sessions everywhere. It is the textbook case of the explicit-over-implicit convention.

5.3 The SQLite backend: one row per event

packages/session/session-persistence-sqlite uses Node's built-in node:sqlite (DatabaseSync); the DDL lives in src/schema.ts, three tables: 

CREATE TABLE persistence_state (   # store identity: singleton row + random store_id
  singleton INTEGER PRIMARY KEY CHECK (singleton = 1),
  store_id  TEXT NOT NULL) STRICT;

CREATE TABLE sessions (              # session metadata table = SessionHeader
  id TEXT PRIMARY KEY, version INTEGER NOT NULL, created_at INTEGER NOT NULL,
  cwd TEXT, parent_session TEXT, seed_length INTEGER, origin TEXT,
  delegation_depth INTEGER, agent_preset TEXT,
  incarnation TEXT NOT NULL,          # stable identity assigned at materialization
  revision   INTEGER NOT NULL) STRICT;   # monotonic log-change token

CREATE TABLE events (                # events table: one row per SessionEvent
  session_id TEXT NOT NULL REFERENCES sessions(id) ON DELETE CASCADE,
  seq INTEGER NOT NULL, type TEXT NOT NULL, time INTEGER NOT NULL,
  data TEXT NOT NULL,               # JSON text of the event data
  source_event_seqs TEXT,       # JSON-encoded number[], or NULL
  surface_op TEXT,                # JSON-encoded SurfaceOp, or NULL
  ignorable  INTEGER,              # 1 when the marker is present
  PRIMARY KEY (session_id, seq)) STRICT;

The row fields (session_id, seq, type, time, data, source_event_seqs, surface_op) map 1:1 onto the event, including the optional surface metadata — hence 「no second persistence schema to maintain」. A few behavioral details:

  • Lazy materialization: the sessions row is written only on the first append. A session created but never written to does not exist in list() — abandoned sessions leave no trace, symmetric with JSONL's 「no file until first append」.
  • Journal mode: wal by default; rollback-journal modes (delete/truncate/persist) are kept for filesystems where the WAL shared-memory file is unavailable (network mounts). memory/ off are excluded — silently discarding log durability contradicts this backend's promise.
  • locate() returns undefined (one shared database, no per-session artifact); it therefore also lacks raw-artifact reads (supportsRawArtifacts === false), while JSONL's readRaw can replay the exact bytes it wrote.
  • revision's SQLite shape: the revision column in the sessions row, monotonically +1 per changing transaction; store_id keeps revisions from different backend instances from ever colliding.

5.4 Two-layer versioning: reject, don't migrate

dsh's version policy is one sentence: a log you cannot read must be rejected — never quietly guessed at. In implementation, each of the two layers guards its own ground:

The session-format layerThe SQLite schema layer
Where the version livesSessionHeader.version, stamped from SESSION_FORMAT_VERSION at creationPRAGMA user_version (SCHEMA_VERSION) + PRAGMA application_id
Current value0 (pinned during pre-release: no compatibility promise)15 (monotonically increasing; application id 0x44534850)
What it coversThe structural semantics of the event vocabulary and envelope (header shape, envelope, core event semantics, the surface mechanism)The table layout (how the three tables grow)
On mismatchThrows SessionFormatUnsupportedError, with direction-aware wording: higher = written by a newer harness — upgrade the harness; lower = this build has no upgrade pathRefuses to open the database; user_version 0 with a non-empty database, or any version other than current, is rejected — never migrated in place
What never touches itAdding an ordinary event type does not bump it — vocabulary growth is covered by the ignorable marker (previous chapter)A session's own version lives in its sessions row, orthogonal to this layer

Note the distinction between rejecting an unsupported format (SessionFormatUnsupportedError: the log is not corrupted; this build simply cannot read it) and corruption (SessionPersistenceCorruptionError: data in the committed prefix is genuinely broken). The direction-aware rejection wording is a product-level detail: the user should see 「upgrade the harness」 and never 「file corrupted」. The JSONL backend can even determine direction from the raw header line — before any structural validation; SQLite first uses the SCHEMA_VERSION pragma to keep whole-database structure out. The repository AGENTS.md's pre-release stance says it plainly: with no external consumers, prefer the correct foundation — reject old formats, rename freely, and update every reference together.

5.5 Crash recovery: closing out orphan turns

Section 4.8 last chapter covered the repair semantics (interruptedTurnClosers: error results for dangling calls, boundary completion, turn/end { interrupted }, existing events untouched); this section adds the persistence layer's execution timing and boundary judgment:

  • Repair only cold sessions. For a still-live session id, load(id) waits for the authoritative in-memory snapshot to become durable and returns it; an open turn on a live session is rejected outright and never receives synthesized interruption boundaries.
  • Torn tail vs half-written turn: a physically half-written record (a broken frame in JSONL, an unparseable row or seq hole in SQLite) is a never-committed torn tail and is discarded; a fully written half turn is a committed fact and is kept by closing it out. SQLite's scanRows uses the last turn/end as the dividing line: holes before it are corruption in the committed region (throw); holes after it are tolerable torn tail (trim).
  • inspect writes no repair: a cold inspection completes the closure in memory, leaving the physical torn tail untouched; load / prepare are what commit the repair back to storage (and revision changes then).
  • prepare's cache reuse: the coordinator keeps cold unpublished sessions in a bounded LRU (5 by default), so repeated history reads and the subsequent resume share one round of read, decompress, validate, freeze, construct.

5.6 Derived state: projections, titles, telemetry

With the session log on disk, a whole class of 「read models」 can derive from it — log first, cache after, and the cache can always be thrown away and re-derived. This section meets three families (all under packages/session/).

Projections and the cold-read ladder (session-projection / session-projection-cache)

ctx.sessionProjections is a framework-drives, domain-computes registry: each domain registers a projection unit { key, schema, init, apply, view, stateVersion } — three pure synchronous functions plus declarations. The framework subscribes to session/event once and streams every committed event through every unit's apply; snapshot(session) yields a consistent snapshot of all units at one asOfSeq. Two performance disciplines are part of the contract: an apply that does not care about the event must return the same state reference (reference equality exempts downstream work); state events must carry whole values, not deltas (last-wins, self-describing).

With session-projection-cache mounted, each session's projection checkpoints persist to storage-domain (see 5.7), and cold reads take the ladder and never load the full log: 

Cache row ((key → ver, seq, val), zero I/O)
  → restoreFloor (anchored one event below the lowest usable watermark)
  → persistence-layer readFrom(id, floor) (reads only the suffix)
  → restore folds → write back refreshed rows (fail-soft)

Session lists therefore never parse a full log: cachedSnapshot(meta) reads whole values straight from stored records; on a ver mismatch the row is discarded and re-derived (not migrated); records are bound to the log's lifecycle identity (createdAt/cwd), so residual caches from a replaced backend are recognized and dropped. Writes have two mandatory points (turn/end, session dispose) plus two throttle configs (writeEveryEvents, writeIntervalMs — both required; flush cadence is a deployment decision with no universal default).

Titles (the session-title family)

The session list needs a one-line title for humans. The strategy: serve a usable one immediately, then asynchronously trade up. The first few words of the first human prompt (byte-limited, control sequences stripped, never cutting a code point) immediately become the fallback title; optional providers (session-title-llm, session-title-first-prompt-llm, session-title-all-prompts-llm, distinguished by summary scope) later generate a better one with a model. Every accepted revision is a log-only session/title session event, and foldSessionTitle() takes the latest — titles are event-sourced too, and a fork inherits the parent's title events. A manual user rename (rename) writes a user-source title event and pins the session: later human messages no longer trigger automatic retitling, and only an explicit refresh unpins. Automatic titling never delays the main response: the provider runs only for requests the loop itself issued and only when routing exactly matches the recorded request/header, appending an independent log-only event when done (opening no turn).

Telemetry (session-telemetry / session-telemetry-otel)

SessionTelemetryCoordinator hands session records to backends implementing SessionTelemetrySink (emit/flush/shutdown) — session-telemetry-otel is the OTel implementation. Capture has two modes: live (hooking session/created / session/event / session/flush / session/disposed / agent/error) or on-demand (an explicit captureSession() replaying a log prefix). Outbound records pass a sessionTelemetry/record redact waterfall — the package ships no rules of its own; how clean the export is depends on which rules the deployment mounts. Redaction touches only the outbound copy; the canonical log is never rewritten. Two trade-offs worth remembering: only the first assistant/chunk per (turn, step) is emitted (the signal that streaming began), so holes in production seqs are normal, not loss; receivers dedupe by (session.id, event.seq). Resume does not backfill records the previous process failed to deliver (at-most-once), and the sharing policy gated by feedback (full/feedback-only/ disabled) is disclosed by the deployment.

5.7 Non-session data: the storage hub and DSH_HOME

Not all durable data is session logs. Application data like workspace preferences and user-feedback records goes through another family (packages/storage/):

  • storage/ — the hub, seam ctx.storage: connects named backends with typed data shapes;
  • storage-json/ (backend json, JSON files) and storage-sqlite/ (backend sqlite) — two swappable backends;
  • storage-domain/ — ctx.storageDomain: typed domain record storage (DomainSpec/Domain, domain/changed events); consumers get domain shapes, not raw backends.

Consumers include workspace (workspace data, with the json backend landing beside workspace.json at the storage root), message-feedback (feedback records), and 5.6's projection cache (the session_projcache domain). The difference from session logs in one sentence: these are not event streams but per-domain record stores — they need no append-only, seq, or projection machinery, which is why they deserve their own seam.

Where these files live is decided by packages/util/home-paths: the $DSH_HOME environment variable overrides the default, which is ~/.dsh (DSH_HOME_DIR_NAME). User-level data like projection caches and preset roots all sit under this roof, directory-partitioned per deployment configuration.

5.8 Chapter recap

  • Persistence is a plugin seam, not the store's job: ctx.sessionPersistence declares locate/create/append/prepare/load/inspect/readFrom/list(listSnapshots); two backends implement the same contract, with no second persistence event type.
  • The coordinator does write-behind: the first event opens a fixed batch window (200ms default, not reset) and later events join the batch; session/flush drains to quiescence; failures retain and retry; revision is the backend's own opaque change token.
  • The JSONL backend: one transcript per session (a concatenation of zstd frames by default), the header line is the SessionHeader, and the packed chunk row is a lossless encoding (reads are layout-blind); root deliberately has no default.
  • The SQLite backend: three tables (store identity, sessions metadata, events with one row per event, 1:1 mapping including surface columns), lazy materialization, WAL by default.
  • Both versioning layers are reject-on-mismatch: the session layer's SESSION_FORMAT_VERSION = 0 covers the event vocabulary (a mismatch throws SessionFormatUnsupportedError with direction-aware wording); the SQLite layer's SCHEMA_VERSION = 15 + application id 0x44534850 covers the table layout. No migration.
  • Crash recovery closes out without truncating: a fully written orphan turn gets synthesized tool/results (TOOL_NOT_STARTED / TOOL_OUTCOME_UNKNOWN), step/end, turn/end { interrupted }; the physically torn tail is discarded; only cold sessions are repaired.
  • Derived state derives from the log: the projection registry (apply returns the same reference; whole-value events) + the projection cache's cold-read ladder (cache row → readFrom suffix → fold and write back; lists never load full logs); titles are session/title events (fallback + optional LLM provider; a user rename pins); telemetry hands off to a sink after the redact waterfall, deduped by (session.id, seq).
  • Non-session data goes through the ctx.storage hub (json/sqlite backends + storage-domain typed shapes) and lives under $DSH_HOME (default ~/.dsh).
Common pitfalls
  • Believing append() commits only after reaching disk. Commit happens at the push into the in-memory log; persistence is asynchronous batching. For a durability barrier, flush explicitly.
  • Conflating the two version layers. SessionHeader.version versions the event vocabulary; SQLite SCHEMA_VERSION versions the table layout; neither stands in for the other.
  • Expecting old logs to auto-migrate to the new format. dsh's policy is reject-on-mismatch versioning: an unreadable log throws a direction-explicit error, leaving migration paths to a future upgrade chain.
  • Believing crash recovery discards half a turn's work. It closes out, not truncates — every fully written event is kept; only the physically torn tail is dropped.
  • Treating the projection cache as authoritative. A cache row may be stale (seq says by how much) but never wrong; the log is the authority, and a ver mismatch discards and re-derives outright.
