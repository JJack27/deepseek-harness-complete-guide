Chapter 19 · Part IV · Product Front Ends and Protocols

Web UI architecture: host, client modules, ui-slots

Behind dsh web is not “a monolith with a UI” but two halves: the host in the Node process and the SPA in the browser. This chapter builds exactly one key intuition — the browser half is plugin-based too: every region of the page is a ui-* feature plugin, composed through ui-slots extension slots. The connection details of RPC and WebSocket are left to Chapter 20; here we only mark where the channels sit.

Learning objectives
  • State the boundary of the two-half architecture: the host half (webserver + frontend-static) and the browser half (a Vite SPA).
  • Describe the browser shell's two-stage boot: the window.__DSH_BOOT__ module graph → the vendored Loader plugin face.
  • Explain ui-slots' register model and the self-nominating election of chain slots.
  • Distinguish the two sources of session data: the cold-read projection cache and the live session/projection frames.
  • Spell out the trigger conditions and granularity of client plugin HMR.

19.1 One product, two halves

The Node process that dsh web starts is the host half; the Vite SPA the browser loads (apps/web, package name @deepseek-ai/dsh-web-frontend) is the browser half. Each has its own set of roles across the two package groups packages/client/ and packages/host/:

  • Host half: dsh-host-webserver provides a plain node:http server (ctx.webServer) that handles only named routes, upgrade routes, and the single fallback seat; dsh-host-frontend-static occupies the fallback seat and serves the built dist/ of apps/web with SPA semantics. The host half also carries every ctx.* business service — agents, sessions, settings, commands, skills… everything from Chapters 3 through 17 runs here.
  • Browser half: dsh-client-web is the boot shell, dsh-client-modules is the module system, dsh-client-web-react connects the shell runtime to React, dsh-client-runtime provides the Session/Workspace object layer, and the thirty-plus ui-* packages are feature plugins.

The most easily overlooked line in this diagram is the small note on “GET static assets”: when frontend-static serves index.html it first passes through the webserver's applyIndexTaps — that is how the boot manifest enters the page. What the browser does after receiving the index unfolds in the next section.

19.2 The host half: webserver and frontend-static

dsh-host-webserver deliberately “knows no harness concepts”: it is a default-exported WebServer plugin (config is only host and port) providing ctx.webServer. Other plugins register named HTTP routes with it (register, exact or prefix), upgrade routes (registerUpgrade, matching WebSocket by exact path), and the single fallback handler (registerFallback; a second registrant throws). Match order is fixed: all-table exact → longest prefix → fallback. The /api bridge, the downstream WebSocket, plugin bundle routes, and the HMR event stream are all routes registered by other plugins — the webserver itself serves not one file. host accepts only 127.0.0.1 (the default posture) and 0.0.0.0 (deliberate network exposure); a bind failure (e.g. EADDRINUSE) throws at activation so the Loader assembly fails together with the binding diagnosis.

dsh-host-frontend-static is the factory occupant of the fallback seat: out-of-bounds traversal is 403, any miss falls back to index.html with HTTP 200 (SPA routing), unknown extensions are served as application/octet-stream, and non-GET/HEAD with no matching route answers 405. distIndex is resolved by the assembling application (the dsh-web-app bundle) from the frontend package's exports — deployments never hardcode it. The seat is single-owner and effect-scoped: dispose this plugin and the seat is released, with the webserver reverting to 404.

19.3 The browser half is plugins too: from __DSH_BOOT__ to app-shell

The browser shell's entry is AppWebEntry(el).run() in packages/client/web (@deepseek-ai/dsh-client-web). It boots in two stages — what the repository docs call web2:

  1. Module face: build dsh-client-modules's ClientModuleLoader from the entry graph window.__DSH_BOOT__ that the host pushed into the page, prefetching the immediately layer in parallel. At this point executing a bundle only registers a factory and produces no side effects.
  2. Plugin face: mount the vendored Cordis Loader and inject the module system through its internal contract — the vendored side's only consumption point is EntryTree.import, so swapping internal is equivalent to swapping “how plugin code arrives”. Each line of the graph becomes one loader entry, plus the shell's own app-shell assembly entry; AppRoot waits for settle (the Loader quiescent + every entry fiber ACTIVE) and renders the full UI in one shot.

dsh-client-modules itself deserves a sentence: it is “the browser counterpart of Node's internal ESM loader”, implemented as a lazy CJS table. Executing a plugin bundle is merely window.__ModuleLoader__.load({id, factory}) registering a factory; all of the module body's side effects (including CSS injection) live inside the factory closure and run only at materialization (factory(require)), which records into loadCache. A factory requiring another registered-but-unmaterialized module recursively materializes it, so load order needs no external sorting; a require cycle throws. The Node half scans the enabled Loader entries for packages carrying the web dsh.client, resolves each one's exports["./client"], and packs the built bundle plus source map into the boot graph, served via /plugins — the host graph decides the composition; the shell makes zero composition decisions.

19.4 ui-slots: the composition law of the browser UI

How do thirty-plus ui-* packages assemble into one interface? The answer is ui-slots' slot terminal design. One register does four things at once: contribute a component to a declared slot, declare child slots (declaration = render authorization = runtime specification, one table), optionally mount a store seat, and expose the registrant's business face. A component's props are the intersection of four shared sets: runtime props (the parent's renderSlot call site + session standard parts + global seats), child-render props, store props, and business props — each derived from a single source of truth, with no second synchronization.

Two kinds of slots are worth distinguishing. A keyed slot is routed by the dispatch site choosing an entryKey; a chain slot is the reverse — each registration carries its own pure ChainSelect selector (optionally with an ascending priority, ties broken by registration order), the first registration to return non-null is elected, and its return value is passed to the component as the matched prop; if all miss, control falls back to the holder's renderSlotChain. The sidebar, the session view, and the settings page's extension areas all grow through this mechanism.

The layering is clean too: dsh-client-web-react provides createSlotRenderer (the SlotRenderer implementation the shell installs into the runtime), SessionProvider, the sole hook constructors bindSnapshotSelector and useInvoke; feature plugins depend only on ui-slots' types, never on web-react. The snapshot store engine (defineStore) lives in the runtime package; host and engine pass only bare observable sources, and hook binding belongs entirely to the rendering machine.

19.5 Session lists and live streams: the two faces of projection

Echoing Chapter 5: the host side has a ctx.sessionProjections projection registry, and cold and hot data take two separate paths.

  • Cold read: opening the page, lists like session.list need not wake any Agent. The gateway keeps two projection cells of its own (e.g. sessionListMetadata caches the monotonic “blank→non-blank” flip and the time of the most recent human prompt); for very small session artifacts (within the default 1 KiB threshold) it can even do an exact fold to derive blank and the latest prompt. Cold sessions stay “metadata only” in the list until you open or resume one, at which point the host attaches the log and folds out a log-backed title.
  • Live: after attaching to a session, the client seeds a ProjectionValueStore from the history tail page's projections block (carrying an asOfSeq watermark) and thereafter updates each cell (title, todos, queue, jobs…) from session/projection mux frames under higher-seq-wins. These frames are live push state and never enter the log — Chapter 4's “model-visible ⟺ logged” invariant is unaffected.

The runtime fans the shared host stream out to Session and Workspace owners and hands every generic host/remote-event frame to ctx.remote.$dispatch (Chapter 20). Session content itself is assembled by ConversationNodeAssembler: a plugin registers a business Definition that maps an event to a stable {kind, id}, builds a Context at the unique initiating event, folds related updates, and produces final nodes for the registered view targets — appends evaluate a Definition once and update only matching Contexts; paging back preserves existing Contexts and node identity. ui-conversation registers the built-in Chat Definition, while ui-trajectory registers an independent Definition and target builder over the same event window; the two views never consume each other's folds.

19.6 Development mode: client plugin hot reload

dsh-client-hmr lets script-loaded client plugins hot-replace, but one precondition is often misunderstood: the web bundle mounts the HMR line unconditionally, yet it rebuilds nothing itself. What actually triggers rebuilds is the separately run pnpm run dev:web watcher rewriting the client bundle; without the watcher, the node-side stat-poll sees no change and the whole chain stays idle.

When a rebuild happens, the browser half subscribes to the system SSE channel (GET /plugins/events), and each rebuilt frame reloads one plugin through a serial queue: invalidate the old factory → prefetch the new bundle (registered while the old fiber still serves) → delete the registry → drain the old fiber → remove owned style tags → entry.refresh() re-imports and re-mounts. Reload of dependents relies on Cordis itself: once a fiber's activation epoch changes, its service providers' uids all change, so replacing one provider cascades to every dependent — zero graph analysis on the client. The granularity is a coarse whole-plugin reload — React internal state is lost while the data layer (connection/runtime fibers, Session objects) stays put; a failed reload does not roll back, the entry stays FAILED and is visible in the loader status projection.

19.7 Chapter recap

  • Two-half architecture: the host half is dsh-host-webserver (plain node:http, all routes registered by other plugins) + dsh-host-frontend-static (the single fallback seat, serving apps/web's dist/); the browser half is a Vite SPA.
  • The browser shell boots in two stages: the module face builds a ClientModuleLoader from window.__DSH_BOOT__ (executing a bundle only registers a factory), and the plugin face mounts the vendored Loader (one entry per graph line); AppRoot waits for settle and lights up once.
  • The browser UI is “everything is a plugin” too: thirty-plus ui-* feature plugins compose through ui-slots' register; chain slots elect via the registration's own ChainSelect; feature plugins depend only on ui-slots types.
  • Cold reads of the session list go through the projection cache and exact folds of small artifacts (waking no Agent); the live stream goes through session/projection frames with higher-seq-wins, never entering the log.
  • client HMR needs the separate pnpm run dev:web watcher to trigger; reload is whole-plugin granularity, and dependent cascades ride fiber activation epochs.
Common pitfalls
  • Assuming the webserver serves files — it serves not one; dist is served by frontend-static occupying the fallback seat, and a second fallback registration throws outright.
  • Treating window.__DSH_BOOT__ as something the browser computes itself — it is the entry graph pushed by the host; the shell makes zero composition decisions.
  • Assuming side effects run as soon as a bundle executes — execution only registers a factory; side effects happen at materialization (factory(require)).
  • Adding a web-react dependency to a feature UI plugin — type dependencies should point only to ui-slots; hook binding belongs to the rendering machine.
  • Expecting session/projection frames in the session log — they are live push state and never touch disk.
  • Complaining HMR does not work — first confirm the separately run pnpm run dev:web; the HMR line is mounted but rebuilds no bundle by itself.
