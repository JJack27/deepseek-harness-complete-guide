Chapter 20 · Part IV · Product Front Ends and Protocols

Typert and the RPC Gateway

The previous chapter left a thread hanging: there is an /api channel between the browser and the host. This chapter takes it apart: how does browser↔host RPC achieve end-to-end type safety? The answer is called Typert — at build time it generates a “type graph” from types, and at runtime a registry consumes it. Above that, the gateway claims the new-style Remote endpoints, apiproxy carries the legacy surface, and two downstream-only WebSockets carry events. By the end you will know every hop of a method call from the browser to a ctx service.

Learning objectives
  • State the division of labor of the Typert trio: generator (build time) → loader (discovery) → registry (ctx.typert).
  • Describe how a call on /api is claimed by the interceptor or falls back to apiproxy.
  • Explain which policy remotes' createApiRemoteAgentResolver unifies.
  • Draw the full channel picture: POST for unary/respond, the events.mux and events.host downstream pair, and the readiness rule.
  • Explain why the /api browser-trust fence fixates on the Host header (DNS-rebinding protection).

20.1 The problem: end-to-end type-safe RPC

Web UI RPC has a structural difficulty: the caller lives in the browser (TypeScript, the Client compilation face), the callee lives in Node (TypeScript, the Host compilation face), and between them sits HTTP and JSON. The usual approaches are either handwriting two interfaces and praying they do not drift, or adopting codegen to generate a whole client. dsh's answer is Typert: a build-time tool generates a compiler-independent type graph (FaceModel, TypeGraph) from the source type tree, and the runtime consumes it as a registry — the calling face the browser side gets (ctx.remote) and the calling face the Node side exposes (ctx.typertGateway) share the same generated InvocationDescriptor contract.

The design also preserves the boundary discipline that Chapter 23 will unfold: business packages mark methods with @Remote or @RemoteScope on their Host service classes and need no RPC runtime dependency; the generated declaration exposes TYPERT as unknown, so contributing business packages need not depend on the type registry itself.

20.2 The Typert trio: generator → loader → registry

The three packages under packages/typert/ layer as analysis / discovery / storage:

PackageRoleCordis key
typert/generatorBuild-time library: analyzes a TypeScript project and generates runtime artifacts— (no plugin)
typert/loaderScans Loader entries, imports and registers the generated Host artifactsconsumes ctx.loader and ctx.typert
typert/registryRuntime registry: package reflection and optional live Zod schemasctx.typert

generator analyzes the source with a standalone ts.Program (seeded from tsconfig.host.json or tsconfig.client.json), produces a compiler-independent model, and an emitter then renders the artifacts. The repository's Host tsdown runs once carrying the workspace Typert generation: it produces the Host reflection artifact (lib/typert.host.{js,d.ts}, exposed through the package/typert subpath) plus the typert.remote-client.* projection for the Client; the Client tsdown afterwards never starts Typert again. Publishing is opt-in per package: a business package without the corresponding public exports needs no Typert artifacts at all. In check mode the analyzer fails on syntax/semantic diagnostics, missing public annotations, and private cross-package references — the type graph is not allowed to quietly miss a piece.

loader is a Node-only plugin: at activation it scans existing Loader entries, follows internal/plugin lifecycle notifications, resolves each entry package's package.json, and when it exports ./typert imports and validates the TYPERT manifest and registers the contributions into the registry. Packages without that export are simply skipped; nested plugins hiding behind another Loader entry must be listed explicitly via the packages config. Resolutions and manifests are cached for the process lifetime — a newly added export requires a restart.

registry provides ctx.typert: package reflection is stored under <package>#<face> keys and schemas under <package>#<name> keys (the producer's Zod instance is retained; JSON Schema is projected on demand at the consumer). It also has two separate ownership faces: lookups (business packages register lookup declarations and default resolvers, and Host assemblies override behavior with configure() — swapping the Agent/Session resolution policy of Section 20.4 happens exactly here) and contexts (Context identity for scoped calls). Registration is an effect: contributions are withdrawn together with the calling side's Cordis fiber.

20.3 gateway and apiproxy: claim and fallback

packages/api/gateway (@deepseek-ai/dsh-api-gateway) is a two-faced plugin: the Host entry provides ctx.typertGateway, and the Client entry (@deepseek-ai/dsh-api-gateway/client) provides ctx.remote. Business services extend TypertRemoteService and mark public methods with @Remote or @RemoteScope; the Host-side call flow is: resolve the current descriptor and Cordis Service → validate exact named parameters → resolve object or Context identity via lookups → invoke the business method → validate the return value.

Two validation modes must be kept apart. strict mode reads the generated call descriptors from ctx.typert.local and validates both parameters and return values exactly against the generated codecs; SRC mode is a development fallback reserved for endpoints that never had a strict definition — it parses only simple parameter names and, for non-lookup parameters, only checks JSON safety. The key red line: withdrawing strict validation from an endpoint whose strict definition has already been observed fails outright rather than silently degrading to SRC — validation strength may only tighten.

On the Client side, ctx.remote.$mount() validates and registers a generated Host-for-Client contribution, installing concrete methods for the caller's fiber (each namespace is a tracked remote.<ns> sub-Service). A call validates positional parameters, constructs the exact named args the descriptor requires, and goes out via ctx.connection.rpc.call('/api', endpoint, …); return values pass validation before entering application code. The event face is ctx.remote.$on(): the legal keys are exactly the forwarding selection the Host assembly makes (Section 20.4), and the listener types are the owning package's own Cordis Events declarations — a second signature has nowhere to drift to.

So what about the legacy surface? A composite handler hangs on the Host's /api FetchHandler: the gateway-registered interceptor claims first, and what goes unclaimed falls to apiproxy (ctx.apiProxy, @deepseek-ai/dsh-host-apiproxy) — a transport-agnostic gateway holding the four-quadrant wire contracts (ClientRequest/ServerResponse/ServerRequest/ ClientResponse) and the large legacy method families (session.*, workspace.*, settings.*…). It registers no routes itself: the HTTP carrier (Chapter 19's connection) is responsible for handing requests over. Migration proceeds method by method: methods moved to Remote are handled by the gateway, unmigrated ones keep going through apiproxy, and both sides share the same Agent/Session resolution policy — exactly the reason remotes exists.

20.4 remotes: the Agent/Session lookup policy

packages/api/remotes (@deepseek-ai/dsh-api-remotes) is a two-faced BFF. Its core export createApiRemoteAgentResolver() answers “who does this sessionId/agentId refer to” as a single policy: reuse a live Agent, resume an ordinary cold session, deduplicate concurrent resumes, and preserve the subagent ownership fence; the same resolver is configured for both the agent and session lookup keys of Typert. After taking Agent defaults and scope assembly, the legacy Web ApiProxy also uses this resolver for legacy methods — migrated and unmigrated methods share one identity-policy implementation, which is the key to “swapping the gateway without swapping behavior”.

Its Client face is the dependency facade for browser business packages: it imports the generated /remote artifact as a runtime value, mounts each contribution via ctx.remote.$mount(), and re-exports the declaration merging; business packages depend on neither the gateway implementation nor any single Remote runtime entry. The current assembly mounts the Goal contribution and a read-only Host plugin-inventory contribution (pluginInventory/list).

The downstream-event allowlist also lives here: API_REMOTE_FORWARDED_EVENTS in src/remote-events.ts is the list of cordis events the Host forwards to consumers — forwarded verbatim, no projection, no redaction, no renaming — so it is also the legal key set of ctx.remote.$on; the Host face further asserts TypertForwardableEvent against this table: anything not a declared event, bound to an AgentScope, or not one-directional in shape cannot enter the allowlist. Forwarding a new event = adding one entry to the array; the type projection, the consumer key face, and the Host forwarding loop all derive from it.

20.5 The full channel picture: POST, the downstream pair, and the fence

Channels come in three forms. Upstream goes over HTTP POST: both unary and respond operations are POST /api/<method>, with respond-style calls (e.g. answering an agent question) using the POST /api/respond receipt. Every POST must declare application/json or it eats a 415 before dispatch — cross-site “simple requests” (the kind the browser sends without preflight) can never execute methods with side effects.

Downstream is two downstream-only WebSockets: /api/events.mux carries session-level mux frames (session events, projection frames, queue and jobs snapshots…), and /api/events.host carries host-level frames (workspace additions and removals, forwarded Remote events…). Both sockets send only from host to browser; the client sends no application data on them. Break either one and the current connection generation fails, with both streams rebuilt together; readiness is decided as “both sockets open and the host.describe HTTP call succeeds” — what a successful handshake publishes is exactly the host.describe value. A plain network GET to either path gets a 426; there is no SSE fallback in production (the SSE codec serves only in-process carriers).

The fence is the only gate standing before both WebSocket upgrades and every /api request. Its core comparison is the Host header: it must be a loopback authority (or a deployment-derived LAN IP literal), or exactly match a trustedHosts entry (host:port exactly, portless entries any port, both sides compared after WHATWG normalization). Why Host? Because it is the one request header a DNS-rebinding attacker cannot forge: over plain HTTP the browser sends neither Origin nor Fetch-Metadata for image and navigation reads, so an “unmarked” request may still be a rebound browser read; when markers are present, Origin must equal the Host authority and an explicit sec-fetch-site: cross-site is refused outright. Non-canonical entries (something with a path like harness.internal/path) fail loud at plugin load. There is also a set of privileged methods pinned to loopback (host.pickDirectory, configuration-surface read/write, the agentPreset read/write family) — a declared trustedHosts authority can reach the other methods but never these; until a real authentication layer exists, these capabilities stay on the local machine. The fence is a reachability policy, not authentication — which is also why dsh web --host 0.0.0.0 remains deliberately unsupported.

20.6 Chapter recap

  • Typert has three layers: the generator produces artifacts from the type tree at build time (triggered by Host tsdown, opt-in per package), the loader scans Loader entries and imports ./typert, and the registry provides ctx.typert (<package>#<face> reflection, <package>#<name> schemas, lookups/contexts).
  • gateway is two-faced: ctx.typertGateway (strict descriptor validation; SRC is only a development fallback, and withdrawing an observed strict definition fails) and ctx.remote ($mount generates methods, $on forwards events).
  • On the /api FetchHandler the interceptor claims Remote endpoints first; unclaimed ones fall to apiproxy's (ctx.apiProxy) legacy method families; both gateways share remotes' createApiRemoteAgentResolver (live Agent reuse, cold-resume dedup, subagent ownership fence).
  • Channels: unary/respond over HTTP POST (application/json required); /api/events.mux and /api/events.host are two downstream-only WebSockets, breaking either rebuilds the whole generation; readiness = both sockets + host.describe succeeding.
  • The fence watches the Host header against DNS-rebinding; trustedHosts declares authorities, privileged methods are pinned to loopback; the fence is a reachability policy, not authentication.
Common pitfalls
  • Assuming Typert analyzes types in the browser at runtime — analysis happens at build time (Host tsdown); the browser only consumes the generated codecs and descriptors.
  • Assuming an unclaimed endpoint is a 404 — it falls into apiproxy's legacy surface; apiproxy is the fallback layer, not a ruin.
  • Withdrawing an endpoint's strict definition hoping to fall back to SRC — endpoints whose strict definition has been observed fail outright; validation may only tighten.
  • Assuming the browser sends data back over the two WebSockets — they are downstream only; upstream always goes over HTTP POST.
  • Treating the fence as authentication — it only gates reachability; that is also the root reason --host 0.0.0.0 is deliberately refused.
  • Writing an “authority” with a path or zero-padded port into trustedHosts — entries that are not bare host[:port] fail loud at plugin load.
