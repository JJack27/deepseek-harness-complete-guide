Chapter 6 · Part II · The Core Spine

The Agent Abstraction and the Scope Mechanism

At the end of the last chapter the session could already be persisted to disk, but 'who drives the session' had not yet appeared. This chapter introduces Agent — dsh's public interface for 'an agent at work' — together with the scope mechanism that makes 'each agent has its own set of tools and prompts' possible: a live agent is the key of its own scope, and the most specific registration wins (shadowing). This is the shared foundation of per-session personas, agent presets, and subagent composition. The concrete driving loop (turn/step) is left for the next chapter.

What you'll be able to do
  • State what each member of the Agent interface and each ctx.agents registry operation (get/list/roots/isOwnedBy) answers
  • Classify agent/* events as observation versus interception, and identify which are waterfalls (must call next())
  • Explain the point of routing create/resume through the AgentFactory seam: interface separated from driver, so the loop is replaceable wholesale
  • Describe the setup window's ordering: assemble the agent's scoped world before publication; roll the whole thing back on failure
  • Use the shadowing rule (most specific scope wins) to work out which same-name registration takes effect across multiple agents
  • Distinguish 'lineage is data' from 'runtime ownership': parentSession is recorded in the header, and a parent does not automatically see its children

6.1 Agent: interface and registry

The Session of Chapter 4 is 'what happened'; Agent is 'the actor doing the work right now'. It is a pure interface (packages/core/agent/src/runtime-types.ts); the concrete implementation is private to the agent-loop package — plugins never import agent-loop; they depend only on this interface. Members are grouped by purpose:

MemberPurpose
id / sessionthe agent and its session share the same id (SessionId); session is the live session it drives, whose log is the durable truth
optionsper-agent options such as provider routing and model (the merge-extensible AgentOptions)
inboxdurable pending-work projection: two ordered queues, next-turn and next-step
statusidle ⇄ running (each transition emits agent/status; dispose is not a third state)
ctxagent-scoped context: contributions registered through it are agent-local; once dispose unwinds, further registration is rejected (protagonist of section 6.5)
send / followup / steer / injectfour ways to deliver input: send is the unified primitive (target + whether to wake); the other three are fixed presets (append a turn / steer the nearest step / context injection without waking)
cancel / whenIdle / runMaintenancecancel (first reason wins; keepInbox can preserve the queues) / wait for quiescence / run a non-turn maintenance task from true idle

The registry ctx.agents (AgentRegistry) tracks who is alive: get(id) looks up a live agent, list() lists all in registration order, roots() lists only top-level agents with no runtime parent, and isOwnedBy(id, owner) asks whether 'this child was created through a specific parent's scoped context' — note this is a runtime relationship, unrelated to durable lineage (expanded in section 6.7).

The consumer that creates an agent receives an AgentHandle ({ agent, dispose() }). dispose is a capability: within the consumer, only the holder can tear down this agent. The other structural owner is the provider that registered the factory (its scoped agents depend on its service API; unloading the provider stops and drains every live handle it created). The teardown order is fixed: stop the loop → await exit → unregister the agent → remove the session from the session store → finally unwind its scoped world. Agents created from configuration (the loop's own startup entries) are owned by the loop fiber and never need a handle.

6.2 agent/* events: observing and intercepting in-flight work

All agent/* events carry the live Agent (in the payload) and are dispatched through scope filtering (the Scoped<Agent> this carrier from the previous section; section 6.6 explains what that means). Remember them in three groups by purpose:

GroupEventModeIn one line
Lifecycle (observation)agent/created / agent/disposedemitpublished to / removed from the registry; a synchronous throw from created can veto publication
agent/statusemitmirror of idle ⇄ running transitions
agent/inbox/inserted / claimed / discardedemittraffic in and out of the live inbox; a message claimed and then rejected stops here
agent/session-startemitthe session lifecycle begins (once per session, before the first turn) — the standard moment for agent.inject() to seed context
Interception (extension points)agent/pre-stepwaterfallreject the proposed step, or rewrite the messages entering it (call next() to keep it)
agent/requestwaterfallreplace the frozen call configuration; cannot change messages (model-visible content goes through the log channel)
agent/request-errorwaterfallclaim a failed request's recovery (return retry without calling next), or delegate
Stop boundaryagent/turn-stoppingserial (no next)the turn is about to close; objection happens through data — steer() injects a new steer and the machine re-reads the inbox
Error notificationagent/erroremitan on-the-scene report of step/turn failures (even when the error has no durable place in the turn)

The contrast with Chapter 4 is worth repeating: session events are durable facts; agent events are live extension points. Facts must survive a restart, so they go to the log; in-flight work (inbox changes, request rewrites, turn stopping) matters only right now, so it travels over the Cordis event bus. The first question when choosing a mechanism is always: does this fact need to still exist after a reload?

The listeners of the three waterfalls (agent/pre-step, agent/request, and agent/request-error) must call next() to delegate to the layer below — returning without it short-circuits the whole chain; these are the three most important landings in dsh of the Cordis waterfall semantics you learned in Chapter 2. agent/turn-stopping is deliberately serial with no next(): it is not a veto point but a last-look point; objection happens through data (steer), not return values.

6.3 create/resume: the factory seam

AgentRegistry does not construct agents itself. It holds at most one AgentFactory (the two methods createAgent + resume), registered by the driving plugin at construction time via ctx.agents.setFactory() — the shipped implementation comes from agent-loop. Calling create/resume with none registered yields a plain error: 'no agent factory registered (load an agent-loop plugin)'. 

// Consumer view: knows only ctx.agents, never agent-loop
const handle = await ctx.agents.create({
  sessionId,              // shared identity: agent and session share one id
  meta: { cwd, parentSession, delegationDepth, agentPreset, ... },
  seed,                   // optional: balanced prefix for a fork
  agentOptions: { provider, model, maxTokens },
  setup,                  // the protagonist of section 6.4
})
// resume is the persistent variant: it goes through ctx.sessionPersistence.prepare(id) first
const resumed = await ctx.agents.resume({ resumeSessionId, agentOptions, setup })

The point of this seam is interface separated from driver: the ACP bridge, test tooling, and any consumer program against ctx.agents, none of them knowing who the driver is. To swap the entire loop for another implementation (say, a special driver that does no tool loop), register your own factory and the plugin ecosystem stays untouched. The factory's internal transaction order (detailed next chapter): mint the scoped context → await setup → insert and announce the session and agent in order → emit agent/session-start → start the loop. Every step is covered by rollback: an already-announced creation is paired with a matching disposed notification.

The registry also provides the initiator scope: causal attribution along in-process async chains. withInitiator(agent, fn) carries the agent through the entire lifetime of fn's return value; currentInitiator() reads it (optional form, for logging/tracing/metrics), requireInitiator() demands it, and withoutInitiator(fn) explicitly clears it (for lazily shared timers or queue pumps that should not inherit whichever agent happened to initialize them). Note the contract: the presence of an initiator is neither proof of liveness nor authorization — it is only an in-process causal annotation; principals and owners are always passed explicitly.

6.4 The setup window: assembling the scoped world before publication

CreateAgentOptions.setup / ResumeAgentOptions.setup is a callback with the signature (agentCtx: Context) => commit | Promise<commit | void> | void. It is the most important assembly window; the ordering contract in one sentence: the factory awaits it after minting agentCtx and before inserting or announcing the session and agent. The consequence is that observers never see a half-configured world: everything registered through agentCtx (scoped tools, prompt sections / variables, restrict(), listeners, awaited sub-plugins) is fully in place before session/created, agent/created, agent/session-start, and the first prompt assembly.

  • setup only assembles, never drives: the callback receives the full scoped context (trusted same-process code); this is a contract, not a runtime restriction — the agent can be driven only after creation resolves.
  • setup may return a synchronous AgentSetupCommit whose commit() is invoked after all setup awaits have settled, at the last moment before publication — letting mutable configuration revalidate at the exact publication boundary.
  • A throw from setup, a throw from commit, or an owner dispose rolls the whole thing back: neither id (session and agent) is published.
  • resume's setup is isomorphic: load persistence first, then mint agentCtx and await setup; the session and agent rebuilt during that window are both unpublished.

The preset system grows directly out of this window: the only supported call site of ctx.agentPresets.mount(agentCtx, id) is the factory's setup(agentCtx) hook — joining there is what guarantees 'composition failure → the whole creation rolls back' instead of leaving a half-assembled session (both the Chapter 3 assembly and the Chapter 14 subagents come back to this).

6.5 The scope mechanism: an agent is the key of its own scope

The machinery behind 'things registered through agentCtx are agent-local' lives in packages/core/scope. Start with three identity facts:

  • It is a library, not a Cordis service — no ctx key; in the module graph it sits below session and system-prompt so they can afford to use it without forming a cycle.
  • ScopeKey is opaque object identity (type ScopeKey = object, compared by identity). The primitives never inspect object contents.
  • In the shipped loop, the live Agent object is its own scope key: in agent-loop/src/agent.ts, this.scope = createScope(loopCtx, this), then this.ctx = this.scope.ctx.extend({ agent: this }) — the agent.ctx you read is exactly this context, carrying the scope tag plus the ctx.agent DX accessor.

createScope(ctx, key, options?) mints a scope: it hangs a shared empty plugin under ctx (owning the lifecycle of all registrations), writes the key into the derived context's tag slot (readable back via scopeOf(ctx)), and returns { ctx, rawDispose, dispose } — rawDispose preserves the exact Cordis disposer identity (for ordered composition of effect nesting), while dispose() is the shared quiescent teardown boundary.

A pair of opposite-direction capabilities is driven by the same parent chain (bindScopeParent, cycle-proof):

  • Registration views inherit downward along the chain: a child scope sees its ancestors' layers (ScopedLayers.chainLayers — the basis of the shadowing in the next section).
  • Event admission passes upward along the chain: scopeTarget(base, key) builds the routing carrier; untagged listeners are admitted globally, while tagged listeners receive events only when they match the key or one of its ancestors — listeners in an ancestor scope receive every descendant scope's events; events flow up the chain, never down. That is why a standing composition (say, a preset's standing mount) can observe every agent assembled beneath it.

6.6 Shadowing: the most specific scope wins

Now the registry side. Scope-aware registries (ctx.tools, ctx.systemPrompt, ...) store two layers in ScopedLayers<L>: an eagerly constructed global layer plus an override layer created lazily per scope. Reads use merge(): 

// What ScopedLayers.merge does (illustrative)
merged = new Map(named entries of the global layer)
for (layer of scope layers along the parent chain, farthest to nearest)
  for ([name, value] of layer) merged.set(name, value)
// On the same name, the later write overwrites the earlier one → the nearest scope on the chain has the final say

The rule is one sentence: the most specific scope wins. A same-name registration appearing in the agent layer shadows the one in the global layer — the shadowed registration is not unregistered: it is still in the global layer and other agents resolve to it as usual; only in this agent's view does the same-name entry on its own layer cover it. Registration and teardown are symmetric: owned via ctx.effect(); after undo, if the whole layer is empty, the layer itself is reclaimed.

This is the underlying mechanism of per-session personas. The dsh-persona plugin registers a deployment:persona prompt section — with the same name as the one system-prompt itself registers unconditionally. Global mounting would fail on the name collision (the deployment persona already has an owner), so it is designed to mount only in an agent scope: when a preset composes it, the persona plugin's copy shadows the deployment copy in that agent's view. The optional complete: true even reduces that agent's system prompt, after assembly, to this one section alone. Shadowing changes the view, not the world — other agents in the same process know nothing about it.

The scope chain can be longer still: a preset's standing mount is mounted in the process once (under the roster service's own fiber), and each session naming it parent-links its own agent scope key to the mount's key. That agent's view resolution order then becomes agent → preset → global: tools and prompt sections on the mount layer take effect for every joining agent with a single instance (plugins key their own state by Session/Agent), while sibling presets' listeners stay deaf to it.

6.7 Lineage is data, not visibility

One last group of easily confused concepts: a session's lineage versus its runtime visibility / ownership. Chapter 4 introduced the SessionHeader lineage fields: parentSession (forked/resumed from whom), seedLength (how long the inherited prefix is), origin: 'subagent', and delegationDepth (the recursion budget, persisted precisely so it survives restarts). The point:

Lineage is data, recorded in the header, used for UI display, recursion budgets, and fork navigation. It creates no runtime visibility whatsoever — a parent does not automatically see its children: writing parentSession in the header does not make the parent agent receive the child's events or read the child's log.

Runtime relationships belong to other mechanisms, deliberately independent of it:

  • Runtime ownership: the owner field on a registry entry — 'through which exact parent agent's scoped context was this child agent created' (queried via isOwnedBy(id, owner)). A fork resumed from disk has no runtime parent and is still a root — durable lineage does not affect this runtime relationship, and vice versa.
  • Event visibility: the upward admission along the scope chain (section 6.5). Whoever wants to observe a child attaches a listener in a suitable ancestor scope (this is exactly how a preset's standing mount observes all agents beneath it); or passes an explicit reference. There is no implicit 'I am the parent, so I receive automatically' channel.
  • Initiator attribution: the causal annotation along in-process async chains (currentInitiator()); Chapter 14's subagents will show how it is used for attribution.

The value of keeping the three separate shows up at the boundaries: after a restart the runtime owner and the initiator are gone, leaving only the header's lineage data; across processes / across the wire (Chapter 20's Typert RPC), even the Agent object is no longer the same one — only the id and the lineage can travel. 'Data belongs to the log, relationships belong to the runtime' — this line runs through all of dsh's boundary design.

6.8 Chapter recap

  • Agent is the public interface (id/session/inbox/status/ctx + the send family + cancel/whenIdle/runMaintenance); the implementation is private to agent-loop. ctx.agents manages the live registry, AgentHandle.dispose is a capability, and the teardown order is: stop the loop → unregister → remove the session → unwind the scoped world.
  • agent/* events fall into three groups: lifecycle observation (emit), interception extension points (the pre-step / request / request-error waterfalls, which must call next()), and turn-stopping (serial; objection via steer data) plus the agent/error notification. Session events are durable facts; agent events are live extension points.
  • create/resume go through the AgentFactory seam: the loop registers via setFactory, consumers depend only on ctx.agents — interface separated from driver, so the loop is replaceable wholesale.
  • The setup window assembles the scoped world before publication: awaited after agentCtx is minted and before the double announcement; every registration is in place before the first event and the first prompt assembly; failure rolls the whole thing back; an optional commit revalidates at the publication boundary.
  • scope is a library, not a service: ScopeKey is opaque object identity and the live Agent object is its own key; agent.ctx is the tagged scoped context.
  • shadowing: ScopedLayers' global layer + scope override layers; merge walks the parent chain farthest to nearest, nearest wins; a shadowed registration is not unregistered. The persona plugin builds per-session personas on this (scoped mounting only; global mounting fails on the name collision); the preset standing mount turns view resolution into agent → preset → global.
  • Lineage is data, not visibility: parentSession/delegationDepth are recorded in the header for budgets and navigation; runtime ownership (isOwnedBy), the scope chain's event admission, and initiator attribution are three independent runtime relationships — a parent does not automatically see its children.
Common pitfalls
  • A plugin importing agent-loop directly to get the driver. Extensions depend only on agent (the interface layer); when you need the initiator, use ctx.agents.currentInitiator().
  • Returning from a waterfall listener without calling next(). The pre-step / request / request-error chains short-circuit on the spot and every layer below is lost.
  • Assuming the persona plugin can mount globally and be toggled per session. The same-name registration collides and fails loudly — it is designed to mount only in an agent scope (preset composition).
  • Treating parentSession in the header as a runtime parent-child relationship. Lineage is data: it survives restarts but grants neither event visibility nor teardown rights; query runtime ownership with isOwnedBy.
  • Driving the agent inside setup. setup only assembles and never drives; any send/followup before creation resolves is misuse.
