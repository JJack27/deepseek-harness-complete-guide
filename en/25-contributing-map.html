The Contribution Map and Expert Navigation

The final chapter does two things: it completes the process map for leaving a change in this repository — the Agent Notes decision ledger, the bilingual documentation contract, PR labels and stack rules; then it assembles all twenty-five chapters into one navigation map, turning I want to change X, so first read Y into a table lookup. After this chapter you go from someone who reads dsh to someone who can start work in dsh. This is the closing chapter; take the diagram slowly.

Learning objectives

  • Explain the archived tree's freeze contract: never edited and never treated as current authority, enforced by verify-archived-agent-notes.
  • Describe the bilingual documentation pairing structure (*.md + *.zh.md + *.i18n.yaml) and the one-home-per-fact hierarchy tax.
  • Recite the PR rules: one kind/*, all material area/*, native Issue Type, and the --force-with-lease discipline for stacked PRs.

25.1 Agent Notes: the ledger of decisions

.agents/notes/ houses exactly one kind of document: a record of a decision that shapes the codebase — why it was settled this way and what was given up — the things code and ordinary documentation cannot carry. The path is itself metadata: {lifecycle}/{class}/yyyy-mm-dd-topic-title.md. Four lifecycle directories: proposed/ (proposals reviewed before implementation), implemented/ (shipped decisions that also stay current with the code — when code moves a file or changes a default, the same change updates the Note's facts), rejected/ (vetoed proposals, kept only while their reasoning still blocks a tempting mistake, otherwise the whole triplet is deleted), and archived/ (frozen history, below). The classes are a closed set enforced by scripts/agent-note-tree.ts and the classification gates: feature / bug-fix / simplification / architecture / process / testing — the dividing line is architecture governs the source code we ship, process governs the tools and workflows around it, while refactor is deliberately excluded (it overlaps simplification).

Timing is a hard rule: every non-trivial change must add or update at least one Agent Note in the same PR. Non-trivial means a change to behavior, architecture, cross-file/cross-package contracts, process or tooling, testing strategy, on-disk/wire/config formats, or any decision a maintainer might reopen. Updating the Note that already owns the decision satisfies the rule — do not create duplicates; purely mechanical/local edits are exempt. File format is enforced by verify-agent-note-format (part of doc-sync): the first two lines are exactly # Agent Note: <title> and Status: <status> (proposed / implemented / rejected — one-line reason; the status must match the directory); the body opens with ## Problem; the implemented skeleton is Problem → Decision → … → Alternatives considered → Consequences, and spec-speak like Proposal/Plan/Acceptance criteria is forbidden. Every Note must carry ## Alternatives considered: a decision without a record of what it defeated is an invitation to relitigate — precisely the failure Agent Notes exist to prevent. Notes cross-link with relative markdown links and never bare numbers, so links can be mechanically verified and survive directory moves.

archived is frozen

An implemented Note is archived once the decision has fully landed and its reasoning is unlikely to guide future work: the whole English/Chinese/sidecar triplet moves into archived/{class}/, gains a line Archived: YYYY-MM-DD, and is thereafter never edited, translated, reordered, updated, moved, or deleted, nor treated as authority on current behavior. Documentation gates skip archived sources; active documents may still reference it deliberately as history. The enforcer is verify-archived-agent-notes: the closed class tree, complete triplets, archive metadata, sidecar hashes, and the append-only freeze manifest. Archiving is judged with the calibrated dsh-archive-agent-notes workflow — not by counting words or age.

25.2 Bilingual documentation and doc-sync

This repository's documentation is English–Chinese in parallel: *.md and *.zh.md mirror each other section by section, with a *.i18n.yaml sidecar alongside recording pairing status; the pairing contract is owned by docs/i18n/README.md and verified by verify-translation-pairing. Routine bilingual work follows docs/AGENTS.md: terminology guidance and a single-pass active-agent translation that re-records the sidecar; only an explicit user invocation runs the dsh-translate-docs skill. On the Git side there is also a pairing merge driver (pre-commit / pre-merge-commit validate staged records).

The hierarchy tax in docs/AGENTS.md is one sentence: one home per fact. The root AGENTS.md keeps only standing commands (one to three lines each, linking to their home); architecture.md is the ordered map; subsystems/ holds one page of type reference per subsystem; Agent Notes hold decision rationale; postmortem/ is the only layer allowed narrative war stories; cookbook/ holds how-tos with numbered verification steps; package READMEs are the per-package contract (including Model Experience); generated references (tool-catalog, config-catalog, module-graph, and others) regenerate from source with freshness gated. The four writing rules that bite most often: documentation states the current state, not the change history (avoid used to / now / no longer; stories go into Notes or postmortems); one physical line per paragraph (verify-md-wrap); fenced ts blocks must compile (doc-typecheck), and quoted types use ts type-equiv with a manifest registration against drift; cross-references use relative markdown links (verify-md-links). Word budgets are guarded by verify-doc-budgets — when red, relocate first, then compress, and only raise the manifest ceiling when truly necessary. All of this, plus catalog regeneration, JSDoc, and Agent Note checks, aggregates into pnpm run doc-sync (Chapter 23).

The documentation website is a projection, not a home: website/ owns only the VitePress configuration, presentation assets, and the publishing manifest (website/docs.ts maps docs/ sources from every layer into the route trees of both locales); Markdown stays in its owning layer and the projection is written into the ignored website/.generated/ — never hand-edited. When changing this subtree run pnpm docs:check.

25.3 PR rules, labels, and stacks

AGENTS.md's requirement for PR history is deliberate choice: split independent changes; fix a bug in the PR that introduced it first, rather than propagating it forward. Standalone PRs and official stacks may merge-forward or rebase after review; history rewrites use --force-with-lease and abort on remote movement, never raw --force; an in-progress merge-forward preserves its checkpoint before taking a newer base (per .agents/notes/implemented/process/2026-08-02-native-github-stacks-and-optional-rebases.md, with the companion skill dsh-merging-stacked-prs). Before pushing, pick the minimal check set with the dsh-pre-push-checks skill (Chapter 23's evidence-surface mappings); gh stack sync is validated immediately after, and nothing merges before checks pass.

The label tax: every PR carries exactly one kind/* (the kind of change), every materially affected area/*, plus the native GitHub Issue Type — the taxonomy is owned by .agents/notes/implemented/process/2026-08-08-unified-github-label-taxonomy.md.

Read CONTRIBUTING.md first: the current state of external PRs

The repository root's CONTRIBUTING.md states it plainly: DeepSeek Harness is still early and under active development, and it currently does not accept external pull requests. Participation is ecosystem-shaped — report problems and vote in GitHub Discussions; write plugins that excite you and tag the GitHub project with the dsh-plugin topic; write blog posts and how-tos; answer community questions. The repository's stance: packages in the official repo are not inherently more important than community packages — this repository is more like an idea, an official showcase, a source of inspiration. So the PR rules of the previous section and this chapter mean two things for you: follow the full process with the same discipline in your checkout/fork (minimal check sets, same-PR Notes and snapshots), and participate in the ecosystem with out-of-tree plugins (Chapter 24).

25.4 The book-wide navigation map

The twenty-five chapters stack into five layers, each lower one the foundation of the next: without the Cordis mental model you cannot read the event streams; without event streams, the loop; without the loop, the tool pipeline; without seams, the wholesale move of the execution world; without the first four parts, what the testing system and gates protect. 25.6 Chapter recap

  • Agent Notes are the decision ledger: proposed/implemented/rejected/archived × six classes; non-trivial changes carry one in the same PR; ## Alternatives considered is mandatory; implemented stays current, archived is permanently frozen and not authority.
  • Bilingual docs = the *.md + *.zh.md + *.i18n.yaml pairing; one home per fact; current state without change history; one physical line per paragraph; doc-sync aggregates all documentation gates; only explicit invocation runs dsh-translate-docs; website/ is only a projection.
  • PRs: split independent changes, fix in the introducing PR; one kind/* + all material area/* + native Issue Type; stacks may merge-forward/rebase, rewrites use only --force-with-lease; dsh-pre-push-checks picks the minimal set before pushing.
  • CONTRIBUTING.md currently takes no external PRs: participation is via Discussions, blog posts, and the plugin ecosystem tagged with the dsh-plugin topic.
  • The navigation mnemonic: behavior goes to extension points, data goes to event streams, implementations go to provider seams; after the change, pick checks by evidence surface, add a keyless snapshot in the same PR, and carry an Agent Note.
  • The graduation route: architecture.md → capability-seams.md → agent.ts in full → test:snapshot → the first PR.
Common misconceptions
  • Citing an archived Note as current authority — it is frozen history; check implemented Notes and the source for current behavior.
  • A non-trivial PR without an Agent Note — hard rule; updating the Note that already owns the decision suffices, so do not create duplicates.
  • Writing should/migration plans/acceptance checklists in an implemented Note — spec-speak is rejected by the format gate; it records only shipped facts.
  • Writing used to / now / no longer in docs — change history goes into Notes and postmortems; current documents state only current mechanisms.
  • Using raw --force on stacked PRs — use only --force-with-lease, and abort on remote movement.
  • Assuming outsiders can submit PRs directly — read CONTRIBUTING.md first; the current channel is Discussions and the dsh-plugin ecosystem.
  • Forgetting required-on-read and SESSION_FORMAT_VERSION's structural-change rules when touching the persistence format — go back to Chapter 4 and SessionEventMap.
