Chapter 18 · Part IV · Product Front Ends and Protocols

dsh CLI and boot in depth

Through seventeen chapters you have been working inside an already-assembled runtime. This chapter returns to the starting point: the dsh command itself. Who parses the arguments, who loads the plugins, and whose hands the remaining argv finally lands in — this boot chain is the territory of the two package groups apps/cli and packages/boot. Read it through and you can answer the two most common field questions: “why didn't my flag take effect” and “how exactly does a profile's plugin tree grow”.

Learning objectives
  • State the division of labor between bin and args in apps/cli, and why bin.ts dynamically imports per mode.
  • Recite dsh's entry modes (profile, one-shot headless, the web alias, plugin management) and which arguments belong to each.
  • Draw the profile's layered configuration tree: bundle patch → profile patch → home patch → --patch overlay.
  • Describe dsh-app-boot's boot guards (layered env, fail-loud, watchUserPatches) and its signal semantics.
  • Explain how the remaining argv is handed back to app plugins via ctx.cmdlineArgs, and the ESM contract of the source launch.

18.1 Entry and argument grammar: the bin/args split

dsh's npm entry is a single line in apps/cli/package.json: "bin": { "dsh": "lib/bin.js" }. In the installed form it starts the build artifact; in the repository's source form it is apps/cli/src/bin.ts. This file is deliberately kept “thin”: read its own version once, call parseDshArgs to parse argv, then dynamically import the runner for the parsed mode — profile-boot.ts, plugin.ts, or dump-config.ts. 

const invocation = parseDshArgs(process.argv.slice(2), readVersion())

switch (invocation.mode) {
  case 'profile': {
    const { runProfile } = await import('./profile-boot.ts')
    await runProfile({ environment: loadLayeredEnv('dsh'), /* … */ })
    break
  }
  // plugin and dump-config likewise only dynamically import the selected runner
}

Dynamic import is not a style preference but load-surface control: when running dsh plugin to manage dependencies, the process has no need at all to pull in the profile boot chain (the Cordis Loader, bundle resolution, the HMR watcher). Each dispatch path loads only the plugin surface it uses — exactly the echo of “everything is a plugin” at the process entry point.

The sole owner of the argument grammar is parseDshArgs in apps/cli/src/args.ts. It is built on commander but configured with restraint: helpOption(false) (the launcher does not own -h), allowUnknownOption() plus passThroughOptions() plus enablePositionalOptions(). Together the three express one positional rule: launcher flags come first, and the first token it does not recognize is the start of the app arguments. So in dsh --profile web --port 8080, --port belongs to the web app, and dsh --profile web --help prints the web app's help; only a bare dsh --help without a profile prints the launcher's own help. One more detail: --patch is implemented as a repeatable single-value collector and never as a variadic argument — a variadic --patch would swallow every app argument after it.

18.2 Four entry modes

args.ts parses an invocation into three kinds (profile / dump-config / plugin); add the hardcoded web alias and you get the four entry modes of the product documentation:

CommandPurpose
dsh --profile <name>Starts the profile under $DSH_HOME/profiles/<name>; the part of argv after the launcher flags is handed to the app unchanged.
dsh --profile headless "task"One-shot execution: creates a brand-new persistent Agent, submits the task, waits for quiescence, flushes the session, prints the final answer, and exits; exit code 0 if the turn ends completed, otherwise 1.
dsh webA hardcoded alias for --profile web; the following flags belong to the web app (--host, --port, repeatable --trusted-host).
dsh plugin --profile <name> <pnpm args>Forwards the arguments unchanged to pnpm inside the profile directory: install, uninstall, and query external plugins.

Two details are worth remembering. First, the web and headless profiles auto-initialize from product-bundled templates on first use (web is base + web-app, headless is base + headless); a missing profile with any other name fails loud and tells you to run dsh plugin --profile <name> add … first. Second, the headless one-shot run is a “pure core” path: it mounts no ApiProxy, no Host, opens no HTTP port, and loads no Web runtime or browser client — a successful run writes not one character to stderr.

The dsh plugin subcommand itself deserves a look: add resolves relative paths (such as . or ../plugin) against the calling directory first, so inside a plugin source checkout, dsh plugin --profile tui add . installs this checkout rather than something already in the profile. After every successful run, dsh.profile.bundles is reconciled with the actual install state: an installed package that declares "dsh": { "bundle": { "patch": "./cordis.patch.yml" } } enters the layering stack, and uninstalled dependencies leave it.

Finally, two “view the tree without starting” diagnostic modes: --dump-config prints the fully composed configuration tree (including user layers and --patch), while --dump-default-config prints only the bundle layer. dump runs no app command-line provider, so what it shows is the tree from before app arguments are parsed — which is also why it refuses to carry app arguments: printing a tree that would not match an actual launch with the same arguments would only mislead.

18.3 Profiles and the layered configuration tree

A profile is a directory: $DSH_HOME/profiles/<name> (~/.dsh when $DSH_HOME is unset). Three things in the directory each have their own job:

  • package.json — out-of-tree plugin dependencies, plus the profile manifest dsh.profile with its ordered bundles list;
  • cordis.patch.yml — your own patch layer;
  • cordis.yml — the root configuration, holding an empty entry list that is rewritten on every launch.

The entire plugin tree is patched into existence on an empty root. The application order is fixed:

  1. each bundle's patch in dsh.profile.bundles, in list order (the boxed bundles @deepseek-ai/dsh-base, @deepseek-ai/dsh-web-app, @deepseek-ai/dsh-headless resolve first from the dsh installation, then from the profile's own node_modules);
  2. the profile's own cordis.patch.yml;
  3. the home-level $DSH_HOME/cordis.patch.yml (machine-level preferences that apply to every profile, hence above the per-profile layer);
  4. each --patch overlay, in argv order.

Later layers win per line, and “winning” means whole-value replacement of the target line's config, not a deep merge — fields you want to keep must be restated in the patch. A patch pointing at a nonexistent line id is only a stderr warning; an empty file or a comment-only file throws (it parses to no list at all; write [] to disable the layer). There is also one environment switch that becomes the topmost patch: any non-empty DSH_TELEMETRY_DISABLED (even 0 or false) generates a patch that disables the telemetry line — the privacy switch errs toward off, never on.

There are also two infrastructure artifacts that let out-of-tree plugins resolve by bare name: healProfilesModuleFallback maintains the flat $DSH_HOME/profiles/node_modules directory on every launch (one symlink per package the installation depends on), so a bare plugin name in any profile resolves through Node's ordinary parent-directory lookup.

18.4 app-boot: the boot chain and fail-loud guards

packages/boot/app-boot (@deepseek-ai/dsh-app-boot) is the shared boot glue; both bins, dsh and dsh-acp-demo, rely on it so that loader failure behavior has exactly one owner. The key sequence of one runProfile:

  1. loadLayeredEnv('dsh') freezes an environment snapshot: inherited environment > the calling directory's .env > the Harness home's .env, rejecting bootstrap-only file variables, with accepted values landing in process.env;
  2. composeProfile stacks the patch list in the previous section's order (each layer cloned with structuredClone — insert lines from patches are pushed into the tree by reference, so reusing the same parsed object would bake user overrides onto in-memory bundle lines);
  3. installFailLoud installs the guard: a Loader rejection during boot or later becomes one labeled stderr line plus exit(1), awaiting one bounded release cleanup before exiting (a surface holding the terminal restores the terminal before dying);
  4. boot() creates the root context, exposes dshHomePath() to the Loader's !!js expressions, installs the vendored Cordis Loader, runs prepare hooks before any configuration-tree entry mounts — the launcher provides the environment-snapshot service and provideCmdline here — then mounts and awaits the entire include tree, asserting every enabled entry is both loaded and activated; on failure it destroys half the context and throws an error carrying the bin name.

Two resident matters remain after boot. First, config-only HMR: watchUserPatches registers the profile-layer and home-layer cordis.patch.yml with the HMR service, and every edit transactionally re-composes the whole patch list — during re-composition the bundle layer always stays at the bottom and the overlays always on top, so user edits can never squeeze them aside; if a read or parse fails, the last good tree keeps running. One-shot surfaces (headless) destroy the watcher through their own bounded shutdown. Second, signal semantics: SIGTERM is a supervisor's ordinary stop request with exit code 0 on all surfaces; SIGINT is a user interrupt with exit code 130; plugin-tree cleanup gets a five-second budget, and a second signal force-exits immediately.

18.5 Where the remaining argv goes: cmdlineArgs and slash commands

The launcher's entire responsibility for app arguments ends at the provideCmdline step. It provides two things to the tree (packages/boot/cmdline, @deepseek-ai/dsh-cmdline): ctx.cmdlineArgs — the invocation's internal arguments, whose get() returns an immutable snapshot (dsh --profile tui --resume abc yields ['--resume','abc']) — and ctx.appExit — a bounded process-exit request wired to the launcher's shutdown controller.

From there it is the app plugins' business. Any plugin can inject cmdlineArgs, parse it, and publish an ordinary service; parseCmdline(ctx, program) is merely a commander adapter. The key ordering mechanism sits on the Loader side: a line's !!js interpolation is deferred until every injection the line declares has activated, so the web bundle can write: 

- id: webserver
  name: '@deepseek-ai/dsh-host-webserver'
  inject: [webStartup]
  config:
    port: !!js ctx.webStartup.port ?? 3080

Cordis has already populated webStartup before the Loader asks for the webserver config, so the flag beats the value written beside it. Note that this precedence depends on keeping that expression in the line: if a user patch replaces the whole config with a literal, the runtime read is gone (the whole-value replacement semantics of Section 18.3). The snapshot is shared and read-only: multiple plugins can each parse the same argv without interfering, and a profile with no readers simply ignores its own app arguments.

Do not confuse argv with slash commands. The latter happen inside a session: the user types /compact into the input box, and the Web front end hands it to the host's ctx.commands registry through the command.execute RPC — that is the human collaboration plane from Chapter 16, unrelated to process launch arguments.

18.6 The source-launch contract: tsx's ESM hook

pnpm dsh <args…> at the repository root goes through no build: the package.json script starts apps/cli/src/bin.ts directly with node --import tsx/esm and forwards all arguments. This brings one contract you must honor: every module the CLI source-launch path reaches must be ESM — CJS-only exports are not acceptable. The reason is that Node's native TypeScript modes are unavailable across the supported engine range, and tsx's ESM-only hook is the only bridge; the full decision is recorded in .agents/notes/implemented/architecture/2026-07-29-dsh-source-launch-tsx-esm.md.

In practice this contract affects two things for you: when adding a dependency to a package the CLI will reach, confirm it loads under ESM; when debugging a module-resolution error from pnpm dsh, first ask “is it the Typert host artifact or a front-end artifact that's missing” — a missing Typert artifact blows up profile boot as a module-resolution error with no build hint, while a missing front-end or client-plugin bundle produces an explicit prompt at boot to run pnpm run build. The installed form has none of this: it starts the built apps/cli/lib/bin.js directly.

18.7 Chapter recap

  • In apps/cli, args.ts owns the argument grammar and bin.ts dynamically imports the runner per mode; launcher flags come first, and from the first unrecognized token on it is app arguments.
  • Four modes: --profile launch, headless one-shot, the web alias, and plugin forwarding to pnpm; --dump-config views the tree without starting.
  • The profile tree is patched in layers onto an empty root: bundle layer (bundles order) → profile layer → home layer → --patch; later layers whole-value-replace the target line's config, no deep merge.
  • dsh-app-boot owns the env snapshot, the fail-loud guard, the vendored-Loader boot, and config-only HMR for the two user patch layers; SIGTERM exits 0, SIGINT exits 130.
  • The remaining argv is handed back to app plugins via ctx.cmdlineArgs (an immutable snapshot); the Loader interpolates !!js only after the declared injections activate, so flags beat hardcoded values; slash commands go through ctx.commands and have nothing to do with argv.
  • The source launch goes through tsx's ESM hook (node --import tsx/esm); every module it reaches must be ESM.
Common pitfalls
  • Treating --port or --resume as launcher flags — they belong to the app being started; the launcher recognizes only --profile, --patch, and the two dumps.
  • Assuming patches deep-merge — they whole-value-replace the target line's config, kept fields must be restated; replacing a config containing a !!js expression with a literal breaks the flag.
  • Writing only comments in an empty cordis.patch.yml — parsing to nothing throws; write [] to disable the layer.
  • Expecting dsh --profile web --help to print launcher help — only a bare dsh --help with no profile to take over is the launcher's.
  • Introducing a CJS-only module into the CLI source path — it simply will not load under the tsx ESM hook.
