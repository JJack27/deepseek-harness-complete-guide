Chapter 1 · Part I · Landscape and Mental Models

What Is dsh: Product and Repository Landscape

Before you write a single line of dsh-related code, build two maps: a layered map of how a model that can only talk becomes an assistant that gets work done, and a physical map of where the code lives in the repository. This chapter gives you both; every later chapter zooms into a region of one of them.

Learning objectives
  • State the responsibility boundary of each of the four layers: LLM, agent harness, frontend UI, operating system
  • Identify which layer decides whether a shell command may run, and why
  • List dsh's four product forms (Web, headless, ACP, JSON-RPC SDK) and who each serves
  • Locate things by directory in the repository: where the bash tool lives, what the core spine is, what sits in vendor/
  • Avoid treating developer-preview interfaces as stable contracts

1.1 How a model that can only talk becomes an assistant that gets work done

Start with the starting point. When you call DeepSeek's model API directly, what do you get? You send over a sequence of messages and it returns a sequence of text — more precisely, it generates text one token at a time. That is all. It has no hands: it cannot start a process, read or write your files, or fetch a page from the web. And every call is independent: once this conversation ends, it remembers nothing the next time.

An LLM agent is exactly the project of turning such a talking-only brain into an assistant that gets work done. The formula:

agent = model + tool-calling loop

The loop looks roughly like this: the model reads the current conversation and says 「please run the bash command ls -la for me」; a program outside the model actually executes the command and inserts the output back into the conversation; the model reads the output and decides the next step; repeat until the model considers the task done. Note the division of labor: the model only decides what to do; the program outside is what acts. That outside program is the agent harness. DeepSeek Harness (command name dsh) is such a harness.

Break the loop open and the harness is responsible for far more than 「executing commands」:

  • Loop driving — when to call the model again, whether more tools need to run, when the task counts as done;
  • Tool execution and guards — actually run commands, but with guardrails such as timeouts, sandboxing, and output truncation;
  • Permission — when a command touches a dangerous operation: allow, deny, or ask the user first;
  • Session persistence — record everything that happened as a log, so the scene can be restored after a process restart;
  • Prompt assembly — assemble the system prompt, tool list, and conversation history into each model request;
  • Multi-surface UI — the same loop serves the browser, the terminal, and automation protocols.

This list is a preview of the whole book's table of contents: dsh implements each item as a set of replaceable plugins. The rest of the book walks into them one by one.

1.2 The four layers: who owns what

Draw the journey of one 「you ask the agent to run the tests」 request as a picture and you get four layers. Top down: you type in the frontend UI; the agent harness (dsh) organizes everything; its two downward arms reach the LLM API for the model's next decision and the operating system to actually execute processes and read or write files.

Three sentences to remember, one per layer, and no dsh code will lose you later:

  • The LLM API layer does not know tools, sessions, or permission exist. It takes messages and emits tokens. All you can do at this layer is swap models and tune parameters.
  • The agent harness layer (dsh) is this book's protagonist. The tool execution pipeline, permission, logging, and prompt assembly all live here.
  • The frontend UI layer consumes the session state the harness projects and paints it as an interface. Replacing the UI does not affect decision logic; conversely, the UI never makes security decisions on the harness's behalf.

The operating system layer holds no mystery: the harness uses it through subprocesses and filesystem calls, with a sandbox and policy in between (Chapter 12 covers this in detail).

1.3 dsh's product forms: one skeleton, four shells

dsh is not a single program but different outlets of the same plugin tree. The four forms you meet first:

FormCommand / entryWho it's for
Web app npx @deepseek-ai/dsh web People. Starts at http://127.0.0.1:3080 by default; you chat in a browser
One-shot task dsh --profile headless "task" Scripts / CI. Runs one fresh session, prints the final answer, exits — no server at any point
ACP server packages/acp/ Automation clients (editors and the like). Speaks only Agent Client Protocol; no human-facing interface
JSON-RPC SDK packages/sdk/ (TS) + python/ (Python) Programs that drive dsh as a subprocess. The Python side ships two distributions: deepseek-harness-sdk and deepseek-harness-runtime-bin

Switching form switches the shell — frontend, entry point, process shape; what stays is the core of the plugin tree underneath (model adapters, tools, persistence). How that tree grows is exactly the subject of Chapter 3 — a thread picked up soon.

developer preview: breaking changes will come

dsh is currently in developer preview: it iterates fast, and the project explicitly says there will be compatibility-breaking changes. When reading or writing its code, treat no interface as a permanent contract. The flip side is why the repository can afford aggressive refactoring — the contribution guide states the position: prefer fixing the foundation properly over leaving compatibility shims.

1.4 The repository map

After cloning, look at the root first. The most important fact: this is a pnpm monorepo; under packages/, work is divided by capability into 49 package groups and 200+ @deepseek-ai/dsh-* packages (the numbers keep growing — remember the principle, grouped by capability with each package small, not the numbers). Everything is a plugin — every package is one block on the plugin tree.

Each directory's role, one by one:

DirectoryWhat's inside
packages/ All @deepseek-ai/dsh-* workspace packages, grouped by capability: core, api, typert, llm, shell, subprocess, terminal, fs, lsp, skill, web, compaction, context, subagent, bundle, workflow, todo, plan, preset, guard, extensions, hooks, session, session-query, settings, credentials, storage, workspace, sdk, acp, interaction, boot, host, client, examples, test-support, util, attachment, code-runtime, feedback, goal, jobs, mcp, runtime-diagnostics, sandbox, schedule, spill, e2b…
vendor/ The vendored Cordis framework source: a pinned upstream copy, rescoped to @deepseek-ai/cordis (Chapter 2's protagonist)
apps/ cli/ (the dsh command itself) and web/ (the browser frontend app)
examples/ Runnable cordis.yml leaf examples (agent-spine + CLI/ACP/JSON-RPC demos)
docs/ Architecture docs (architecture.md, cordis-primer.md), generated catalogs, cookbook
python/ The Python SDK and bundled runtime: deepseek-harness-sdk and deepseek-harness-runtime-bin
native/ @deepseek-ai/node-addon-landlock-run: a Node native module for the Linux Landlock sandbox
scripts/ Repository quality-gate scripts and generators (the machinery behind pnpm run hygiene and doc-sync)
website/ VitePress source for the documentation site
Key insight: grouped by capability

packages/ is not split into frontend / backend; it is split by capability: the shell group owns command execution, fs owns files, web owns search and fetch, subagent owns delegation, session owns persistence, and so on. Each group usually contains finer-grained roles (interface, implementation, model-visible tool) — Chapter 11 covers that in depth. For now remember one thing: to find a feature, first find its capability group.

1.5 First hands-on lesson: where the bash tool lives

Practice with one concrete question: where is the code for the bash tool the model sees and calls? A beginner's instinct is to dig through packages/core/ — after all, that is the core. But by the group-by-capability principle, bash belongs to the shell capability, so it lives in packages/shell/: 

# Layout under packages/shell/ (bash-related parts)
packages/shell/shell/          # shell capability interface (Service Definition): executor seam
packages/shell/shell-local/    # local implementation (Provider): actually starts processes on this machine
packages/shell/tool-bash/      # the model-visible bash tool (Consumer) ← this is what you're looking for
packages/shell/tool-pwsh/      # the PowerShell twin for Windows

The model-visible tool (tool-bash), the local implementation that executes commands (shell-local), and the interface between them (shell) are three distinct packages. This interface / implementation / consumer trichotomy is one of dsh's core designs; Chapter 11 expands it into the full capability seam model.

So what is core/? The spine — a set of foundation services that every capability hangs from:

core packageWhat it ownsService entry
core/sessionappend-only session event log and in-memory storectx.sessions
core/system-promptassembly of prompt sections and tool schemasctx.systemPrompt
core/toolsscoped tool registry + guarded execution pipelinectx.tools
core/agentAgent interface and live registry, agent/* eventsctx.agents
core/agent-loopthe default driving loop implementing that interfacectx.agentLoop
core/scopeprimitives for scoping registrations per agentlibrary, no ctx key

Note the last column — names like ctx.tools and ctx.sessions. They are the keys plugins use to find one another's services, and they are the protagonists of the next chapter. Even the loop itself (agent-loop) is just one mounted plugin and can be replaced.

1.6 Chapter recap

  • A bare LLM API only generates tokens; agent = model + tool-calling loop. Loop driving, tool execution and guards, permission, persistence, prompt assembly, and the multi-surface UI are all the harness's work.
  • Four-layer division: LLM API (generation) ↔ agent harness (dsh, decisions and execution) ↔ frontend UI (rendering) ↔ operating system (the actual processes/files/network). 「May this command run」 belongs to the harness.
  • dsh's four forms: Web (npx @deepseek-ai/dsh web, default 127.0.0.1:3080), the headless one-shot task, the ACP automation server, and the TS + Python JSON-RPC SDK. Developer preview; there will be breaking changes.
  • The repository is a pnpm monorepo: packages/ grouped by capability (49 groups, 200+ packages), vendor/ the pinned Cordis, apps/ the cli + web, plus python/, native/, examples/, docs/, scripts/, website/.
  • The bash tool lives in packages/shell/tool-bash (its capability group), not in core; core/ is the spine: session, system-prompt, tools, agent, agent-loop, scope.
Common pitfalls
  • Believing the model 「executed」 the command — the model only requests execution; the harness both acts and checks.
  • Believing dsh is one big program — it is a plugin tree assembled at startup; Chapter 3 shows the assembly.
  • Looking for the bash tool in packages/core/ — core is the spine; concrete capabilities live in their capability groups (packages/shell/).
  • Believing permission decisions happen in the UI layer — the UI only renders; replacing it changes no decision logic.
  • Treating any developer-preview interface as a stable contract — an upgrade can replace it wholesale.
