Chapter 4 · Part II · The Core Spine

The Session Log: Event Sourcing's Source of Truth

This is the heaviest chapter in the book. dsh's entire answer to 「what is one agent conversation」 is compressed into one package, packages/core/session: an append-only SessionEvent log. The history the model sees, the transcript the UI displays, recovery after a crash, new sessions forked from the middle, telemetry export — all are projections of the same event stream. After this chapter you should be able to explain to anyone why dsh stores conversations this way.

What you'll be able to do
  • Explain the event-sourcing orientation: dsh stores no 「current conversation state」 and only appends 「facts that happened」, and why that lets fork/resume/transcripts/telemetry all derive from the same stream
  • Read a SessionEvent's envelope fields and the full event vocabulary, including how plugins extend SessionEventMap with declaration merging
  • Describe deriveMessages()'s projection rules, especially the division of labor between assistant/chunk and assistant/message
  • Apply the 「model-visible ⟺ logged」 invariant to a new requirement: decide whether to add a session event or use another channel
  • State what problem SessionHeader, session/end-seed, fork() boundaries, and repair.ts each solve

4.1 Store facts, not state

Imagine you must record an agent conversation. The most intuitive approach maintains a 「current state」: an array of messages, push one in each time the model replies, edit history in place when needed. The problem with this approach is not writing but reading — state can answer 「what is it now」 but never 「how did it get here」. You want to fork and retry from turn 3, replay the streaming output as it happened, account for token usage per step, restore the scene after a crash — every one of those needs forces you to record a separate 「how it evolved」, and the truth scatters into several competing copies.

dsh chooses the reverse: append only facts that happened; store no current state. One conversation is one Session, whose entire content is a grow-only, never-edited SessionEvent log (an append-only log). The user sent a message — a fact. The model emitted a streaming fragment — a fact. A tool call and its result, the start and end of a turn — all facts. Any 「current state」 — most typically the model history — is a projection derived from this log; the deriving function is pure and can be rerun at any time.

That is what 「the session truth exists exactly once」 means:

  • resume (continue the session after a process restart): pour the persisted event stream back into memory and the projections hold as before;
  • fork (branch a new session from some historical moment): take a stable prefix of the event stream as the seed;
  • transcripts (UI replay): render in event order — even the typewriter-like streaming process replays token by token;
  • telemetry: consumes projections of the same stream;
  • persistence: writes the stream to disk verbatim, with no second serialization format to maintain.

The vehicle is ctx.sessions (SessionStore, a Cordis service): it holds the registry of all live sessions in the current process; each Session object internally is a SessionEvent[] log plus a few projection caches. Note the division — the in-memory log is the live truth, and writing to disk is a plugin's job: the persistence plugin subscribes to the session/event broadcast and drains its buffer at session/flush checkpoints. The whole persistence seam is the next chapter's protagonist.

Documentation lives in docs/subsystems/session.md and the Session log section of docs/architecture.md.

4.2 SessionEvent: what one log entry looks like

Each event is a member of a discriminated union (over type), with fixed envelope fields: 

type SessionEvent<T extends SessionEventType = SessionEventType> = {
  type: T            // the event type; the discriminating tag for switches
  seq: number        // monotonic sequence within the session; always equals the number of events before it
  time: number       // Unix epoch milliseconds
  data: SessionEventMap[T]  // typed payload, pure JSON
  ignorable?: true   // marker letting readers safely skip unknown types
}

Two contracts are worth engraving in your mind:

  • The seq = log.length continuity contract. Event sequence numbers start at 0 and are strictly contiguous; an event's index in the log is its own seq. This contract is the foundation of the whole system: persistence backends can write line by line, and after a crash one can tell 「where to truncate」 — all thanks to it. Even high-frequency events like assistant/chunk are not allowed to be filtered out — drop one and seq grows a hole.
  • Payloads must be lossless JSON. Session.append() runs one recursive validation-plus-snapshot at the entrance: values like BigInt, functions, undefined, circular references, Date, and Map throw on the spot — a bad event never enters the log, rather than failing later at flush time. Validated data is deep-frozen — once an event is in the log, no code can rewrite the established fact.

The core event vocabulary

SessionEventMap declares the payloads of all event types. The core members (the ones you will see again and again in any session):

Event typePayload essentialsRole
turn/start / turn/end{ turn }; end carries a TurnEndReasonTurn boundaries. A turn is the shell around zero or more steps
step/start / step/end{ turn, step }Step boundaries. A step = one model call + the tool executions it requests
user/messageA complete UserMessageUser-side messages entering the model-visible surface: human questions, context injected via agent.inject(), goal continuation turns — source distinguishes the three
assistant/chunk{ turn, step, chunk }Raw streaming fragments; token-by-token replay fidelity
assistant/message{ turn, step, message, usage? }The assembled assistant message; derived history uses it, and usage travels with the message
tool/call{ turn, step, callId, name, arguments }The tool call the model requested; arguments is the model's verbatim unparsed JSON string
tool/result{ turn, step, message, error?, meta? }The model-visible result of a tool call; meta is tool-private presentation data (must be JSON-serializable)
request/header{ header: EpochHeader, reason }The full envelope of the next request: call config + rendered system prompt + tool schemas. Log-only
request/contextResolved routing and capacity metadataLog-only, recorded only when routing or capacity changes
session/end-seedEmpty payloadThe boundary marker where the construction seed ends (see 4.6)

「What configuration did the model actually see in this step」 is answered by request/header: the first request of every loop instance records one complete snapshot (reason: 'initial' or 'resume'), and another is recorded whenever the configuration changes ('change'). The latest snapshot alone reconstructs the request envelope — every conversation request is a pure function of the log, which is the other half of reconstructability (4.5).

The vocabulary is merge-extensible

SessionEventMap is not a closed enum. Plugins declare their own event types through declaration merging — for example compaction/start / compaction/end added by the compaction seam, or agent/inbox/spliced added by the agent package: 

// inside some plugin: merge a new event type into the session vocabulary
declare module '@deepseek-ai/dsh-session/types' {
  interface SessionEventMap {
    'my-plugin/notice': { text: string }
  }
}

After the merge, session.append('my-plugin/notice', { text }) is type-safe. These plugin events are log-only by default: they are replayable fact records, carrying no surface metadata and never entering model history.

Extensibility immediately raises a reader's question: what happens when an older dsh reads events written by a newer plugin? The answer is required-on-read by default: on encountering an unknown type with no ignorable: true marker on the envelope, the reader must refuse to rebuild the session rather than silently drop the event — an unrecognized required event may change how the rest of the log reads. Writers mark ignorable only when the event is 「purely informational, and losing it cannot affect reconstruction」. The direction of this default deserves reflection: forgetting the marker results in a refusal (inconvenient but harmless to data), not a silently gutted session (harmful to data). In this repository's builds, all known types are generated into the KNOWN_SESSION_EVENT_TYPES set in known-event-types.ts, and the persistence read path uses it for exactly this decision.

4.3 The append path: append, broadcast, and invariants

Session.append(type, data, ...opts) is the log's only entrance. What it does, in order:

  1. Run one lossless-JSON validation + snapshot each on data and the surface metadata, throwing on failure — the log's entrance is the validation's entrance;
  2. Construct the event object (seq = log.length, time = Date.now()) and deep-freeze it;
  3. Validate the surface transition's legality (4.4);
  4. Resolve a snapshot of the session/event listeners;
  5. Push into the log — the append is committed at this moment;
  6. Invoke listeners one by one; each listener's failure is only logged — it affects neither the return value nor the listeners after it.

Note the order of commit and notification: the event enters the log first, the listeners run after. The append is synchronous and touches no I/O on the hot path — the persistence plugin batches asynchronously in its own buffer (next chapter). Even a crashing observer cannot make a committed fact disappear; that is the 「contained observer」 semantics.

The boundary between log events and Cordis events is most easily blurred here, so it deserves its own paragraph: a SessionEvent is a log entry, not a Cordis event. A log event reaches listeners through the single Cordis emit channel session/event, whose payload is (session, event). There are exactly four Cordis events around the session lifecycle:

Cordis eventModeSemantics
session/createdemitSession publication completed. A synchronous throw can veto publication and roll back
session/disposedemitA published session leaves the store (including the paired notification of a publication rollback)
session/eventemitThe post-commit, fire-and-forget append stream. Persistence, telemetry, and projections all hook here
session/flushparallelAn awaited durability checkpoint: all listeners run in parallel and are awaited, with no waterfall veto

4.4 deriveMessages(): projecting model history from the log

session.deriveMessages() is the pure projection that folds the event log into Message[] (the messages field of a model request). It does not scan all events directly; it walks an ordered surface maintained by surface metadata: only three 「message-producing events」 (SurfaceEventType) can enter the surface — user/message, assistant/message, tool/result — and each of their appends must declare a surfaceOp (how to join the surface); the compiler enforces at the call site that non-surface types (like turn/start, assistant/chunk) cannot pass this parameter. 

// appending a surface event must declare surfaceOp; the ordinary path is append
session.append('user/message', message, {
  surfaceOp: 'append',
  sourceEventSeqs: [],  // optional: which earlier events this references
})

surfaceOp has two forms:

  • 'append': add to the tail of the surface. The ordinary path for user messages, assistant messages, and tool results.
  • { op: 'replace', start, end }: shadow the surface nodes from start to end (inclusive) and substitute this event for them. This is compaction's (context compression) mechanism: the summary event replaces the summarized stretch of history, the old nodes vanish from derived history, but the original events remain in the log — the human transcript reads the original events of append origin while the model reads the compacted surface, and neither disturbs the other.

The per-node projection rules (deriveEventMessage, a public pure function — external rebuilders and the core use the same rules, so they cannot diverge):

  • user/message → one user message, content projected verbatim (human questions, injected context, and goal continuation turns alike; source distinguishes origin);
  • assistant/message → one assistant message; an assistant/message with empty content is skipped — a step truncated by max-tokens or that produced no content still records an assistant/message to carry usage and provider/model, but empty content must not enter the model transcript;
  • tool/result → one user-role message containing a tool-result block;
  • Everything else (turn/*, step/*, plugin log-only events) is structural record and projects to no message.

The chunk/message division of labor (a frequently tested detail)

One step's model output appears in the log twice: one assistant/chunk per fragment during streaming, and one assembled assistant/message after the stream ends. The division of labor:

  • assistant/chunk: replay fidelity and metering. UI typewriter replay and per-token timestamps rely on it; token accounting also reads each step's usage-type chunk first, and for a failed request with no assistant message, its usage chunk is the only metering record.
  • assistant/message: the derivation authority. deriveMessages() recognizes only it. Raw chunks are skipped in derivation — the assembled message is the authoritative copy. It may carry sourceEventSeqs pointing back at the chunks that compose it.

So 「delete chunks to save space」 sounds tempting but directly violates the seq continuity contract — the persistence layer may only change encoding (the JSONL backend's packed chunk row is such an encoding, see next chapter), never delete events. The projection itself is cached: each surface node projects once, later calls process only new nodes, O(new nodes); one replace rewriting the surface rebuilds the cache wholesale (controlled by the replaceGeneration counter). The returned array is a fresh snapshot each time, and its Message objects are shared with the log and deep-frozen — mutating history through the projection is not even representable in JavaScript.

4.5 The core invariant: model-visible ⟺ logged

The repository's most important session rule can now be stated in full:

Whatever enters a model request must be reconstructable from the session log (model-visible means logged). A runtime invariant (the invariant plugin) asserts it. Therefore: adding a new model-visible input necessarily means adding a session event — extend SessionEventMap and make the consuming path render from the log.

This rule turns 「can it be recovered」 from a prayer into a mechanical check. Consider its coverage:

  • Message history: deriveMessages() derives solely from the log (4.4).
  • Request envelope: the system prompt, tool schemas, and call config are carried by request/header snapshots; the latest one rebuilds it, and the request is a pure function of the log.
  • The composition itself: which preset assembled the agent determines the tools and prompts the model sees, so a preset switch must land an agent-preset/selected session event — otherwise the composition rebuilt after resume differs from the one that produced this history, and the model faces a history it cannot act on.
  • Injected context: file-change notices, skill contents, and the like that agent.inject() stuffs into the next request land as user/message events (source marks the origin), not as request-time side-channel magic.

Conversely, runtime details that need no reconstruction after resume — say a tool execution's internal process beyond its presentation metadata — need not and should not invent events. The test: 「can the model still perceive it on its next request?」 If yes, it must be rebuildable from the log; if no, do not pollute the vocabulary. The repository convention writes this as a hard constraint (AGENTS.md: a new model-visible input requires a session event); you will meet it again in Chapter 23 on gates.

One corollary deserves its own call-out: modifying request config at an interception point is allowed — the agent/request waterfall may replace LlmCallConfig — but once changed, the header is recorded into the log (the next request/header snapshot), and the next request compares against the log. You may change the facts; you may not bypass the bookkeeping.

4.6 SessionHeader and session/end-seed

One category of information deliberately stays outside the log: the session's creation metadata. SessionHeader is a small deep-frozen object, read via session.header:

FieldMeaning
versionThe on-disk format version, from SESSION_FORMAT_VERSION (currently 0). Persistence backends reject any other version at load — no migration
id / createdAtSession identity and creation time
cwdThe absolute working directory at creation (must be absolute; storage backends directory by it)
parentSessionSeed lineage: which session this one was forked/resumed from
seedLengthThe prefix length inherited through the seed, letting resume/fork tell 「the parent's history」 from 「this one's own work」
origin / delegationDepthSubagent classification and delegation depth (the recursion budget must survive restarts, hence persisted)
agentPresetThe preset id that assembled this session's agent (4.5 explained why it must persist)

Why outside the log? Because they are storage concerns, not replayable conversation state: they produce no messages, take no part in derivation, and should not consume seq. The lineage fields are pure data — 「who I branched from」 grants no runtime visibility, a point Chapter 6 returns to when discussing scope.

session/end-seed: the persisted projection of the seed boundary

A session created by resume or fork carries an event seed at construction. Seeded events and live writes are byte-indistinguishable, so the Session constructor appends one empty-payload session/end-seed event at the end of the seed, as the boundary of 「where this lifetime began writing」. Three things trip people up:

  • It is the persisted projection of firstLiveSeq (a field on the in-memory object): with the object in hand you read the field; with only disk bytes you read the event.
  • Read the last session/end-seed; do not assume it sits at the firstLiveSeq position — a session opened repeatedly with no work in between does not get a fresh marker each time.
  • The constructor is the only legitimate writer. A plugin appending one itself would silently misread its earlier live writes as seed history. That is why the core's invariant companion deliberately ignores it — writing it wrongly is 「misuse of a power reserved for its author」.

4.7 fork: branching from any stable boundary

Event sourcing pays out in this section. Forking a session copies no 「state」; it takes a prefix of the event stream as the seed: 

// grow a live child session from a stable prefix of source
const child = ctx.sessions.fork(source, boundary?, childSessionId?)

The semantics, parameter by parameter:

  • source: a live Session object or a live SessionId. Passing an object no longer in the store yields SESSION_NOT_LIVE.
  • boundary: an inclusive source event seq; omitted it means 「the current last event」.
  • childSessionId: an optional child session id; omitted, the store assigns one.

The child automatically carries lineage metadata: parentSession, seedLength (= the seed length), and the inherited cwd. Rejections are typed (SessionForkError carries an error code):

Error codeThrown when
SESSION_NOT_FOUND / SESSION_NOT_LIVEThe source id is not in the store / the source object is not a live instance of the store
SESSION_ALREADY_EXISTSThe requested child id is already taken
INVALID_BOUNDARYboundary is not a non-negative safe integer, or points at a nonexistent/non-contiguous seq
OPEN_TURNThe selected prefix ends inside an unclosed turn

OPEN_TURN deserves a pause. The selected prefix is allowed to end on a standalone log-only event between turns (say after one turn/end and before the next turn/start), but not allowed to stop in the middle of an open turn — such a seed would carry dangling tool calls and unclosed boundaries, and the restored transcript would be invalid for the provider. The API chooses to refuse rather than quietly trim: to fork, name a stable boundary explicitly. (The dsh-subagent-fork-in-process scenario, where a tool delegates to a subagent mid-flight, keeps its own completion-prefix trimming because the parent turn is usually still open — that is another package's explicit policy.)

4.8 Crash repair and pre-publication preparation

The log world's last set of mechanisms handles two corners: what to do when a process crashes mid-turn, and who owns a disk-rebuilt session before it is published.

repair.ts: close out, don't truncate

When a process crashes, the on-disk log may stop mid-way: a turn/start never got its turn/end, and a tool call in an assistant message never got its tool/result. dsh's repair semantics (interruptedTurnClosers(events), a pure, deterministic function):

  1. Scan the log, tracking open turns, open steps, and dangling tool calls (an assistant message's tool-call block appeared but has no paired tool/result);
  2. Synthesize one error tool/result per dangling call, with error codes distinguishing two cases: TOOL_NOT_STARTED (never recorded as started — safe to retry) and TOOL_OUTCOME_UNKNOWN (started but the result never reached disk — outcome unknown; the synthesized text explicitly warns the model to 「verify external state before deciding whether to retry」);
  3. Append one step/end (if a step is open) and one turn/end, with reason { kind: 'interrupted' };
  4. The synthesized events' seq continues the log, and time reuses the last real event's timestamp.

The key trade-off: not one event already on disk before the crash is touched. A large turn in a long task may hold enormous tool output; truncation would destroy the work. Closing out merely adds the boundaries so the restored transcript is valid for the provider. Incidentally, interrupted is the one TurnEndReason the loop itself never emits — it belongs exclusively to crash recovery (the persistence backend invokes this repair at load; next chapter). If the log is already balanced (no open turn), nothing is synthesized.

preparation.ts: ownership before publication

Between being rebuilt from disk and being mounted into the store and published to observers, a session passes through a window: whose is it? SessionPreparation answers — it wraps one definite unpublished Session and implements Disposable (usable directly with using syntax): on successful publication or rollback, [Symbol.dispose]() releases the provider's held state exactly once (an optional release callback decides whether to return it to cache or discard it). This lets the resume path share the expensive work — read, validate, freeze, construct the session — across multiple cold reads and the eventual resume; the details belong to the persistence coordinator, expanded next chapter.

4.9 Chapter recap

  • dsh appends facts only and stores no state: Session is an append-only SessionEvent log; fork/resume/transcripts/telemetry/persistence are all projections of the same stream, and the session truth exists exactly once.
  • The event envelope is type/seq/time/data (surface events additionally carry surfaceOp/sourceEventSeqs); seq = log.length is strictly contiguous; payloads must be lossless JSON and are deep-frozen on entry.
  • The vocabulary is declared by SessionEventMap and is declaration-merge extensible by plugins; unknown events are required-on-read by default unless the envelope carries ignorable: true.
  • append validates synchronously, commits on push, then broadcasts session/event; persistence rides the session/flush checkpoint.
  • deriveMessages() projects model history along the surfaceOp-maintained ordered surface; assistant/chunk preserves replay and metering but never enters derivation, assistant/message is the derivation authority; compaction shadows ranges with replace.
  • model-visible ⟺ logged: everything entering a model request must be rebuildable from the log, asserted by a runtime invariant; a new model-visible input requires a new session event.
  • SessionHeader (version, cwd, lineage, preset) is storage metadata outside the log; session/end-seed is the persisted projection of the seed boundary, and the constructor is its only legitimate writer.
  • fork(source, boundary?, childSessionId?) takes a stable prefix as the seed and refuses to stop inside an open turn (OPEN_TURN).
  • Crash repair closes out without truncating: dangling tool calls get error results (TOOL_NOT_STARTED / TOOL_OUTCOME_UNKNOWN), then step/end and turn/end { interrupted }; SessionPreparation holds the unpublished session until publication or rollback.
Common pitfalls
  • Reading SessionEvent as a Cordis event. A log entry is not a member of the event bus; it reaches listeners only through the single session/event emit.
  • Believing assistant/chunk participates in model-history derivation. Derivation recognizes only assistant/message; chunks serve replay and token metering, yet the persistence layer may not drop a single one (seq continuity).
  • Stuffing new model input through a 「request-time side channel」 instead of adding an event. It violates model-visible ⟺ logged, and the runtime invariant rejects it on the spot.
  • Stamping ignorable: true on every new event for convenience. The marker belongs only to purely informational records whose loss cannot affect reconstruction; required-on-read by default is a deliberate safety stance.
  • Treating session/end-seed as a 「session start」 marker, or assuming it always sits at firstLiveSeq. It is the boundary where the seed ends; read the last one.
