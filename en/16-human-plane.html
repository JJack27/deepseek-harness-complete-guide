Chapter 16 · Part III · Capability Seams in Depth

The Human Plane: commands, permission, approval, ask-user

The /compact command in the previous chapter already gave away this chapter's core distinction: human-agent interaction in dsh splits across two planes. On the command plane, slash commands dispatch through ctx.commands and execute directly, without a model turn; on the message plane, everything that must reach the model is logged as a SessionEvent. This chapter walks through the entire interaction service family — the command registry, the one-shot approval waterfall, permission presets, structured questions — and then, together with the three state plugins plan-mode, todo, and feedback, lays out the complete mechanics of how a human steers a running agent.

Learning objectives
  • Use the command-plane/message-plane dichotomy to decide, for any interaction, which route it takes, whether it writes to the log, and whether it enters model history
  • Describe the registration and dispatch contracts of ctx.commands, including the command/run/command/done event pair and agent-scope shadowing
  • Explain the one-shot approval waterfall: the outcome vocabulary, fail-closed behavior, and how a tools/pre-execute ask decision routes to ctx.approval
  • Name the two mechanism knobs that permission-presets bundles, and why custom can only be derived, never selected
  • Distinguish plan-mode's logged state from enforcement: plan mode is soft guidance, while sandbox and approval enforce independently
  • Identify the two destinations of todo and feedback — session log events vs a Host-side sidecar — and why neither enters the model conversation

16.1 Two planes: commands vs messages

dsh's interaction services are all assembled on existing contracts, with no loop changes. The first sentence of the packages/interaction/ group README states the scope: these are the services and plugins for “humans collaborating with a running agent” — questions, approvals, permission presets, commands. Set them on the event-sourcing foundation from Chapter 4 and you get the axis of judgment that runs through this chapter:

  • Command plane: the human types a slash command, and ctx.commands.execute(agent, line, signal) parses and runs the handler directly. No model turn — no request, no tokens; the result is rendered directly by the UI adapter and never enters model history. But the command lifecycle itself is an audit subject: every parsed call appends a log-only command/run (minting a commandId first) and command/done (at settlement) event pair to that agent's session, with no turn wrapping them.
  • Message plane: anything to be sent to the model — direct prompts, steering, injected context — is logged as a surface event (model-visible ⟺ logged) and enters the request through the turn/step loop from Chapter 7.

That the command plane “bypasses the model yet still lands in the log” is not a contradiction: the log is the sole authority for audit and replay, while model history is one projection of it (deriveMessages() takes only surface events). If a command handler does need to trigger model work, it must explicitly use the recipient's Agent (for example, /plan [message] submits the message via agent.steer()) — at that point it has switched to the message plane and owns the resulting message contract itself. The registry never implicitly submits rawInput to an agent.

This dichotomy also explains the differences across surfaces: the Web client provides a command adapter; headless, ACP automation, and JSON-RPC do not — so commands like /compact and /feedback do not exist there, while automatic compaction keeps working. The corresponding row in the “Where new behavior goes” table in docs/architecture.md reads: Add a human command → register on ctx.commands; it dispatches without a model turn.

16.2 ctx.commands: the command registry

dsh-commands owns ctx.commands. Registering a command is register(definition): a lowercase command name (letters, digits, _, -), a description, an optional input hint, an optional recordInput policy, and a cancellable handler. recordInput defaults to true; set it to false when the command's authoritative domain event carries its own payload, and command/run then omits args instead of recording the input twice — /feedback does exactly this (the text lives only in the feedback/record event).

Scoping follows the host+per-scope layering you saw in Chapter 11: registrations on a plain context are global; a command producer mounted under agent.ctx declares its own commands injection, creates an exact agent-scope definition, and shadows the same-named global definition. Duplicate names within a layer fail at registration. Registration and removal notify all commands/change observers so the active adapter can refresh its discovery list. parseCommand() accepts only “byte 0 is a slash + lowercase name + whitespace or end”; every byte after the name is rawInput — command-specific syntax is parsed by each command itself.

The dispatch settlement contract: a handler returns success or error plus optional UI text; on success it may also return sourceEventSeq pointing at an earlier non-command event in the same session, for when that domain event carries a richer presentation (e.g. /compact points at compaction/summary). A lifecycle invariant requires the reference to be to a prior non-command event. An unknown command or invalid syntax returns undefined and produces no log at all (admission misses are not recorded); the bundled adapters refuse unknown slash input outright rather than turning it into a prompt for the model.

16.3 user-approval: the one-shot approval waterfall

dsh-user-approval defines the channel-neutral one-shot approval seam (ctx.approval). An approval.request(req) returns one of four outcomes: allowed-once, rejected, cancelled, unavailable — note that the vocabulary contains only once: there is no allow-always, no memory rule, no grant store, and one grant covers only the single action requested. When the answerer is absent or fails, it fails closed. Every request must belong to an open agent turn; the service appends a paired approval/asked and approval/decided audit record (log-only), and all the model ever sees is the final requesting tool's result.

Answerers are approval/request waterfall listeners — the waterfall semantics from Chapter 2 are a hard requirement here: either return an outcome to answer for this agent, or call next() to delegate; returning silently cuts off the whole chain. Agent-scoped listeners receive only that agent's requests; each deployment assembles exactly one terminal answerer, because sibling listener order is not a policy-precedence mechanism. The ACP automation bridge provides a machine-decided one-shot answerer for the sessions it owns.

The junction with the tool pipeline is from Chapter 8: the tools/pre-execute decision union includes {kind:'ask', reason?} — the registry routes it to ctx.approval; when the seam is not mounted it degrades to deny (the registry consumes approval opportunistically via ctx.get('approval'), with no static injection, so a deployment without it keeps ask→deny semantics). The sandboxed bash tool also goes through this seam on escalation retries. Session-level policy has exactly two settings: ApprovalPolicy is ask or never, the effective value is the last approval/policy event (falling back to configuration), and setApprovalPolicy() is the write path; never refuses before interactive dispatch. The first request and every effective policy change append a short runtime-context snapshot for the model (for example, under never the model is told explicitly to stop requesting sandbox escalations).

Why one-shot only

“Remember my choice” would require grant storage, invalidation, and revocation semantics — a separate domain that does not exist yet. One-shot keeps the audit semantics minimal: one explicit decision per dangerous action, with approval/asked / approval/decided replayable as a pair. To reduce interruptions, switch the whole policy group with a preset from 16.4 instead of letting a single grant generalize.

16.4 permission-presets: user-facing knob bundles

sandbox/mode and approval/policy are two independent mechanism knobs; dsh-permission-presets (ctx.permissionPresets) bundles them into presets a user can understand. Each configured preset name binds one set of values; the bundled defaults are workspace-write (workspace-write + ask) and danger-full-access (danger-full-access + never). A UI adapter can render the table as a picker, while sandbox execution and approval keep consuming their own knobs — a preset is a presentation and user-intent layer, not a new enforcement mechanism.

set(session, name) first appends a log-only permissionPresets/preset event recording the user's choice, then calls each knob's setter when an effective value changes — the choice event comes first, preserving the user's intent when presets share the same bundle; a net-zero choice appends nothing. current(events) prefers a recorded selection that still matches, then the first matching table entry, and returns custom when nothing matches: custom can only be derived, never selected — the user can switch away from a knob combination that no longer matches, but cannot persist it as a target. A table entry named custom throws at load.

Session creation pins three things: permissionPresets/preset, sandbox/mode, and approval/policy land in that session, and later default changes no longer touch existing sessions; a restored seed (including an explicitly empty seed) keeps its effective permissions. The service requires a restricted ctx.shell executor and ctx.approval — loading fails when the combination matches no preset and no defaultPreset is given. Two optional subcomponents activate with the registry: a session projection cell (folding the three whole-value knob events into a selection view) and the /permissionPresets command (a bare invocation reports the current preset and table; with an argument it switches).

16.5 user-questions and tool-ask-user: the model asks the user

So far the human initiates (commands) and the human approves (approvals); dsh-user-questions completes the reverse direction: the model pauses its work and asks the human for a decision. The Service Definition ctx.userQuestions has only two verbs: registerProvider(provider) on the UI side (one context allows a single active provider; duplicate registration throws DUPLICATE_PROVIDER) and ask(request) (awaits the active provider's answer). The vocabulary is the shape of a question form: questions: [{ id, question, detail?, header?, options?, multiSelect? }], with the answer as { answers: [{ id, selected, custom? }] } — for single select, custom overrides selected; for multi-select it supplements it. The loop is unchanged: one tool call awaits one promise, and the tool result returns to the agent loop as usual; while waiting, not a single token is spent.

The Consumer package dsh-tool-ask-user exposes it as the model-visible ask_user_question tool: it accepts the same questions array (the recommended option goes first with (Recommended) appended to its label), calls ctx.userQuestions.ask(), and returns compact JSON. It renders no UI and does not know how input is collected — it only translates parameters and results.

Two boundary designs are worth recording. First, a runtime-owned subagent cannot ask the user: when the request carries an agent, ask() authenticates the exact runtime root identity through the active AgentRegistry; a subagent owned by another live agent is refused (the tool side surfaces this as a DELEGATED_CALLER error instructing the subagent to write the pending question into its final result) — durable lineage is not authoritative: a session with historical delegation depth that is restored as a new runtime root can ask normally. This continues Chapter 14's principle that lineage is data, not visibility. Second, presentation intent: a question's intent field declares it a known kind of decision (such as plan-review); a UI that recognizes it can render a review card, one that does not renders the generic option table, and in both cases the caller reads the same answer fields.

16.6 plan-mode: logged state, not a privileged mode

dsh-plan-mode is the best specimen of two-plane collaboration. Its durable state is a log-only, whole-value-replacement plan/mode ({ active: boolean }) SessionEvent: foldPlanMode(events) returns the last recorded value or false, so resume, fork, and compaction all restore plan state straight from the session log, and the UI observes flips through session/event. Plan mode is state recorded in the log, not a privileged mode of the process — there is no such thing as the runtime gaining special permissions after entering plan mode.

For the model, an activated plan mode renders the configured section text into the system prompt (prompt order 50); for the human, it registers /plan [message] via ctx.commands (a bare invocation selects plan mode; a non-empty argument other than off first selects the mode, then submits the message via agent.steer() as an ordinary logged user message — this is the example of a command handler explicitly switching to the message plane) and /plan off (exits directly, sending no model input). Exit review goes through the always-registered exit_plan_mode tool: executable only while active, and it must obtain the user's explicit approval through ctx.userQuestions (the question carries the plan-review intent, and Approve is the approval label); when the user dismisses the review and speaks instead, the model is told to stay in plan mode and await a message. The tool schema is stable across states — mode switches do not change the tool catalog.

The most easily misunderstood point: plan mode is soft guidance. It steers the model toward exploring a design before delivering a plan, but enforces no restrictions — sandbox mode and approval policy enforce independently and never read or write plan state. Deployments that need hard constraints should configure sandbox and approval (16.3, 16.4) rather than counting on section text. On the session-projection side, when ctx.sessionProjections is mounted it registers a plan cell folding both command/run (named plan) and plan/mode events; view derives { active, pending } — pending is a pure replay quantity that a host restart, another tab, or a cold read can each recover from the log alone.

16.7 todo and feedback: two destinations for plans

dsh-tool-todo registers the model-visible todo_write tool with a maximally restrained design: whole-list replacement is the only operation — every call sends the complete task list ({ content, status }, with status as pending/in_progress/completed); there is no partial update and no per-item editing. Each call appends a full-snapshot event via agent.session.append('todo/write', { todos }); the current list is simply the latest one (last-write-wins on replay). The list belongs to the single agent session that called it — there is no subagent/shared/swarm scope, and non-agent callers are refused outright. allowParallelInProgress is a required config field: whether concurrent active tasks are legal is the deployment's choice, not a fixed rule; but the durable-log invariant does not tighten with it (a log written during the parallel era must still replay after tightening). When the projection registry is mounted, the todos cell clears on every turn/start — a standing plan lives only until the next turn starts, and turn/end preserves the completed list.

The feedback family is two deliberately separated contracts for “recording human feedback.” Command side: dsh-command-feedback's recordFeedback(session, text) appends a log-only feedback/record event, and the /feedback <text> command is merely the human entry to that write path (hence recordInput: false — the command pair event does not duplicate the text). Feedback is trigger-agnostic: another UI, a hook, or a host integration can call the producer directly. The text receives no parsing, truncation, or merging; the log is append-only, with no retraction. dsh-session-telemetry-otel optionally observes this event to release the feedback-gated telemetry prefix. Message side: dsh-message-feedback (ctx.messageFeedback) is an editable per-assistant-message rating/note stored in storage-domain sidecar rows, publishing the Host messageFeedback.list/put/delete Remote contracts with ifVersion compare-and-set and per-message version-conflict semantics — it is not a Session event, not a projection, and triggers no telemetry handover.

Key points

Four kinds of human input, four destinations: slash commands → direct execution on the command plane + a log-only lifecycle; approvals/questions → one-shot decisions inside a tool call, with a log-only audit pair while the model sees only the tool result; plans → log-only plan/mode state + soft guidance in the system prompt; feedback → a log-only feedback/record event or the Host sidecar. None of them stuffs the UI interaction itself into model history.

16.8 Chapter recap

  • Two planes: the command plane dispatches through ctx.commands — no model turn, results never enter model history, but it records log-only command/run/command/done; on the message plane, everything model-visible is logged as surface events.
  • Command registry: global registration + agent.ctx scope shadowing, duplicate names within a layer fail; recordInput: false lets the authoritative domain event own the payload alone; unknown slash input is refused by the bundled adapters rather than becoming a prompt.
  • Approval is one-shot: allowed-once | rejected | cancelled | unavailable, and a grant covers only the requested action; the answerer waterfall either answers or calls next(); absence/failure fails closed; a tools/pre-execute ask decision routes to ctx.approval and degrades to deny when unmounted.
  • permission-presets bundles sandbox/mode + approval/policy (defaults workspace-write/danger-full-access); custom can only be derived; session creation pins the three events.
  • ctx.userQuestions has a single provider; ask_user_question is the Consumer; a subagent owned by a live parent is refused (DELEGATED_CALLER) and durable lineage is not authoritative; intent (such as plan-review) changes only presentation, never the answer fields.
  • plan-mode is logged state: a plan/mode whole-value-replacement event + soft guidance in the system prompt + exit_plan_mode exiting through explicit approval; enforced restrictions come from sandbox and approval independently.
  • todo_write does whole-list replacement, single owner, todo/write full-snapshot events, projection clears on turn/start; feedback splits two ways: the log-only feedback/record event (command-triggerable but trigger-agnostic) and the ctx.messageFeedback sidecar (a Host Remote with CAS).
Common pitfalls
  • Assuming a slash command's result enters model context — it does not; a command handler that wants to trigger model work must use the Agent explicitly and own the resulting message contract.
  • Returning undefined from an approval waterfall listener without calling next() — the whole chain is cut off; waterfall listeners must delegate.
  • Expecting allow-always or “remember my choice” — the vocabulary has only allowed-once; to reduce interruptions, switch policy with a preset.
  • Assuming ask either allows through or raises to the user when the approval seam is not mounted — it degrades to deny; fail closed is deliberate.
  • Treating plan mode as an enforced boundary — it is soft guidance; hard constraints belong to sandbox/approval, and neither reads or writes plan state.
  • Designing a partial-update API for todo_write — whole-list replacement is the only operation, and extending the item shape (ids, nesting) fails loud in validation.
  • Treating message-feedback as a Session event or projection — it is a storage-domain sidecar, a separate contract from the immutable feedback/record event.
