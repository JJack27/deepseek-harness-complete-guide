Chapter 24 · Part V · Engineering and Contribution

Extension Practice: Writing a Plugin from the Cookbook

The first twenty-three chapters had you reading dsh; this chapter has you changing it. Taking add a new capability to dsh as the main thread, we walk docs/cookbook/ three times: add a package, add a tool, add an LLM adapter — each pass extracts a real code skeleton, cites its source, and calls out the contracts that bite. At the end we see how an out-of-tree plugin layers an insert overlay over a shipped composition without ever entering the repository. By the end of this chapter you should be confident submitting your first extension PR.

Learning objectives
  • Create an @deepseek-ai/dsh-<name> package from the docs/cookbook/adding-a-package.md checklist and pass the constraints gate.
  • Write a model-visible tool with defineTool that satisfies the execute() contract and the render-intent discipline.
  • Write an LlmAdapter that satisfies the protocol obligations (usage before finish, two error paths, exec.signal).
  • Explain cordis.yml's !!js boundary and the bare-plugin dependencies requirement, and layer out-of-tree capabilities with an insert overlay.
  • Name the verification obligation for each kind of extension (the same-PR keyless snapshot, the examples' dual smokes).

24.1 The practice mainline: pick the extension point first, then write code

The feature → mechanism map in extension-cookbook.md is the entry point for every extension: every product feature in the repository maps to a listener on some documented extension point — the testable form of the microkernel claim, with not one line changing the loop. Before writing anything, find your place in that table: to add a model tool go through ctx.tools, to change the prompt go through ctx.systemPrompt.section(), to connect a new vendor go through ctx.llm.registerAdapter, and to give your plugin its own settings card go through the namespace schema on ctx.settings (the settings surface is plugin-owned; its companion guide docs/cookbook/adding-a-settings-card.md shipped in 2026-08, see Section 17.9 in Chapter 17). Pick the wrong extension point and every line after it pays interest.

This chapter's three practice passes cover the three most common paths: add a package (when a new capability needs a new home), add a tool (a new model-visible capability), and add an LLM adapter (a new vendor). Each pass ends with the same step: the verification obligation. examples/AGENTS.md requires every example to carry dual smokes — the keyless one (boot the cordis.yml through the real Loader, drive it, assert output and a clean exit; it exists to catch the Loader export errors that hand-mounted tests miss, the lesson of postmortem 0001) and the keyed one (send a real prompt and verify the external world rather than the model's self-report).

24.2 Pass one: add a package

docs/cookbook/adding-a-package.md gives a file-by-file checklist (it is validated against the bash and adapter packages as templates; if it drifts, fix the doc first): 

packages/<group>/<pkg>/
package.json     # copy from packages/core/tools, change name/description/deps
tsconfig.json    # extends ../../../tsconfig.base.json, rootDir src,
                 # outDir lib/types, references point at vendor and each dsh dependency
src/index.ts     # service default export or plugin (name/inject/apply/Config)
README.md        # service API, events, extension points, design notes
                 # + the Model Experience and Known Limitations sections required by gates

The package.json invariants are enforced by pnpm run constraints (scripts/check-workspace-constraints.ts): private: true, version matching the root package.json, type: module, main: lib/index.js, types: lib/types/index.d.ts, and exports["."] types/default pointing at the same pair of files; @deepseek-ai/cordis must appear in both peerDependencies and devDependencies (same version range); every dsh peer dependency is mirrored in devDependencies; @deepseek-ai/schemastery belongs in dependencies (it is the runtime validator); the files list enumerates exactly lib/index.js, lib/invariant.js, lib/types/**/*.d.ts, and the package's own runtime artifacts — no src, declaration maps, or JS maps are published. In-package relative imports carry an explicit .ts suffix in source (for example export * from './types.ts'); the compiler rewrites it to .js in the output.

Registering into the root configuration means touching two places: add one line to the references of tsconfig.host.json (Host packages) or tsconfig.client.json (Client packages) — an ordinary package belongs to exactly one aggregate and never both (the api/remotes split is a repository special case that new packages must not imitate); only a new group requires touching the wildcard in tsconfig.base.json. Everything else (root workspaces, publint, tsdown, oxlint, constraints) is covered automatically by glob or manifest discovery.

Naming is part of the design: name a responsibility that exists stably, not the first implementation or a possible future. A single engine takes a singular ctx key; registries take the plural; role words must match the behavior — Registry owns a named set of registrations that can be added and removed (including lookup, duplicate/priority rules, and lifecycle), Runtime runs live work and owns scheduling and cancellation, Provider supplies one implementation of one capability definition, Store owns exactly one body of data plus its CRUD/snapshot/subscription. The README ends in a fixed order: Model Experience (What the model sees → Verbatim text → Token effect → KV Cache effect) plus Known Limitations and Deferred Work — both sections are gated by doc-sync validators. Finally run step five of the checklist: 

pnpm install        # register the workspace
pnpm run doc-sync
pnpm run constraints && pnpm run typecheck && pnpm run lint
pnpm run build && pnpm run hygiene

24.3 Pass two: add a tool

Tools follow docs/cookbook/adding-a-tool.md (the tutorial version is docs/user/develop/basic/tool.md). The minimal shape — defineTool is the typed helper for first-party tools (tools sourced from MCP enter ctx.tools.register() directly as bare JSON-Schema ToolDefinitions): 

import { readFile } from 'node:fs/promises'
import type { Context } from '@deepseek-ai/cordis'
import { defineTool } from '@deepseek-ai/dsh-tools'

export const name = 'my-tool'
export const inject = ['tools']

export function apply(ctx: Context) {
  ctx.tools.register(defineTool({
    name: 'read_file',
    description: 'Read a file from disk.',   // what the model sees
    parameters: {
      path: { type: 'string', required: true, description: 'Absolute path' },
      limit: { type: 'number' },                // optional by default
    },
    output: {
      schema: { type: 'string' },
      render: (_args, value) => [{ type: 'text', text: value }],
    },
    async execute(args, exec) {
      // the args type is derived from the schema: { path: string; limit?: number }
      return readFile(args.path, { encoding: 'utf8', signal: exec.signal })
    },
  }))
}

Registration is an effect: disposing the plugin fiber unregisters the tool; the schema flows into system-prompt assembly automatically. The contract points of execute(): the arguments are already validated — defineTool validates the model-generated arguments against the unified ParameterSchemaSpec before execute (types, required fields, literal constraints, exact-one unions, nested values); only constraints the DSL cannot express (non-empty strings, positive numbers, cross-field rules) need your own checks. Return exactly one canonical JSON value — output.schema may have an object/array/scalar/null root, and the registry snapshots, validates, and freezes the return value before handing it to output.render; do not return content blocks in the body and do not make callers parse prose to find an id. Throwing or returning an invalid value both count as isError — infrastructure failures use throw, while imperfect-but-successful domain results (like a nonzero exit code) stay in the canonical value for the render layer to interpret. Respect exec.signal; for asynchronous notification use exec.agent.inject() (appends persistent context visible to the next model request — not a wake-up signal).

Render intent is part of the design, decided up front

The tool's UI card is separate from the model result and declared with pure projections: presentCall(args) returns the pending card (generic by default / terminal — your call is a shell command / diff — your call creates or modifies files, optionally with locations so the editor can follow); presentResult(args, { content, isError, meta }) returns the completion card (there are also search and web result shapes). Hard rule: these functions run both on the live stream and on session-log replay, so they must be pure functions of args (+ result) — no I/O, no reading session state, no clock or randomness. Want the file's previous content or the working directory? Stop — that belongs in persisted result metadata or a UI adapter. UI-only formatting (console fencing, relativized paths) never enters the model result. A tool with no UI presentation falls back to the generic card automatically.

Long tasks go to the background: enable run_in_background via producer config, then register through ctx.jobs.start({ kind, label, owner: exec.agent, run }). A successful background branch returns a typed handle (for example { kind: 'background', jobId }); the Native renderer may keep the human-readable started background job bash-1, but Code Mode must never parse the jobId out of that prose. Once the id is published, use the job's own cancellation signal rather than exec.signal — cancelling the outer call merely stops waiting; what kills published work is job_kill, owner disposal, and service teardown.

Deployment policy does not go into the tool itself: extensible allow/deny/ask uses tools/pre-execute (a waterfall returning typed decisions), irrevocable final rejection uses ctx.tools.guard(), timeout/retry/metrics wrap the scheduling lifecycle with tools/execute (only exec.signal is replaceable), explicitly transforming results uses tools/post-execute, and observing the immutable final result uses tools/result. And in Code Mode, every visible registered tool becomes await tools.<name>(args) for free — with types supplied by the ToolArgsMap/ToolOutputMap generated from the same set of schemas.

24.4 Pass three: add an LLM adapter

docs/cookbook/adding-an-llm-adapter.md connects a new model vendor; the reference implementations are packages/llm/llm-deepseek (direct HTTP, eventsource-parser framing) and packages/llm/llm-pi-ai (wrapping an LLM library). Before starting, read the StreamChunk documentation in packages/llm/llm/src/types.ts — both adapters were validated against the protocol conventions it records. The shape: 

class MyAdapter extends LlmAdapter {
  async * stream(options: GenerateOptions): AsyncIterable<StreamChunk> { … }
}

export const name = 'llm-myprovider'
export const inject = ['llm']
export const Config = z.object({ apiKey: z.string(), … })

export function apply(ctx: Context, config: Config) {
  ctx.llm.registerAdapter(['my-provider'], new MyAdapter(…))
}

Registration goes through effects (HMR-safe); one adapter per provider route — duplicate registration throws, and multi-route registration is all-or-nothing. options.provider selects the adapter and options.model is the vendor's model id, so a dynamic-catalog adapter serves new models without lifecycle reconfiguration. Keys take the native cordis path: schemastery Config with an env fallback, fed from cordis.yml via !!js process.env.MY_KEY — the code never reads ad-hoc key files.

Protocol obligations (contracts validated against both implementations): emit usage before finish, and nothing after finish — the safe approach buffers finish/usage until the vendor's end-of-stream marker and then flushes. Tool-call arguments are a bare JSON string end to end; streaming fragments use argumentsDelta, and if the vendor returns parsed objects, re-serialize at block-end. A block's index is assigned by first appearance in the stream and reused by every delta of the same block. Errors have exactly two legitimate paths — throwing from stream() (transport/protocol failure, using an LlmError with a stable code) or ending the stream with finish {kind: 'error' | 'aborted'} (in-band vendor failure); pick one per failure class and document it. Respect options.signal; GenerateOptions fields you cannot honor must throw LlmError(..., 'UNSUPPORTED') rather than be silently dropped. When the vendor needs native metadata like response ids or signatures, emit a minimal lossless JSON projection as finish.replayState and validate it when rebuilding history — never infer native replay from provider/model names alone. Model metadata goes through the provider-neutral capability surface: implement resolveModel(), with reasoning effort as an ordered opaque id the adapter maps onto the vendor request. Structurally, keep wire types, request serialization, transport parsing, chunk translation, and the adapter class as distinct responsibilities.

24.5 Out-of-tree: insert overlays and the third-party boundary

Not every extension has to enter the repository. examples/web-schedule/cordis.yml is the minimal runnable out-of-tree overlay — the entire file is one insert: 

# Opt-in Schedule patch over the shipped Web composition.
# The owner observes only roots published after this overlay loads.
- insert:
    - id: time-context
      name: '@deepseek-ai/dsh-time-context'

    - id: schedule
      name: '@deepseek-ai/dsh-schedule'

It is a patch overlay over the shipped Web composition (the bundle layer of dsh-base + dsh-web-app): the insert appends these lines to the tail of the same include layer, and load order decides visibility — the owner observes only roots published after the overlay loads. dsh web --patch <path> enables it. Comparing with examples/web-cordis/cordis.yml shows the other kind of patch: lines without insert directly replace the entire config of the target line (same id) — it pins 127.0.0.1:3081 on the webserver line, then uses an insert to add the cordis self-check tool.

Two security boundaries of cordis.yml come from the root AGENTS.md: !!js (never !js) is allowed only under plugin config and entry disabled, while all other metadata stays literal — which is why conditional composition is also expressed with overlays; and bare plugins in Raw/Web cordis.yml must appear in their resolver manifest's dependencies, enforced by verify-cordis-config. The template for third-party capabilities is examples/mcp-memory/: three reference configurations, off by default (memorix, mcp-reference-memory, engram), one insert each, pointing @deepseek-ai/dsh-mcp-client at their respective stdio commands — DSH resolves the overlay, starts the subprocess, discovers the MCP tools, and exposes them as mcp__<serverName>__<tool>; DSH does not download servers, create databases, or manage accounts. The stdio bridge deliberately strips environment variables whose names usually carry credentials, plus all DSH_* variables, before spawning the subprocess.

The boundary for examples

examples/AGENTS.md: examples are runnable compositions, not build targets; reusable logic is extracted into packages/ (which has per-file coverage and README gates), and examples keep only cordis.yml wiring, demo artifacts, and e2e/snapshot scenarios; the app package's bin owns the launch glue. Every example has both a keyless and a with-key smoke.

24.6 The end of every pass: the verification obligation

The Verification sections of all three cookbook passes point back to the same docs/testing.md (Chapter 22). Mapped onto this chapter's three kinds of extension: a new package — package-level behavior goes to unit + the coverage gate, and product-visible plugins must have a non-unit real-composition test (a hand-assembled ctx.plugin(...) does not count; it must boot a test-dedicated cordis.yml through the Loader); a new or changed tool — shipped model-visible and UI-visible changes both need assembled coverage (a keyless snapshot scenario in the same PR, with UI card changes going into web snapshots), and rendering replays must replay on macOS/Linux; a new adapter — testing.md owns adapter coverage, real-vendor checks, and release-entry requirements: every protocol obligation has a test, real provider behavior runs e2e, and the release entry runs a built smoke. If the harness cannot yet express your scenario, the policy requires extending the harness before implementing — which is also why acp-snapshot concentrates the comparison machinery into one package.

24.7 Chapter recap

  • Pick the extension point in the feature → mechanism map first, then write code; no path leads into agent-loop.
  • Add a package: the five-piece checklist (package.json/tsconfig/src/README/registration), the constraints gate's invariants, names matching roles, README ending with Model Experience + Known Limitations.
  • Add a tool: defineTool's execute() contract (arguments pre-validated, one canonical JSON value, throw means isError, respect the signal); render intent decided up front and a pure function of args; background work goes through ctx.jobs.start returning a typed handle; policy goes on extension points, not into the tool body.
  • Add an adapter: ctx.llm.registerAdapter registers per route; usage before finish, arguments are a bare JSON string, errors have only the throw and finish {kind} paths, unsupported options throw UNSUPPORTED, native replay state goes through finish.replayState.
  • Out-of-tree: an insert overlay layers over the shipped composition (web-schedule is the minimal template); lines without insert replace the target line's entire config; !!js only under config and disabled; bare plugins must be in the resolver manifest's dependencies.
  • Every pass ends with the verification obligation: the same-PR keyless snapshot + the examples' dual smokes + a real-composition test.
Common misconceptions
  • Hand-writing argument validation inside execute() — defineTool already validates against the schema; add only constraints the DSL cannot express.
  • Wanting to read a file's previous content or the working directory inside presentCall — that is persisted result metadata or a UI adapter's job; the presenter must stay pure.
  • Making Code Mode parse a jobId out of rendered prose — background branches return typed handles; prose is for humans only.
  • Writing deployment policy (timeouts, permissions) into the tool body — put them on tools/execute and tools/pre-execute respectively.
  • An adapter dropping trailing usage after finish or emitting it out of order — buffer until the end-of-stream marker, then flush.
  • Passing a vendor-returned parsed arguments object straight into the stream — arguments are a bare JSON string end to end; re-serialize at block-end.
  • Writing !!js on plugin id/name metadata in cordis.yml — only config and disabled are allowed.
  • Mounting a new package into both the Host and Client aggregates — an ordinary package belongs to exactly one; the api/remotes split must not be imitated.
