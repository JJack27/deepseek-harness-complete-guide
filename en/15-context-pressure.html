Chapter 15 · Part III · Capability Seams in Depth

Context Pressure Management: compaction, spill, and the context plugins

The Chapter 7 turn/step loop assumed every request can hold the entire history — but the context window is finite, and one bash output or one web fetch can fill it instantly. dsh answers with three gates: spill offloads oversized outputs the moment they are produced, pruner trims tool results once pressure triggers, and compaction summarizes older history into a checkpoint when pressure persists. This chapter takes the three gates apart one by one, then adds the final link in the pressure picture: the queued agent.inject() injection waiting for admission.

Learning objectives
  • Draw the three gates' trigger timing and cost ordering: spill (at result production), pruner (after pressure triggers, before region selection), compaction (summary replacement)
  • Explain compaction's surface contract — why the only surface change is a user/message carrying surfaceOp: replace, while all compaction/* events are log-only
  • Configure dsh-compaction-basic's thresholds and retention policy (thresholdRatio / retainRatio / modelPolicies), and explain how the summary call reuses the KV cache
  • Distinguish the pruner's trimming from spill's offloading: one rewrites a surface node, the other moves the full text out of context leaving only a locator
  • State that /compact is a human command rather than a model tool, and describe agent.inject()'s queuing and admission semantics

15.1 The problem: a finite window that tool results fill instantly

The context window is everything a model can see in one request: the system prompt, tool schemas, routing information, assistant completions, tool results, buffered context, and steering. Chapter 9 showed how the system prompt is assembled; Chapter 8 showed how tool results land in tool/result surface events. Put together, an engineering problem appears: history grows monotonically, and the window does not. An unbounded grep -r, a full web-page fetch, or a massive test output can blow up every following request within a single step.

dsh's answer is not a new branch in agent-loop but three independent plugin families hanging on existing extension points:

  • packages/spill/ — spill: when a tool result is produced (tools/post-execute), offload oversized plain-text results to storage, leaving only a bounded preview plus a locator in the model context.
  • packages/compaction/compaction-tool-result-pruner/ — pruner: after the pressure trigger and before selecting the summary region, rewrite over-budget tool/result surface nodes into head + omission marker + tail.
  • packages/compaction/ (the other three packages) — compaction: summarize an older history region into a single checkpoint message, replacing the shadowed region.

The division of labor is written into the group README's role table: measurement (how big is this request, really) belongs to the LLM family's ctx.tokenMeter, not to any gate; spill owns only storage and locating (no retention policy, no retrieval API); compaction owns only the contract for when-is-it-too- big and how-to-summarize, with concrete strategy implemented by backends. This is a group application of Chapter 11's capability seam methodology.

15.2 The three gates: timing and cost

Place the three families into the life cycle of one tool result and the order becomes clear. Gate 1 (spill) is the preventive gate: it intercepts the final result at tools/post-execute, and plain text over maxInlineBytes is offloaded before it ever enters the context — the big output never reaches the window at all. Gates 2 (pruner) and 3 (compaction) are responsive gates: only when the pressure reported by ctx.tokenMeter crosses the threshold (or the provider confirms a window overflow) does the pruner first trim over-budget tool results and re-measure; only if pressure persists does compaction perform the summary replacement.

This ordering is also cost economics: spill and pruner make no model calls — one trades for storage, the other slices plain text; compaction pays one auxiliary llm.stream() call and invalidates the KV cache of the replaced region. So the repository orders them most expensive last: if re-measuring after the pruner's trim is already below pressure, compaction-basic skips the summary outright. Conversely, some situations defeat all three gates: the compaction README states plainly that a single indivisible huge unit (a non-tool node, an untrimmable tool unit) and a system prompt/tool schema that overflows the window by itself are both outside the surface-compaction contract — those are the assembly layer's business (Chapter 9).

15.3 The compaction seam: ctx.compaction's contract

packages/compaction/compaction/ is the Service Definition package: CompactionEngine (ctx.compaction) defines what compaction does — deciding when history is too large and summarizing older regions into a single surface node — without saying how. All three operations are abstract:

MemberSemantics
compactIfNeeded(agent, trigger, signal)Automatic compaction entry; trigger is pressure or context-overflow; returns a CompactionResult, or null when there is no safe region
compactNow(agent, signal)Explicit compaction: summarizes a useful balanced region even below automatic pressure; synchronously reserves an idle-turn admission and records an independent bracket with turn: null
compactRegion(start, end, agent, signal?)Forcibly summarizes the surface-position region [start, end] (inclusive seq); note it is a surface-position region, not a numeric seq range — after one replace, surface order no longer follows seq order

The part of the contract most worth memorizing is the surface contract. Chapter 4 showed that SurfaceEventType is a closed union: only user/message, assistant/message, and tool/result can carry surfaceOp, so compaction/* events can never appear on the surface. A successful compaction is five steps:

  1. Append compaction/start (log-only) — acquiring the lock;
  2. Summarize the selected region;
  3. Append compaction/summary (log-only), carrying the summary, the region, the shadowed seqs, token counts, and the provider/model call envelope;
  4. Append one user/message with source compactCheckpointSource(compactionId) carrying surfaceOp: { op: 'replace', start, end } — the operation's only surface change;
  5. Append compaction/end (log-only) — releasing the lock.

So the model history rendered by deriveMessages() is: the checkpoint summary (in the user role, framed by a <compacted-summary> tag) plus the retained recent nodes; the shadowed original events remain in the append-only log, and replay stays deterministic. The lock itself is a log record: an unpaired compaction/start is the busy signal, and a crash leaves behind a detectable orphan lock rather than a compaction/end that would falsely claim the compaction completed.

Two more deviations from Chapter 11's methodology deserve attention. First, the Definition exports the boundary helper toolPairingBalancedBefore/After(session, seq): a safe cut edge cannot cross an unanswered assistant tool call, and this pairing-balance validation belongs to the Definition for every backend to reuse. Second, this Definition departs from the depend-only-on-cordis convention by depending on dsh-session and dsh-llm — because its verbs are defined on Session and its output is the ContentBlock vocabulary; the two packages are unavoidable. The deviation is deliberate and recorded in the compaction capability-seam Agent Note.

Why the only surface change is that one user/message

Because model-visible ⟺ logged (the Chapter 4 invariant). For the model to see the summary, it must exist as a surface event; while locks, ledgers, and call envelopes are implementation details the model does not need, so they are all log-only. compactCheckpointSource(compactionId) ties the checkpoint to its compaction/* transaction, and isCompactCheckpointSource() lets client code recognize the marker without knowing the backend's identity.

15.4 compaction-basic: the pressure, retention, and summarization backend

dsh-compaction-basic is the basic backend (Service Provider): it requires ctx.llm, ctx.tokenMeter, and ctx.sessions, and owns the complete compaction strategy. Pressure measurement is delegated to the singleton ctx.tokenMeter — it prices the latest canonical log envelope + current surface against the same consumed log version, so the pressure at a step boundary already includes the actual consumption of the system prompt, tools, routing, assistant completions, tool results, buffered context, and steering. The threshold is not an absolute token count but resolves against the currently routed model's window: floor(routedContextWindow × thresholdRatio). This explains why the same compact plugin can safely serve models of different capacities.

There are two trigger paths: with the default auto: true, a serialized agent/pre-step listener checks pressure before request derivation; a provider-confirmed window overflow enters through agent/request-error and takes a separate overflow-recovery path (trim first, then one maximal balanced head reduction). The retention policy compacts the oldest complete surface units and retains a recent tail, with cut edges going through the Definition's pairing-balance helper; old steps inside a runaway turn get no turn-boundary protection.

The summary itself is one direct one-shot ctx.llm.stream() call, not a loop step (so per-call interception happens at llm/stream, not agent/request). It replays the session's own system prompt, tool schemas, and the shadowed region's messages verbatim — image references included — then appends the compaction instruction as the final user message. Because the prefix is byte-identical to the last routed request, the provider's warm-prefix cache is reused; only the trailing instruction and the summary are uncached. The call carries GenerateOptions.purpose: 'compaction' (the DeepSeek adapter sends the x-deepseek-harness-compact: 1 attribution header without touching the model-visible body); only returned text enters the checkpoint — reasoning and tool calls are excluded, or private reasoning would leak and orphan calls would be created.

Config keyDefaultMeaning
thresholdRatio0.8Compact at floor(routed window × ratio)
retainRatio0.16Retain a recent surface as a fraction of the routed window (mutually exclusive with retainTokens)
retainTokens—Absolute token budget for retaining recent surface; must be below the resolved threshold
summarizationProvider / summarizationModel''Paired settings for the summarization model; empty falls back to the newest logged request target, then the agent target
maxTokens8192Generation cap for the summary call
compactionRetries1Extra attempts when pressure is still over threshold
maxOverflowRetries1Maximum retries after a window overflow (0 disables only recovery)
modelPolicies[]Partial policy overrides for exact { provider, model } pairs
autotrueRegister the step-boundary pressure and overflow-recovery listeners; false is fully manual

Every key is optional and validated at plugin load (unknown keys, duplicate targets, mutually exclusive retention forms, and retainRatio not below thresholdRatio all fail the load) — the standard embodiment of the repository's misconfiguration-fails-loud and no-hardcoded-tunables conventions. To swap the summarization implementation, subclass BasicCompactionEngine and override the protected summarize() — the only subclassing hook; pressure, retention, and the event ledger all stay in the base class.

15.5 compaction-tool-result-pruner: model-free trimming

dsh-compaction-tool-result-pruner registers ctx.toolResultPruner; it is an optional companion plugin of compaction-basic — neither a backend nor a model tool. compact-basic reads it through the optional ctx.get('toolResultPruner'), so the two packages assemble independently — enabling it is just placing it before compact-basic as a sibling plugin in load order.

What it does is purely syntactic with zero model calls: pruneSession(session) scans a stable snapshot of the current surface and replaces each over-budget tool/result with a newly appended tool/result carrying surfaceOp: { op: 'replace', start: originalSeq, end: originalSeq } and sourceEventSeqs: [originalSeq]. The replacement copies the original event data in full and changes only content: a retained head, the fixed omission marker [... tool result middle pruned ...], and a retained tail. The original events stay in the append-only log, available for persistence, replay, and exact log inspection.

The three config keys are all Unicode code-point counts: thresholdChars (default 8192), headChars (default 4096), and tailChars (default 1024), constrained by head + marker + tail ≤ threshold, guaranteeing a second scan produces no further replacements. Two points prevent misunderstanding: first, step checks below pressure never trim — the pruner runs only after a pressure or overflow trigger qualifies and before region selection, and after trimming compact-basic re-measures and skips the summary if already safe; second, the character budget is not a token budget — the verdict on whether trimming relieved request pressure still belongs to ctx.tokenMeter.

15.6 command-compact: /compact is a human command

The first line of the group README's known limitations says it plainly: Human command, not a model tool. dsh has no model-visible compact tool — no model-side entry point for triggering compaction exists; automatic pressure and the human command are the only two entries. dsh-command-compact registers a global command on ctx.commands: a bare /compact calls ctx.compaction.compactNow(agent, signal), summarizing a useful balanced region even below automatic pressure, then reports the number of replaced history entries and an estimated token count. Any argument returns a usage error; with no compactable history it returns No compactable history yet..

Notice what happens when the command executes: no model turn. The slash input and the direct result never enter a model request (and spend no tokens), but every resolved invocation records a log-only command/run / command/done event pair on that agent's session — command/done.sourceEventSeq points at the transaction's compaction/summary event, letting the presentation layer fold the command's lifecycle onto the corresponding checkpoint without parsing result text. The closed error codes of ManualCompactionError (busy | changed | summary | commit | persistence) are translated into stable direct-error wording.

Why not let the model compact on its own? Because the entry's owner is the human control plane: the command plane dispatches without a model turn, which is exactly the next chapter's protagonist. Plant the seed here: /compact's bypasses-the-model-yet-logs pattern is the command plane's standard shape.

15.7 spill: offload, don't truncate

The pruner's strategy is keep-head-keep-tail-cut-the-middle — enough for log-type output, but some results carry their value precisely in the full text: the model may later want to grep inside it or read it in segments. The spill family answers that: move the full text out of context, leave a locator. The three packages' role table:

PackageRoleResponsibility
dsh-spillService DefinitionAbstract ctx.spillStore service + vocabulary types (SaveTextSpill / SpillRef / the branded SpillLocator)
dsh-spill-localService ProviderSession-scoped private local file storage
dsh-spill-policyConsumertools/post-execute transformer deciding when to offload and assembling the notice

The seam owns storage only: saveText(input) persists input.content verbatim and returns a SpillRef (locator, bytes written, retrieval hint); genuine storage failures reject. It has no retention policy (that is the util family's dsh-output-retention), no tool-result replacement (that is spill-policy), and no retrieval/search API — the backend's retrievalHint tells the model what to do with the locator. SpillLocator is a branded type rendered to the model as an opaque string: spill-local returns a local path, and future remote backends can return a URI, a database key, or a command token, with the policy and tool consumers unchanged by a single line.

dsh-spill-local's storage layout is a model of safe design: files land in <root>/session-<hash>/<random>-<safeName> — when root is omitted it is a lazily created 0700 private directory under the OS temp directory (a predictable, world-readable root would let other local users read offloaded output or plant symlinks); session-<hash> is a sha256(sessionId) prefix so one session's offloaded files group together for future per-session cleanup; the file name carries an unpredictable hexadecimal prefix, and writes use exclusive owner-only creation (open(path, 'wx', 0o600)), so any already-existing path (including a planted symlink) fails.

dsh-spill-policy is the sole Consumer: a tools/post-execute transformer. It does exactly four things — lets the tool run first (delegating with next()), acts only when the result is plain text over maxInlineBytes, offloads the full text through ctx.spillStore, and replaces the model-visible result with a bounded head/tail preview plus a notice, staying within budget overall: 

<retained head/tail preview>

(Omitted N bytes. Full formatted result stored at: /…/session-…/…-web_fetch.txt.
Use read with offset/limit, or grep this path to search within it.)

The exemption list matters just as much: nested execution (exec.parent present), accepted value substitution, results of the read tool (avoiding a read → spill → read again cycle), decisions other than accept, and results containing any non-text block — all pass through untouched. Everything is best-effort: no session owner, no mounted backend, or a rejected saveText each logs a warning and keeps the inline result — an offload failure never turns a successful call into isError or hides the result. It also has a second arm: it listens on tools/code-dispatch-log and applies the same cap to the durable log copies of Code Mode run_code sub-call results (Code Mode returns in Chapter 17).

Key point

The threshold is policy, not a constant: maxInlineBytes is a load-time validated Config key in UTF-8 bytes; leaving it unset disables the plugin entirely (it registers nothing). The replacement result's byte count never exceeds the cap — the notice's own byte cost is reserved out of the budget and the preview shrinks to fit, so offloading never adds bytes.

15.8 The context group: injections queue, waiting for admission

The last link in pressure management is the party that adds things to the window. The packages/context/ group is a set of product plugins that define no tools and only add model-visible request context: agent-instructions (the workspace instruction chain, assembled by default with the agent spine demo bundle and disableable via bundle config), time-context (current time and elapsed time), tmux-context (tmux location context), and session-reference (bounded snapshots of other sessions, ctx.sessionReferenceResolver). You saw them from the assembly angle in Chapter 9; from the pressure angle the question is: when does this content enter a request?

The answer is agent.inject(message)'s queuing semantics: it queues non-waking next-step context into the inbox. A running driver claims it at the nearest next pre-step boundary; an idle driver holds it suspended until followup() or steer() wakes it. It can even miss a request — if that request's pre-step already claimed its own batch. The Where new behavior goes table in docs/architecture.md compresses this into one line: Add model-visible context → call agent.inject(); it lands in the next admitted request. The injected content lands in the log as user/message events, so Chapter 4's model-visible ⟺ logged invariant holds as usual — and this chapter already showed the evidence: during a manual /compact, an idle-injected context can land between compaction/start and compaction/end, and positional replacement keeps it visible after the checkpoint.

The pressure view adds two more crossings. First, ctx.tokenMeter's pricing includes buffered context and steering — queued injections are already counted in pressure; they are not free. Second, compaction resets the context plugins: agent-instructions's scope re-arms after its context event leaves the visible surface, and the next entering pre-step reassembles the current baseline; the skill catalog (Chapter 17) likewise rebuilds on the next full observation after being shadowed by compaction. The three gates narrow the window, and the context plugins rebuild the necessary context in the freed space — the cooperation of these two forces is complete pressure management.

15.9 Chapter recap

  • The three gates divide by timing: spill prevents at tools/post-execute (offloading oversized plain text, leaving preview + locator); pruner trims over-budget tool/result after pressure/overflow qualifies; compaction summarizes-and-replaces when pressure persists.
  • Cost ordering: spill and pruner make zero model calls, compaction pays one auxiliary llm.stream() call and invalidates the replaced region's cache; if below pressure after the pruner's trim, the summary is skipped.
  • Compaction's surface contract: compaction/start → compaction/summary → user/message (surfaceOp replace, the only surface change) → compaction/end; the lock is a log bracket, and an orphan start means busy.
  • compaction-basic's policy lives entirely in Config: thresholdRatio (default 0.8, resolved against the routed window), retainRatio/retainTokens, modelPolicies, auto; the summary replays the prefix verbatim to reuse the KV cache.
  • The pruner's replacement preserves original events; the character budget is not a token budget — the verdict stays with ctx.tokenMeter; below pressure, nothing is ever trimmed.
  • There is no model-visible compact tool: /compact is a human command on ctx.commands, bypassing model turns while recording the log-only command/run/command/done pair.
  • The spill seam owns storage only: saveText → SpillRef (branded SpillLocator + retrievalHint); policy (maxInlineBytes, unset means disabled) and file layout (0700 root, sha256 session prefix, exclusive 0600 writes) belong to spill-policy and spill-local respectively.
  • agent.inject() queues non-waking context that lands in the next admitted request; injections count toward tokenMeter pressure, and after compaction the context plugins rebuild the catalog and instruction baseline.
Common pitfalls
  • Assuming a model-visible compact tool exists — there is none; the only entries are automatic pressure/overflow and the human /compact command.
  • Confusing pruner with spill: the pruner rewrites a surface node (head + marker + tail, original events stay in the log); spill moves the full text out of context, leaving a retrievable locator.
  • Assuming compaction/* events appear on the surface — the closed union lets only user/message / assistant/message / tool/result carry surfaceOp.
  • Hardcoding thresholds as token counts: compaction thresholds resolve as a ratio of the routed model's window capacity, and the pruner threshold is a character count; all policy goes through load-time-validated Config.
  • Expecting compaction to solve every overflow: indivisible units and system-prompt/tool-schema overflow are outside the surface-compaction contract.
  • Dropping entries from spill-policy's exemption list: nested execution, read results, non-text blocks, and non-accept decisions all pass through untouched — read especially, to prevent an offload cycle.
  • Assuming injections take effect immediately: agent.inject() queues for the next admitted request; when idle it waits for a followup()/steer() wake.
