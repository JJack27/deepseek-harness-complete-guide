Chapter 13 · Part III · Capability Seams in Depth

The Filesystem Capability: the fs seam and the observation policy

Every file change the model makes passes through one and the same seam: ctx.fs. It is the file half of the execution world — twelve storage primitives, three replaceable providers (local / sandbox / E2B), a set of observation policies hanging on event gates, and a cleanly four-layered tool stack. Beyond explaining the seam itself, this chapter answers a subtler question: why is a policy like read-before-write not built as a service but as a companion plugin on the fs/* events. By the end you will be able to follow a single edit call from the tool schema all the way down to the provider's atomic commit.

Learning objectives
  • List FileSystem's primitive groups (identity resolution / execution-world coordinates / reads / atomic changes) and explain why the version guard is optional
  • Compare the three providers: fs-local, fs-sandbox (fences writes only, reads pass), fs-e2b (remote world)
  • Explain the division of labor among the three fs/* events and how fs-observation-policy implements read-before-write with single-slot decisions that don't call next()
  • Explain why tool-fs goes through ctx.fs while tool-fs-search goes through ripgrep under ctx.subprocess
  • Describe str_replace_editor's editing model: view/create/str_replace/insert, unique literal match, no replace_all

13.1 ctx.fs: twelve primitives and an optional version guard

FileSystem (ctx.fs, package dsh-fs) defines the storage primitives within one execution world, without saying how. Backends subclass it and implement twelve primitives. Grouping them by responsibility is the fastest way to remember:

GroupPrimitivesKey points
Identity resolutionresolve(path, opts?)Resolves a path into a stable FsTarget (opaque targetKey + displayPath); the same file reached through different paths must yield the same targetKey. opts.cwd is the base for relative paths (callers pass the session workspace).
Execution-world coordinatesprocessPath / fileUrl / containsGives the canonical absolute path a subprocess in this world can open, the file: URI of this world, and containment judgments — consumers never interpret a targetKey.
Metadatastat / lstat / listDirstat returns metadata only, never content; lstat does not follow the final symlink (a consumer can reject repo-bundled symlinks up front); listDir is one level, in stable name order, and never reads content.
ReadsreadText / streamText / readBytesText reads own UTF-8 decoding and binary/NUL rejection (FS_NOT_TEXT); streaming reads keep cross-chunk decoding in the provider; readBytes requires maxBytes — a known or discovered overrun raises FS_TOO_LARGE immediately, never buffering unboundedly.
Atomic changeswriteText / editTextAtomic create/replace and literal edits; the expected guard is optional — omitted means unconditional; provided means CAS by createIfAbsent / replaceIfVersion / { version }. Changes always run inside the backend's per-target lock; unconditional only drops the version precondition, not the atomicity.

The same package also owns the fs/* policy event vocabulary — expanded in 13.3. The README sums up the seam's stance as fsspec-style storage primitives, half a level above byte-level cat/open: mounted alone, ctx.fs is a complete, unconstrained storage seam; policy is a layer stacked on afterwards.

Why the version guard is optional

Because a bare, policy-less provider is a legal shape. The absence of the guard parameter is not an oversight but part of the contract: omitted = create or overwrite unconditionally. The policy plugin (13.3) has exactly the job of filling the guard in — it translates what version this agent has observed into the provider's CAS precondition. The layering follows: the provider owns atomicity and consistency; the policy owns authorization logic.

13.2 Three providers: local, sandbox, e2b

fs-local (LocalFileSystem) is the local implementation and the base of the other two:

  • Identity: the targetKey is the file's realpath — two paths reaching the same file through symlinks are the same identity, and writes land on the link target (links are preserved). The version is an opaque token derived from dev:ino:size:mtimeNs:ctimeNs.
  • Atomic writes: a temp file is created exclusively with wx (0o600) inside a private staging directory next to the target, fsynced, then published; an existing file's mode is preserved, and on Windows replacement goes through ReplaceFileW to keep the original DACL. createIfAbsent uses a hard link for an atomic publish-without-replace — a file that appears concurrently after the initial probe is preserved and refused with FS_NOT_OBSERVED.
  • Literal edits: an atomic read-modify-write on the same primitive, serialized per target; matching normalizes LF and writes back in the file's dominant CRLF/LF style; empty oldString, zero matches (FS_EDIT_NOT_FOUND), and multiple matches without replace_all (FS_AMBIGUOUS_EDIT) are all rejected.

fs-sandbox (SandboxedFileSystem) inherits all of local's mechanism and adds only a per-call mode fence on writeText/editText: read-only rejects every change (structured FS_SANDBOX_DENIED); workspace-write allows only targets whose normalized path falls inside the writable roots — the workspace root plus the platform temp area, derived by the same writableRoots function as the Seatbelt profile, so the fs fence and the bash runner cannot drift apart; danger-full-access passes everything through. Reads always pass — every mode allows reading. Swapping it in at load time replaces fs-local and completes the switch, with not one line of the model tools changed.

fs-e2b lands the same contract in Chapter 12's remote world: relative paths resolve against ctx.e2b.cwd, GNU realpath -mz supplies canonical identity, and writes publish through a staging directory + same-filesystem atomic rename. It copies nothing, mounts nothing, and syncs nothing from the host workspace — handing cwd a host path only creates a remote directory of the same name.

Threat model: a policy fence, not a kernel boundary

The fs-sandbox README states it deliberately: this fence is a check inside trusted code, checking model-controlled paths. The operations themselves (open, rename) belong to the seam; only the target paths are untrusted, so normalize-then-test-containment is the complete answer; re-normalizing in place right before the write narrows residual TOCTOU. Kernel-level isolation of adversarial code is the job of the ctx.shell sandbox route (Chapter 12) — the two share the same sandboxPolicy, but the mechanism and threat model differ.

13.3 The observation policy: hanging on the fs/* event gates

Who reads and writes what, and whether it was read before writing — that is product policy, not a storage primitive. dsh's answer is a four-layer stack: tools/executor (tool-fs) → policy (fs-observation-policy) → provider contract (dsh-fs) → provider (fs-local and friends). The policy layer has no service: it registers no ctx.fsPolicy, and tools don't inject it — it only registers three listeners on the fs/* events, and the event vocabulary belongs to the Definition.

The three events (declared by dsh-fs, dispatched by tool-fs, heard by the policy plugin):

EventShapeWhat fs-observation-policy's listener does
fs/write-intentsingle-slot decision waterfallUnobserved/observed-absent → { kind: 'createIfAbsent' }; observed-present → { kind: 'replaceIfVersion', version }. Decides fully, never calls next().
fs/edit-intentsingle-slot decision waterfallUnobserved → FS_NOT_OBSERVED; observed-absent → FS_NOT_FOUND; observed-present → { version } as the CAS baseline. Likewise no next().
fs/observedfire-and-forget recordingRecords { kind: 'present', version } or { kind: 'absent' } — synchronous, side-effect-only WeakMap.set.

Observation state is a record of prior observations: a weak map from owner to target with three states (unobserved / confirmed absent / present at some version). A successful read or change records present; when read or str_replace_editor's view/str_replace/insert hits a metadata miss, it first records absent and then returns FS_NOT_FOUND. The policy itself does no file I/O — it only converts observation state into provider guards: present means supply the version; absent means allow only createIfAbsent; an edit without a version baseline is FS_NOT_FOUND outright. A windowed read observes the version of the whole file, so a later targeted edit is allowed only while the file is unchanged.

Single-slot, first-registered-wins is deliberate: the fs/write-intent/fs/edit-intent slots hold exactly one decision-maker, and this plugin occupying the seat is a default-deployment convention, not a hard invariant enforced by the events. It is not a composable authorization chain — layered permissions, auditing, and sandbox interception belong to the tools/execute pipeline (Chapter 8). The biggest dividend the event gate pays is graceful mounting and unmounting: the policy influences the world only through events, so removing it never breaks tool-fs at a service-injection boundary — the tools fall back to the bare provider (unconditional writes/edits, no observation state), and remounting stacks the policy back on. Deployments that mount tool-fs are expected to mount it too, so the default behavior is read-before-write.

13.4 The tool family: tool-fs and tool-fs-search

tool-fs is the model-facing read/write layer: the four tools read / read_image / write / edit plus the executor itself. It owns the tool names, schemas, parameter validation, prompt sections, read windowing (readLimit default 2000 lines, readMaxLineLength 2000 characters per line, readMaxBytes 51200 bytes), and result formatting. The execution sequence per call (the README counts the stats):

  • read: resolve (passing the session cwd) → one stat (type, size routing, version) → readText/streamText → line windowing → ctx.emit('fs/observed').
  • write: resolve → ctx.waterfall('fs/write-intent', …) to get the optional guard → writeText(target, content, intent) → fs/observed. (0 stats.)
  • edit: resolve → ctx.waterfall('fs/edit-intent', …) → editText(target, edit, intent) → fs/observed. (0 stats.)
  • read_image: registered only when a persistent ctx.attachments is mounted and the currently routed model declares image input; reads PNG/JPEG/WebP/GIF through bounded readBytes, commits via attachments.saveImage, and returns an image block.

The tool passes the exec (tool execution context) along as an opaque actor with every dispatch — the events carry only the dsh-fs vocabulary plus the opaque actor, with no model-facing concepts and no agent/session ownership structure. When a fencing provider is mounted (ctx.fs.sandboxMode reports constraints), write/edit likewise advertise the sandbox_permissions + justification escalation surface, mechanically identical to bash in Chapter 12.

tool-fs-search is a deliberate exception: the two discovery tools glob / grep don't go through ctx.fs primitives; instead they spawn the bundled @vscode/ripgrep binary through ctx.subprocess (a --no-config prefix guards against the host's RIPGREP_CONFIG_PATH injecting --pre; model-controlled values are all plain argv elements, and with no shell layer there are no quoting problems). The rationale is in the README: local workspace discovery is inherently a process-based rg workflow, and putting search on ctx.fs would force every filesystem backend to grow a search API. Note that it injects subprocess and not fs — under a remote execution world, search only means something to the model when it is co-located with the workspace.

13.5 str_replace_editor: the model's primary file editor

dsh-tool-str-replace-editor provides a standalone str_replace_editor tool — freely composable with persistent bash, one-shot bash, sandbox bash, or other terminal surfaces. Its schema is four commands:

CommandBehavior
viewFile views use one-based line numbers and preserve tabs verbatim — the text shown is legal input for a literal replacement; directory views omit hidden, dependency, and Python cache entries and go two levels down.
createCreates a new file.
str_replaceReplaces one literal text span: requires exactly one unique match; zero or multiple matches are errors, and the errors speak only in the public old_str vocabulary. There is no replace_all parameter.
insertInserts at the chosen zero-based insertion boundary, adding no implicit trailing newline.

The editing model's orientation is clear: precise beats lenient. No regex, no replace-all, tabs outside the edited span preserved verbatim, matching defined over the displayed text — together these constraints guarantee that what the model sees is what it can replace, and one view's output is legal input for the next str_replace. A metadata miss first records confirmed-absent and then returns FS_NOT_FOUND, so a path deleted externally can be restored with create through the mounted policy's guarded file creation; but absence does not authorize str_replace or insert.

It is not a bypass: every change goes through fs/write-intent or fs/edit-intent, resolves the current session sandbox policy, and delegates enforcement to the mounted filesystem and policy plugin. Put differently, str_replace_editor owns the editing model, while atomicity, version guards, and the sandbox fence all come from the machinery of 13.1–13.3 — exactly the payoff of seam layering: swap the editor and the policy keeps working; swap the provider and the editor keeps working.

13.6 Chapter recap

  • ctx.fs's twelve primitives fall into five groups: identity resolution, execution-world coordinates, metadata, reads, atomic changes; the version guard is optional — omitted means unconditional, atomicity is always there.
  • Three providers: fs-local (realpath identity, staging + atomic publish, DACL preservation), fs-sandbox (fences writes only, reads pass, FS_SANDBOX_DENIED, shares writableRoots with Seatbelt), fs-e2b (remote world, no host sync).
  • Policy is not a service: fs-observation-policy hangs only on the fs/* event gates — two single-slot decision waterfalls (no next() calls) + one fire-and-forget recording event; mounting and unmounting are graceful, and tools never break at an injection boundary.
  • Observation state = a record of prior observations; windowed reads observe the whole-file version; read-before-write converts observation records into provider CAS guards.
  • tool-fs is tools and executor in one (read/write/edit/read_image + windowing + fs/* dispatch); tool-fs-search deliberately bypasses ctx.fs and runs bundled ripgrep through ctx.subprocess.
  • str_replace_editor: view/create/str_replace/insert, unique literal match, no replace-all, tabs preserved, with every change going through the fs/* gates.
Common pitfalls
  • Adding a search method to ctx.fs — search is an rg workflow; putting it into the provider contract would force every backend to implement it.
  • Stacking another decision-maker on fs/* as an authorization chain — the slot is single-slot, first-registered-wins; layered interception belongs to tools/execute.
  • Expecting observation state to survive across sessions — the WeakMap is an in-process weak reference; after a resume you must read again.
  • Assuming fs-sandbox fences reads — every mode passes reads; the fence sits only on writeText/editText.
  • Looking for replace_all in str_replace_editor — it is deliberately absent; multiple matches are an error and the model should pick a longer anchor text.
  • Assuming readBytes truncates — maxBytes is required; an overrun raises FS_TOO_LARGE immediately, and buffering is never unbounded.
