Chapter 22 · Part V · Engineering and Contribution

The Testing System: Five vitest Channels and Replay

The preceding twenty-one chapters had you read the dsh runtime; this chapter reads its burden of proof. The repository splits testing into five vitest channels — unit, e2e, snapshot, web, web-stress/perf — and each channel answers only one class of evidence question: who needs a key, who runs in CI, and who produces the golden fixtures committed to the repo are all clearly divided. Once you understand this system, you know what tests your change must add, and why package tests can never substitute for the assembled application transcript.

Learning objectives
  • State each of the five vitest channels' entry command, include pattern, and evidence surface.
  • Explain why test:coverage (not test) is the CI coverage gate, and what per-file 100% means.
  • Distinguish what each of DSH_SNAPSHOT's replay / record / refresh modes needs and whether it writes golden fixtures.
  • Describe how llm-replay turns a persisted session log into a keyless replay script, including grouping by (turn, step) and binding child sessions by first-call order.
  • Recite the core policies of docs/testing.md: add a keyless snapshot through a real runnable example in the same PR, fixtures must replay on macOS/Linux, and fix fixtures rather than normalizers.

22.1 The five channels: one matrix

Each channel has its own vitest configuration at the repository root: vitest.config.ts (unit), vitest.e2e.config.ts (real API), vitest.snapshot.config.ts (golden-fixture replay), vitest.web.config.ts (browser), plus vitest.web-stress.config.ts and vitest.web.perf.config.ts (stress and performance). They are not layered by fast-versus-slow but by evidence surface: unit proves in-package behavior, e2e proves real provider behavior, snapshot proves the complete assembled transcript, web proves real rendering in the browser, and stress/perf proves how the Web interface behaves under load.

Note one easily missed detail in the matrix: e2e's self-skip without a key is not a degraded run — the whole suite simply skips. Keyless CI and keyless contributors always see green, but that is not a cost signal. Real provider evidence comes only from a run with a key. Conversely, snapshot's replay is complete evidence: it genuinely assembles an ACP/headless example, genuinely runs the process and protocol, and only swaps the model responses for a recorded script.

22.2 The unit channel and the coverage gate

The include list of vitest.config.ts draws the unit channel's territory: 

const testIncludes = [
  'packages/*/*/tests/**/*.spec.{ts,tsx}',
  'apps/*/tests/**/*.spec.ts',
  'examples/*/tests/**/*.spec.ts',
  'scripts/**/*.spec.ts',
]

Tests live next to the code under test (tests stay beside the code region they examine). The configuration has two vitest projects: thread-safe and process-bound — the latter houses suites that depend on process-global state or timing-sensitive process I/O and cannot be reliably isolated by worker threads under aggregate-gate contention (for example packages/session/session-persistence-jsonl/tests/jsonl.spec.ts and packages/boot/app-boot/tests/app-boot.spec.ts); both sides use a forks pool for Node stability. Every suite loads the setup file scripts/test-invariants.ts.

docs/testing.md sets three writing disciplines for the unit channel. First, every registry needs an HMR-safety test: dispose the fiber that contributes it and assert the cleanup is complete — the test-side reflection of Chapter 3's registrations-are-effects. Second, prioritize edge cases, error paths, event ordering, and concurrency races. Third, contract regressions get permanent tests; the exemplar is packages/core/agent-loop/tests/contract-regressions.spec.ts.

Coverage: the gate is test:coverage, not test

The CI coverage gate is pnpm run test:coverage (vitest run --coverage): 100% of statements / branches / functions / lines per file under packages/*/*/src. Per file rather than per total, so that a well-covered large file cannot subsidize an uncovered small one. Every exemption in the configuration (types-only files, thin bin/worker entries, the GUI debt list, Windows-only sources, and so on) is explicitly listed with a justification comment; for example, on a host without a real pwsh, the pwsh-local executor suite self-skips and the configuration exempts that file accordingly, while the CI runner has pwsh and still enforces the full bar.

There is also a reading discipline: an uncovered line is often the gate correctly flagging dead code to delete, not a missing test to add. Line coverage is necessary and never sufficient — it proves the line ran, not that the feature works in its released form. The remaining three channels supply that other half, the sufficient one.

22.3 e2e: real API and the with-key policy

vitest.e2e.config.ts takes only **/*.e2e.ts, and its scope is deliberately narrow: packages/*/*/tests, apps/cli/tests (only cli, not apps/* — apps/web e2e belongs to the web channel), and examples/*/tests. It spends real money on tokens, and the configuration shows it everywhere: a 120-second testTimeout, retry 2 (a shared internal key hits concurrency quotas, so transient jitter gets retried), DSH_E2E_MAX_WORKERS (default 4) limiting parallel files, and no coverage — coverage belongs to the unit channel.

The with-key policy in docs/testing.md is titled inference is cheap here: do not skimp on real-API tests. Keyless tests prove only that the pipeline works; only a run with a key proves the agent works against a real model. Cover prompts that write files, multi-turn conversations, tool use, and mid-flight cancellation. The highest-value form is the smoke test: start a real example, send one prompt, then inspect the world. They specifically kill the failure class where unit is all green but the product is broken — mocks cannot catch it; the postmortem is recorded at docs/postmortem/0001-acp-default-export-drops-inject.md (a default export silently dropped an inject).

The e2e channel has two more iron rules. Verify the world, not self-reporting: assertions should re-run commands and re-read files outside the agent; keyword-probing the agent's own output lets a cheating agent pass. Untouched files must be asserted byte-identical. e2e tests own their resources: create the harness inside the test, afterEach disposes it (also on failure, retry, and timeout); shared fixtures go in an ordinary tests/harness.ts, never inside another *.e2e.ts — importing a spec re-registers its describe and doubles the real API calls.

Real implementations over mocks

Mock only expensive or non-deterministic boundaries — the LLM adapter, the network, the clock; everything downstream of the boundary stays real. A hand-rolled stand-in can only prove the bridge moves bytes, not that the released tool works as asserted. The bridged tool-call tests pair a scripted mock model with real tools and executors: makeBridgeHarness({ withBash: true }) plugs in dsh-bash-local and dsh-tool-bash, then genuinely runs echo.

22.4 snapshot: record / refresh / replay

The snapshot channel's configuration file vitest.snapshot.config.ts takes scripts/**/*.snapshot.ts, apps/cli/tests/**/*.snapshot.ts, and examples/*/tests/**/*.snapshot.ts (plus apps/web/tests when DSH_EXAMPLE_MODE=lib). It switches among three modes with the DSH_SNAPSHOT environment variable:

ModeCommandKeyBehavior
replay (default) pnpm run test:snapshot Keyless Replays model responses from committed golden fixtures, runs the full assembly path, and compares the assembled requests, normalized protocol/transcript output, and re-persisted logs. It never writes the committed expected outputs.
record pnpm run test:snapshot:record Requires DEEPSEEK_API_KEY Calls the real API, reruns scenarios, and writes model responses and expected outputs back to the fixtures and expected files (quoting the config comment: only record reads the key from the environment or the root .env; replay/refresh never load .env). Use it to re-record when the model transcript changes.
refresh pnpm run test:snapshot:refresh Keyless Replays the committed scripts but updates the current expected outputs — for when the replay inputs are still valid and only the output side needs refreshing. Every JSONL and expected diff must be reviewed by a human.
Try it — the record / replay snapshot modes
Switch modes.

The parallelism strategy also differs by mode: replay writes no golden fixtures and each scenario holds its own mutable runtime state, so it parallelizes at file level, with DSH_SNAPSHOT_MAX_CONCURRENCY (default 5) limiting concurrency within a file — the value 1 restores fully serial execution on constrained machines; record and refresh stay serial — every record scenario spends real API quota, and refresh's write-back harvests volatile values from fixtures already on disk, where concurrent writers would destroy the golden fixtures.

The golden fixtures have clear ownership: ACP automation scenarios live in examples/<name>/tests/snapshots/ (examples/acp-agent is the main venue); examples/headless-agent owns internal canonical-event JSONL snapshots and replay fixtures; apps/cli alone owns the product-grade dsh --profile headless acceptance; completed interactive terminal journeys use JSONL-driven scenarios under apps/cli/tests/snapshots/; browser-rendered Web GUI journeys are in apps/web/tests/snapshots/. There is also one famous piece of fine-grained design: only a single ACP scenario (text-turn) pins the full system-prompt/tool-schema content; the other fixtures tokenize it, so a single edit only churns one line.

22.5 llm-replay: the session log is the fixture

packages/test-support/llm-replay (package @deepseek-ai/dsh-llm-replay) is the engine of replay mode. Its core insight: the fixture is the persisted session log itself — <scenario>/session.jsonl. In Chapter 4 you learned that assistant/chunk events carry every StreamChunk; grouping them by (turn, step) reconstructs the chunk sequence of every stream() call the agent-loop makes. Recording is therefore just run the real agent once and harvest the .jsonl — this plugin does no recording of its own. 

// ACP / headless snapshot suites mount it via the Loader, replacing the real LLM adapter
- id: llm-replay
  name: '@deepseek-ai/dsh-llm-replay'
  config:
    providers:
      - id: deepseek-official
        name: DeepSeek
        models:
          - id: deepseek-v4-flash
            contextWindow: 128000
  # file / overrideFile / childFiles default to $DSH_SNAPSHOT_FILE and similar
  # environment variables, injected per scenario by the snapshot harness

Log derivation cannot cover two failure shapes: a pure throw before any chunk (for example HTTP 401, where the log holds only turn/end {error}) and cancellation/hang (a timing matter, not chunk content). Scenarios that need them provide an optional sidecar <scenario>/replay.override.json: it either replaces the derived script wholesale (a bare ReplayEntry[]) or patches by 0-based call index ({ patches: [{ at, entry }] }; when at equals the derived length, a retry attempt is appended after an injected one-shot transient throw). The sidecar document, every patch, every entry, and every chunk discriminant tag are validated at file load — misconfiguration fails loud is just as much an iron law here.

Nested agents are the second subtlety. A scenario where the parent delegates to in-process subagents records multiple logs: session.jsonl (the parent) plus session.1.jsonl, session.2.jsonl, and so on — each agent is its own Session on the same context. A live session id is a fresh random value on every run and never equals the recorded one, so replay binds by first-call order: scripts are sorted by the header's createdAt (the parent first — it must stream before it can delegate), the first live session to make any call claims the first script, the next new session claims the next, and each advances its own cursor. More live sessions than recorded scripts fails loud.

The programmatic entry point is installLlmReplay(ctx, config), which returns a ReplayHandle: dispose() keeps HMR safety, and assertConsumed() asserts at teardown that every recorded script was bound to a live session and that every binding cursor is exhausted — turning the scenario quietly drove the model fewer times than expected into a clear diagnosis. The web browser e2e channel bypasses the Loader and installs it directly precisely to keep this teardown consumption handle.

22.6 The six-piece test infrastructure

Besides llm-replay, packages/test-support/ holds five more support packages. They are test-tier infrastructure, not product APIs:

PackageRole
llm-replay The keyless replay plugin that rebuilds model streams from recorded session logs (Section 22.5).
llm-mock-server A scriptable OpenAI-compatible HTTP/SSE server for exercising real LLM adapters, the agent loop, and recovery strategies without a provider key. --sequence is a FIFO behavior table: connection_reset, partial_disconnect, stall, rate_limit, success, tool_call_success, and more. Start it with pnpm run mock:llm and point the released DeepSeek adapter at it (DEEPSEEK_BASE_URL).
acp-snapshot The ACP snapshot suite toolbox, four layers importable separately: launchAcpTestAgent (the process launcher), runScenario (the scenario harness), the normalization pure functions (stdout/session log/cwd tokenization/system-prompt and tool-schema scrubbing), and defineAcpSnapshotSuite (the factory that registers a whole describe/it tree from one scenario table).
agent-loop-testkit mountAgentLoopTestDependencies(ctx) installs the LLM, session, system-prompt, tool, and agent services in dependency order; the adapter, optional plugins, the AgentLoop itself, and Context teardown stay with the caller, keeping scenario-specific ordering visible.
client-runtime The jsdom slot-test runtime: a real Cordis Context, the production SlotRegistry and web-react renderer, paired with typed doubles implementing the same outward-facing surface. When the production surface changes, the test bench breaks at compile time — instead of drifting silently.
loader-smoke The shared subprocess harness that boots apps and cordis.yml through the Cordis Loader: resolveExampleLaunch chooses between local src mode (tsx) and CI lib mode (plain Node + package exports); runLoaderSmoke owns the isolated cwd, DSH homes, deadline, and cleanup; runFixtureTurn drives one task and returns the final answer and usage.

The reason this infrastructure exists is written in the first paragraph of acp-snapshot's README: all comparison/guard mechanisms are concentrated in one package under the per-file coverage gate, rather than each example rolling its own copy. A consumer's *.snapshot.ts is usually just one scenario table plus one factory call.

22.7 The core policy: why snapshots are irreplaceable

The When a snapshot test is required section of docs/testing.md is the constitution of the whole system: every non-trivial model-visible, protocol-visible, or human-visible behavior change must add or update a keyless scenario through a real runnable example's snapshot suite in the same PR. Package tests, e2e assertions, mock/test-only compositions, PR descriptions — none can substitute for the assembled application transcript; extend the harness first when needed. AGENTS.md lists the same rule as a repository-level convention and adds two more: fixtures must replay on macOS/Linux (fix fixtures, not normalizers); and a new capability seam, lifecycle variant, or transcript surface must name its coverage at every layer at planning time, and you must verify the harness can express it before implementing.

Why are package tests not enough? Return to the postmortem-0001 class of failure: a default export drops an inject, unit-level composition stays green, and the product only breaks under a real Loader composition. So the policy also demands testing the real entry path: product-visible plugins must have a non-unit real-composition test; a hand-assembled ctx.plugin(...) suite does not count — it must boot a test-dedicated cordis.yml through the Loader and the app/process. The real entry path also means released artifacts: a package's bin runs the built lib/bin.js under plain node, exposing failures tsx would mask (settle races, module resolution, swallowed load failures); built-artifact smokes must stay green (packages/examples/*/tests/built-bin.e2e.ts and the like) and must assert a nonzero exit when config is genuinely missing.

The resolution side has its own discipline: test resolution stays on the source plane — every vitest config points vite-tsconfig-paths at tsconfig.base.json, so bare workspace imports resolve to src and never fall through package exports to the built lib/ (where stale artifacts would install a second module singleton). Built artifacts are consumed only in explicitly declared settings: lib-mode subprocesses and built smokes.

Test subprocess launch modes

CI and the build-carrying test channels run every example or Cordis-config subprocess from the built lib/ through a shared dual-mode launcher — do not hand-write --import tsx for these subprocesses. Protocol/OS fixtures that load no Cordis run plain Node directly on erasable .ts files, without tsx and without the root paths mapping. Choosing src is optional only when the thing under test is itself source-path resolution, and the test must state that contract. AGENTS.md's one-line summary: config subprocesses run the built lib/ under plain Node; source regressions use their declared launcher.

22.8 Chapter recap

  • The five channels divide by evidence surface: unit (package-level behavior), e2e (real providers), snapshot (assembled transcripts), web (Chromium rendering), stress/perf (load).
  • test:coverage, not test, is the CI coverage gate: per-file 100% on packages/*/*/src; an uncovered line is often dead code to delete.
  • e2e self-skipping without a key is not a cost signal; smoke tests (start a real example, send one prompt, inspect the world) specifically kill the unit-all-green-product-broken class.
  • DSH_SNAPSHOT: replay is keyless, writes no golden fixtures (the CI default); record needs a key to re-record fixtures; refresh is keyless and refreshes expected outputs; every diff must be human-reviewed.
  • llm-replay's fixture is session.jsonl: assistant/chunk grouped by (turn, step) rebuilds streams; the override sidecar supplies pure throws/cancellations; child sessions bind by first-call order; assertConsumed() is the backstop.
  • The constitutional clause: a non-trivial model/user-visible change must add a keyless snapshot through a real runnable example in the same PR; fixtures replay on macOS/Linux, and you fix fixtures, not normalizers.
  • Test resolution stays on the source plane; config subprocesses use the built lib/ plus the shared dual-mode launcher — never hand-written --import tsx.
Common misconceptions
  • Assuming a green pnpm run test satisfies coverage — the gate is test:coverage, per-file 100%.
  • Reading e2e's self-skip as e2e running keyless too — a skipped suite produces no provider evidence at all.
  • Calling package tests or a PR description enough after a model-visible change — the constitution requires a keyless snapshot scenario in the same PR.
  • Editing the normalizer when a snapshot diff looks wrong — fix the fixture first; normalizers are shared pure functions, and changing one affects every scenario.
  • Hand-writing --import tsx for example subprocesses — use the shared dual-mode launcher; CI runs from the built lib/.
  • Importing shared fixtures between *.e2e.ts files — importing a spec re-registers its describe and doubles real API calls; shared code goes in tests/harness.ts.
