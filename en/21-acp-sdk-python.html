Chapter 21 · Part IV · Product Surface and Protocols

ACP, the SDKs, and Python

The Web UI is only one way for a human to drive. When the driver is another program — an orchestrator, a test framework, another agent harness — dsh offers three out-of-process paths: the ACP server, the TypeScript SDK, and the Python SDK. The three differ in form but share one foundation: each drives a complete harness process over JSON-RPC on stdio, and none needs a browser. This chapter lays them out side by side and gives you the criteria for choosing.

Learning objectives
  • State the shared foundation of the three out-of-process drive paths and the form each takes.
  • Describe ACP's automation-only positioning, its method surface, and the trade-off of putting only committed messages on the wire.
  • Distinguish the roles of the SDK's three packages: protocol (the wire contract), server (the plugin), client (the TS client).
  • Explain the division of labor between the two Python distributions, and why zero configuration is explicit parameter injection rather than a hidden fallback.
  • Choose a path for a caller by situation: a standard-protocol client, repo-adjacent TS automation, or pip-install-and-go.

21.1 Three out-of-process drive paths

Remove the entire browser half of Chapters 19 and 20, and the remaining host process is still a complete harness: agents, the session log, the tool pipeline, and the full capability surface are all there. So a program acting as the client needs exactly one thing — an inter-process protocol. dsh provides three:

  • ACP (packages/acp/acp): implements the external Agent Client Protocol, JSON-RPC over stdio, for any client that speaks that standard protocol; the typical in-repo client is dsh-subagent-acp (Chapter 14).
  • TypeScript SDK (packages/sdk/): a TS client plus a server plugin for the in-house deepseek-harness-style protocol — newline-delimited JSON-RPC 2.0 over stdio; the example bin is dsh-jsonrpc-agent.
  • Python SDK (python/): a Python client for the same protocol, plus a distribution that bundles the runtime binary — usable straight after pip install.

21.2 ACP: the automation-only Agent Client Protocol

packages/acp/acp (@deepseek-ai/dsh-acp) is the automation-only ACP server on stdio. Read its positioning precisely: it is a transport adapter, not a UI integration and not a capability seam — it provides no editor navigation, transcript replay, commands, modes, configuration selector, elicitation, reasoning display, plans, titles, or tool presentation; interactive rendering and human-facing questions belong to the Web host and client modules (Chapter 19). The plugin's apply opens an AgentSideConnection over stdin/stdout and drives ctx.agents; stdout is reserved for protocol frames, and diagnostics go to stderr.

The method surface is small and deliberately restrained:

MethodBehavior
initializeNegotiates the supported version and advertises only the baseline-only prompting capability; it declares no session, editor, terminal, filesystem, or MCP capabilities. authenticate is a no-op.
session/newCreates a brand-new agent; the primary cwd is resolved to an absolute path; empty additionalDirectories and mcpServers are accepted, non-empty ones are rejected.
session/promptConcatenates text blocks and renders baseline resource links as bracketed text references; rejects empty input; one in-flight request per session; waits for the whole agent to be idle. A normal quiet finish reports end_turn; an explicitly cancelled or abandoned admission reports cancelled.
session/cancelCancels only the named agent; unknown ids are a no-op.
session/updateEmits one agent_message_chunk for each non-empty text block of each committed assistant/message; raw deltas and non-message events never reach the wire.
session/request_permissionOffers an allow/reject choice for one-shot approval requests carrying a tool-call id; the client may answer automatically.

Sending only committed messages deliberately trades token-level latency for a clean automation result: uncommitted provider stream chunks and retry attempts can never leak half-finished text; reasoning and tool activity stay in the session log for other interfaces to observe. The model's view stays as clean as always (the rule from Chapter 4 holds here too): the text of session/prompt is joined verbatim into a single user message, and protocol metadata, client capabilities, permission choices, and session ids never enter a model request; the product of a permission decision is just the owning tool's ordinary tool result. On lifecycle, disconnection and Cordis disposal share one memoized cleanup: first reject new sessions and prompts and settle in-flight prompts, then drain and destroy in parallel only within the continuable descendants this connection precisely owns — Contexts shared with other frontends keep their own forests, and an ACP-only plugin reload leaves no orphan agents. The runnable composition is pnpm run demo:acp (the dsh-acp-demo bin of packages/examples/acp-demo: agent spine + JSONL persistence + checkpoint policy + ACP transport, where stdout is the protocol).

21.3 The TS SDK: protocol, server, client

The three packages under packages/sdk/ split the in-house protocol into three layers:

  • dsh-sdk-protocol — the shared wire contract: JsonRpcLineTransport frames JSON-RPC 2.0 onto a caller-owned byte stream (one frame per line, compact JSON terminated by \n; a message with both id and method is a request, id-only is a response, method-only is a notification; malformed JSON lines are ignored), plus the named request/result/notification types both ends share. A pure library, no plugin.
  • dsh-sdk-jsonrpc-server (server) — the jsonrpc plugin with inject: ['agents']: gets or creates one agent per sessionId, streams every persisted session fact as session.event and every whole-agent lifecycle flip as session.status. After replying to shutdown it destroys the root context to quiescence and then exits 0.
  • dsh-sdk-client (client) — the TS client, two layers: DeepSeekHarness is the high-level owned-run API and HarnessClient the low-level protocol client. It is a design twin of the Python SDK; the difference is that the launch spec is fully explicit (command/args) — discovery of the bundled runtime is left to the Python distribution.

The wire's request/notification surface is worth memorizing. Three requests: initialize (cwd crosses the wire absolutized, carrying provider/model routing and an optional positive-integer maxTokens output cap — effective for the root agent and its in-process descendants), session/prompt (queues an id-bearing user message and immediately returns a { messageId } enqueue receipt), and shutdown. Four notifications: session.event (events of every session in the runtime, unfiltered — narrowing by session is the client's own job), session.status (whole-agent running/idle flips), subagent.started, and subagent.finished (in-process runs only). messageId identifies the queued UserMessage — not the assistant message that follows, not the turn end, and not the result of that prompt. The protocol has no cancel method: the way to abandon a turn is to kill the runtime process.

How the high-level DeepSeekHarness builds run-once-get-a-result on top of these primitives: 

await using harness = new DeepSeekHarness({
  launch: { command: 'node', args: ['lib/bin.js', 'cordis.yml'] },
  provider: 'deepseek-official',
  model: 'deepseek-v4-flash',
})
const result = await harness.run('say hi')
console.log(result.finalResponse)

run() owns one activity interval: it submits the prompt, waits for its MessageId to appear in the persisted agent/inbox/spliced receipt, then collects everything up to the next whole-agent idle; it returns a RunResult (sessionId, finalResponse, events, notifications). finalResponse is the last committed assistant text of the root session within that interval — not the reply causally attributable to this prompt; steering messages, injected context, and other queued work can all contribute content before idle. The subprocess starts lazily and is held by the instance, reused across run() calls; close() (or await using) must be called, and internally it walks the protocol shutdown → stdin-EOF → SIGTERM → SIGKILL ladder until the process actually exits. The example bin is dsh-jsonrpc-agent from packages/examples/jsonrpc-demo: it only launches an external cordis.yml ($DSH_CORDIS_CONFIG or a positional argument; missing config prints one usage line and exits 1) and does not pick the server plugin — the composition must include dsh-sdk-jsonrpc-server for there to be anything to serve. stdin EOF and signals go through the same teardown; EOF can cut off an in-flight turn, so use the protocol-level shutdown for an orderly finish.

21.4 Python: two distributions and the bundled runtime

python/ ships two distributions: deepseek-harness-sdk (module deepseek_harness, the high-level turns API + the low-level JSON-RPC client) and deepseek-harness-runtime-bin (module deepseek_harness_runtime, the bundled runtime binary and the default agent configuration). Installing the former pulls in the same-version platform wheel of the latter: 

from deepseek_harness import DeepSeekHarness

with DeepSeekHarness() as harness:
    result = harness.run("Say hi.")

When no channel is pinned, the SDK automatically launches the matching bundled runtime: by default it launches the single-file executable dsh-jsonrpc-agent-pkg-<platform>-<arch> (linux/macos × x64/arm64; the target machine needs no Node install) and injects the distribution's own default composition via DSH_CORDIS_CONFIG — the stdio JSON-RPC service entry, the agent core, the preloaded DeepSeek adapter, JSONL persistence with an explicit semantic checkpoint policy, and local bash. There is also a dev-only node carrier (the full deploy closure running on the system Node), which is selected only when DSH_RUNTIME_MODE=node is set explicitly — a production deployment must never silently ride on a source build. To use your own plugin composition: keep the @deepseek-ai/dsh-sdk-jsonrpc-server entry in the config and point cordis= at your cordis.yml. The runtime inherits DEEPSEEK_API_KEY, DEEPSEEK_BASE_URL, and other environment variables.

One piece of the design must be read precisely: the runtime always requires an explicit configuration — without $DSH_CORDIS_CONFIG or a positional argument it exits loudly, and that is the runtime's designed semantics, which deepseek-harness-runtime-bin does not soften. Zero configuration is a single explicit, visible parameter injection on the wrapper side, not a hidden fallback inside the runtime. The high-level API matches its TS twin semantically: Session.run() owns the activity interval from the persisted enqueue receipt to the next whole-agent idle and returns RunResult(session_id, final_response, finish_reason, events, notifications, session_root); finish_reason is the kind of the root session's last turn/end within the interval (for example completed, max-tokens, error), or None if no turn ended. events contains only root-session events — descendant messages cannot stand in for the root answer; notifications and on_notification receive, in wire order, all notifications from the root session plus discovered descendants. The low-level session_prompt() likewise returns only a MessageId; you manage the activity boundary yourself.

21.5 How to choose

The three paths are not three tastes; they are three situations:

SituationChooseReason
The client speaks standard ACP (orchestrators, other harnesses, general agent clients)ACPThe standard protocol surface is small and stable; automation-only semantics fit external driving naturally; dsh can serve as another dsh's subagent backend (dsh-subagent-acp, Chapter 14).
Repo-adjacent TypeScript automation, CI, in-house toolingTS SDKThe launch spec is fully explicit and the types come straight from dsh-sdk-protocol; fits callers who know exactly which runtime they are starting.
The Python ecosystem, scripts, notebooks, fastest startPython SDKUsable right after pip install; the bundled runtime spares a Node install; DeepSeekHarness().run() shows a result in three lines.

Whichever you choose, three things hold: stdout is the protocol (deployments must not compose a stdout logger into it); the result is an aggregate over an activity interval, not a causal attribution (if you need causality, define the interval yourself on the event stream); cancellation is by killing the process or ACP's explicit session/cancel — the SDK wire has no per-prompt cancel.

21.6 Chapter recap

  • The three out-of-process drive paths (ACP, TS SDK, Python SDK) share one foundation: all drive a full harness subprocess over stdio JSON-RPC, and none needs a browser.
  • ACP is an automation-only transport adapter: method surface initialize/session/new|prompt|cancel/update/request_permission; it emits only committed assistant text; permission choices never enter a model request; connection teardown cleans only the continuable descendants it precisely owns.
  • The SDK's three packages: protocol (the newline-delimited JSON-RPC 2.0 wire contract, a pure library), server (the jsonrpc plugin, inject agents), client (DeepSeekHarness/HarnessClient, fully explicit launch).
  • Wire semantics: session/prompt immediately returns a { messageId } enqueue receipt; notifications are session.event/session.status/subagent.started|finished; there is no cancel method — abandoning a turn means killing the process.
  • Python's two distributions: the sdk automatically launches the matching bundled runtime and injects the default composition via DSH_CORDIS_CONFIG; the runtime itself always requires explicit configuration — zero config is an explicit wrapper injection, not a hidden fallback.
Common pitfalls
  • Treating ACP as a UI integration or a capability seam — it is an automation-only transport adapter; editor navigation, transcript, and mode switching are not on its surface.
  • Expecting streaming tokens from ACP — only committed assistant/message text blocks reach the wire; raw deltas never leave.
  • Reading { messageId } as the id of the prompt's reply — it identifies the enqueued UserMessage; the final reply comes from aggregating an activity interval.
  • Adding a stdout logger to the runtime's composition — stdout is the JSON-RPC channel; logs go to stderr.
  • Assuming Python's zero config is default runtime behavior — without explicit configuration the runtime exits loudly; the injection happens in the wrapper's start().
  • Forgetting close()/await using — the subprocess is held by the instance and leaks if you do not close it.
