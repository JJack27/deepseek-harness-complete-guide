Chapter 12 · Part III · Capability Seams in Depth

The Execution World: shell, subprocess, terminal, sandbox

Last chapter you learned the seam methodology; this chapter enters its heaviest application site. The execution world is where model commands actually happen — a coherent environment formed jointly by processes, the filesystem, and terminals. dsh organizes it with a set of interlocking seams: ctx.shell executes commands, ctx.subprocess spawns process trees, ctx.terminals holds persistent PTYs, ctx.sandbox constrains processes, and ctx.e2b moves the whole world to the cloud. After this chapter, the three deployment routes (local direct / local sandbox / E2B cloud sandbox) will look to you like three provider choices over one and the same diagram.

Learning objectives
  • Draw the execution world's layering: model tools → shell / terminals seams → providers → the subprocess / sandbox foundation
  • Explain ShellExecutor's vocabulary and the request/spec split, and why default resolution must be an explicit resolve() step
  • Describe ctx.subprocess's process-tree semantics (tree-scoped termination, the three stdio dispositions, environment scrubbing) and the PTY primitive
  • Explain ctx.sandbox.confine(argv, policy)'s wrapping model, why the three modes govern file effects only, the fail-closed semantics, and why sandbox-policy is the single policy home
  • Distinguish one-shot bash from persistent terminal sessions, and place the E2B and pwsh families on the map

12.1 Panorama: one execution world, three routes

Take in the whole diagram first, then take it apart layer by layer. The model-visible tools sit at the top — they are all Consumers as defined in Chapter 11. The middle is the seam layer: one-shot commands go through ctx.shell, persistent sessions through ctx.terminals, and both stand on the same ctx.subprocess process foundation; the sandbox is not a fourth parallel world but a wrapping inserted by the provider before spawn (ctx.sandbox + ctx.sandboxPolicy). The bottom holds the three switchable routes.

The sandbox is not a replacement for the execution world

The dsh-sandbox README states a boundary that is easy to misread: same-world confinement only. The bwrap/Landlock/Seatbelt/ACL backends share the filesystem and kernel with the host; they merely wrap the spawned argv with constraints. Containers, micro-VMs, and remote executors are not backends of this seam — they replace the entire provider group behind ctx.shell / ctx.fs (a world-consistent group). Keep this in mind and the confine model below will not lead you astray.

12.2 ctx.shell: the execution seam and the request/spec split

ShellExecutor (ctx.shell) defines what a bash backend does — run a foreground command, start a background process — without saying how. Its API is small:

MemberSemantics
run(spec)Foreground execution; resolves when the command ends. Only infrastructure failures reject (unusable working directory, missing shell, pre-abort signal); non-zero exits, timeout kills, and abort kills all resolve with a descriptive ShellRunResult.
start(spec)Background execution; returns a ShellProcess handle without a Task immediately, with no timeout set; the caller may adapt it into ctx.jobs.
sandboxModeCapability fact: SANDBOXING executors report their default constraint mode; the base class leaves it undefined (does not sandbox).
ShellProcess.readOutput()Incremental reads — successive reads never redeliver the same bytes; a read that lost data to the buffer cap is marked lossy and points at the full spill file.
ShellProcess.kill()Kills the whole process group; returns false if already exited.

The rule a non-zero exit is not an error deserves a pause: when the model writes a command that fails, that is an outcome, not an incident. That is why tool-bash raises isError only on spawn errors and aborts, leaving the exit code for the model to interpret (the tool's tool:bash prompt section exists precisely to remind the model to check the [exit code: N] marker).

On vocabulary: ShellExecRequest (command, workdir?, timeoutMs?, stdoutMaxBytes?, signal?, stdin?, env?, dshEnv?, sandboxPolicy?) is resolved before execution into ShellExecSpec (all required or explicitly nullable). This is the request/spec split template that AGENTS.md names:

request/spec split

Explicit > implicit at package boundaries: default resolution is an explicit resolve(request): Spec step in the owning implementation, never a ?? default hidden inside run(). dsh-shell is the template for this convention: sandboxPolicy is optional on the request and required-nullable on the spec — after resolution, the executor receives a fully explicit spec with no hidden path where an omitted field silently becomes some default. Deployment-varying choices (timeouts, output caps) are supplied by the provider's Config, validated in from cordis.yml.

The behavioral outline of the local provider dsh-bash-local (details beyond the Chapter 8 tool pipeline — here we look at the executor side):

  • Each invocation spawns a brand-new non-login bash -c, no rc files, no shell state — pass workdir when you need a directory; don't expect cd to survive.
  • Configured budgets: default foreground timeout timeoutMs: 120000, ceiling maxTimeoutMs: 600000, in-memory per-stream cap maxOutputBytes: 64000 (overflow spills to disk), graceMs: 3000 kill grace.
  • Timeout/cancel classification: only the executor's own timeout reports timedOut, upstream cancellation reports aborted, and a command that receives a signal on its own reports neither.
  • Model-friendly terminal environment: NO_COLOR=1 TERM=dumb PAGER=cat GIT_PAGER=cat, keeping pagers and ANSI colors from dirtying results.

12.3 ctx.subprocess: the process-tree foundation

The first sentence of the dsh-subprocess README states its position: the subprocess seam is the process half of one execution world. The abstract SubprocessRuntime exposes executable lookup, ordinary managed spawn, and the single terminal primitive spawnTerminal. Its direct-consumer list explains the word foundation: the two bash executors, the PTY backend terminal-bash, the LSP host lsp-stdio, and the three out-of-process subagent backends (acp, codex, claude-code) — every capability that starts a process goes through this one seam.

Contract highlights (packages/subprocess/subprocess/README.md):

  • Fully explicit spec — argv, cwd, per-stream stdio disposition, and grace are all given by the caller; argv is never shell-interpreted, and consumers that want a shell pass ['bash', '-c', command] themselves. Working directories and executable paths belong to the provider's execution world: resolveExecutable resolves PATH in that world.
  • Three stdio dispositions: 'pipe' hands the raw stream to the caller to do its own protocol framing (LSP's JSON-RPC, ACP's ndjson); 'inherit' passes through the parent's descriptors; the collect mode { maxBytes, spill? } keeps a bounded tail plus an optional full spill file. Collect reads are keyed by whole-stream byte offset and never consume — multiple independent readers never steal each other's increments; a read whose offset slid out of the in-memory tail is marked lossy and pointed at the spill.
  • Termination is tree-scoped (on all platforms): POSIX uses detached process groups with a direct-child fallback; Windows goes through taskkill /T. The single termination verb terminate() escalates SIGTERM → grace → SIGKILL; waitForExit() watches the liveness of the whole tree so the consumer's teardown ladder ends on true silence. The manager only reacts and never classifies causes — deadlines, ladders, and cause classification all belong to the caller.
  • Single-source environment scrubbing: scrubbedParentEnv() / SENSITIVE_ENV_PATTERN is the one shared scrubbing definition — credential-shaped names and DSH_* names in the environment are dropped, and an explicit env is merged after scrubbing. Service disposal terminates every still-running managed process and waits for exit.

The local implementation dsh-subprocess-local (LocalSubprocessRuntime) has a counter-intuitive property: it has no config at all. Every disposition, cap, terminal size, grace, and directory comes from the capability seam calling it (bash-local, lsp-stdio, terminal-bash). The PTY is allocated by node-pty, paired with a platform process check; spill files carry 0600 permissions inside a 0700 per-process private directory. This continues the request/spec philosophy: deployment variance belongs to the upper capability's Config; the foundation only provides mechanism.

12.4 ctx.sandbox: the pre-spawn constraint wrapper

The sandbox seam's contract compresses into one line: ctx.sandbox.confine(argv, policy) returns the argv to run instead — the consumer hands the provider the exact argv it was about to spawn and gets back a wrapped argv to spawn directly, plus the backend's enforcement completeness (enforcement), denial dialect signatures (denialSignatures), and structured runner failure evidence. When no backend is available it throws rather than letting unconstrained execution through — fail closed.

Three hard facts:

  • The mode vocabulary covers file effects only: read-only (default, forbids all writes with /dev/null as the sole exception), workspace-write (writes allowed only inside workspaceRoot and temp areas), danger-full-access (no constraints, no provider consultation). Network and process visibility are deliberately absent from the vocabulary — the modes do not pretend to cover what backends do not enforce.
  • Platform backends are selected inside sandbox-local: Linux first probes for an available bwrap, otherwise the Landlock launcher; macOS uses Seatbelt (sandbox-exec, allow-default + (deny file-write*) plus write allowlists); Windows uses the ACL restricted-token runner chain (dsh-sandbox-windows-acl, a WRITE_RESTRICTED token + a workspace-derived SID). When an old kernel ABI covers only some access classes, it honestly reports enforcement: 'partial'. The Landlock launcher's source of record lives in native/landlock-run/ — the npm package @deepseek-ai/node-addon-landlock-run (a self-restrict-then-exec launcher + capability probes + CLI argument vocabulary); the harness shares its repository and lockfile with it, so contract changes and consumer updates land together.
  • sandbox-policy is the single policy home. The deployment default mode (default read-only) and the fallback workspaceRoot (default process.cwd()) live here; ctx.sandboxPolicy.resolve({ session, mode }) resolves the full policy for each call — explicit approval > the session's last sandbox/mode event (the effectiveSandboxMode fold) > the deployment default; the session-immutable SessionHeader.cwd, normalized through filesystem semantics, becomes the workspaceRoot. The three enforcing families — bash, fs, terminal — all read this same resolution, so no one can fence bash and fs to different roots. Switching itself is a log-only sandbox/mode event — recovered after restart by replay, and two sessions never see each other's state.

The presentation path for a sandbox denial is also worth walking through: when a confined command fails, stderr carries the chosen backend's own denial dialect (bwrap's EROFS, Landlock's EACCES, Seatbelt's EPERM); the executor conservatively classifies it against the signatures as ShellRunResult.sandbox.denied: true — denial is an outcome fact, not an exception. The tool layer renders it as [sandbox: file access denied under <mode> mode] and, where the composition supports escalation, appends a hint: within the same turn you may retry once with sandbox_permissions (a strictly wider mode) + justification, with the approval question going to the user through ctx.approval. When no backend is available at all it throws SANDBOX_UNAVAILABLE (with platform installation guidance), never silently degrading.

12.5 ctx.terminals: persistent PTY sessions

One-shot bash is a brand-new bash -c every time, but some work needs persistent terminal state: exported environment variables, an activated virtualenv, a service running in the foreground. ctx.terminals (dsh-terminal) is the owner-scoped persistent PTY seam: it mints opaque session ids, creates sessions through named backends, and fences every operation to the exact live Agent. dsh-terminal-bash is the local backend, built on ctx.subprocess.spawnTerminal — PTY allocation, environment scrubbing, foreground process groups, signals, and full terminal-session cleanup all belong to the subprocess provider, so the same PTY backend fits both the local and the remote execution world.

Compared with one-shot bash:

tool-bash (one-shot)tool-terminal (persistent sessions)
StateBrand-new bash -c each time, nothing persistscwd, exported variables, and foreground processes persist across calls
Process shapeManaged process tree with plain pipesA real PTY (the spawnTerminal primitive), UTF-8 text I/O
Tool surfacebash (+ background-job adaptation)Six tools: terminal_open / send / read / signal / close / list
OwnershipBackground processes register into ctx.jobs and are controlled as jobsEvery operation requires the exact originating Agent — a model that learned someone else's id still cannot operate
ReadinessNo readiness concept neededPrivate PS1 marker + foreground stdin-wait fact + silent fallback + absolute timeout

The family has one more variant, dsh-tool-bash-persistent: the model-visible bash(command) tool, but backed by an owner-scoped ctx.terminals shell per Agent — commands share one shell, so cwd, exported variables, activated environments, functions, and background jobs all persist across calls. It demonstrates the decoupling of the tool contract from the execution surface: a bash tool of the same name can stand on the one-shot seam or on a persistent session.

12.6 E2B, the pwsh family, and shell-env

E2B is the third route (POC positioning). dsh-e2b owns ctx.e2b — the shared lifecycle owner of an E2B sandbox: construction opens the sandbox (pinned e2b@2.29.1), sets up the cwd (default /home/user/workspace, which must be an absolute POSIX path) and the private cwd/.dsh-e2b state directory; timeoutMs (default five minutes) governs the sandbox's lifetime, and expiry deletes it. fs-e2b and subprocess-e2b inject it and await the same SDK handle, so the file tools and the bash/PTY/LSP consumers land in the same remote Linux world — the instantiation of Chapter 11's swap a provider, move the execution world. Note its boundary (stated plainly in the README): Cordis services, session state, the session log, and LLM requests all stay in the host process; sandbox state is volatile with no host synchronization.

The pwsh family is the symmetric design for Windows. dsh-pwsh-local mirrors bash-local item by item: a brand-new pwsh -NoLogo -NoProfile -NonInteractive -Command <command> each time, with the command string passed to -Command as a single argv element (parsed by PowerShell itself; no intermediate shell, hence no escaping layer); UTF-8 output encoding is pinned up front; Windows tree termination goes through taskkill, and a forced kill settles as exit 1 with no signal. dsh-pwsh-sandbox mirrors bash-sandbox, and the substance of the constraint is platform-neutral: on Windows it resolves to the ACL runner chain; on Linux/macOS it is bwrap/Landlock/Seatbelt as usual. dsh-tool-pwsh aligns with tool-bash call for call (foreground/background, DSH_* environment, denial rendering, and the escalation surface).

shell-env fills in the last piece of the managed environment: it owns the ctx.shellEnv registry — every model shell call gets a freshly captured, trusted DSH_* snapshot (the built-in facts DSH_HOME, DSH_SHELL=1, DSH_SESSION_ID, plus DSH_SESSION_JSONL when the persistence layer lands on JSONL). The snapshot travels the dedicated channel ShellExecRequest.dshEnv; the local executor first strips every inherited DSH_* and then merges the snapshot — so nested harnesses and concurrent parent/child agents cannot leak stale identities into subprocesses; process.env is never modified. Other plugins register their own managed facts through effect scopes; duplicate names or undeclared runtime keys fail loud.

12.7 Chapter recap

  • The execution world = the coherent environment formed by processes + filesystem + terminals; the three routes (local / local sandbox / E2B) are just provider choices.
  • ctx.shell: run/start/sandboxMode; only infrastructure failures reject; request → explicit resolve() → spec is the repo-wide template.
  • ctx.subprocess: argv is never shell-interpreted; stdio pipe/inherit/collect; tree-scoped termination (SIGTERM→grace→SIGKILL, taskkill /T); scrubbedParentEnv single-source scrubbing; the local implementation has zero config.
  • ctx.sandbox.confine(argv, policy) returns the argv to run instead; the three modes govern file effects only; fail closed throws SANDBOX_UNAVAILABLE; the Landlock launcher's source lives in native/landlock-run/.
  • ctx.sandboxPolicy is the single policy home: sandbox/mode events + the session-immutable cwd, shared by the three enforcing families as one resolution.
  • ctx.terminals persistent PTYs: owner fencing, six tools, readiness inference; terminal-bash stands on spawnTerminal and migrates with the execution world.
  • E2B (ctx.e2b + fs-e2b + subprocess-e2b) is the POC of a cloud execution world; the pwsh family mirrors bash call for call; shell-env governs the DSH_* managed environment.
Common pitfalls
  • Treating a non-zero exit code as isError — only infrastructure failures (spawn errors, aborts) are errors; the exit code is an outcome for the model to interpret.
  • Expecting cd or exported variables to survive a bash call — every call is a brand-new bash -c; for state use workdir, env, or a persistent terminal.
  • Hiding a ?? default inside run() — default resolution must go through the owning implementation's explicit resolve(request): Spec.
  • Assuming sandbox modes govern network/processes — the vocabulary covers file effects only; containers and micro-VMs are not sandbox backends but whole-group provider replacements.
  • Spawning on your own, bypassing ctx.subprocess — process-tree termination, environment scrubbing, spill, and dispose cleanup are all lost with it.
  • Expecting E2B to sync the host workspace — the remote cwd starts as an empty directory; upload/write-back are out of the POC's scope.
