Chapter 8 · Part II · The Core Spine

The Tool System: Registry and Execution Pipeline

In the last chapter you saw the tool-call in an assistant message dropped into 'the tools pipeline'. This chapter unrolls that pipe: how tools register, which gates a call passes through from model request to the tool/result event, where it can be rejected, where it can be rewritten, and why even a rejected call is guaranteed to leave a log record. By the end you will write a tool plugin of your own and know which pipeline layer your policy belongs in.

Learning objectives
  • Register a tool with ctx.tools.register() and state what 'registration is an effect' means
  • Recite the composition of a ToolDefinition: schema, the output declaration, execute, optional callbacks
  • Name the execution pipeline stages in order, and what each stage may rewrite or reject
  • Explain why a rejection also produces a tool/result event (model-visible ⟺ logged)
  • Distinguish the intended use of monotonic guards, tools/execute wrappers, and post-execute plugins
  • State why a tool's UI render intent is a pure function of args

8.1 ctx.tools: the scoped tool registry

The ToolRuntime service from packages/core/tools/ hangs on ctx.tools. It is two things at once: a scoped registry and a guard-style execution pipeline. The registry half first.

Registering a tool is an effect (Chapter 2's rule holds here too): 

export const name = 'my-tool'
export const inject = ['tools']

export function apply(ctx) {
  const dispose = ctx.tools.register(defineTool({ /* … */ }))
  return dispose  // or hand it to the plugin fiber: unregisters automatically when the fiber disposes
}

The disposer returned by register() is the unregister function; which scope a registration lands in is decided by the caller's ctx — a plain plugin context registers a global tool, while registering through some agent's agent.ctx makes it visible to that agent only and shadows the same-name global tool (Chapter 6's shadowing caught at its first scene here). A duplicate name within the same layer throws immediately, and the error message even tells you: for a per-agent variant, register via agent.ctx. Registration/unregistration/scope changes broadcast tools/change (an unfiltered notification — a global change concerns every agent's next assembly).

Two companion operations live on the scope: ctx.tools.restrict({allow?, deny?}) puts an allow/deny mask over an agent's inherited surface (multiple masks intersect; the layer's own registrations are unaffected); ctx.tools.presentAs('code') lets a single agent opt into Code Mode presentation (the deployment-level default is the tools plugin's mode config: native / code / both). Both methods can be called only from a scoped context — calling them from a plain context throws immediately, because 'global mask' and 'global presentation' belong in configuration, not hidden inside some plugin's side effects.

8.2 ToolDefinition: everything a tool declares

A ToolDefinition (wrapping it in defineTool() gets you type inference) has four blocks; the minimal example in docs/cookbook/adding-a-tool.md is the fastest memory anchor:

  • The model-visible schema: name, description, parameters. These are the only three fields the model ever sees — everything else (timeouts, concurrency classification, presentation callbacks) is never sent to the model.
  • The required output declaration: {schema, render, presentationMeta?}. The tool body returns only a canonical JSON value conforming to output.schema; render(args, value) projects it into model-visible content blocks; presentationMeta projects it into replayable UI card data (landing in tool/result's meta field). Registering without output is an immediate TypeError.
  • execute(args, exec): the actual work. The contract: arguments are already validated and frozen (defineTool validates first; violations become an INVALID_ARGS error result); it must observe exec.signal for cooperative cancellation; a throw or a value off the declaration is normalized into an isError result — tool failure is a normal result path, not a crash. exec also carries deferContext(msg) (defers context injection until after the result lands) and concludeTurn() (marks a successful result as concluding this turn).
  • Optional metadata: timeoutMs (a cooperative timeout budget; policy metadata, never sent to the model), isConcurrencySafe(args) (only a strict true allows parallelism; see Chapter 7), finalizeContent (a last-pass content rewrite, which must be synchronous and total), presentCall / presentResult (8.6).

8.3 The execution pipeline: five gated stages + two short-circuits

When the agent loop's scheduler launches a call, it first records tool/call into the log (recorded before execution), then enters the pipeline described in docs/tool-execution-pipeline.md. Stage by stage:

  1. tools/pre-execute (waterfall): the extensible allow / deny / ask gate — hooks, permission policy, and sandbox wrapping all hang here. Listeners must call next(); when ask is returned, a deployment with a ctx.approval service gets a one-shot approval prompt (continue if allowed, otherwise treat as rejected); with no approval service it degrades to deny. Note that pre-execute deliberately offers no argument rewriting — the arguments are already logged and presented at this point.
  2. Registered monotonic guards: synchronous guards registered with ctx.tools.guard(g), running after pre-execute and before the body. They have only two return values: a reason (final rejection) or undefined (abstain). There is no allow — so no matter how listeners are ordered, nobody may flip a guard-rejected call back to allowed. That is what 'monotonic' means: tighten-only.
  3. tools/execute (around-dispatch waterfall): wraps the actual dispatch. 'Around execution' concerns — timeouts, retries, metrics — belong here. A wrapper may only temporarily replace exec.signal (say, to impose a tighter deadline); it cannot change the call's identity; the registry re-attaches the caller's original signal before the body.
  4. tools/post-execute (waterfall): post-processing of the already-normalized result — accept (rewriting content or the canonical value, attaching additionalContexts context) or block (turning corrective feedback into an error result). Rejected/timed-out calls also arrive here (failure is a result too).
  5. tools/result (emit, read-only): observation of the frozen final outcome. The agent loop then lands the tool/result durable event, with the meta used by UI cards.

One gatekeeper in the pipeline is easy to miss: after post, the registry performs outer normalization (errors thrown at any stage and snapshot failures all become isError uniformly), then gives the tool definition's finalizeContent one last content-rewrite chance, and only then materializes, freezes, and broadcasts. Whichever path is taken — normal, rejected, timed out, exceptional — the destination is one tool/result event. This is the tool-side shape of the Chapter 4 invariant: model-visible ⟺ logged. A call rejected by policy shows the model the rejection reason so it can change course, rather than vanishing into thin air and leaving the model to guess at a dangling call.

8.4 A policy-plugin example: two plugins from the guard group

The packages/guard/ group holds two loop-hygiene/timeout plugins; they are the model examples of 'policy goes in the pipeline, not into tools'. Note one detail easy to misread from the name: the two plugins in this group do not both hang at the ② guard position — each demonstrates a different pipeline layer:

  • dsh-repeat-tool-reminder (loop hygiene, observing at ④): counts how often each agent calls the same tool with the same arguments in a row; at the thresholds (default 3/5/8) it injects an escalating reminder to make the model change method or wrap up. It never vetoes and never rewrites calls — detection hangs on tools/post-execute (denied calls count too: repeatedly ramming a rejected call is exactly the loop worth interrupting), and the reminder is injected as additionalContexts with the step, becoming a user/message reconstructible from the log. The decision is left entirely to the model, so it is an advisory plugin.
  • dsh-tool-call-timeout-policy (timeout, wrapping at ③): a tools/execute around-dispatch listener. For tools that declare timeoutMs, it puts a deadline on exec.signal; when the deadline wins it replaces the result with a structured TOOL_TIMEOUT error. The budget comes from the tool's own declaration, so this plugin is zero-config. Note that it is cooperative: only tools that actually forward exec.signal can be 'timed out' — tools that ignore the signal are not hard-killed.

So who is ② for? For the deployment owner's final veto that cannot be reordered — the monotonic guards registered by ctx.tools.guard(reason | undefined). The pipeline doc sums it up: reorderable extension policy goes in pre-execute, owner policy in guard, around-concerns (timeout/retry/metrics) wrap execute, and result observation and rewriting go in post-execute / tools/result.

8.5 Parallel versus sequential: the registry view

Chapter 7 covered how the scheduler groups with executionMode; here are the facts on the registry side: ctx.tools.executionMode(exec) looks up the definition visible in that scope, and only when its isConcurrencySafe(args) returns exactly true is it parallel — unknown tools, shadowed, undeclared, or a throwing classifier are all treated as exclusive (fail closed). Multiple parallel calls form a bounded rolling pool (default 10); exclusive calls form barriers; dispatch may overlap, but pre-execute, result commits, and result context all keep model order. On cancellation, already-started calls drain normally and unstarted ones get synthetic error results — in the log, call and result are always paired.

8.6 Tool UI render intent: part of the design

A repository-level rule: a tool's UI render intent is part of the tool's design, decided up front, not something the UI guesses after the fact. Tools declare their cards through two pure functions:

  • presentCall(args) → the pending card: shown when the call starts and there is no result yet. The card vocabulary is generic (default; may carry locations so the editor follows file positions), terminal (this call is a shell command — tool-bash), and diff (this call creates/modifies files, with an inline diff — tool-fs's write/edit).
  • presentResult(args, {content, isError, meta}) → the completed card: besides the three base cards there are result views such as search (grep/glob hit structures) and web (structured sources for web_search/web_fetch), with data from the persisted result.meta.

Why must they be pure functions of args? Because these methods run both in the live stream and during session-log replay: at replay time there is no live session state, no clock, no filesystem. So the rule is strict: no I/O, no reading session state, no time/randomness — if you need result-time facts (say, the actually applied diff hunks), store them into the durable meta via output.presentationMeta and read them back from there at replay. Meanwhile, model-visible content and UI-visible cards are two separate tracks: UI-facing formatting (console fences, path relativization) must never leak into the model result.

8.7 The interface to prompt assembly

The last puzzle piece: how do registered tool schemas become what the model sees? ToolRuntime's constructor contains the line ctx.systemPrompt.tools(context => this.wireSchemas(context.scope)) — the registry hangs itself as one of system-prompt's tool schema providers, resolving the visible tools per scope and projecting the three fields name/description/parameters. So 'which tools the model can see this round' and 'which tools this scope can resolve' are forever the same answer. The full assembly story (section ordering, toolOrder validation, Code Mode's SDK section) is next chapter's topic.

8.8 Chapter recap

  • ctx.tools = scoped registry + guard-style execution pipeline; register() is an effect returning a disposer; scoped registrations shadow same-name global tools.
  • ToolDefinition = model-visible schema + required output (schema/render/presentationMeta) + execute + optional metadata; the tool body returns only canonical JSON values.
  • Pipeline order: tool/call hits the log → ① pre-execute (allow/deny/ask + approval degradation) → ② monotonic guards (deny only) → ③ execute around (timeout/retry/metrics) → the tool body → ④ post-execute (accept/block/replace/context) → normalize + finalizeContent → ⑤ tools/result (read-only) → the tool/result event.
  • Every stage may rewrite or reject; rejection/timeout/exception all produce a tool/result — model-visible ⟺ logged.
  • repeat-tool-reminder hangs on post-execute for advisory loop hygiene; timeout-policy wraps execute to enforce the tool-declared timeoutMs; the owner's final veto uses ctx.tools.guard().
  • Parallelism fails closed: only a strict isConcurrencySafe(args) true is parallel; exclusive forms barriers; results commit in model order.
  • UI render intent (generic/terminal/diff/…) is decided up front; presentCall/presentResult are pure functions of args that must work during log replay.
  • The registry feeds schemas into prompt assembly via ctx.systemPrompt.tools() — the model-visible tool set and the scope-visible tool set share one source.
Common pitfalls
  • Assuming a rejected call means 'nothing happened' — the pipeline short-circuits execution, not the record; tool/result still lands.
  • Writing deployment policy into tool bodies — it belongs in the pipeline: pre-execute for extensible policy, guard for the final veto, execute for timeout/retry, post-execute for result handling.
  • Expecting pre-execute to rewrite arguments — deliberately unsupported: arguments are already logged and presented; rewriting would desynchronize the log from execution.
  • Assuming timeoutMs is a hard kill — it is a cooperative budget that presupposes the tool forwards exec.signal.
  • Reading session state or the filesystem inside presentCall — none of that exists at replay; cards must depend only on args (+ durable meta).
