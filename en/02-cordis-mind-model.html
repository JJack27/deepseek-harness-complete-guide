Chapter 2 · Part I · Landscape and Mental Models

The Cordis Mental Model: Context, Plugins, Services, Events

Chapter 1 described dsh as a plugin tree. This chapter covers what that tree grows in: the Cordis plugin framework. Context, plugins, services, events, effects — master these five concepts and you can read the code in any later chapter directly. This is the most important foundation chapter in the book; it deserves a slow read.

Learning objectives
  • State where Cordis sits inside dsh and what 「everything is a plugin, no privileged core」 implies
  • Explain Context (ctx) as the service registry and find services by key (e.g. ctx.tools)
  • Read both plugin forms — function plugins and Service subclasses — and how inject expresses load order
  • Explain 「registrations are effects」: why every contribution goes through ctx.effect() / ctx.on(), and how unload reverses them automatically
  • Distinguish the four event dispatch modes and state waterfall's next() semantics and short-circuit consequences precisely

2.1 Cordis: the foundation dsh stands on

dsh did not invent a plugin system from scratch. It stands on Cordis — an open-source plugin framework whose design is written up in the paper A Programming Paradigm for Spatiotemporal Composability (reading it now is optional). You can think of Cordis as dsh's stand-in for an OS kernel: it does not manage processes or memory; it manages how plugins mount, find each other, communicate, and retire.

One fact that matters for this book: Cordis's source is not in node_modules; it lives in the repository's vendor/ directory.

  • vendor/ is a pinned copy of the upstream source: each entry records its upstream commit; it can be audited and patched, its version is pinned, and it never drifts with whatever npm serves.
  • Every vendored package is rescoped to @deepseek-ai/: cordis → @deepseek-ai/cordis. Publishing dsh thereby publishes this framework layer too, without squatting the upstream package names on npm.
  • Every harness package declares @deepseek-ai/cordis as a peerDependency: the whole tree shares one Cordis instance.
  • To update vendored code, follow the sync procedure documented in vendor/README.md and re-apply (or retire) the logged local modifications.

On this foundation dsh establishes one constitution that runs through the whole repository: everything is a plugin. Model adapters are plugins, the tool registry is a plugin, the session log is a plugin, even the agent loop itself is a plugin — all replaceable at the configuration layer. That means there is no privileged core to patch: you extend dsh not by forking core code but by mounting your plugin next to the others. How to mount is Chapter 3's topic; this chapter first covers how plugins coexist once mounted.

2.2 Context: a shared service registry

When Cordis mounts a plugin, the plugin receives a ctx (a Context instance). Think of it as a shared registry: Context is the store of services. A service occupies a stable key in the registry, and other plugins consume it by key instead of importing a concrete implementation class.

You have already seen several keys (that column in Chapter 1's table):

  • ctx.tools — tool registry and execution pipeline (core/tools)
  • ctx.sessions — session event log (core/session)
  • ctx.systemPrompt — prompt assembly (core/system-prompt)
  • ctx.llm — model adapter interface (llm/llm)
  • ctx.agents / ctx.agentLoop — live agent registry / default loop

Find-services-by-key yields a key property: interface and implementation are separate. A caller (say the bash tool) depends only on the name ctx.shell and its TypeScript type; whether a local or a sandbox implementation sits behind it is decided by configuration. Swapping implementations touches not one line of caller code — this is the mechanism that makes Chapter 1's 「everything is replaceable」 real.

What does a service look like in code? It is a subclass of Cordis Service that reports its key to Cordis at construction. Real code — the tool registry (excerpted from packages/core/tools/src/index.ts): 

// packages/core/tools/src/index.ts (excerpt, simplified)
export class ToolRuntime extends Service {
  static inject = ['systemPrompt']   // I need the systemPrompt service to activate

  constructor(ctx: Context, config: Config = {}) {
    super(ctx, 'tools')              // <-- the key it occupies on ctx
    …
  }
}

The second argument of super(ctx, 'tools') is the most important string in this world: it determines that ctx.tools is exactly the instance other plugins retrieve.

So where does the TypeScript type of ctx.tools come from? Not from a hand-maintained central registry — it uses declaration merging: the tools package merges a member into Cordis's Context interface in its own file: 

// packages/core/tools/src/index.ts (excerpt)
declare module '@deepseek-ai/cordis' {
  interface Context {
    tools: ToolRuntime      // ctx.tools is typed from here on
  }
}

Every service package contributes its key this way; the merged Context interface is the menu of the whole registry. Event types extend through the same mechanism (see 2.5).

Service Definition: the name for interface/implementation separation

From here on, this book calls the code that declares what interface a key should carry a Service Definition, and the plugin that actually implements that interface a Service Provider. dsh's rule in one sentence: extension plugins depend on Service Definitions, never on concrete Providers. That is why dsh-agent-loop can be replaced wholesale while UI and tool plugins come out unharmed.

2.3 What a plugin looks like: a function, or a Service subclass

Cordis plugins come in exactly two forms, and dsh uses both.

Form one: the function plugin. A module with the three-part set of name, inject, apply. Real example — the bash tool (packages/shell/tool-bash/src/index.ts):

// packages/shell/tool-bash/src/index.ts (excerpt)
export const name = 'tool-bash'
export const inject = ['tools', 'shell', 'systemPrompt', 'shellEnv']

export function apply(ctx: Context, config: Config = {}): void {
  // register the bash tool on ctx.tools; call ctx.shell to run commands
}

apply(ctx) is called when the plugin mounts; ctx is its entry ticket. It suits plugins that register things on other plugins' services — most capability plugins in dsh are this form.

Form two: the Service subclass plugin. Like ToolRuntime above, it extends Service, and Cordis hangs its lifecycle (construct, start, deactivate) on the current context. It suits plugins that are themselves a service and need to occupy a key in the registry.

The field both forms share is inject:

inject: load order expressed as service requirements

inject declares 「I need these services」. Cordis activates the plugin only once they all exist. Load order therefore no longer relies on manual sorting; it emerges from dependencies: tool-bash declares it needs tools and shell, so no matter which of the two lines comes first in the configuration, it never starts while a service is absent. Who waits for whom is decided by the code itself.

Look back at Chapter 1's core table and you can now read a second layer of meaning: core/agent-loop depends on the interface declared by ctx.agents, yet it is only a plugin — remove it from the configuration, substitute a loop you wrote yourself, and every other plugin works as before. 「Everything is a plugin」 is not a slogan; it is a fact held up by inject.

2.4 Registrations are effects: every contribution can retire

What a plugin does in apply (or its constructor) is collectively a 「contribution」: register a tool, add a prompt section, subscribe to an event, install a model adapter. dsh's iron rule is registrations are effects — every contribution must go through ctx.effect() or ctx.on() and take the disposer.

  • ctx.effect(setup) takes a generator function in which you yield cleanup actions; it returns a disposer whose call undoes the whole set of registrations.
  • ctx.on(event, listener) subscribes to an event; its return value is the unsubscribe function.
  • Registry-style APIs (such as registering a tool on ctx.tools) also return disposers — 「the return value of register is the unregister function」 is the universal convention.

Real code (simplified from ToolRuntime.presentAs, packages/core/tools/src/index.ts): 

const dispose = ctx.effect(function* () {
  yield this.layers.effect(ctx, layer => {
    layer.mode = mode
    return () => { layer.mode = undefined }   // cleanup: restore
  })
  yield ctx.systemPrompt.section(this.sdkSection()) // the return value is likewise a disposal function
})
// one dispose() call undoes both, in reverse order

Why elevate 「registration」 to an 「effect」? For reversibility:

  • When a plugin unloads, all its registrations retire automatically and in order — the tree stays consistent at all times;
  • Hot reload (HMR) relies on it: swapping a plugin version = unload old, mount new, without restarting the process;
  • Testing relies on it: each case mounts its own small tree and tears it down at the end, with no cross-contamination.

The converse matters just as much: mutating global state directly, bypassing ctx.effect(), leaves dirt on the tree that nobody cleans at unload. dsh code review treats that as a defect, not a style issue. If unload order matters, put the related steps into the same effect so cleanup unwinds in reverse order of your yields.

2.5 Events: how plugins talk to each other

Service methods suit direct commands: ctx.shell.run(...) just runs a command. But often what you need is to observe or intercept — a tool is about to execute and you want to inspect it, modify it, even veto it. That is the territory of events: subscribe with ctx.on(), dispatch in four ways.

The four dispatch modes are the key to dsh's event system (from docs/cordis-primer.md):

ModeWaits for listeners?OrderReturn value?Typical use
emitNoRegistration orderNonePure observation: a tool finished, a registry changed
waterfallNoRegistration orderYesWrapping and interception: rewrite a request, veto a call (the onion model)
parallelYesParallelNoneFan-out notification: broadcast to mutually independent observers
serialYesRegistration orderYesOrdered processing that also needs results

Two things to note. First, the dispatch mode is part of the event's public contract: one event is dispatched only by the mode that belongs to it; dsh requires a new event's JSDoc to carry @mode, and the generated catalog cross-checks declarations against dispatch sites. Second, the types behind event names also come from declaration merging — the same move as with the Context interface, except this time the merged interface is Events: 

// packages/core/tools/src/index.ts (excerpt, simplified)
declare module '@deepseek-ai/cordis' {
  interface Events {
    /** Allow, deny, or ask before dispatch. …
     *  @mode waterfall */
    'tools/pre-execute'(exec: ToolExecution,
                      next: () => Promise<PreToolDecision>): Promise<PreToolDecision>
    /** Observe the frozen final outcome. …
     *  @mode emit */
    'tools/result'(exec: readonly ToolExecution,
                  result: readonly ToolExecutionResult): undefined
  }
}

Three lessons from this real declaration: tools/pre-execute is a waterfall (has next, has a return value), used for allow / deny / ask-the-human decisions; tools/result is an emit (no return value), used to observe the final outcome; each event's JSDoc states its contract, and @mode lets tooling verify it mechanically.

2.6 waterfall: onion, wrapping, and short-circuits

The one mode worth mastering is ctx.waterfall() — all of dsh's interception layers are built on it: agent/pre-step, agent/request, llm/stream, tools/pre-execute, tools/execute, tools/post-execute are all waterfalls (for contrast: agent/turn-stopping is serial and has no next).

The semantics in one sentence: waterfall is around middleware. A listener receives (…args, next):

  • Call next(): hand the (possibly rewritten) request to the next layer; next()'s return value is that layer's result;
  • Return without calling next(): the whole chain short-circuits here — later listeners and the real execution never happen, and your return value becomes the final result.

Both endings in pseudocode:

// cooperative listener: modify, then pass through
ctx.on('tools/execute', async (exec, next) => {
  exec.timeoutMs = 30_000                    // wrap: rewrite the shared request
  return await next()                        // must delegate; the result returns through this layer
})

// decision-owning listener: I own this decision; stop here
ctx.on('tools/pre-execute', async (exec, next) => {
  if (exec.name === 'bash' && isDangerous(exec.args)) {
    return { kind: 'deny' }               // no next() call: short-circuit is the veto
  }
  return await next()                        // allow everything else
})

When is a short-circuit correct and when is it an incident? The criterion in one line:

  • In a single-decision event, short-circuiting is design. When a policy listener owns the decision (deny a dangerous command), not calling next() is precisely how it expresses that.
  • Listeners that only annotate or observe must call next(). A wrapping layer that forgets next() is not 「skipping itself」 — it is choking off everyone after it: later listeners and the real execution all vanish silently, the incident mode dsh's documentation stresses again and again.
  • Two more details: the result travels back through next()'s return value, and a listener may also replace the downstream result wholesale, in which case downstream sees the replaced value. prepend: true is used only when that listener must run before ordinary registrations.

2.7 Three event domains: the forest first

dsh's events split into three domains by who owns the fact. For now you only need the three names and the intuition for choosing; each domain gets full chapters later: session events in Chapter 4, agent events in Chapters 6/7, capability events in Chapters 8/11.

Event domainExamplesEssenceWhen to choose it
session events user/message, assistant/message, tool/call, turn/* Persistent facts, appended to the session log and broadcast via session/event The fact must survive a restart and be replayable
agent events agent/pre-step, agent/request, agent/turn-stopping Carries a live Agent: inbox, steps, state, requests, validation, continuation You want to observe or intercept work in progress
capability events tools/*, fs/*, telemetry/* Policy and adapter hooks on a capability seam You want to add policy to one capability without touching the agent loop

The intuition: the fact must be recorded → session; watching running work → agent; adding policy to a capability → capability. dsh's architecture doc says events are the extension points and choosing the right domain is the first decision of most changes — you will feel that repeatedly when practicing in Chapter 24.

One more rule: model-visible ⟺ logged

dsh has one more iron rule tied to the event domains; remember the conclusion now (Chapter 4 expands it): whatever reaches a model request must be reconstructable from the session log. Adding a new model-visible input requires adding a session event — what the model sees and what the log records always correspond one to one.

2.8 Chapter recap

  • Cordis is the plugin framework dsh stands on, vendored in vendor/ (a pinned upstream source copy, rescoped to @deepseek-ai/cordis, a peerDependency of every harness package); updates go through the procedure in vendor/README.md.
  • Everything is a plugin: model adapters, the tool registry, the session log, and the agent loop itself are all plugins, all replaceable at the configuration layer; there is no privileged core to patch.
  • Context is the service registry: services register under keys (ctx.tools, ctx.llm, ctx.sessions…), plugins consume by key; services are Service subclasses, interface (Service Definition) and implementation are separate; types come from declaration merging.
  • Plugins come in two forms: function plugins (name + inject + apply) or Service subclasses; inject declares service dependencies, and load order is expressed by dependencies.
  • Registrations are effects: every contribution goes through ctx.effect() / ctx.on(), registration returns a disposer, and a plugin's registrations retire automatically and in order at unload.
  • Events have four dispatch modes (emit / waterfall / parallel / serial); the mode is part of the event's contract (@mode annotation); waterfall listeners must call next() — not calling short-circuits the whole chain. In single-decision events the short-circuit is design; an observing listener forgetting to call it is an incident.
  • Three event domains: session (persistent facts), agent (work in progress), capability (policy over a capability).
Common pitfalls
  • Importing a service's implementation class to use it — fetch it from ctx by key; depend on the Service Definition, not the Provider.
  • A waterfall listener forgetting next() — that is not skipping itself, it is choking off every later layer and the real execution.
  • Expecting emit events to return a value — emit only observes, no return value; for wrapping and interception use waterfall.
  • Treating ctx.effect() as an optional style preference — bypassing it and mutating global state leaves dirt nobody cleans at unload; that is a defect.
  • Reaching to modify agent-loop to change behavior — first find the right domain's event and hook it; changing the loop itself requires updating the architecture docs and is the last resort.
  • Believing vendor/ is an ordinary npm-installed dependency — it is a pinned source copy with its own sync procedure and local-modification log.
