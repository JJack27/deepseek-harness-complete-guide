Chapter 14 · Part III · Capability Seams in Depth

Delegation and Subagents

When one agent can't keep up, dsh's answer is delegation: hand tasks to subagents, each with its own session and context. ctx.subagents is the busiest seam in the repository — unlike bash, which allows exactly one executor, it is a multi-provider registry: in-process fork, fresh in-process subagents, out-of-process ACP, real Codex and Claude Code, out-of-process full dsh — seven backends coexisting under one contract. This chapter covers the provider lineage, the three model-facing tool families, the lineage recorded in the SessionHeader together with the depth cap, and the Ralph loop that swaps in a fresh agent every round.

Learning objectives
  • Explain why ctx.subagents is a named registry (multiple coexisting providers) rather than a single-service seam, and list the differences among the seven providers
  • Distinguish the seed boundaries of fork versus spawn, and name the shared machinery that in-process-driver carries
  • Split tool-subagent / tool-subagent-control / tool-subagent-report into their responsibilities
  • Explain how parentSession + delegationDepth form lineage, and what lineage is data, not visibility means
  • Describe the Ralph loop's strategy: fresh subagents + bounded structured handoff + the shared workspace as long-term memory

14.1 ctx.subagents: one interface, many backends

docs/subsystems/subagent.md opens by calling out this seam's specialty: it allows multiple provider implementations to coexist by name in the same context (the ctx.subagents registry), whereas bash allows exactly one executor. The registry's shape follows the LLM adapter registry (Chapter 10's ctx.llm), not the single-service bash executor. The Service Definition is dsh-subagent: it owns provider registration, the shared request/result contract, durable descriptors, and (optionally enabled) continuable subagent orchestration.

The core provider contract is start(request): Promise<SubagentRun> — the ownership-transfer boundary. Before fulfill, the provider owns the startup process, and any failure must cancel, roll back, and silently dispose unpublished resources; after fulfill, the caller owns the run and must dispose() it on every path. SubagentRun.result resolves to { output, structured?, stopReason }: subagent-level failures resolve with a reason other than completed, and only infrastructure failures the seam cannot express reject.

Providers advertise four startup capabilities through static capabilities — outputSchema (enforce structured final results), depthLimit (enforce maxDepth), toolFilter (subagent tool restriction), and persona (subagent persona). The service validates the request against the capabilities before the subagent is created, refusing loudly when a capability is missing (UNSUPPORTED_CAPABILITY) — never accept first and pretend not to see it later.

There is also one shared piece that never appears in the registry: subagent-in-process-driver — the run driver shared by spawn and fork (next section).

The fork seed boundary is the most delicate part of this family. When the parent agent initiates delegation, its current tool-calling turn has not ended: the log holds the assistant's tool calls but not the paired tool results, and no turn/end. Copying the raw log verbatim would hand the subagent an unbalanced, illegal session. Fork therefore takes only the contiguous prefix up to the last turn/end — the subagent sees every completed turn and nothing of the turn in progress; if the parent has completed no turn at all, the seed is empty and fork degenerates into spawn. The seed transfers conversation history only: the subagent still gets a brand-new flat registration scope and does not inherit the parent's tool restrictions or permissions.

The rest of the two in-process providers' machinery lives in subagent-in-process-driver's startInProcessRun: depth validation → ctx.agents.create (with the mandatory cancellation signal) → inside the unpublished setup window, install the persona / tool filter / structured-output runtime → publish the subagent → drive one task with child.followup(prompt) + child.whenIdle() → read the subagent's own output (the last non-empty assistant message, or accumulated assistant text). The depth check is also inside the driver: parent depth + 1 is written into the subagent's header (next section).

The three out-of-process backends (acp, codex, claude-code) all spawn their subprocess through ctx.subprocess (Chapter 12's foundation), with the working directory taken from the delegating parent session's cwd — never the server process's own cwd, because one server process serves sessions of many workspaces. The dsh-sdk backend instead makes the subagent a full peer harness: its own cordis.yml composition, session persistence, model routing, and tools; it differs from the ACP backend in wire and subagent contract — ACP drives any ACP agent, while the SDK drives specifically a harness runtime.

The permission boundary of delegation

Both in-process delegation paths fix the subagent's permission scope at the delegation boundary: they snapshot the parent session's explicit sandbox overrides and pin the subagent's approval policy to 'never' (whenever the approval capability is in the composition) — the delegated subagent acts only within the inherited sandbox scope, and any ask (for example a sandbox_permissions escalation) is refused deterministically instead of waiting on a prompt nobody is watching. These values are written into the subagent's own log as sandbox/mode / approval/policy events with source: 'delegation' — the subagent's effective policy is reconstructable from its own log alone. The subagent also receives a subagent:delegation runtime-context statement: the scope is fixed, and when it needs more permission it should state the limitation in its reply rather than retry.

14.3 The tool families: launch, control, report

The model face is shared by three packages, each pointing a different direction:

PackageDirectionTools and key points
tool-subagentparent → child (launch)Each plugin instance binds one provider to one tool name (default subagent); the model gets no provider selector — to expose a second transport, mount another renamed instance. Foreground calls await run.result and always run.dispose() before returning; backgroundMode picks one-shot (registers a plain Task when backgrounded, returns a jobId) or continuable (background by default, returns a durable childId). maxDepth defaults to 3 (0 forbids delegation).
tool-subagent-controlparent → child (follow-up)send_message / interrupt_agent / list_agents registered once globally (the listing tool via the detachable ./list-agents plugin). A message becomes the subagent's next FIFO turn (Agent.followup()) and cannot redirect the turn in progress; interrupt_agent stops only the current turn (keepInbox) — queued messages stay and published descendants keep running.
tool-subagent-reportchild → parent (report)The report tool, registered only inside a continuable subagent's scope — installed via the registerContinuableSetup contribution, invisible to the root session, one-shot subagents, remote providers, and sibling scopes. It takes no recipient parameter: exec.agent is the sender credential, and the service derives the single recipient from the subagent's durable parentSession. The in-scope registration deliberately survives the subagent's toolFilter — the delegation allowlist cannot delete the only return channel.

The continuable-subagent world adds one more thing: a settlement notification. When the subagent's residence (Activation) ends, the orchestration manager tells the parent in its own turn that the subagent has finished everything it was going to do — attaching the stop reason and the final assistant content. This notification is delivered unconditionally: it does not depend on whether the subagent ever called report, because the endings most in need of an account (token exhaustion, model failure, cancellation, teardown) are exactly the ones where the subagent never got to choose.

14.4 Lineage: parentSession and delegationDepth

Subagents are not rootless: when publishing the child agent/session, the local run records request.parent.session.id into the child session header's parentSession field; the in-process driver writes parent depth + 1 into the child session header's delegationDepth. Both fields are durable — persisted with the session and still valid after a cold recovery.

Three depth semantics to memorize. First, the durable header is authoritative and monotonic: runtime options may deepen the count but never shallow it — a restored subagent cannot be recounted as top-level. Second, the cap is checked on every start: the tool remains visible at the cap (the model sees the tool exists), but the refused derivation returns an error tool result; setting maxDepth to 0 forbids delegation outright. Out-of-process providers may configure 'provider-managed' — the budget belongs to the harness on the subagent's side, and the parent sends no cap. Third, lineage is data, not visibility: inheritsParentContext only describes whether the subagent sees the parent session's completed conversation history (fork sees it; spawn and out-of-process providers don't); it does not mean inheriting tools, services, or permissions; parentSession grants no sibling-to-sibling visibility either — it serves delivery authorization (who may message this subagent), report routing (who receives the report), and list_agents' directory traversal.

14.5 Continuable subagents and Activation

One-shot delegation is ask once, get one result; a continuable subagent is a durable conversation object: one durable Session plus at most one process-local Activation — the latter is not a request, not a Task, not a result boundary; it is one residence epoch of the reconstructed child Agent. The Agent inbox is the only turn queue: every follow-up (send_message, a wake-style report, the settlement notification) becomes the next FIFO turn through Agent.followup(), never redirecting a turn in progress. A subagent in residence receives directly (waking the waiting Activation); a subagent not in residence cold-recovers from the durable Session — the reconstruction input is the subagent/descriptor event in the log (recording the provider name, lifecycle mode, creation labels, model routing, and more), and cold recovery goes through no provider at all.

From agent silence and its owned set of subagents, the orchestration manager derives three internal residence states: running (an active turn or un-woken inbox work), waiting (silent but still owning undisposed subagents), and settled (every subagent disposed, whereupon it disposes the AgentHandle and removes the Activation). Teardown propagates cancellation top-down and releases handles bottom-up (child-first) — a parent agent counts as silent only after every subagent it started is truly disposed, so a runaway recursive tree has a definite closing point.

14.6 The Ralph loop: a brand-new agent every round

The delegation lineage solves parallel division of labor; the Ralph loop solves another class of problems: iterative execution toward a long objective. dsh-tool-ralph (workflow group) provides the model-facing ralph({ objective, maxRounds? }) tool: a fixed foreground workflow that hands an immutable objective to a sequence of brand-new subagents. It demonstrates that a specialized orchestration policy is just an ordinary plugin — no Ralph mode was added to agent-loop; everything is built on the two seams ctx.workflowEngine and ctx.subagents (the workflow engine's full story waits for Chapter 17).

The loop's rules:

  • Each round starts one subagent through the configured subagentProvider (default spawn); that provider must support structured output and report inheritsParentContext: false — every round is a clean mind.
  • Each subagent receives only: the immutable objective, the current round number and cap, the shared-workspace-is-permission instruction, and the previous round's structured handoff report. The parent conversation and earlier subagent sessions are never seeded — the workspace is the long-term memory.
  • Reports are structured: status: continue | complete | blocked, plus a non-empty summary, evidence, next steps, and a blocker statement; once serialized they are capped by maxHandoffChars (default 16384 characters). Invalid, missing, or over-cap reports fail the workflow rather than being truncated or misread as exhausted rounds.
  • The terminal outcome complete / blocked / budget-limited returns together with the last round's bounded report and the round count; the rendering explicitly marks it as the working agent's self-report, not an independent verification. The round cap defaults to 256 (the deployment config doubles as the ceiling for per-call overrides).
  • An ordinary subagent failure produces an error (naming the failed round, preserving the last successful handoff), and Ralph does not retry that round; cancellation is likewise an error, and partial output never counts as success.

Ralph closes this chapter because it strings every theme into one sentence: the unit of delegation is the session, the unit of memory is the workspace, and the unit of transfer is the bounded structured report. A brand-new subagent every round means the context never bloats (Chapter 15's topic gets its answer early here); a bounded handoff means controllable inter-round state; lineage and depth are recorded as usual — Ralph's subagents are a sequence of depth-1 siblings derived directly from the parent, not an ever-deepening chain.

14.7 Chapter recap

  • ctx.subagents is a multi-provider registry seam (modeled on ctx.llm, not single-service bash): six registered names — spawn / fork / acp / codex / claude-code / dsh-sdk — plus the shared in-process-driver.
  • The provider contract makes start() the ownership-transfer boundary: before fulfill the provider rolls back; after fulfill the caller must dispose(); the four capabilities are validated before startup, and a missing one refuses loudly.
  • The fork seed is the contiguous prefix up to the last turn/end — the subagent always gets a balanced session; the seed gives history only, no tool restrictions or permissions.
  • Three tool families: tool-subagent (per-provider launch, one-shot/continuable background modes), tool-subagent-control (send_message / interrupt_agent / list_agents), tool-subagent-report (in-scope report return, surviving toolFilter).
  • Lineage = SessionHeader.parentSession + delegationDepth (authoritative, monotonic, durable); the depth cap guards against runaway recursion; lineage is data, not visibility.
  • The delegation boundary fixes the subagent's permissions: approval pinned to 'never', sandbox overrides snapshotted into events written to the child log, and the subagent receives the subagent:delegation statement.
  • A continuable subagent = durable Session + process-local Activation; the inbox is the only FIFO, and the settlement notification is delivered unconditionally.
  • The Ralph loop = a sequence of brand-new subagents + bounded structured handoff + the workspace as long-term memory, all built on two existing seams.
Common pitfalls
  • Assuming a subagent seam works like bash with one implementation — ctx.subagents is a named registry with coexisting providers, bound one tool instance at a time.
  • Expecting send_message to interrupt the subagent's current turn — it only queues as the next FIFO turn; to stop the current turn use interrupt_agent, which does not dispose the subagent.
  • Treating parentSession as visibility — lineage only serves delivery authorization and directories; sibling subagents cannot see each other, and nobody but fork sees the parent session.
  • Assuming toolFilter is a permission boundary — it is a visibility/composition restriction; the subagent's permission boundary is fixed at delegation time by the delegated policy.
  • Configuring a fork subagent in continuable mode — the shipped compositions all bind fork to one-shot: the in-scope report tool would break the byte-level prefix the KV cache needs.
  • Treating Ralph's complete as independent verification — it is the last round's working agent self-report; the renderer marks this explicitly.
  • Expecting an ACP subagent to appear in list_agents — an ACP run has no local child session and is not in the trace-enumerable directory.
