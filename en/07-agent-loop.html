Chapter 7 · Part II · The Core Spine

The Agent Loop: Turn/Step Lifecycle

In the first six chapters you met plugins, events, the session log, and the Agent interface — but one black box remained: after messages enter the inbox, who exactly, and in what order, keeps the machine of 'model request → tool call → request again' turning? This chapter opens that black box. By the end you will know everything that happens in a turn from open to close, which events go into the log, which live only in the process, and at which points you can intercept it.

Learning objectives
  • State how ctx.agentLoop and ReactLoopAgent relate to the Agent interface from Chapter 6
  • Distinguish the three layers: driver (the outer loop), turn (one drain of admitted input), step (one model request + its tools)
  • Recite, in order, every event and extension point of a complete turn
  • Separate durable session events from live in-process events, and name the waterfalls whose listeners must call next()
  • Explain the inbox's followup / steer / inject deliveries, parallel tool scheduling, and cancel/recovery behavior

7.1 The one driver: ReactLoopAgent and ctx.agentLoop

Chapter 6 said that Agent is the surface all plugins (UI, hooks, orchestrators) program against: ctx.agents.get(id) retrieves it, you call followup() upward on it and await whenIdle() downward. But Agent is only an interface — who implements the loop that 'turns messages into model requests, model replies into tool calls, and tool results into the next request'?

The answer lives in packages/core/agent-loop/. It has two roles:

  • AgentLoop service (ctx.agentLoop): plugged in at packages/core/agent-loop/src/index.ts; it is an AgentFactory — responsible for creating/resuming agents per configuration, publishing them into the ctx.agents / ctx.sessions registries, and owning orderly teardown. It declares static inject = ['agents', 'sessions', 'llm', 'tools', 'systemPrompt'], which is to say an agent loop naturally stands at the junction of those five services.
  • ReactLoopAgent (src/agent.ts): the driver that actually implements the Agent interface. Its module doc states it in one sentence: 'Default Agent driver over queued turns and step-boundary input. Every request is derived from the session log.' It is the repository's only concrete driver of the Agent interface, and it is a private implementation inside the package — no code outside the loop depends on this class; everyone depends on the interface.

'Every request is derived from the session log' deserves a pause. This is not a style preference but the landing spot of the Chapter 4 invariant: in every step, the model history is not an array accumulated in memory but a projection from the log's event stream produced by calling session.deriveMessages(). At the end of this chapter you will see that packages/core/agent-loop/src/invariant.ts even hangs a runtime assertion on llm/stream: the request's messages must match the log-derived result byte for byte.

Internally, ReactLoopAgent maintains a three-state Phase: idle (no activity), running (a driver is executing turns, with turn/step counters and an AbortController), and maintenance (running a non-turn maintenance job). State switches broadcast agent/status (idle / running) externally — the source of that little status light in the UI.

7.2 Three layers of vocabulary: driver, turn, step

Let's fix the vocabulary first. Three layers, outside in:

  • driver (the outer loop; some systems call it a round): a woken driver keeps starting turns until nothing is owed and no input is queued, then returns to idle. For honesty's sake: the dsh source has no entity named round — the outer layer is just the while (await this.turn()) {} loop inside kick(); durable numbering also goes down only to the turn/step two levels. Remember this layer as the 'policy-iteration layer': it decides whether to open another turn.
  • turn: one complete 'drain of admitted input' process, containing zero or more steps. The definition in docs/architecture.md, verbatim: a turn opens before the first input that claims it and closes when nothing is owed. Every turn has a monotonically increasing number; in the log it is framed by the turn/start / turn/end event pair, and turn/end carries the end reason TurnEndReason: completed / max-tokens / blocked / aborted / error.
  • step: one model request plus all the tools it calls. In the log it is framed by step/start and step/end, numbered from 1 within the turn. Tool results that 'owe' a response, or new input cutting in, both spawn the next step.

A turn can also have zero steps: if the input is rejected by agent/pre-step, or the first batch is rewritten to empty, the turn still opens and closes (7.3 below explains why this is not waste). Conversely, the number of steps in a turn has no static upper bound; it is decided solely by 'is anything owed'.

7.3 The lifecycle of a complete turn

The flow below follows the 'Turn flow' section of docs/architecture.md; for each step I have marked the corresponding code location in agent.ts. Treat this section as a checklist when debugging.

Let's walk the flow, watching four gates in particular:

Opening (turn()). The driver first lands turn/start, numbered as the previous turn + 1 (when resuming a session, the number is recovered from the log via findLast(turn/start), so numbering continues across processes). Then it enters the loop: each candidate step first passes through preStep() — which does three things: this.inbox.claim(target, turn) claims the next-step input plus one queued message; it calls ctx.systemPrompt.assemble() to assemble the prompt sections and tool schemas (expanded in Chapter 9); and finally it hands the claim result to the agent/pre-step waterfall.

The admission gate (agent/pre-step). This is the authoritative decision point for 'what the model sees this round'. The default decision is enter(messages); listeners may rewrite that batch of messages or return reject. Two endings are worth memorizing:

  • reject → the turn closes with {kind:'blocked'}, spending not a single step;
  • the first enter rewritten to empty → the turn closes with {kind:'completed'}, likewise spending no step. The code comment puts it plainly: a removed wake-up message, or an enter decision rewritten to empty, still owns this turn boundary, but it costs no model call.

Note that 'spends no step' does not mean 'leaves no trace': turn/start and turn/end are already in the log, so the attempt is forever queryable. That is exactly the intent of Chapter 4's 'durable boundary events frame everything'.

Inside a step (step() and buildRequest()). Once admitted: land step/start, append each enter message to the log as user/message (including context carried by the previous step's tools and plugin-injected context); then derive the model history from the log with session.deriveMessages(); buildRequest() first lets the agent/request waterfall propose the request configuration (provider/model/sampling parameters), binds an adapter via ctx.llm.prepareCall(), and — when the configuration changes — lands request/header and request/context events (expanded in Chapter 10). The request then enters llm/stream: every chunk in the stream is immediately logged as assistant/chunk and fed to BlockAssembler; when the stream ends normally, one assistant/message event is assembled (carrying usage and the sequence of chunks it references, sourceEventSeqs).

If the assistant message contains tool-call blocks, it is executeToolCalls()'s turn (7.6): each call is first logged as tool/call (recorded before execution), passes through Chapter 8's execution pipeline, and finishes with tool/result. Tool results naturally owe a model response — unless a result is flagged concludesTurn — so the loop claims again and opens the next step. When the assistant message has no tool calls, or hits max-tokens (a reason that is 'sticky' within the turn: later steps that complete normally cannot downgrade it), the step ends with the corresponding reason.

Closing. After a step ends, if 'nothing is owed and the next-step inbox is empty', the loop first broadcasts agent/turn-stopping — a final checkpoint that is serial and has no next() (wrap-up plugins make their last moves here) — and then lands turn/end. Whatever happens in between, turn/end is appended in a finally block: crash, cancellation, and error all still produce a closing event with a reason.

7.4 Two classes of events: durable and live

Slice the 7.3 flow by 'does it go into the log' and you get a table worth memorizing. Durable events are part of the session log; replay, resume, fork, and transcripts all depend on them. Live events are broadcast only within this process, for coordination and interception, and they die with the process.

ClassEventsNotes
durable turn/start, turn/end, step/start, step/end boundary frames; turn/end carries TurnEndReason
durable user/message, assistant/chunk, assistant/message the conversation surface; chunks serve replay, messages serve derivation
durable tool/call, tool/result tool-call pairs; recorded before execution
durable request/header, request/context (plus llm/retry and friends from llm-retry) a reconstructable snapshot of request configuration and environment
live agent/status, agent/error, agent/inbox/inserted|claimed|discarded status and queue coordination signals
live · waterfall agent/pre-step, agent/request, agent/request-error, llm/stream, tools/pre-execute, tools/execute, tools/post-execute interceptable and rewritable; listeners must call next() to delegate downstream or the whole chain short-circuits
live · serial agent/turn-stopping serial broadcast, no next(); observation/wrap-up only, cannot rewrite the decision
Runtime evidence of the invariant

packages/core/agent-loop/src/invariant.ts hangs an assertion at the very front of llm/stream: the loop-built request must be frozen, carry a live sessionId, its request.messages must match the result of session.deriveMessages() exactly, and its header must match the request/header collapsed from the log. Any plugin that slips the model something mid-flight that does not exist in the log gets caught here — 'model-visible ⟺ logged' is not a documentation slogan; it is an executed check.

7.5 The inbox: the single entry point for all input

The UI chat box, the command system, hooks, subagents, compaction plugins — everyone who wants to talk to the agent goes through the same inbox. ReactLoopAgent's constructor creates new Inbox(session, {...}) and maps insert/discard/claim immediately to the three live events agent/inbox/inserted / agent/inbox/discarded / agent/inbox/claimed. The semantics of the unified entry live on send(message, target, wakeup):

MethodtargetWakesSemantics
followup(msg)next-turnyesa new utterance, handled by the next turn
steer(msg)next-stepyesa cut-in instruction, entering the model's view at the next step as soon as possible
inject(msg)next-stepnoinjected context, queued for the next admitted request

The key difference is wakeup: some messages wake the driver immediately (followup/steer), some do not (inject). The line in docs/architecture.md's extension table — 'Add model-facing context → call agent.inject(); it lands in the next admitted request' — means: the injected content rests quietly in the next-step queue until some message wakes the driver, or the current turn's next step comes to claim it. An idle agent stays idle after inject().

The interaction between cancellation and wake-up has one fine point (the source comments call it the wake latch): a waking input that collides with an in-flight cancellation is reassigned to next-turn and replayed after the activity settles to idle; and a wake-up delivered to an already-idle agent always opens its own turn boundary. You do not need to memorize the details — just know this: wake-ups are never lost, at most delayed.

7.6 Scheduling tool calls: the parallel pool and barriers

One step's assistant message can carry multiple tool-call blocks. executeToolCalls() in src/tool-calls.ts schedules them, with only three rules:

  • Classify first. Each call is classified via ctx.tools.executionMode(exec): only when the tool's isConcurrencySafe(args) returns exactly true is it parallel; undeclared, throwing, or returning non-true are all treated as exclusive — fail conservative.
  • Exclusive is a barrier. An exclusive call forms its own group, creating a sequential barrier; parallel calls form a bounded rolling pool (maxParallelToolCalls, default 10, adjustable at runtime via agent-loop's settings). Inside the pool, 'dispatch may overlap while policy and results keep model order': pre-execute runs serially in order, tool bodies run concurrently, and results are committed to the log in the order the model gave.
  • Re-classify before launch. Before each call launches, the current registry is re-queried (tools may be registered/unregistered mid-flight); a call that has since become exclusive waits for the current pool to drain and forms its own barrier.

Cancellation semantics likewise serve replay: after an abort, already-started calls drain normally and commit their results; unstarted calls get a synthetic pair of tool/call + tool/result (error code ABORTED_BEFORE_DISPATCH), guaranteeing that every call in the log has a result and replay has no gaps.

7.7 Cancel, maintenance, and error recovery: the agent handle

The 'The agent handle' section of docs/subsystems/core.md lays out the public lifecycle methods clearly; here are the four most relevant from the loop's perspective:

  • cancel(cause, options?): by default clears the inbox and aborts activity; pass {keepInbox:true} to preserve queued work. The first cause wins; a no-op when nothing is running. Cancellation is not a hard kill — it propagates cooperatively along the AbortSignal to the step, the stream, and every tool (Chapter 8's tool-cancellation contract shares this source).
  • whenIdle(): waits for the whole agent to reach quiescence (the current driver and every successor finish). The teardown flow (dispose) is exactly 'one cancel({kind:'disposed'}) plus whenIdle()'.
  • runMaintenance(job): runs a non-turn maintenance job (say, compaction wrap-up) from true idle; wake-up inputs arriving meanwhile stay in the inbox and replay when the job ends, with the visible status remaining idle.
  • Error recovery: structured failure. LlmError keeps its own code/facts; other exceptions are flattened by errorChain() into UNKNOWN-code text; after a failure is reported via agent/error it is contained at the driver boundary, and turn/end records {kind:'error', error}. In-stream failures first pass through the agent/request-error waterfall: by default the original error is kept; returning {kind:'retry'} re-issues the request within the same step (the llm-retry plugin lands llm/retry and llm/retry-started events around the wait; the failed attempt's chunks stay in the log but are never assembled into a message, so the model history stays unpolluted).
The key intuition of this chapter

The agent loop is a log-first state machine: events land first, actions follow; every model input derives from the log, and every boundary (turn/step/tool call) has a durable frame. Whenever you write a plugin, just ask 'which cell of the log does my behavior land in, and which live point do I intercept at' and you will not get lost.

7.8 Chapter recap

  • ctx.agentLoop (the AgentLoop service) creates/resumes agents; ReactLoopAgent is the only concrete driver of the Agent interface — private to the package, deriving every request from the session log.
  • Three layers of vocabulary: the driver outer loop (called round in this book; no such name in the source) > turn (a drain of zero or more steps) > step (one model request + its tools).
  • A complete turn: turn/start → claim → assemble → agent/pre-step (reject | enter) → step/start → user/message → derive → agent/request → llm/stream → assistant/chunk* → assistant/message → tool/call* → the tools pipeline → tool/result* → step/end → (next step if anything is owed) → agent/turn-stopping → turn/end.
  • reject or an emptied first enter → the turn closes with no step (blocked/completed), but the log records the attempt; turn/end always lands and carries a reason.
  • durable: turn/*, step/*, user/message, assistant/*, tool/*, request/*; live: agent/*, llm/stream, tools/*. Waterfall listeners must call next(); agent/turn-stopping is serial with no next().
  • The inbox is the unified entry: followup (next-turn, wakes), steer (next-step, wakes), inject (next-step, does not wake).
  • Tool scheduling: isConcurrencySafe strictly gates parallel; exclusive forms barriers; the pool is bounded; results commit in model order; abort backfills synthetic results for unstarted calls.
  • The handle: cancel/keepInbox, whenIdle, runMaintenance; errors are structured, and retry re-issues within the same step.
Common pitfalls
  • Assuming 'a turn that executed nothing never happened' — a step-less turn still leaves turn/start + turn/end, which is exactly what audit needs.
  • Forgetting to call next() inside a waterfall listener — you are not 'adding a hook', you are cutting off the entire chain (the Chapter 2 semantics are a hard rule here).
  • Treating inject() as 'send the model a message right now' — it does not wake the agent; it only queues for the next admission.
  • Assuming a parallel tool's 'result order' equals its 'completion order' — dispatch may overlap, but commits always follow model order.
  • Assuming a retry opens a newly numbered turn — per agent.ts and the llm-retry tests, the retry action re-issues the request within the same step.
