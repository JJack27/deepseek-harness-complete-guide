Chapter 17 · Part III · Capability Seams in Depth

A Tour of Capabilities

shell, fs, subagent, compaction — the capabilities the previous chapters dug into are only half the repository. This chapter is a one-page map: it walks through the remaining fourteen capability families, one short section each, by what problem they solve, how the packages split, and where to extend. You do not need to memorize every detail — you only need to know which door to walk through when a need arises, and inside every door the three-role structure is the same methodology you already mastered in Chapter 11.

Learning objectives
  • Given a capability need (search, orchestration, scheduling, credentials, …), name the matching capability family and its ctx.* service key
  • For each family, point to its extension point: registering a provider, listening on events, or mounting a Consumer tool
  • State a few deliberately tightened boundaries: lsp exposes only four operations, schedule includes no external notification channel, credentials configuration carries no values
  • Cross-reference this map against the full map in docs/capability-seams.md and fill in the details this chapter does not expand on

17.1 The capability map

The fourteen families fall into five groups by concern. Knowledge and external information answers “how does the model know more”; orchestration and continuation answers “how does work carry across steps and turns”; configuration and credentials answers “where do deployment differences live”; data and execution answers “how do binaries and model-written programs run”; introspection and bridging answers “how does the agent modify itself and connect to outside ecosystems”.

17.2 skill: a catalog and loader for reusable instructions

The skill family discovers reusable agent instructions (SKILL.md and the like) and exposes them to the model through a provider-neutral catalog. dsh-skill is a pure registry: providers register sources with registerProvider(create) (local files, embedded data, HTTP — anything works), and consumers read with snapshot()/list()/get(); skills/change is an invalidation notification that carries no catalog content. The registry layers host+per-scope (the shape the tool registry established in Chapter 11), and the invocation policy separates modelInvocable from userInvocable. dsh-tool-skill snapshots the catalog on every qualifying agent/pre-step, publishes an ordered name/description catalog as a durable user-role <available_skills> message, and appends a full replacement only when the summary digest changes; the skill tool loads by name, and renderSkillContent() guarantees that catalog injection and tool loading render the same <skill_content> shape.

17.3 web: search and fetch share one seam

dsh-web's WebRuntime (ctx.web) spans two operations (search, fetch) on one seam: registerSearchProvider and registerFetchProvider each register a backend, and at execution time resolution follows “explicitly configured provider id, otherwise the exactly one available is auto-selected, otherwise throw” — selection never depends on registration or HMR order. Errors go through the structured WebError vocabulary (e.g. a configured id that is not registered is WEB_PROVIDER_CONFIGURED_MISSING; unconfigured with several available is WEB_PROVIDER_AMBIGUOUS). Providers register capabilities, not tools: dsh-tool-web is the sole owner of the model-visible names (web_search/web_fetch), schema, and presentation. To attach a new search or fetch backend, registering a provider is all it takes.

17.4 lsp: four semantic operations, no escape hatch

The LSP family pulls language-server capability into a deliberately narrowed seam: ctx.lsp exposes only four semantic operations — goToDefinition, findReferences, goToImplementation, hover — with no general JSON-RPC escape hatch. Swapping providers therefore never changes how the model asks, and no protocol payloads or unreviewed changes can reach the model contract. dsh-lsp-stdio is the general multi-server backend, built on ctx.fs and ctx.subprocess (the shared execution world from Chapter 12), opening documents transiently per query; dsh-tool-lsp is the model-visible lsp tool, using one-based UTF-16 cursor coordinates. Providers register capabilities, not tools — the model-facing names and schema belong exclusively to tool-lsp.

17.5 mcp-client: a bridge to external tool ecosystems

dsh-mcp-client connects to external MCP (Model Context Protocol) servers and registers their tools on ctx.tools, so the model uses them as native tools: the public name is mcp__<serverName>__<rawName>, the same shape as Claude Code and Codex. Each MCP server is one plugin instance in cordis.yml, with transport as stdio or streamable-http; tool names are a pure function of (serverName, rawName) — connection order, re-syncs, and other servers never rename anything. A supervisor restarts dropped connections with exponential backoff and rediscovers; when the budget is exhausted it unregisters the tools until reload. Note that it bridges tools only: MCP Resources and Prompts have no consumers yet.

Packagectx key / roleExtension points
dsh-mcp-clientconsumes ctx.toolsone instance per server in cordis.yml (transport / serverName / command / url / reconnect…)

17.6 workflow and ralph: orchestration written by the model

The workflow family runs orchestration scripts written by the model. dsh-workflow defines execution and lifecycle (ctx.workflowEngine), and dsh-workflow-worker-thread runs the script on a worker thread — the thread isolates execution from the host event loop but is not a security boundary. dsh-tool-workflow exposes the workflow tool (meta/script/args) and projects the run into the caller session's workflow/* log-only events. dsh-tool-ralph is a fixed-policy Consumer on the same engine: ralph({ objective, maxRounds? }) hands an immutable objective to a chain of brand-new subagents — one fresh child per round (the provider must support structured output with inheritsParentContext: false), the shared workspace serves as long-term memory, and structured handoffs pass between rounds. Nothing in agent-loop was changed for it (echoing Chapters 7 and 14: orchestration is a plugin, not a loop branch).

17.7 jobs: one protocol for background jobs

Long-running tools (builds, watches, collection) need observation, cancellation, waiting, and completion notification — the jobs family gives them one owner-fenced protocol. dsh-jobs defines the ctx.jobs registry contract (start/get/list/read/kill/wait/onJobDone/onJobsChanged), and dsh-jobs-local is the in-process implementation. Access is fenced by SessionId (owner fence), and a controller's registration is owner-relative too: an assembly without the controller loaded cannot start work under someone else's control. dsh-tool-jobs exposes three kind-agnostic tools — job_output, job_list, job_kill — plus completion notification. Notifications use two lanes: when the owner is busy, inject into the next-step inbox (Chapter 15's agent.inject(); several jobs settling at once cost a single step); when the owner is idle, wake it with a follow-up turn, with a maxConsecutiveWakes budget against self-excitation.

17.8 goal and schedule: two views of time in the same session

Both families store state in the existing session log, but with opposite directions of time. goal targets objectives pushed forward across many turns: ctx.goals keeps at most one current objective and appends a goal/change event carrying the complete post-change snapshot on every change; activation (the continuation authorization) is never persisted — it is process-local, and resume/fork keeps the objective and its stage but does not act; an explicit resume must re-arm it afterwards. dsh-goal-round-driver turns an activated objective into sequential goal rounds: when idle it reserves a turn and queues a <goal_round> prompt as GoalMessageSource's user/message; human messages take priority and do not consume the goal turn budget. schedule targets future reminders: the single package dsh-schedule provides the session-scoped schedule_create/schedule_list/schedule_delete three tools, with durable state in the session log; the process-local owner waits only while that session has a live root agent, and due work enters the conversation through the ordinary follow-up queue — it implies no external notification channel whatsoever.

17.9 settings and credentials: configuration and credentials

The settings family resolves user-editable configuration: on ctx.settings plugins register namespace schemas, and reads resolve in layers — “schema default → the registrar's assembled base → the user document section”; with no provider mounted, consumers keep resolving entry config only, so every assembly works with or without settings. dsh-settings-file stores the document in a local file and observes external edits. The credentials family's doctrine is three sentences: configuration carries references, never values (CredentialRef is branded, and resolve(ref) runs at the start of every operation with no caching across operations — swap a key and the next request already uses it); describe returns no values (configuration UIs are safe); an empty value counts as absent. dsh-credentials-local layers the process environment over $DSH_HOME/.credentials.yaml with an .env layer as fallback; when a read-only source shadows a reference, set/unset deliberately refuse.

17.10 attachment and code-runtime: bytes and programs

The attachment family handles durable binaries: ctx.attachments validates and atomically commits immutable image bytes and returns a serializable ImageAttachmentRef — consumers never stuff browser paths, object URLs, or base64 into session events; unsent draft images stay on the browser side, and bytes reach durable storage only when the user submits a prompt or a provider adapter submits structured output. dsh-attachment-local puts content-addressed private storage under DSH_HOME. The code-runtime family is the foundation of Code Mode: ctx.codeRuntime defines a runtime that “executes a model-written program, evaluates host-provided async bindings, and captures prints and return values”, and dsh-code-runtime-worker-thread is the worker-thread backend; the Consumer is the tool registry's own Code Mode (tools: { mode: code }) — the run_code tool plus an SDK generated for the loaded runtime's language. You already saw one facet of it in Chapter 15: the durable log copy of sub-call results accepts a spill ceiling through tools/code-dispatch-log.

17.11 extensions and hooks: introspection and bridging

The extensions family lets the agent inspect and modify its own runtime: dsh-tool-cordis registers model-visible runtime-inspection and dynamic-package tools on ctx.tools — inspect loaded plugins and service APIs, define and run model-written dynamic packages, then withdraw them; dsh-cordis-host-runner provides ctx.dynamicCordisRunner (a definition registry + node:vm sandbox + request-run round trip), dsh-cordis-client-runner is the browser half, and dsh-ui-cordis provides the operations panel and read-only define cards. This is the machinery behind “demo:cordis lets the agent modify its own runtime”. The hooks family faces outside ecosystems: it faithfully maps Claude Code / Codex style external shell hooks (hooks.json) onto dsh's typed interception points — dsh-hook-protocol is the shared wire-protocol library, while dsh-hooks-claude-code and dsh-hooks-codex each own their dialect's event mapping. Remember the stance: dsh's native extension surface is exactly those typed interception points, and a “native hook” is just an ordinary Cordis plugin mounted on them.

17.12 Chapter recap

  • Knowledge and external information: skill (ctx.skills catalog + skill tool), web (ctx.web search/fetch on one seam, multiple providers, explicit selection policy), lsp (four operations, no JSON-RPC escape hatch), mcp-client (mcp__server__tool registered on ctx.tools).
  • Orchestration and continuation: workflow (ctx.workflowEngine + worker thread + workflow tool), ralph (fixed fresh-agent loop, workspace as long-term memory), jobs (ctx.jobs owner fencing + job_* tools + inject/wake two-lane notification), goal (ctx.goals event sourcing, activation process-local), schedule (reminders in the session log, no external notification channel).
  • Configuration and credentials: settings (namespaced layered resolution + file provider), credentials (references carry no values, per-operation resolve, empty means absent).
  • Data and execution: attachment (immutable image bytes + ImageAttachmentRef), code-runtime (ctx.codeRuntime + Code Mode's run_code and generated SDK).
  • Introspection and bridging: extensions (ctx.dynamicCordisRunner, the model inspecting/mounting its own plugins), hooks (external shell-hook protocols bridged to typed interception points).
  • The shared pattern: providers register capabilities, not tools; model-facing names, schemas, prompts, and presentation belong exclusively to Consumer tool packages; state either enters the session log or stays in a sidecar, never model history.
Common pitfalls
  • Giving web/lsp providers tool names — providers register capabilities; model-visible names belong to tool-web/tool-lsp.
  • Expecting web to auto-pick among multiple available providers — unconfigured with several available throws WEB_PROVIDER_AMBIGUOUS; selection must be explicit.
  • Treating worker threads as a security boundary — the threads in workflow and code-runtime only isolate the event loop; they are not a sandbox.
  • Assuming schedule pushes notifications — it is an in-session reminder, delivered only while a live root agent exists.
  • Writing credential values into configuration — config carries only CredentialRef; values are resolved by the provider, and empty counts as unconfigured.
  • Adding a “Ralph mode” or changing agent-loop for ralph — it is a fixed-policy workflow on ordinary plugins.
  • Bypassing ctx.attachments to stuff base64/URLs straight into session events — the only durable reference is ImageAttachmentRef.
