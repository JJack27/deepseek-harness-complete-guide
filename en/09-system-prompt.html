Chapter 9 · Part II · The Core Spine

System Prompt Assembly

The system block and runtime context the model sees at each step are not a hardcoded string; they are assembled fresh every time: plugins register sections, dynamic contexts, variables, and tool schemas into ctx.systemPrompt, and the agent loop calls assembly after claiming input to obtain this round's complete input. This chapter lays out all the parts of assembly, how scoped registrations produce per-agent personas, and why the model-visible content contributed by the context group's plugins all travels the 'reconstructible from the log' path.

Learning objectives
  • Name the four kinds of registrations on ctx.systemPrompt: section, context, variable, tools provider
  • Recite the merge rules of assemble(): scoped shadowing, order sorting, toolOrder validation, the waterfall, complete sections
  • Distinguish the two model-visible channels, 'system section' versus 'runtime context' (the latter lands in the durable log)
  • Implement a per-agent persona by shadowing deployment:persona with a scoped section
  • State what each of the context group's four plugins contributes and with which events it lands in the log

9.1 The registry: four kinds of input

The SystemPrompt service (ctx.systemPrompt) from packages/core/system-prompt/ is a registry of 'ordered prompt inputs'. Exactly four kinds of things can be registered; each returns an effect disposer, and each supports scoped registration (registering via agent.ctx takes effect for that agent only):

APIWhat it isWhich channel it enters
section({name, order, text, complete?}) a piece of the system block; text is a static string or a function evaluated at each assembly; may reference {{variable}} the system prompt proper
context({name, order, text}) dynamic runtime context (facts-of-now such as time, environment, location) runtime-context snapshot → durable user-role message
variable(name, provider) an evaluator for a {{name}} variable (e.g. cwd, provider, model) interpolation into section/context text
tools(provider) a tool schema provider (Chapter 8's registry hangs here) the request's tools field

Two built-in sections are worth remembering: order -100 is the harness identity (You are an AI agent powered by DeepSeek Harness., which can be turned off with the includeHarnessIdentity: false config); order 0 is the deployment persona slot deployment:persona (filled from the persona configuration). Conventional numbering bands: the negative range comes before the persona, and tool self-descriptions use 100–199. Additionally suppressRuntimeContext() can turn off all dynamic context contributions within a scope, without touching the services that own those facts.

9.2 Assembly: assembled fresh at every step

Recall Chapter 7: after preStep() claims input it immediately calls ctx.systemPrompt.assemble({scope, signal}). Assembly happens in a fixed order:

  1. Merge the scope chain: variables resolve by 'most specific scope wins'; in sections / contexts, scoped same-name entries shadow global entries; tool providers participate both globally and along the chain.
  2. Sort: sections and contexts each sort by order ascending; tool schemas sort by the toolOrder config (which must contain the <unlisted-tools> placeholder exactly once; without config, lexicographic order); configuring a nonexistent tool name throws at assembly time.
  3. Waterfall: system-prompt/assemble is an expert waterfall — listeners may rewrite the assembly result wholesale, and the return value is authoritative — with one exception: sections marked complete: true. After assembly, such a section is restored as the only prompt section (two complete sections coexisting fails the assembly).
  4. Render: renderPrompt(assembly) does strict interpolation — {{name}} references must be registered and have values; malformed or unknown references throw immediately; sections rendering empty are dropped, and the rest are joined with blank lines. Tool schemas enter the request's tools field.

Why don't contexts go into the system prompt? Because the system prompt is 'identity and rules' — identical each round (or changed only by configuration) — while runtime context is 'facts of now': time moves, tmux windows shift. Making it a durable user-role message lets the log faithfully record 'what the model knew then', and the replacement relationship between snapshots ('this snapshot replaces the earlier runtime-context snapshot') is written into the message text itself. This is another application of the Chapter 4 invariant: model-visible input must be reconstructible from the log — sections travel via the system in request/header, contexts via user/message, each in its proper place.

9.3 Scoped sections and per-agent personas

The registry is scoped, which directly yields the per-agent persona recipe: register a same-name section deployment:persona in some agent's agent.ctx, and it shadows the deployment layer's persona slot, taking effect for that agent only. Persona-style preset packages use exactly this: same-name shadowing rather than appending, so an agent always has exactly one persona section and never two personas fighting each other. packages/core/system-prompt/src/index.ts deliberately exports the PERSONA_SECTION constant so the 'deployment side' and the 'shadowing side' reference the same name — each side writing its own magic string is the easiest place to drift; the shared constant makes replacement hold by construction. 

// Inside some agent's agent.ctx (pseudocode illustrating the shadowing mechanism)
agent.ctx.systemPrompt.section({
  name: PERSONA_SECTION,        // 'deployment:persona': same-name shadowing of the deployment persona
  order: PERSONA_ORDER,         // 0: the persona slot stays unchanged
  text: 'You are a read-only reviewer; never modify files. Current directory {{cwd}}.',
})

The same mechanism covers variables and tools: scoped variables shadow global ones, and Chapter 8's scoped tools shadow global tools. Chapter 6's shadowing mental model needs no new concepts on the prompt side.

9.4 The context group: four real sources of model-visible content

The four plugins of the packages/context/ group are the official implementations of 'add context for the model'. Let's walk through them, watching in particular how each plugin's content lands in the log:

  • dsh-agent-instructions (the AGENTS.md instruction chain): loads $DSH_HOME/AGENTS.md plus the instruction files of every directory from the project root down to cwd (candidates such as AGENTS.md/CLAUDE.md, deduplicating byte-identical ones). The baseline is synthesized at the session's first qualifying agent/pre-step and folded into the enter batch — landing as a durable user-role message (a <system-reminder> frame) right after the user's direct prompt; afterwards it observes successful read/write/edit tool results, and on discovering a new directory's instruction file it queues add/change/remove notices into the inbox, likewise landing in the log as sourced user/message events.
  • dsh-time-context (time context, opt-in): appends a listener at the head of the agent/pre-step chain; when due, it appends to the returned batch a sourced UserMessage (source: {kind:'plugin', plugin:'time-context', form:'snapshot', …}), which agent-loop persists after step/start and before request derivation. The browser timezone comes from the current turn's user-rpc message origin; the default composition does not load it (only the Schedule Web overlay mounts it).
  • dsh-tmux-context (tmux location, opt-in): at the first step of every turn, it runs a read-only probe command via ctx.shell to confirm it really runs inside a tmux pane (having $TMUX_PANE alone does not count — environment variables get inherited); only on a hit does it insert, at the head of the enter batch, a UserMessage with source {kind:'plugin', plugin:'tmux-context'}, likewise landing in the log after step/start.
  • dsh-session-reference (cross-session references): provides ctx.sessionReferenceResolver; prepare() projects other sessions mentioned via @ into bounded read-only snapshots and returns one sourced UserMessage. When the agent is idle, it is wrapped through a one-shot agent/pre-step into the enter batch; while running, inject() follows steer(), and both messages wait together for the next claim. Snapshots are pinned at capture time — later changes in the source session do not affect the target log's replay.

Four plugins, four entry styles (folded into the batch at pre-step, appended at pre-step, inserted at the head at pre-step, inject+steer) — but all roads converge: none of them quietly slips text into the system prompt. Model-visible content all exists as sourced durable user messages; the log records both 'what the model saw' and 'who gave it'. If you write a fifth context plugin, follow this pattern — this is not a style suggestion but a direct corollary of the repository-level rule that 'a new model-visible input requires a new session event'.

Connection to Chapter 7

Assembly happens inside preStep(), before the agent/pre-step waterfall; the assembly result (PromptAssembly) then follows the enter decision into step(): sections render into the request's system, and contexts are projected by RuntimeContextProjection into context messages in the enter batch. In other words: assembly runs once per step — tool registration changes and variable value changes take effect on the very next step.

9.5 Chapter recap

  • ctx.systemPrompt takes four kinds of registrations: section (the system proper), context (dynamic snapshots), variable ({{}} interpolation), tools provider (tool schemas).
  • assemble(): merge the scope chain (scoped shadows global) → order / toolOrder sorting and validation → the system-prompt/assemble waterfall → complete-section restore; renderPrompt does strict interpolation and drops empty sections.
  • Sections and tool schemas enter the request body; contexts take a different channel — durable user-role snapshot messages carrying the 'replaces the old snapshot' declaration.
  • A per-agent persona = registering a same-name deployment:persona section in agent.ctx to shadow the deployment slot; the shared PERSONA_SECTION constant guarantees both sides use the same name.
  • The context group's four plugins: agent-instructions (the AGENTS.md chain), time-context, tmux-context, session-reference — content all travels as sourced durable user/message events, reconstructible from the log.
  • Assembly happens before pre-step of every step, assembled fresh each step; registration changes take effect on the next step.
Common pitfalls
  • Assuming runtime context gets spliced into the system prompt — it is a separate durable user-message channel; stuffing 'facts of now' into system breaks the log's reconstructibility.
  • Writing each agent its own persona but forgetting same-name shadowing — you get two stacked personas; the correct way is same-name deployment:persona shadowing.
  • Writing {{var}} in a section without registering the variable — rendering throws immediately (strict interpolation, no silent blanks).
  • Configuring toolOrder that omits <unlisted-tools> or names a nonexistent tool — assembly fails; nothing is silently ignored.
  • Writing a context plugin that edits the system prompt directly or bypasses the log — it violates model-visible ⟺ logged; follow the context group's pattern and land user/message via pre-step / inject.
