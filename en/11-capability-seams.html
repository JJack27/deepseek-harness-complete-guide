Chapter 11 · Part III · Capability Seams in Depth

The Capability Seam Pattern: A Three-Role Methodology

Every capability you met in the first ten chapters — ctx.llm, ctx.tools, ctx.systemPrompt — has the same structure behind it. This chapter names that structure precisely: the capability seam, a complete cut through a replaceable capability, formed jointly by three roles: Service Definition, Service Provider, and Consumer. Once you own this pattern, you can answer the most important engineering question in dsh: which pieces do you design to add a capability, and which pieces do you touch to swap an implementation? The answers are three and one.

Learning objectives
  • State each role's responsibilities and boundaries, and why a Service Definition must be a Cordis Service subclass rather than a TypeScript interface
  • Using the dsh-shell family as the template, identify which package plays which role
  • Explain the chain reaction of swapping one provider for a whole product shape — why execution worlds migrate as a group
  • Consult the script-generated full map at docs/capability-seams.md to locate any ctx.* service's owner, implementations, and consumers
  • Given a new capability requirement, complete the design with the three-role checklist instead of writing just one plugin

11.1 What is a capability seam

One convention recurs throughout the dsh repository: A capability seam comprises Service Definition / Service Provider / Consumer roles. It is complete, never one role. A capability seam is a complete cut through a replaceable capability: cut along this seam and the capability can be swapped out whole, while neither side of the cut knows the other's concrete implementation.

The capability-seam entry in docs/glossary.md gives the precise definition. The three roles are:

  • Service Definition — a Cordis Service subclass that owns its own ctx.<key> service key and all the vocabulary types. It can be an abstract class (such as ShellExecutor) or a concrete registry (such as the web capability's registry), but it is never a TypeScript interface. An interface has no declaration merging, no ctx.shell key, no lifecycle — it cannot attach to Cordis's service graph.
  • Service Provider — the implementer. It subclasses the abstract Service or registers into the registry, filling in the how. A seam can have one provider or a set of parallel providers.
  • Consumer — the user. It obtains ctx.<key> through inject and programs only against the Definition's vocabulary. The most common Consumers are model-visible tools (such as dsh-tool-bash), but any other plugin can be one too.

Two easily missed details. First, roles usually live in separate packages, but this is not enforced: when two roles evolve together, one package can hold several roles — dsh-llm owns both the LLM capability's Service Definition (ctx.llm) and its Consumer (the streaming invocation logic); but holding a single role does not constitute a seam — the word seam always refers to the complete cut. Second, vocabulary types belong to the Definition: request, spec, result, and event-name types shared across packages are defined in the Definition package; providers and consumers both import them, and neither writes its own copy.

Why not an interface

Cordis service discovery relies on declaration merging: a package writes declare module '@deepseek-ai/cordis' { interface Context { shell: ShellExecutor } }, and only then does the ctx.shell key exist. A TypeScript interface cannot express I registered a service key, nor effect scoping and disposal. So the Definition must be a Service subclass — it is a type and a runtime object at once.

11.2 The three-role relationship

Draw the dependency directions and the heart of the pattern is plain: both sides point at the middle, and the two sides do not know each other. The Provider subclasses the Definition's abstract service; the Consumer injects the Definition's ctx.<key>. There is no edge from Provider to Consumer — that is exactly where replaceability comes from.

The red dashed line in the diagram is the edge most worth watching when reviewing PRs. If you find tool-bash directly importing dsh-bash-local, or bash-local importing some tool package in return, the seam has cracked — the freedom to swap providers vanishes instantly.

11.3 The template: the dsh-shell family

The repository's own designated template is packages/shell/. Here is the role table at the top of packages/shell/shell/README.md:

PackageRoleResponsibility
@deepseek-ai/dsh-shellService DefinitionAbstract ShellExecutor + vocabulary types (ShellExecRequest / ShellExecSpec / ShellRunResult)
@deepseek-ai/dsh-bash-localProviderLocal subprocess implementation
@deepseek-ai/dsh-bash-sandboxProviderReuses bash-local's mechanism, but wraps every spawn with ctx.sandbox constraints
@deepseek-ai/dsh-pwsh-localProviderLocal implementation for the Windows PowerShell family
@deepseek-ai/dsh-tool-bashConsumerThe model-visible bash tool, built on ctx.shell
@deepseek-ai/dsh-tool-pwshConsumerThe model-visible pwsh tool

When reading this template, note three details about what the Definition owns; they demonstrate where vocabulary lives:

  • The capability fact sandboxMode. On the base class it defaults to undefined (this executor does not sandbox); bash-sandbox reports its constraint mode at mount time. tool-bash reads this fact at registration and decides whether to expose the sandbox_permissions escalation parameter to the model — probe the capability, don't import the provider. A containerized or remote executor plugs in the same way, with not one line changed in the tool layer.
  • SHELL_SETTINGS_NAMESPACE (value bash) is exported by the Definition, because it names the capability, not any implementation. The host assembles exactly one ctx.shell provider — the Windows layer swaps the POSIX lines for pwsh lines, and mounting both would fail on duplicate service registration — so every provider registers this same namespace and they never collide; one settings.yaml stays resolvable across platforms.
  • The rendering contract parseExitStatus. The parser for the [exit code: N] / [killed by signal: X] markers lives in the Definition package, so the two Consumers tool-bash and tool-pwsh can never drift apart on marker format.
Key point

The Definition owns more than abstract methods: capability facts, the settings namespace, parsing contracts shared across implementations, and the event vocabulary all belong to it. To decide which package a type belongs in, one question suffices: is it part of the capability, or part of one implementation?

11.4 Swap one provider, move the entire execution world

The replaceability of a single seam is already useful, but dsh's real product-level power comes from a group of seams sharing one execution world. Recall the two edges in docs/capability-seams.md: fs-e2b and subprocess-e2b both inject ctx.e2b — they are not two isolated providers but two local faces of the same remote Linux world.

Who consumes ctx.subprocess? The bash executors (bash-local, bash-sandbox), the PTY backends (terminal-bash), the LSP hosts (lsp-stdio), and the three out-of-process subagent backends (subagent-acp, subagent-codex, subagent-claude-code). Who consumes ctx.fs? The file tools, tool-fs. This means: swap fs-local for fs-e2b and subprocess-local for subprocess-e2b, and Bash, the terminal, LSP, and file reads/writes move together into the remote sandbox — no tool package changes code, and no provider forks an E2B-specific tool variant.

11.5 Extension plugins depend on the Definition, never import a provider

This rule applies not just to tool packages but to every extension plugin that wants to build on top of a capability. Want to audit bash results? Listen to the seam's events and inject the seam's services; don't import dsh-bash-local. Want to add behavior over every provider group? Write it as consumption of the Definition, and all providers get it for free.

One step further: dsh-agent-loop itself is swappable. In the table in docs/capability-seams.md, the role of ctx.agentLoop is bundle — the sole concrete loop plugin; extension packages depend on dsh-agent's events and services, not on this package. The turn/step loop is part of the product API spine (changing it requires updating docs/architecture.md), but from the plugin system's point of view it is just one assembly-time choice: extensions never couple directly to the loop implementation; they hook documented extension points such as agent/pre-step and tools/*. Every interception point you learned in Chapter 7 is a beneficiary of this decoupling.

From this we get a quick-reference table of dependency directions:

When writing this codeMay depend onMust not depend on
A new providerThe Definition package (types + base class)Other providers, Consumer packages
A new Consumer (tool, bridge)The Definition package's ctx.<key> and vocabularyAny concrete provider
An extension plugin over a capabilityThe seam's events and services (such as the fs/* event gate)The seam's concrete implementation packages
A loop-behavior extensiondsh-agent events and services, documented extension pointsThe dsh-agent-loop package itself

11.6 Reading the map: the docs/capability-seams.md panorama

You don't need to memorize the dependency relations of 150 packages — the repository generates the full map for you. docs/capability-seams.md is generated by scripts/gen-doc-graphs.ts (rerun locally with pnpm run gen-doc-graphs), and the file header reads do not edit by hand. The current snapshot covers 56 ctx.* services, of which 26 are marked seam; the rest are core (spine services such as ctx.sessions, ctx.tools) or bundle (assembly points such as ctx.agentLoop).

Each table row looks like this (taking ctx.fs as the example). How to read the seven columns:

ColumnMeaningContent of the ctx.fs row

OwnerThe package holding the Definitionfs (packages/fs/fs)
ImplementationsKnown provider packagesfs-local, fs-sandbox, fs-e2b

Companion pluginsPlugins that participate through event gates rather than service injectionfs-observation-policy
NoteDesign notes for this rowfs-sandbox fences changes by shared sandbox mode; the observation policy participates through the fs/* event gate

Three typical lookups:

  • Who owns this ctx.foo? — scan the ctx key column. The Owner column gives the Definition package path directly; above the table there is also a mermaid diagram where pkg_* --> svc_* edges mean who implements/injects whom, and svc_* --> pkg_* edges mean who consumes whom.
  • Which packages must change to add an implementation to this capability? — look at Owner and Implementations. You write exactly one new provider package and register it under the same service key; the Owner and all Consumers stay untouched.
  • This plugin never injects the service — how does it participate? — check the Companion plugins column and the dashed edge in the diagram (svc_fs -. event gate .-> pkg_fs_observation_policy). Companion plugins go through event gates rather than method injection; Chapter 13 makes them the protagonist.

Note that generating this table is guarded for completeness: the role classification lives in the generation script, and if a new service is missing its implementation/consumer classification, the doc-sync gate fails. So it is a living document you can quote as truth, not a hand-maintained README that drifts out of date.

11.7 A practical checklist: adding a capability = designing all three roles

Let's condense the pattern into an actionable checklist. Suppose the requirement is add a screenshot capability to dsh. Design it role by role:

  1. Definition package dsh-screenshot: a Cordis Service subclass (ctx.screenshot), vocabulary types (request / spec / result), and any facts and error codes shared across implementations. Decide up front whether it is an abstract class (single provider, like ShellExecutor) or a named registry (multiple coexisting providers, like ctx.web's search/fetch or ctx.subagents' seven backends).
  2. At least one provider (say screenshot-local), subclassing or registering the implementation; every deployment-varying parameter goes into its validated Config (validated by cordis.yml), never a hardcoded DEFAULT_*.
  3. At least one Consumer (say tool-screenshot), injecting inject: ['tools', 'screenshot', 'systemPrompt'], programming only against the vocabulary types; the rendering intent (generic / terminal / diff / locations) is decided once, up front.
  4. Check the event surface: a model-visible input requires a SessionEvent (model-visible ⟺ logged, the invariant from Chapter 4); a companion policy means an event gate, not another service.
  5. Backfill the full map: let gen-doc-graphs include the new service in docs/capability-seams.md, and update the package/ctx-key tables of the group README in the same PR.

Every item in this checklist corresponds to a hard convention in the repository: seam completeness, a configurable Config, misconfiguration fails loud, docs travel with code. Chapter 24 walks this checklist again as a cookbook-level exercise.

11.8 Chapter recap

  • A capability seam = a complete cut through a replaceable capability: Service Definition (a Cordis Service subclass owning ctx.<key> and the vocabulary types) + Provider + Consumer; missing any one, there is no seam.
  • Dependency direction: both sides point at the Definition; Provider and Consumer never import each other; probe capabilities with capability facts (such as sandboxMode), not type references.
  • dsh-shell is the template: shell (Definition) / bash-local, bash-sandbox, pwsh-local (Providers) / tool-bash, tool-pwsh (Consumers).
  • fs and subprocess share one execution world: swap in fs-e2b + subprocess-e2b, and Bash, PTY, LSP, and file tools move into the remote sandbox together.
  • Extension plugins depend on Definitions and events, never concrete providers; even dsh-agent-loop holds the swappable bundle role.
  • docs/capability-seams.md is a script-generated living map (56 services, 26 seams); the owner / implementations / consumers / companion columns locate the structure of any capability.
  • Adding a capability = designing all three roles at once + the event surface + backfilling the full map.
Common pitfalls
  • Treating a seam as just an interface: writing the Definition as a TypeScript interface leaves ctx.<key> nonexistent — declaration merging has nothing to attach to.
  • A Consumer importing a concrete provider (or the reverse) — the seam cracks and the freedom to swap implementations vanishes; probe provider traits with capability facts.
  • Vocabulary types in the wrong package: request/result types living in a provider must be copied when the second provider arrives.
  • Writing one plugin and calling it a new capability — one role is not a seam; at minimum think through all three role boundaries and write them into the group README.
  • Hand-editing docs/capability-seams.md — it is a generated artifact; change scripts/gen-doc-graphs.ts and regenerate.
