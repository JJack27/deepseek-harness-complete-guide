Chapter 23 · Part V · Engineering and Contribution

Quality Gates and Repository Conventions

What keeps the plugins of dozens of packages from fighting in an everything-is-a-plugin repository? The answer has two layers: one is executable gates — the dozens of verification commands scheduled by run-gates.ts plus the lefthook hooks; the other is the hard conventions written in AGENTS.md — each one answering why writing it this way keeps the code from rotting. This chapter spreads both layers out: first the command map and the local philosophy of choosing checks by evidence surface, then the twenty-one conventions one by one. By the end you will have internalized standards for judging whether a given approach is acceptable in this repository.

Learning objectives
  • Reproduce the common command map from memory: clean / test / test:coverage / test:e2e / test:snapshot[:record] / typecheck / lint / duplication / build / hygiene / doc-sync / website:build, and dsh --profile headless.
  • Pick the minimal check set for a change by evidence surface → check, rather than defaulting to the full suite.
  • State what each of the three lefthook hooks checks, what they deliberately do not, and run-gates.ts's CI lane division.
  • Recite AGENTS.md's twenty-one hard conventions item by item and give the why for each.
  • Distinguish test from test:coverage: only the latter is the CI coverage gate.

23.2 The local checking philosophy: choose checks by evidence surface

The repository's attitude toward local checks is one sentence: match the evidence surface, never default to the full suite. The Run relevant checks locally section of AGENTS.md lists five mappings — behavior changes get focused tests; model or user output gets snapshots; docs get doc-sync; published paths get build/hygiene plus built-artifact smokes; provider behavior gets e2e. Re-running an already-green check for a commit or push is considered a mistake, not prudence. Exhaustive coverage and the platform matrix (Node 22.19 / 24 / 26, Linux / Windows) are CI's job; only three situations justify rehearsing the full suite locally: an explicit request, CI diagnosis, or an irreducibly repository-wide change.

23.3 The gate family: run-gates, CI lanes, and Git hooks

scripts/run-gates.ts is the gate scheduler: it organizes dozens of gates as a directed dependency graph, runs processes under bounded concurrency, and aggregates diagnostics. Its Mode list is exactly the CI lane division — ci-primary (ci-linux-primary additionally adds web browser snapshots), ci-static, ci-coverage, ci-snapshot, ci-artifacts, ci-consumers, three Windows lanes (blocking / complete / observational), node-compat, plus the optional local check-all and the documentation aggregate doc-sync. Within a lane, artifact consumers wait on one build of the same lane instead of each building their own.

The leaf list of doc-sync gives you a feel for how many executable assertions this repository turns documentation correctness into: cordis/client/tool/config/persistence catalog regeneration and comparison, export JSDoc verification, the documentation graph, scoped events, Markdown wrapping and links, public-repository links, doc references, package paths, config-source ownership, the README model-experience and limitations sections, Agent Note classification/format/freeze checks, type-equiv (types quoted in docs match the source verbatim), translation prompts and pairing, documentation budgets, and the VitePress site build. Change any one of them and a gate goes red.

On the Git side, lefthook provides three quick checkpoints. pre-commit: validates staged translation-pairing records, lints staged files with the project-agnostic .oxlintrc.staged.json profile and applies Oxlint fixes with one bounded retry, regenerates THIRD_PARTY_NOTICES.md when input files change, checks the staged diff for whitespace errors (git diff --cached --check — this is the enforcer of exactly one trailing newline per file), and runs the vendor manifest guard. pre-merge-commit: runs the same pairing checks. pre-push: runs pnpm run typecheck. Note that the hooks deliberately do not run tests, snapshots, documentation checks, builds, or hygiene — those belong to contributors choosing by evidence surface, and to CI for exhaustiveness.

The retry rule for host sandbox failures

When a required gh, pnpm, build, test, or generator command fails because the agent sandbox blocks credentials, network, IPC, file watching, or nested sandbox-exec, first retry the command unchanged with the narrowest host escalation, then diagnose an authentication or project failure. Demand sandbox evidence; never bypass a genuine test failure or the product sandbox under test.

23.4 Runtime contracts: five conventions about Cordis and events

1) Registrations are effects. Every contribution goes through ctx.effect() / ctx.on(), and a registry's register() returns the disposer. Why: Cordis fiber lifecycles are the basis of plugin unload/HMR, and any registration that bypasses effects is a leak that cannot be unloaded; the HMR-safety tests of Chapter 3 verify exactly this convention.

2) Runtime invariants assert owned relationships. Check authoritative event streams or mutable data, not service or method presence, plugin metadata, effects, or fixed pure examples. Why: the service is still there does not prove the relationship still holds — a presence check goes green on an implementation that registered but never writes the log. When there is no plausible relationship to assert, an explained empty companion is the correct answer; do not fabricate evidence just to have an assertion.

3) Typed events use declaration merging. Event interfaces extend merge-extensible maps via declaration merging; event JSDoc needs @mode, payloads need @param, and scoped keys absent from payloads must be marked @dshScopeScan unsupported. SessionEventMap members are required-on-read by default: a build that does not know the event's type refuses the log unless the event carries ignorable: true; only structural format changes bump SESSION_FORMAT_VERSION. Why: this is the type-level insurance that the log can rebuild the runtime; between silently dropping unknown events and refusing to load, the repository chose refusing.

4) Switch on discriminant tags. Closed unions end in assertNever; merge-extensible unions fall through a documented default. Why: discriminant tags let the compiler enforce exhaustiveness — add a member to a closed union and every switch that forgot a case immediately goes red; omitting assertNever dismantles that insurance.

5) Waterfall listeners MUST call next(). Returning without calling next() short-circuits the whole chain. Why: waterfall semantics are delegation layer by layer (like chained approval of permissions); a listener that forgets to delegate silently hides every downstream listener — the hardest-to-debug kind of suddenly everything is denied.

23.5 Model visibility and extension points: four structural conventions

6) Model-visible ⟺ logged. Anything that reaches a model request must be reconstructable from the session log; a new model-visible input requires a new session event. Why: the session log is the single source of truth for replay, auditing, and snapshot golden fixtures (Chapter 4); from llm-replay to ACP snapshots, the entire testing system stands on this equivalence. Content smuggled into a request while bypassing the log vanishes on replay and drifts the snapshots.

7) Plugins, not loop changes. New behavior lands on documented extension points; changing the agent-loop itself requires updating docs/architecture.md in step. Why: the loop is the scheduling core shared by all plugins, and stuffing private logic directly into it plants a mine for everyone; extension points are the contract that keeps plugins from stepping on each other.

8) A capability seam comprises all three roles. A capability surface consists of the Service Definition / Service Provider / Consumer roles; it is a seam only when complete, and splits only when the roles genuinely evolve at different tempos. Why: a capability missing its Provider cannot swap implementations, one missing its Consumer has no user, and one missing its Definition leaves both ends with their own understanding of the protocol — the three roles are the minimal complete set behind Chapter 11's replaceability.

9) Both SDKs project the loop. Any change to the agent-loop, the session lifecycle, or the SessionEventMap updates the TypeScript and Python SDK expected outputs in the same PR; pnpm run test covers neither. Why: the two SDKs are two projection surfaces of one loop (Chapter 21) — update one side only and the other side's golden fixtures rot silently, and the unit-test lane cannot see that drift, so only the convention forces the sync at the moment of the change.

23.6 Package boundaries and configuration: six engineering conventions

10) Prefer maintained dependencies over hand-rolling. Use a dependency when it genuinely deletes owned code and tests — this carries a policy note (.agents/notes/implemented/process/2026-07-26-dependencies-over-hand-rolling.md). Why: the intuition that writing it ourselves is faster usually ignores the long-term bill of maintenance and tests; but conversely, pulling in a dependency to save three lines is also a loss, so the criterion is genuinely deleting owned code and tests.

11) Explicit over implicit at package boundaries. Defaulting is an explicit resolve(request): Spec step in the owning implementation, never a hidden ?? default inside run() — the dsh-shell request/spec split is the template. Why: a default hidden in the execution path is invisible to both review and configuration surfaces, and policy drifts silently; an explicit resolve makes who owns the default answerable in one place.

12) No hardcoded tunables in plugins. Deployment-varying options are validated Config fields changeable from cordis.yml; a DEFAULT_* constant or test hook is not configurability. Protocol constants, external specs, and security invariants stay fixed. Why: a hardcoded timeout is an outage in some other deployment; and a security invariant made configurable is no longer an invariant.

13) Misconfiguration fails loud. Fail at load when self-contained, otherwise at the earliest resolvable point; never silently skip a missing referent. Why: silently skipping defers the error to the most expensive moment of runtime while disguised as normal; fail loud makes bad configuration explode at --dump-config or startup.

16) The source plane and the artifact plane never mix. Static gates and tests resolve workspace imports to src through tsconfig paths and pass on a clean tree; gates that consume the built lib/ declare that dependency explicitly. Why: mixing installs a second module singleton and lets stale artifacts seep into source verification, at which point neither side can trust what it proves (Section 22.7).

17) One aggregate compiler face per package. The sole exception is api/remotes (Host and Client tsconfigs, split because the Host Typert graph and the Client /remote declarations depend on each other in that order). Repo-wide programs seed from tsconfig.host.json or tsconfig.client.json, never the root solution. Why: the two sides declaration-merge different Contexts under the same keys, and crushing them into one ts.Program collides in merge conflicts — the compilation-side reflection of the two-aggregate architecture (Chapter 3).

23.7 Type and code discipline: six small hard rules

14) Opaque cross-boundary ids are branded. Branded<B> (from dsh-brand), never a bare string. Why: session ids, turn ids, and goal ids are all strings at runtime, but passing them interchangeably is a real bug class; branded types move that error from runtime to compile time with zero runtime overhead.

15) Trust TypeScript at typed same-process boundaries. Do not add runtime validation, fallback behavior, or hostile-input tests for values the static interface already requires; validation happens only at parser/config, queued, model/tool JSON, durable/file, worker, process, and wire boundaries. Why: writing defensive code for what types already guarantee amounts to declaring your own type system untrustworthy — such code cannot be meaningfully triggered by tests and only rots. The boundary list is exactly where distrust begins.

18) An empty catch names what it swallows and why nothing else can reach it; the try wraps one statement. Why: an empty catch is a fossil of something once went wrong here and someone smothered it — left unexplained, the next reader cannot tell whether it swallowed an expected branch or a new failure; narrowing try to a single statement leaves what was swallowed no syntactic place to hide.

19) Keep parallel values symmetric. Unexplained asymmetry usually signals a missed extraction. Why: when paired values (two providers, two directions, request and response) go asymmetric, it is either a bug or an undocumented design decision; the convention forces the choice: restore symmetry or write the reason down.

20) Tests describe behavior, not correctness. When behavior becomes obsolete, change it together with its tests and explain why in the PR. Why: treating tests as correctness headstones locks implementation improvements behind stale assertions; a test's lifetime should equal the lifetime of the behavior it describes.

21) TODO markers by urgency: FIXME (should block a new release) < TODO (fix soon) < XXX (maybe someday). Files end with exactly one trailing newline, gated by git diff --cached --check in pre-commit. Why: someone scanning the code must tell release-blocking from someday-maybe at a glance; and the newline convention gives diffs and tooling a definite end of file.

Reading the twenty-one conventions as one sentence

Cordis layer: registrations are revocable, invariants assert relationships, events are mergeable, unions are exhaustible, waterfalls must delegate. Visibility layer: model-visible means logged, behavior goes on extension points rather than the loop, seams have all three roles. Boundary layer: dependencies first but judge by deletion, defaults resolve explicitly, tunables live in Config, configuration fails loud, source and artifact planes stay separate, one aggregate face per package. Discipline layer: ids are branded, same-process trusts TS, empty catches account for themselves, parallel values stay symmetric, tests change with behavior, TODOs are graded, files end with one trailing newline.

23.8 Chapter recap

  • The command map is in place: clean / test / test:coverage / test:e2e / test:snapshot[:record] / typecheck / lint / duplication / build / hygiene / doc-sync / website:build / dsh --profile headless.
  • Local philosophy: pick the minimal check set by evidence surface (behavior → focused tests, model/user output → snapshots, docs → doc-sync, published paths → build+hygiene+smoke, provider → e2e); CI owns exhaustive coverage and the platform matrix; the coverage gate is test:coverage.
  • run-gates.ts's Mode list is the CI lanes; doc-sync turns documentation correctness into dozens of executable assertions; the three lefthook hooks (pre-commit whitespace/staged lint/vendor guard, pre-merge-commit pairing, pre-push typecheck) deliberately run no tests.
  • Runtime contracts: registrations are effects, invariants assert owned relationships, typed events use declaration merging + required-on-read + the ignorable: true exception, switch + assertNever, waterfalls must call next().
  • Structural contracts: model-visible ⟺ logged, plugins not loop changes, seams complete with all three roles.
  • Boundaries and discipline: explicit resolve(request): Spec, tunables in Config, fail loud, branded ids, same-process trusts TS, source/artifact plane separation, one aggregate face, empty catches account for themselves, symmetry, tests change with behavior, TODO grading + one trailing newline.
Common misconceptions
  • Habitually running the full pnpm run test before committing — choose focused checks by evidence surface; re-running green checks is explicitly opposed in this repository.
  • Treating pnpm run test as the coverage gate — the gate is test:coverage (per-file 100%).
  • Filling in request defaults with ?? inside run() — defaults belong to the owning implementation's explicit resolve(request): Spec.
  • Adding runtime validation to same-process function parameters — trust TS; validation belongs at parser/config, model/tool JSON, durable/file, worker, process, and wire boundaries.
  • A waterfall listener returning right after its own decision — it must call next(), or the whole chain is short-circuited.
  • Writing a default in a closed union's switch instead of ending with assertNever — the compiler can no longer help you.
  • Changing only request assembly for a new model-visible input — without a matching session event it violates model-visible ⟺ logged, and snapshots and replay will drift.
