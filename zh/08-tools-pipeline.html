工具系统：注册表与执行管道

上一章你看到 assistant 消息里的 tool-call 被丢进了「tools 管道」。 这一章就把这根管子铺开：工具怎么注册、一次调用从模型请求到 tool/result 事件要过哪几道闸门、哪里能拒绝、哪里能改写、 以及为什么一个被拒绝的调用也一定会留下日志记录。读完你会自己写一个工具插件， 并知道该把策略放进管道的哪一层。

学习目标
  • 用 ctx.tools.register() 注册一个工具，并说出「注册即效应」的含义
  • 复述 ToolDefinition 的组成：schema、output 声明、execute、可选回调
  • 按顺序说出执行管道的阶段，以及每阶段能改写/拒绝什么
  • 解释为什么拒绝也会产生 tool/result 事件（model-visible ⟺ logged）
  • 区分 monotonic guard、tools/execute 包装器与 post-execute 插件各自的适用场景
  • 说出工具 UI 渲染意图（render intent）为何是 args 的纯函数

8.1 ctx.tools：scoped 工具注册表

packages/core/tools/ 提供的 ToolRuntime 服务挂在 ctx.tools 上。 它同时是两样东西：一个带 scope 的注册表和一条守卫式执行管道。 先看注册表这一半。

注册一个工具就是一次效应（第 2 章的规矩在这里同样成立）： 

export const name = 'my-tool'
export const inject = ['tools']

export function apply(ctx) {
  const dispose = ctx.tools.register(defineTool({ /* … */ }))
  return dispose  // 或者交给插件 fiber：fiber 销毁时自动注销
}

register() 返回的 disposer 就是注销函数；注册进哪个 scope 由调用方的 ctx 决定 —— 普通插件上下文注册全局工具，而通过某个 agent 的 agent.ctx 注册则只对该 agent 可见， 并遮蔽同名全局工具（第 6 章的 shadowing 在这里的第一现场）。同一层内重名直接抛错， 错误信息还会提示你：想要 per-agent 变体，就该用 agent.ctx 注册。 注册/注销/范围变化会广播 tools/change（不过滤的通知 —— 全局变化关乎每个 agent 的下一次装配）。

scope 上还有两个配套操作：ctx.tools.restrict({allow?, deny?}) 给某个 agent 的继承面套一层 allow/deny 掩码（多个掩码相交；本层自己注册的不受影响）； ctx.tools.presentAs('code') 让一个 agent 单独选择 Code Mode 呈现 （部署级默认是 tools 插件的 mode 配置：native / code / both）。这两个方法都只能从 scoped context 调用 —— 在普通上下文调用会直接抛错，因为「全局掩码」和「全局呈现」该走配置， 不该藏在某个插件的副作用里。

8.2 ToolDefinition：一个工具的全部声明

一个 ToolDefinition（用 defineTool() 包装可获得类型推导）由四块组成， docs/cookbook/adding-a-tool.md 的最小示例是最快的记忆锚点：

  • 模型可见的 schema：name、description、parameters。 这是模型唯一看到的三个字段 —— 其他一切（超时、并发分类、呈现回调）都不会发给模型。
  • 必选的 output 声明：{schema, render, presentationMeta?}。 工具体只返回一个符合 output.schema 的规范 JSON 值； render(args, value) 把它投影成模型可见的 content blocks； presentationMeta 把它投影成可回放的 UI 卡片数据（落 tool/result 的 meta 字段）。缺 output 的注册直接 TypeError。
  • execute(args, exec)：真正干活。约定：参数已被校验冻结（defineTool 会先验，违规变 INVALID_ARGS 错误结果）；必须观察 exec.signal 做协作取消； 抛异常或返回不合声明的值都会被规范化成 isError 结果 —— 工具失败是正常结果路径，不是崩溃。 exec 上还有 deferContext(msg)（把上下文推迟到结果落地后注入）与 concludeTurn()（标记成功结果终结本 turn）。
  • 可选元数据：timeoutMs（协作超时预算，策略元数据、不发模型）、 isConcurrencySafe(args)（只有严格 true 才可并行，见第 7 章）、 finalizeContent（最后一步内容改写，必须同步且全面）、 presentCall / presentResult（8.6）。

8.3 执行管道：五段闸门 + 两条短路

当 agent loop 的调度器启动一个调用，它首先把 tool/call 先记进日志（先记再执行）， 然后进入 docs/tool-execution-pipeline.md 描述的管道。逐段看：

  1. tools/pre-execute（waterfall）：可扩展的 allow / deny / ask 闸门， hooks、权限策略、沙箱包装都挂这里。监听器必须调 next()；返回 ask 时， 若部署挂了 ctx.approval 服务则弹一次性审批（通过则继续，否则按拒绝），没有审批服务就 降级为 deny。注意 pre-execute 故意不提供参数改写 —— 参数此刻已经落日志并被呈现过了。
  2. 已注册的 monotonic guards：用 ctx.tools.guard(g) 注册的同步守卫， 在 pre-execute 之后、本体之前运行。它只有两个返回值：给出 reason（终局拒绝）或 undefined（弃权）。 没有 allow —— 所以无论监听器怎么排序，谁都无权把一个已被守卫拒绝的调用改回允许。 这就是「单调」的含义：只紧不松。
  3. tools/execute（around-dispatch waterfall）：包住真正的 dispatch。 超时、重试、指标这类「围绕执行」的关注点在这里。包装器只能临时替换 exec.signal （比如套一个更紧的截止时间），不能改调用身份；注册表会在本体前把调用方的原信号重新接回。
  4. tools/post-execute（waterfall）：对已规范化的结果做后处理 —— 接受（可改写内容或规范值、附加 additionalContexts 上下文）或 block（把纠正性反馈变成错误结果）。 被拒绝/超时的调用也会到达这里（失败也是结果）。
  5. tools/result（emit，只读）：观测冻结的最终结局。随后由 agent loop 落 tool/result durable 事件，附 UI 卡片用的 meta。

管道里还有一个容易漏掉的守门人：注册表在 post 之后做外层规范化（任何阶段抛的错、 快照失败都统一成 isError），再给工具定义的 finalizeContent 一次最后的内容改写机会， 然后才物化、冻结、广播。无论走哪条路 —— 正常、拒绝、超时、异常 —— 终点都是一条 tool/result 事件。这正是第 4 章不变量在工具侧的形状：模型可见 ⟺ 已记录。 一个被策略拒绝的调用，模型会看到拒绝原因，并据此改道；而不是调用凭空消失、让模型对着悬空的 call 猜测。

8.4 策略插件实例：guard 组的两个插件

packages/guard/ 组里有两个循环卫生/超时插件，它们是「策略放管道、不放进工具」的范本。 注意一个容易望文生义的细节：这个组的两个插件并不都挂在第②段的 guard 位置 —— 它们分别演示了管道的不同层：

  • dsh-repeat-tool-reminder（循环卫生，观测在 ④）：数每个 agent 连续用同样参数调同一工具的次数，到阈值（默认 3/5/8）就注入一条递进的提醒，让模型换个方法或收尾。 它从不否决、从不改写调用 —— 检测挂在 tools/post-execute （被 deny 的调用也计数：反复撞一个被拒的调用正是值得打断的循环），提醒以 additionalContexts 的形式随步骤注入，成为可从日志重建的 user/message。 决定权完全留给模型，所以它是 advisory（建议性）插件。
  • dsh-tool-call-timeout-policy（超时，包装在 ③）：一个 tools/execute around-dispatch 监听器。对声明了 timeoutMs 的工具， 它给 exec.signal 套上截止时间；超时赢面时把结果替换为结构化的 TOOL_TIMEOUT 错误。预算来自工具自己的声明，所以这个插件零配置。 注意它是协作的：只有真正转发 exec.signal 的工具才会被「超时」 —— 忽略信号的工具不会被硬杀。

那么第②段留给谁？留给部署所有者不可被重排的最终否决 —— ctx.tools.guard(reason | undefined) 注册的单调守卫。 管道文档把它总结为：可重排的扩展策略放 pre-execute，所有者策略放 guard， around 关注点（超时/重试/指标）包 execute，结果观察与改写放 post-execute / tools/result。

8.5 并行与顺序：注册表视角

第 7 章讲了调度器怎么用 executionMode 分组；这里补注册表这一侧的事实： ctx.tools.executionMode(exec) 查的是该 scope 可见的定义， 只有其 isConcurrencySafe(args) 恰好返回 true 才是 parallel —— 未知工具、被遮蔽、未声明、分类器抛异常，全部按 exclusive 处理（fail closed）。 多个并行调用组成有上限的滚动池（默认 10），exclusive 调用形成屏障； 调度可以重叠，但 pre-execute、结果提交、结果上下文都保持模型顺序。 取消时已启动的调用照常排空，未启动的补合成错误结果 —— 日志里 call 与 result 永远成对。

8.6 工具的 UI 渲染意图：设计的一部分

一条仓库级约定：工具的 UI 呈现意图（render intent）是工具设计的一部分，事前决定， 不是 UI 事后猜测。工具通过两个纯函数声明卡片：

  • presentCall(args) → pending 卡：在调用开始、还没结果时显示。 卡片词汇表是 generic（默认；可带 locations 让编辑器跟随文件位置）、 terminal（这条调用就是一条 shell 命令 —— tool-bash）、 diff（这条调用创建/修改文件，带 inline diff —— tool-fs 的 write/edit）。
  • presentResult(args, {content, isError, meta}) → 完成卡： 除三种基础卡外还有 search（grep/glob 的命中结构）与 web （web_search/web_fetch 的结构化来源）等结果视图，数据来自持久化的 result.meta。

为什么必须是 args 的纯函数？因为这些方法既在实时流中跑，也在会话日志回放时跑： 回放时没有活的会话状态、没有时钟、没有文件系统。所以规则写得很硬：不许 I/O、不许读会话状态、 不许用时间/随机 —— 需要结果期事实（比如实际套用的 diff hunk）就把它通过 output.presentationMeta 存进 durable 的 meta，回放时从那里取。 同时，模型可见的 content 与 UI 可见的卡片是两条轨道：给 UI 的格式（console 围栏、路径相对化） 不许混进模型结果里。

8.7 与 prompt 装配的接口

最后一块拼图：注册的工具 schema 如何变成模型看到的东西？ToolRuntime 构造函数里有一行 ctx.systemPrompt.tools(context => this.wireSchemas(context.scope)) —— 注册表把自己挂成 system-prompt 的一个工具 schema 提供者，按 scope 解析可见工具、 投影出 name/description/parameters 三个字段。于是「模型这轮能看到哪些工具」 与「这个 scope 能解析哪些工具」永远是同一个答案。装配的完整故事（section 顺序、 toolOrder 校验、Code Mode 的 SDK section）是下一章的主题。

8.8 本章回顾

  • ctx.tools = scoped 注册表 + 守卫式执行管道；register() 是效应，返回 disposer；scoped 注册遮蔽同名全局工具。
  • ToolDefinition = 模型可见 schema + 必选 output（schema/render/presentationMeta）+ execute + 可选元数据；工具体只返回规范 JSON 值。
  • 管道顺序：tool/call 落日志 → ① pre-execute（allow/deny/ask + 审批降级）→ ② monotonic guards（只许 deny）→ ③ execute around（超时/重试/指标）→ 工具本体 → ④ post-execute（accept/block/replace/context）→ 规范化 + finalizeContent → ⑤ tools/result（只读）→ tool/result 事件。
  • 任何阶段可改写或拒绝；拒绝/超时/异常都会产出 tool/result —— 模型可见 ⟺ 已记录。
  • repeat-tool-reminder 挂 post-execute 做建议性循环卫生；timeout-policy 包 execute 执行工具声明的 timeoutMs；所有者终局否决用 ctx.tools.guard()。
  • 并行判定 fail closed：只有 isConcurrencySafe(args) 严格 true 才 parallel；exclusive 成屏障；结果按模型顺序提交。
  • UI 渲染意图（generic/terminal/diff/…）事前决定，presentCall/presentResult 是 args 的纯函数，必须在日志回放时可用。
  • 注册表通过 ctx.systemPrompt.tools() 把 schema 汇入 prompt 装配 —— 模型可见工具集与 scope 可见工具集同源。
常见误区
  • 以为拒绝的调用「什么都不发生」—— 管道短路的是执行，不是记录；tool/result 照落。
  • 把部署策略写进工具本体 —— 该上管道：pre-execute 做可扩展策略，guard 做终局否决，execute 做超时/重试，post-execute 做结果处理。
  • 期待 pre-execute 改参数 —— 故意不支持：参数已落日志并被呈现，改写会造成日志与执行不一致。
  • 以为 timeoutMs 是硬杀 —— 它是协作预算，前提是工具转发 exec.signal。
  • 在 presentCall 里读会话状态或文件系统 —— 回放时这些都不存在，卡片必须只依赖 args（+ durable meta）。
