dsh CLI 与 boot 深入

前面十七章里你一直在「已经组装好的运行时」里工作。本章回到起点：dsh 这条命令本身。谁解析参数、谁加载插件、剩余的 argv 最后落到谁手里——这条启动链路是 apps/cli 与 packages/boot 两组包的领地。读懂它，你才能回答「我的 flag 为什么没生效」 和「profile 的插件树到底怎么长出来」这两类最常见的现场问题。

学习目标
  • 说出 apps/cli 中 bin 与 args 的分工，以及 bin.ts 按模式动态 import 的理由。
  • 默写 dsh 的入口模式（profile、一次性 headless、web 别名、plugin 管理）与各自的参数归属。
  • 画出 profile 的分层配置树：bundle 补丁 → profile 补丁 → home 补丁 → --patch overlay。
  • 描述 dsh-app-boot 的启动守卫（分层 env、fail-loud、watchUserPatches）与信号语义。
  • 解释剩余 argv 如何经 ctx.cmdlineArgs 交还 app 插件，以及源码启动的 ESM 契约。

18.1 入口与参数语法：bin 与 args 的分工

dsh 的 npm 入口在 apps/cli/package.json 里只有一行： "bin": { "dsh": "lib/bin.js" }。安装形态下它启动构建产物；仓库里源码形态则是 apps/cli/src/bin.ts。这个文件刻意保持「薄」：读一次自己的版本号，调用 parseDshArgs 解析 argv，然后按解析出的模式动态 import 对应的 runner——profile-boot.ts、plugin.ts 或 dump-config.ts。 

const invocation = parseDshArgs(process.argv.slice(2), readVersion())

switch (invocation.mode) {
  case 'profile': {
    const { runProfile } = await import('./profile-boot.ts')
    await runProfile({ environment: loadLayeredEnv('dsh'), /* … */ })
    break
  }
  // plugin 与 dump-config 同样只动态 import 选中的 runner
}

动态 import 不是风格偏好，而是加载面的控制：走 dsh plugin 管依赖时，进程完全不需要 把 profile 启动链（Cordis Loader、bundle 解析、HMR watcher）拉进来。每个分发路径只加载自己用得到的 插件面，这正是「everything is a plugin」在进程入口处的回声。

参数语法的唯一属主是 apps/cli/src/args.ts 的 parseDshArgs。它基于 commander，但配置得非常克制：helpOption(false)（launcher 不拥有 -h）、allowUnknownOption() 加 passThroughOptions() 加 enablePositionalOptions()。三者合起来表达一条位置规则：launcher 的 flag 在最前，第一个它不认识的 token 就是 app 参数的开始。所以 dsh --profile web --port 8080 里 --port 属于 web app， dsh --profile web --help 打印的是 web app 的帮助；只有不带 profile 的裸 dsh --help 才打印 launcher 自己的帮助。另一个细节：--patch 用可重复的单值收集器实现，绝不做成变长参数——变长的 --patch 会把后面的 app 参数整口吞掉。

18.2 四种入口模式

args.ts 把一次调用解析成三种 invocation（profile / dump-config / plugin）， 加上 web 这个硬编码别名，构成产品文档里的四种入口模式：

命令用途
dsh --profile <name>启动 $DSH_HOME/profiles/<name> 下的 profile，argv 里 launcher flag 之后的部分原样交给 app。
dsh --profile headless "任务"一次性执行：创建一个全新持久化 Agent，提交任务，等到静默，flush 会话，打印最终回答后退出；turn 以 completed 结束则退出码 0，否则 1。
dsh web--profile web 的硬编码别名；后面的 flag 属于 web app（--host、--port、可重复的 --trusted-host）。
dsh plugin --profile <name> <pnpm args>在 profile 目录里把参数原样转发给 pnpm：安装、卸载、查询外部插件。

两个细节值得记。第一，web 与 headless profile 首次使用时从随产品 分发的模板自动初始化（web 是 base + web-app，headless 是 base + headless）；其他名字的 profile 缺失时 fail-loud，提示你先跑 dsh plugin --profile <name> add …。 第二，headless 的一次性运行是「纯核」路径：它不挂 ApiProxy、不挂 Host、不开 HTTP 端口、 不加载 Web runtime 与浏览器 client——成功的运行 stderr 一字不出。

dsh plugin 子命令本身也值得看一眼：add 相对路径（如 .、../plugin）会先锚定到调用目录，所以在插件源码检出里 dsh plugin --profile tui add . 安装的是这份检出而不是 profile 里的什么。每次成功 运行后，dsh.profile.bundles 会和实际安装状态对账：装上的包若声明了 "dsh": { "bundle": { "patch": "./cordis.patch.yml" } } 就进入层叠栈，卸载的依赖 离开栈。

最后是两个「看树不启动」的诊断模式：--dump-config 打印组合完成的配置树 （含用户层与 --patch），--dump-default-config 只打 bundle 层。dump 不运行任何 app 命令行 provider，因此它展示的是 app 参数被解析之前的树—— 这也是它拒绝携带 app 参数的原因：打印一棵和同参数实际启动不一致的树只会误导。

18.3 profile 与分层配置树

profile 是一个目录：$DSH_HOME/profiles/<name>（$DSH_HOME 未设时是 ~/.dsh）。目录里三样东西各司其职：

  • package.json —— 树外插件依赖，外加 profile 清单 dsh.profile，其中有有序的 bundles 列表；
  • cordis.patch.yml —— 你自己的补丁层；
  • cordis.yml —— 根配置，内容是一个空 entry 列表，每次启动都会重写。

整棵插件树是在空根上贴补丁贴出来的。应用顺序固定：

  1. dsh.profile.bundles 里每个 bundle 的补丁，按列表顺序（盒内 bundle @deepseek-ai/dsh-base、@deepseek-ai/dsh-web-app、 @deepseek-ai/dsh-headless 先从 dsh 安装处解析，再从 profile 自己的 node_modules 解析）；
  2. profile 自己的 cordis.patch.yml；
  3. home 级的 $DSH_HOME/cordis.patch.yml（机器级偏好，对每个 profile 生效，所以排在 per-profile 层之上）；
  4. 每个 --patch overlay，按 argv 顺序。

后层按行获胜，而「获胜」的方式是整体替换目标行的 config， 不是深合并——想保留的字段要在补丁里重述一遍。补丁指向不存在的行 id 只是 stderr 警告； 空文件或只有注释的文件会抛错（它解析不出任何列表；想禁用这一层写 []）。 另外有一个环境开关会变成最顶层的补丁：任何非空的 DSH_TELEMETRY_DISABLED（哪怕是 0 或 false）都会生成 一条把 telemetry 行 disable 掉的 patch——隐私开关宁可误关，不可误开。

还有两个基础设施工件让树外插件能被裸名字解析：healProfilesModuleFallback 每次启动维护 $DSH_HOME/profiles/node_modules 这个扁平目录（安装所依赖的每个包 一条符号链接），让任何 profile 里的裸插件名都能走 Node 的普通父目录查找。

18.4 app-boot：启动链路与 fail-loud 守卫

packages/boot/app-boot（@deepseek-ai/dsh-app-boot）是共享的启动 胶水，dsh 与 dsh-acp-demo 两个 bin 都靠它，使 loader 失败行为只有 一个属主。一次 runProfile 的关键序列：

  1. loadLayeredEnv('dsh') 冻结环境快照：继承环境 > 调用目录的 .env > Harness home 的 .env，拒绝 bootstrap-only 的文件变量，接受的值落进 process.env；
  2. composeProfile 按上节顺序叠出补丁栈（每层用 structuredClone 克隆——补丁里的 insert 行是按引用推进树的，复用同一解析对象会把用户覆盖烤死在内存里的 bundle 行上）；
  3. installFailLoud 装上守卫：启动期或之后的 Loader 拒绝变成一行带标签的 stderr 加 exit(1)，退出前先 await 一次有界的 release 清理（终端持有面先恢复终端再死）；
  4. boot() 创建根 context，向 Loader 的 !!js 表达式暴露 dshHomePath()，安装 vendored Cordis Loader，在任何配置树条目挂载之前运行 prepare 钩子——launcher 在这里提供环境快照服务和 provideCmdline——然后挂载并等待整棵 include 树，断言每个启用的 entry 既 loaded 又 activated；失败则销毁半个 context 再抛带 bin 名的错。

启动完成后还有两件常驻事。第一，config-only HMR：watchUserPatches 把 profile 层和 home 层两个 cordis.patch.yml 注册到 HMR 服务，每次编辑都事务性地 重组合整份补丁列表——重组合时 bundle 层始终在下、overlay 始终在上，用户编辑永远无法把它们挤开； 读或解析失败时上一棵好树继续运行。一次性 surface（headless）则通过自己的有界 shutdown 把 watcher 销毁。第二，信号语义：SIGTERM 是 supervisor 的普通停止请求，所有面 退出码 0；SIGINT 是用户打断，退出码 130；插件树的清理有五秒预算，第二个信号直接强制退出。

18.5 剩余 argv 的归宿：cmdlineArgs 与斜杠命令

launcher 对 app 参数的全部责任在 provideCmdline 这一步就结束了。它向树提供两样 东西（packages/boot/cmdline，@deepseek-ai/dsh-cmdline）： ctx.cmdlineArgs——一次调用的内部参数，get() 返回不可变快照（ dsh --profile tui --resume abc 得到 ['--resume','abc']）；以及 ctx.appExit——有界的进程退出请求，接到 launcher 的 shutdown 控制器上。

之后是app 插件的事。任何插件都可以 inject cmdlineArgs、解析它、 发布一个普通服务；parseCmdline(ctx, program) 只是一个 commander 适配器。关键的 排序机制在 Loader 一侧：一行的 !!js 插值会推迟到该行声明的注入全部激活 之后才执行，所以 web bundle 能这样写： 

- id: webserver
  name: '@deepseek-ai/dsh-host-webserver'
  inject: [webStartup]
  config:
    port: !!js ctx.webStartup.port ?? 3080

Cordis 已经在 Loader 询问 webserver 的 config 之前把 webStartup 填好，于是 flag 赢过写在旁边的值。注意这条优先级依赖行里保留那个表达式：用户补丁若把整段 config 换成字面量，运行时读取就没了（第 18.3 节的整体替换语义）。快照是共享 只读的：多个插件可以各自解析同一份 argv 而互不干扰，没有读取者的 profile 则干脆忽略自己的 app 参数。

别把 argv 和斜杠命令混为一谈。后者发生在会话内部：用户在输入框敲 /compact，Web 端经 command.execute RPC 交给 host 的 ctx.commands 注册表处理——这是第 16 章讲过的人类协作面，与进程启动参数无关。

18.6 源码启动契约：tsx 的 ESM hook

仓库根的 pnpm dsh <args…> 不经过构建：package.json 的脚本用 node --import tsx/esm 直接启动 apps/cli/src/bin.ts，并转发全部参数。 这带来一条必须遵守的契约：CLI 源码启动路径触及的每个模块都必须是 ESM——不能只有 CJS 导出。 原因是引擎版本范围内 Node 的原生 TypeScript 模式不可用，tsx 的 ESM-only hook 是唯一的桥； 完整的决策记录在 .agents/notes/implemented/architecture/2026-07-29-dsh-source-launch-tsx-esm.md。

实务上这条契约影响你两件事：给 CLI 会触及的包加依赖时，确认它在 ESM 下可加载；排查 pnpm dsh 报的模块解析错误时，先想「缺的是 Typert 主机工件还是前端产物」—— 缺 Typert 工件会以模块解析错误炸掉 profile 启动且不带构建提示，缺前端或 client 插件 bundle 则启动时明确提示跑 pnpm run build。安装形态没有这一切：它直接启动构建好的 apps/cli/lib/bin.js。

18.7 本章回顾

  • apps/cli 里 args.ts 拥有参数语法，bin.ts 按模式动态 import runner；launcher 的 flag 在最前，第一个不认识的 token 起是 app 参数。
  • 四种模式：--profile 启动、headless 一次性、web 别名、plugin 转发 pnpm；--dump-config 看树不启动。
  • profile 树在空根上分层贴补丁：bundle 层（bundles 顺序）→ profile 层 → home 层 → --patch；后层整体替换目标行 config，不深合并。
  • dsh-app-boot 负责 env 快照、fail-loud 守卫、vendored Loader 启动与两层用户补丁的 config-only HMR；SIGTERM 退出 0、SIGINT 退出 130。
  • 剩余 argv 经 ctx.cmdlineArgs（不可变快照）交还 app 插件；Loader 等注入激活后才插值 !!js，所以 flag 赢过旁边写死的值；斜杠命令走 ctx.commands，与 argv 无关。
  • 源码启动走 tsx 的 ESM hook（node --import tsx/esm），触及模块必须 ESM。
常见坑
  • 把 --port、--resume 当成 launcher 的 flag——它们属于被启动的 app；launcher 只认 --profile、--patch 和两个 dump。
  • 以为补丁是深合并——它整体替换目标行的 config，保留字段要重述；把带 !!js 表达式的 config 换成字面量会让 flag 失效。
  • 在空 cordis.patch.yml 里只写注释——解析为空会抛错；禁用该层写 []。
  • 期望 dsh --profile web --help 打印 launcher 帮助——没有 profile 接手时的裸 dsh --help 才是 launcher 的。
  • 给 CLI 源码路径引入 CJS-only 模块——tsx ESM hook 下直接不可加载。
