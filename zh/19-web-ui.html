Web UI 架构：host、client modules、ui-slots

dsh web 背后不是一个「带界面的单体」，而是两个半区：Node 进程里的 host 和浏览器里的 SPA。本章要建立的关键直觉只有一个——浏览器这一半也是插件化的： 页面上的每个区域都是一个 ui-* 特性插件，通过 ui-slots 的扩展槽组合出来。RPC 与 WebSocket 的连接细节留给第 20 章，这里只画通道的位置。

学习目标
  • 说出两半架构的边界：host 半区（webserver + frontend-static）与浏览器半区（Vite SPA）。
  • 描述浏览器壳的两段式 boot：window.__DSH_BOOT__ 模块图 → vendored Loader 插件面。
  • 解释 ui-slots 的 register 模型与 chain slot 的自荐选举。
  • 区分会话数据的两条来路：冷读的 projection cache 与实时流的 session/projection 帧。
  • 说清 client 插件 HMR 的触发条件与粒度。

19.1 一个产品，两个半区

dsh web 启动的 Node 进程是 host 半区；浏览器加载的 Vite SPA （apps/web，包名 @deepseek-ai/dsh-web-frontend）是浏览器半区。 两者在 packages/client/ 与 packages/host/ 两组包里各有一套角色：

  • host 半区：dsh-host-webserver 提供一个纯 node:http 服务器（ctx.webServer），只管具名路由、升级路由和唯一 的 fallback 座位；dsh-host-frontend-static 占据 fallback 座位，把构建好的 apps/web 的 dist/ 按 SPA 语义服务出去。host 半区还承载全部 ctx.* 业务服务——agents、sessions、settings、commands、skills……第 3 到 17 章讲的一切都在这里跑。
  • 浏览器半区：dsh-client-web 是启动壳， dsh-client-modules 是模块系统，dsh-client-web-react 把壳运行时 接到 React，dsh-client-runtime 提供 Session/Workspace 对象层，三十余个 ui-* 包是特性插件。

这张图里最容易被忽略的一条线是「GET 静态资源」上的小注释：frontend-static 服务 index.html 时会先过 webserver 的 applyIndexTaps——启动清单（boot manifest）就是这样进入 页面的。浏览器拿到 index 后要做的事，下一节展开。

19.2 host 半区：webserver 与 frontend-static

dsh-host-webserver 刻意「不认识任何 harness 概念」：它是一个默认导出的 WebServer 插件（config 只有 host 与 port），提供 ctx.webServer。别的插件向它注册具名 HTTP 路由（register，exact 或 prefix）、升级路由（registerUpgrade，按精确路径匹配 WebSocket）和唯一的 fallback 处理器（registerFallback，第二个注册者抛错）。匹配顺序固定：全表 exact → 最长 prefix → fallback。/api 桥、下行 WebSocket、插件 bundle 路由、HMR 事件流 全是别的插件注册进来的路由——webserver 自己一个文件都不服务。 host 只接受 127.0.0.1（默认姿态）和 0.0.0.0 （刻意的网络暴露）；绑定失败（如 EADDRINUSE）在激活时抛出，让 Loader 组合带着绑定诊断一起失败。

dsh-host-frontend-static 是 fallback 座位的出厂占用者：遍历出界 403、任意 miss 以 HTTP 200 回落 index.html（SPA 路由）、未知扩展名按 application/octet-stream 发出、无匹配路由的非 GET/HEAD 答 405。 distIndex 由组装应用（dsh-web-app bundle）从前端包的 exports 解析，部署永远不硬编码。座位是单主人且 effect 作用域的：这个插件 dispose，座位释放， webserver 回到 404。

19.3 浏览器半区也是插件：从 __DSH_BOOT__ 到 app-shell

浏览器壳的入口是 packages/client/web（@deepseek-ai/dsh-client-web） 的 AppWebEntry(el).run()。它分两段 boot，也就是仓库文档说的 web2：

  1. 模块面：基于 host 推进页面的入口图 window.__DSH_BOOT__ 搭起 dsh-client-modules 的 ClientModuleLoader，并行预取 immediately 层。此时 bundle 的执行只是注册工厂，不产生副作用。
  2. 插件面：挂载 vendored Cordis Loader，把模块系统从它的 internal 契约注入——vendored 侧唯一的消费点是 EntryTree.import， 换掉 internal 就等于换掉「插件代码怎么到达」。图上每行一个 loader entry，外加壳自有的 app-shell 装配 entry；AppRoot 等到 settle（Loader 静默 + 每个 entry fiber ACTIVE）一次性 渲染完整 UI。

dsh-client-modules 本身值得一句：它是「Node 内部 ESM loader 的浏览器对等物」， 实现为懒 CJS 表。执行一个插件 bundle 只是 window.__ModuleLoader__.load({id, factory}) 注册工厂；模块体的全部副作用（包括 CSS 注入）住在工厂闭包里，物化 （factory(require)）时才执行并记入 loadCache。工厂 require 另一个 已注册未物化的模块会递归物化它，所以加载顺序不需要外部排序；require 环抛错。Node 那一半扫 启用的 Loader entry 里带 web dsh.client 的包，解析各自的 exports["./client"]，把构建出的 bundle 连 source map 打进 boot 图、经 /plugins 服务——host 图决定组合，壳一个组合决策都不做。

19.4 ui-slots：浏览器 UI 的组合律

三十余个 ui-* 包怎么拼成一个界面？答案是 ui-slots 的槽终端设计 （slot terminal design）。一次 register 同时做四件事：向某个已声明的槽贡献一个 组件、声明子槽（声明 = 渲染授权 = 运行时规格，一张表）、可选地挂一个 store 座位、给出注册者 的业务面。组件的 props 是四份共享的交集：runtime props（父的 renderSlot 调用点 + 会话标准件 + 全局座位）、子渲染 props、store props、业务 props——每份都从单一事实推导，不需要二次同步。

两种槽值得分清。keyed 槽由派发点选 entryKey 路由； chain 槽反过来——每个注册自带一个纯 ChainSelect 选择器 （可带升序 priority，平局按注册序），第一个返回非 null 的注册当选，其返回值作为 matched prop 传给组件；全落空则回到持有者的 renderSlotChain 兜底。 侧栏、会话视图、设置页的扩展区都靠这套机制长大。

分层也干净：dsh-client-web-react 提供 createSlotRenderer（壳装进 runtime 的 SlotRenderer 实现）、SessionProvider、唯一的 hook 构造器 bindSnapshotSelector 和 useInvoke；业务插件只依赖 ui-slots 的类型，从不依赖 web-react。快照存储引擎（defineStore）在 runtime 包里，宿主与引擎只传递裸 observable 源，hook 绑定全部归渲染机器。

19.5 会话列表与实时流：投影的两张面孔

呼应第 5 章：host 侧有一个 ctx.sessionProjections 投影注册表，冷热数据走两条路。

  • 冷读：打开页面时 session.list 之类的列表不必唤醒任何 Agent。网关自持两个投影单元（如 sessionListMetadata 缓存「空白→非空白」的 单调翻转和最近人类提问时间）；对很小的会话工件（默认 1 KiB 阈值内）还能做一次精确折叠 得出 blank 与最近提示。冷会话在列表里保持「只有元数据」，直到你打开或恢复它，host 才 附着日志、折叠出日志支持的标题。
  • 实时：附着会话后，客户端从历史尾页的 projections 块种下 一份 ProjectionValueStore（带 asOfSeq 水位），此后靠 session/projection mux 帧按 higher-seq-wins 更新各单元 （标题、todos、队列、jobs……）。这些帧是活推送状态，永不入日志——第 4 章 的「model-visible ⟺ logged」不变量不受影响。

runtime 把共享的 host 流扇出到 Session 与 Workspace 拥有者，把每条通用 host/remote-event 帧交给 ctx.remote.$dispatch（第 20 章）。会话 内容本身由 ConversationNodeAssembler 组装：插件注册业务 Definition，把一个 事件映射成稳定的 {kind, id}，在唯一起始事件处建 Context，折叠相关更新，为 注册的视图目标产出最终节点——追加只评估一次 Definition、只更新匹配的 Context；翻旧页保留 既有 Context 与节点身份。ui-conversation 注册内置 Chat Definition，ui-trajectory 在同一 事件窗口上注册独立的 Definition 与目标构建器，两套视图互不消费对方的折叠。

19.6 开发态：client 插件热更

dsh-client-hmr 让脚本加载的 client 插件可以热替换，但有个前提常被误解： web bundle 无条件挂载 HMR 行，可它自己不重建任何东西。真正触发重建的是单独 跑的 pnpm run dev:web watcher 重写 client bundle；没有 watcher，节点侧的 stat-poll 观察不到变化，整条链保持空闲。

有重建时，浏览器半区订阅系统 SSE 通道（GET /plugins/events），每个 rebuilt 帧经串行队列重载一个插件：invalidate 旧工厂 → prefetch 新 bundle （旧 fiber 还在服务时注册）→ 删注册表 → 排干旧 fiber → 删自有 style 标签 → entry.refresh() 重导入重挂载。依赖方的重载靠 Cordis 本身：fiber 的激活纪元一变， 其服务提供者的 uid 全部串味，替换一个 provider 会级联所有依赖方，客户端零图分析。粒度是 粗的整插件重载——React 内部状态丢失，数据层（connection/runtime 的 fiber、Session 对象）不动；失败的Reload不回滚，entry 停在 FAILED 并在 loader 状态投影里可见。

19.7 本章回顾

  • 两半架构：host 半区是 dsh-host-webserver（纯 node:http，路由全靠别的插件注册）+ dsh-host-frontend-static（唯一 fallback 座位，服务 apps/web 的 dist/）；浏览器半区是 Vite SPA。
  • 浏览器壳两段式 boot：模块面用 window.__DSH_BOOT__ 建 ClientModuleLoader（执行 bundle 只注册工厂），插件面挂 vendored Loader（每图行一个 entry），AppRoot 等 settle 一次点亮。
  • 浏览器 UI 一样「everything is a plugin」：三十余个 ui-* 特性插件经 ui-slots 的 register 组合；chain 槽由注册者自带的 ChainSelect 选举；业务插件只依赖 ui-slots 类型。
  • 会话列表冷读走 projection cache 与小工件精确折叠（不唤醒 Agent）；实时流走 session/projection 帧 + higher-seq-wins，永不入日志。
  • client HMR 需要单独的 pnpm run dev:web watcher 触发；重载按整插件粒度，依赖方级联靠 fiber 激活纪元。
常见坑
  • 以为 webserver 会服务文件——它一个文件都不服务；dist 是 frontend-static 占 fallback 座位服务的，第二个 fallback 注册直接抛错。
  • 把 window.__DSH_BOOT__ 当成浏览器自己算出来的东西——它是 host 推送的入口图，壳对组合零决策。
  • 以为 bundle 一执行副作用就跑了——执行只注册工厂，副作用在物化（factory(require)）时才发生。
  • 给业务 UI 插件加 web-react 依赖——类型依赖只该指向 ui-slots；hook 绑定是渲染机器的事。
  • 期望 session/projection 帧出现在会话日志里——它们是活推送状态，永不落盘。
  • 抱怨 HMR 不生效——先确认有没有单独跑 pnpm run dev:web；HMR 行挂载着但不会自己重建 bundle。
