Typert 与 RPC 网关

上一章留下了那条线：浏览器和 host 之间有一个 /api 通道。本章把它拆开： 浏览器↔host 的 RPC 怎么做到端到端类型安全？答案叫 Typert——构建期从类型生成「类型图」， 运行期用注册表消费它。再往上，gateway 认领新式 Remote 端点、apiproxy 承接遗留面， 两条只下行的 WebSocket 负责事件。读完你会知道一个方法调用从浏览器到 ctx 服务的每一跳。

学习目标
  • 说出 Typert 三件套的分工：generator（构建期）→ loader（发现）→ registry（ctx.typert）。
  • 描述 /api 上的一次调用如何被 interceptor 认领或回落到 apiproxy。
  • 解释 remotes 的 createApiRemoteAgentResolver 统一了什么策略。
  • 画出通道全貌：unary/respond 的 POST、events.mux 与 events.host 双下行、readiness 判定。
  • 说明 /api browser-trust fence 为什么盯住 Host 头（DNS-rebinding 防护）。

20.1 问题：端到端类型安全的 RPC

Web UI 的 RPC 有个结构性难题：调用方在浏览器（TypeScript，Client 编译面），被调方在 Node（TypeScript，Host 编译面），中间是 HTTP 与 JSON。常规做法要么手写两份接口再祈祷它们 不漂移，要么上 codegen 生成整套客户端。dsh 的答案是 Typert：让构建期工具 从源码类型树生成一份与编译器无关的类型图（FaceModel、 TypeGraph），运行期以注册表形态消费它——浏览器一侧拿到的调用面 （ctx.remote）和 Node 一侧暴露的调用面（ctx.typertGateway） 共享同一份生成的 InvocationDescriptor 契约。

这个设计同时守住了第 23 章会展开的边界纪律：业务包把方法用 @Remote 或 @RemoteScope 标在 Host 服务类上，不需要依赖任何 RPC 运行时；生成的声明把 TYPERT 暴露成 unknown，贡献业务包不必依赖类型注册表本身。

20.2 Typert 三件套：generator → loader → registry

packages/typert/ 三个包按「分析 / 发现 / 存储」分层：

包角色Cordis key
typert/generator构建期库：分析 TypeScript 工程，生成运行期工件—（无插件）
typert/loader扫描 Loader 条目，导入并注册生成的 Host 工件消费 ctx.loader 与 ctx.typert
typert/registry运行期注册表：包反射与可选的活 Zod schemactx.typert

generator 用独立的 ts.Program（以 tsconfig.host.json 或 tsconfig.client.json 为种子）分析源码，产出与编译器无关的模型，再由 emitter 渲染工件。仓库里的 Host tsdown 会带着 workspace Typert 生成跑一遍：产出 Host 反射 工件（lib/typert.host.{js,d.ts}，经 package/typert 子路径暴露） 以及给 Client 用的 typert.remote-client.* 投影；随后的 Client tsdown 不再启动 Typert。发布是按包 opt-in 的：没有相应公共导出的业务包不需要任何 Typert 工件。 check 模式下分析器对语法/语义诊断、缺失的公共标注、私有的跨包引用都会失败—— 类型图不允许悄悄缺一块。

loader 是 Node-only 插件：激活时扫描既有 Loader 条目，跟随 internal/plugin 生命周期通知，解析每个条目包的 package.json， 在它导出 ./typert 时导入并校验 TYPERT 清单、把贡献注册进注册表。 没有该导出的包直接跳过；藏另一个 Loader 条目后面的嵌套插件要靠 packages 配置显式列出。解析与清单按进程生命周期缓存，新加导出要重启。

registry 提供 ctx.typert：包反射按 <package>#<face> 键存，schema 按 <package>#<name> 键存（保留生产者的 Zod 实例，JSON Schema 在消费端按需投影）。它还有两个独立的归属面： lookups（业务包注册查找声明与默认解析器，Host 组合用 configure() 覆盖行为——把第 20.4 节的 Agent/Session 解析策略换掉就是这里）与 contexts （scoped 调用的 Context 身份）。注册即效应：贡献随调用方的 Cordis fiber 一起撤出。

20.3 gateway 与 apiproxy：认领与回退

packages/api/gateway（@deepseek-ai/dsh-api-gateway）是两面插件： Host 入口提供 ctx.typertGateway，Client 入口 （@deepseek-ai/dsh-api-gateway/client）提供 ctx.remote。 业务服务继承 TypertRemoteService、给公开方法标 @Remote 或 @RemoteScope；Host 侧调用流是：解析当前描述符与 Cordis Service → 校验精确的命名参数 → 经 lookups 解析对象或 Context 身份 → 调用业务方法 → 校验返回值。

两种校验模式要分清。strict 模式从 ctx.typert.local 读生成的 调用描述符，参数、返回值都按生成 codec 精确校验；SRC 模式是给从未有过 strict 定义的端点留的开发回退，只解析简单参数名、对非查找参数只验 JSON 安全。关键的红线： 撤回一个已被观察过 strict 定义的端点会直接失败，而不是悄悄降级到 SRC—— 校验强度只允许变严。

Client 侧的 ctx.remote.$mount() 校验并注册一份生成的 Host-for-Client 贡献， 为调用方的 fiber 安装具体方法（每个命名空间是带追踪的 remote.<ns> 子 Service）。调用时校验位置参数、构造描述符要求的精确命名 args，经 ctx.connection.rpc.call('/api', endpoint, …) 发出；返回值先过校验再进应用代码。 事件面是 ctx.remote.$on()：合法键恰好是 Host 组装的转发选择（第 20.4 节）， 监听器类型就是属主包自己的 Cordis Events 声明——第二份签名想漂移都没有落点。

那遗留面怎么办？Host 的 /api FetchHandler 上挂着一个复合 handler：gateway 注册的 interceptor 先认领 Remote 端点，没被认领的落到 apiproxy（ctx.apiProxy，@deepseek-ai/dsh-host-apiproxy） ——一个 transport 无关的网关，持有四象限 wire 契约 （ClientRequest/ServerResponse/ServerRequest/ ClientResponse）与庞大的遗留方法族（session.*、 workspace.*、settings.*……）。它自己不注册路由：HTTP 载体（第 19 章的 connection）负责把请求递过来。迁移是逐方法进行的：迁到 Remote 的方法由 gateway 处理， 未迁移的继续走 apiproxy，两边共享同一个 Agent/Session 解析策略——这正是 remotes 存在的理由。

20.4 remotes：Agent/Session 查找策略

packages/api/remotes（@deepseek-ai/dsh-api-remotes）是两面 BFF。 它的核心导出 createApiRemoteAgentResolver() 把「这个 sessionId/agentId 指的是 谁」回答成了唯一一份策略：复用活 Agent、恢复普通冷会话、对并发的恢复去重、保住 subagent 所有权 fence；同一位解析器同时配置给 Typert 的 agent 与 session 查找键。遗留的 Web ApiProxy 取 Agent 默认值和 scope 装配后， 也用这个解析器处理遗留方法——迁移过与没迁移的方法共享同一份身份策略实现， 这是「换网关不换行为」的关键。

它的 Client 面是浏览器业务包的依赖门面：导入生成的 /remote 工件作为运行期值、 经 ctx.remote.$mount() 挂载每份贡献、再导出声明合并；业务包不依赖 gateway 实现 或单个 Remote 运行期入口。当前组合挂载了 Goal 贡献和只读的 Host 插件清单贡献 （pluginInventory/list）。

下行事件的白名单也在这里：src/remote-events.ts 的 API_REMOTE_FORWARDED_EVENTS 是 Host 转发给消费者的 cordis 事件列表——逐字转发、 无投影、无脱敏、不改名——因此它也就是 ctx.remote.$on 的合法键集；Host 面还会拿 这个表对 TypertForwardableEvent 断言：不是已声明事件、绑定 AgentScope、或形状 非单向的都进不了白名单。转发一个新事件 = 在数组里加一项，类型投影、消费键面、Host 转发循环 全部从它派生。

20.5 通道全貌：POST、双下行与 fence

通道一共三种形态。上行走 HTTP POST：unary 和 respond 操作都是 POST /api/<method>，respond 类（如回答 agent 提问）走 POST /api/respond 回执。每个 POST 必须声明 application/json， 否则在分发前吃 415——跨站「简单请求」（浏览器不发预检的那种）永远执行不了有副作用的方法。

下行是两条只下行的 WebSocket：/api/events.mux 承载会话级 mux 帧（会话事件、投影帧、队列与任务快照……），/api/events.host 承载 host 级 帧（workspace 增删、转发 Remote 事件……）。两条 socket 都只从 host 发向浏览器， 客户端不在其上发送任何应用数据。断任意一条，当前连接 generation 即失败、两条流一起重建； readiness 的判定是「两条 socket 都开着 且 host.describe 的 HTTP 调用 成功」——成功握手发布的正是 host.describe 的值。普通网络 GET 打到这两个路径 得到 426，线上没有 SSE 回退（SSE 编解码器只服务于同进程内载体）。

fence 是唯一横在两条 WebSocket 升级和所有 /api 请求前的门。 它的核心比较是 Host 头：必须是 loopback 权威（或部署推出的 LAN IP 字面量）， 或精确命中一条 trustedHosts 条目（host:port 精确、无端口条目任意 端口，两侧都过 WHATWG 规范化比较）。为什么是 Host？因为这是 DNS-rebinding 攻击者唯一 伪造不了的请求头：纯 HTTP 下浏览器对 image 与导航读取既不带 Origin 也不带 Fetch-Metadata，一个「无标记」的请求仍可能是被重绑的浏览器读取；marker 存在时 Origin 必须等于 Host 权威、显式的 sec-fetch-site: cross-site 直接 拒绝。非规范条目（比如 harness.internal/path 这种带路径的东西）在插件加载时就 大声失败。另有一组钉死在 loopback 的特权方法（host.pickDirectory、 配置面读写、agentPreset 读写那一族）——声明的 trustedHosts 权威够得着其他方法， 却够不着它们；在真正的认证层存在之前，这些能力不出本机。fence 是可达性策略， 不是认证：这也是 dsh web --host 0.0.0.0 至今刻意不支持的原因。

20.6 本章回顾

  • Typert 分三层：generator 构建期从类型树生成工件（Host tsdown 触发，按包 opt-in），loader 扫 Loader 条目导入 ./typert，registry 提供 ctx.typert（<package>#<face> 反射、<package>#<name> schema、lookups/contexts）。
  • gateway 两面：ctx.typertGateway（strict 描述符校验，SRC 仅开发回退且撤回已观察的 strict 定义会失败）与 ctx.remote（$mount 生成方法、$on 转发事件）。
  • /api FetchHandler 上 interceptor 先认领 Remote 端点，未认领的落 apiproxy（ctx.apiProxy）的遗留方法族；两网关共享 remotes 的 createApiRemoteAgentResolver（活 Agent 复用、冷恢复去重、subagent 所有权 fence）。
  • 通道：unary/respond 走 HTTP POST（必须 application/json）；/api/events.mux 与 /api/events.host 两条只下行 WebSocket，断任一即整代重建；readiness = 双 socket + host.describe 成功。
  • fence 盯 Host 头防 DNS-rebinding；trustedHosts 声明权威，特权方法钉死 loopback；fence 是可达性策略，不是认证。
常见坑
  • 以为 Typert 在浏览器运行期分析类型——分析在构建期（Host tsdown），浏览器只消费生成的 codec 与描述符。
  • 以为没被认领的端点是 404——它落进 apiproxy 的遗留面；apiproxy 是回退层，不是废墟。
  • 给端点撤 strict 定义指望退回 SRC——已被观察过 strict 定义的端点会直接失败，校验只许变严。
  • 以为浏览器会在两条 WebSocket 上回发数据——它们只下行；上行永远走 HTTP POST。
  • 把 fence 当认证——它只挡可达性；这也是 --host 0.0.0.0 被刻意拒绝的根因。
  • 在 trustedHosts 里写带路径或零填充端口的「权威」——非裸 host[:port] 条目在插件加载时就大声失败。
