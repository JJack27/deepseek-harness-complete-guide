第 17 章 · 第三部分 · Capability Seams 专题

能力面速览

shell、fs、subagent、compaction——前几章深挖的能力只是仓库的一半。本章是一页式地图： 把其余十四个能力家族按「解决什么问题、包怎么分、去哪扩展」各用一小节过一遍。 你不需要记住每个细节，只需要在遇到需求时知道该走进哪扇门； 每扇门里的三角色结构，都是第 11 章你已经掌握的那套方法论。

学习目标
  • 拿到一个能力需求（检索、编排、定时、凭据……）能说出对应的能力家族与它的 ctx.* 服务键
  • 对每个家族能指出扩展点：注册 provider、监听事件、还是挂 Consumer 工具
  • 能说出几个刻意收紧的边界：lsp 只有四个操作、schedule 不含外部通知通道、credentials 配置不带值
  • 能把本地图与 docs/capability-seams.md 全图对照，自行补齐本章未展开的细节

17.1 能力地图

十四个家族按关注点分成五组。知识与外部信息组回答「模型怎么知道更多」； 编排与续跑组回答「工作怎么跨 step、跨轮次延续」；配置与凭据组回答「部署差异放哪」； 数据与执行组回答「二进制与模型写的程序怎么跑」；自省与桥接组回答「agent 怎么改自己、 怎么接外来生态」。

17.2 skill：可复用指令的目录与加载

skill 家族发现可复用的 agent 指令（SKILL.md 一类）并以 provider 中立的目录暴露给模型。 dsh-skill 是纯注册表：provider 用 registerProvider(create) 注册来源 （本地文件、内嵌数据、HTTP 都行），消费方用 snapshot()/list()/get() 读取；skills/change 是不带目录内容的失效通知。注册表按 host+per-scope 分层 （第 11 章工具注册表确立的形状），invocation 策略把 modelInvocable 与 userInvocable 分开。 dsh-tool-skill 在每次合格的 agent/pre-step 做目录快照， 以持久 user 角色 <available_skills> 消息发布有序的 name/description 目录， 摘要 digest 变化才追加完整替换；skill 工具按名加载， renderSkillContent() 保证目录注入与工具加载渲染出同一个 <skill_content> 形状。

包ctx 键 / 角色扩展点
dsh-skillctx.skills · DefinitionregisterProvider() / register()（runtime 内嵌技能）；skills/change
dsh-skill-filesystem注册于 ctx.skills本地文件系统发现
dsh-skill-badge注册于 ctx.skills随船的可选 dsh badge 技能
dsh-tool-skill注册于 ctx.toolsskill 工具 + pre-step 目录发布

17.3 web：search 与 fetch 共用一条 seam

dsh-web 的 WebRuntime（ctx.web）跨两个操作（search、fetch） 于一条 seam：registerSearchProvider 与 registerFetchProvider 各自注册后端， 执行时按「显式配置的 provider id，否则恰好一个可用者自动选中，否则抛错」解析—— 选择从不依赖注册或 HMR 顺序。错误走结构化的 WebError 词汇 （如配置的 id 未注册是 WEB_PROVIDER_CONFIGURED_MISSING，未配置且多个可用是 WEB_PROVIDER_AMBIGUOUS）。providers 注册的是能力不是工具： dsh-tool-web 是模型可见名（web_search/web_fetch）、 schema 与展示的唯一 owner。想接新的搜索或抓取后端，注册一个 provider 就够了。

包ctx 键 / 角色扩展点
dsh-webctx.web · DefinitionregisterSearchProvider() / registerFetchProvider()
dsh-web-search-exa / -perplexity / -deepseek注册于 ctx.web三个搜索 provider
dsh-web-fetch-http注册于 ctx.web匿名公共 HTTP(S) 抓取
dsh-tool-web注册于 ctx.toolsweb_search / web_fetch 工具

17.4 lsp：四个语义操作，没有逃生口

LSP 家族把语言服务器能力收进一条刻意收窄的 seam：ctx.lsp 只暴露四个语义操作—— goToDefinition、findReferences、goToImplementation、hover—— 没有通用 JSON-RPC 逃生口。这样换 provider 不改变模型提问的方式， 也没有协议载荷或未审查的变更能到达模型契约。dsh-lsp-stdio 是通用多服务器后端， 建在 ctx.fs 与 ctx.subprocess 之上（第 12 章的共享执行世界）， 文档按查询临时打开；dsh-tool-lsp 是模型可见的 lsp 工具， 使用一基 UTF-16 光标坐标。providers 注册能力而非工具——模型面的名字与 schema 归 tool-lsp 独有。

包ctx 键 / 角色扩展点
dsh-lspctx.lsp · Definition按 branded id 注册 provider 与扩展名映射
dsh-lsp-stdio注册于 ctx.lspstdio JSON-RPC 多服务器后端（消费 ctx.fs/ctx.subprocess）
dsh-tool-lsp注册于 ctx.toolslsp 工具（四操作）

17.5 mcp-client：外部工具生态的桥

dsh-mcp-client 连接外部 MCP（Model Context Protocol）服务器， 把它们的工具注册到 ctx.tools，模型以原生工具的形式使用： 公开名是 mcp__<serverName>__<rawName>，与 Claude Code、Codex 同形。 cordis.yml 里每个 MCP 服务器一个插件实例，传输为 stdio 或 streamable-http；工具名是 (serverName, rawName) 的纯函数—— 连接顺序、re-sync、其他服务器都不改名。断线由监督者按指数退避重启并重新发现， 预算耗尽则注销工具直到重载。注意它只桥接 tools：MCP 的 Resources 与 Prompts 尚无消费者。

包ctx 键 / 角色扩展点
dsh-mcp-client消费 ctx.toolscordis.yml 每服务器一实例（transport / serverName / command / url / reconnect…）

17.6 workflow 与 ralph：模型写的编排

workflow 家族运行模型编写的编排脚本。dsh-workflow 定义执行与生命周期 （ctx.workflowEngine），dsh-workflow-worker-thread 在 worker 线程里跑脚本 ——线程把执行与 host 事件循环隔离，但不是安全边界。dsh-tool-workflow 暴露 workflow 工具（meta/script/args）， 把运行投影进调用方会话的 workflow/* log-only 事件。 dsh-tool-ralph 是同一引擎上的固定策略 Consumer：ralph({ objective, maxRounds? }) 把一个不可变目标交给一串全新子代理——每轮一个 fresh child（provider 必须支持 结构化输出且 inheritsParentContext: false），共享工作区是长期记忆， 轮与轮之间传递结构化 handoff。没有为它改 agent-loop（呼应第 7、14 章：编排是插件不是循环分支）。

包ctx 键 / 角色扩展点
dsh-workflowctx.workflowEngine · Definition注册引擎后端；workflow/* 事件
dsh-workflow-worker-thread注册于 ctx.workflowEngineworker 线程执行
dsh-tool-workflow注册于 ctx.toolsworkflow 工具（通用脚本）
dsh-tool-ralph消费 engine + ctx.subagentsralph 工具（固定 fresh-agent 循环）

17.7 jobs：后台作业的一个协议

长时间运行的工具（构建、watch、采集）需要观察、取消、等待与完成通知——jobs 家族给它们 一个 owner 隔离的协议。dsh-jobs 定义 ctx.jobs 注册表契约 （start/get/list/read/kill/wait/onJobDone/onJobsChanged）， dsh-jobs-local 是进程内实现。访问按 SessionId 圈定（owner fence）， controller 的注册也是 owner 相对：没加载 controller 的组合不能借着别人的控制开工。 dsh-tool-jobs 暴露三个与种类无关的工具——job_output、job_list、 job_kill——加上完成通知。通知走两条车道：owner 忙碌时注入 next-step 收件箱（第 15 章的 agent.inject()，多个作业同时结算只花一个 step）； owner 空闲时用 follow-up turn 唤醒，且唤醒有 maxConsecutiveWakes 预算防自激。

包ctx 键 / 角色扩展点
dsh-jobsctx.jobs · Definition扩展 JobKindMap 的 producer 插件；attachController()
dsh-jobs-local注册于 ctx.jobs进程内注册表
dsh-tool-jobs注册于 ctx.toolsjob_output / job_list / job_kill + 完成通知

17.8 goal 与 schedule：同会话的两种时间观

两个家族都把状态存进原有会话日志，但时间方向相反。goal 面向「跨多轮持续推进的 目标」：ctx.goals 维护至多一个当前目标，每次变更追加携带完整变更后快照的 goal/change 事件；activation（续跑授权）从不持久化——进程本地， resume/fork 保留目标与阶段但不动手，之后必须显式 resume 才重新武装。 dsh-goal-round-driver 把激活目标变成顺序的 goal round：空闲时预留轮次、 以 GoalMessageSource 的 user/message 排入 <goal_round> 提示；人类消息优先，不消耗 goal 轮次预算。schedule 面向「未来的提醒」：单包 dsh-schedule 提供会话作用域的 schedule_create/schedule_list/ schedule_delete 三工具，durable 状态在会话日志里；进程本地的 owner 只在该会话有 live root agent 时等待，到期工作经普通 follow-up 队列进入对话——不隐含任何外部通知通道。

包ctx 键 / 角色扩展点
dsh-goalctx.goals · Definition服务动词 + goal/changed 事件；continuation consumer 以 GoalMessageSource 准入轮次
dsh-goal-round-drivercontinuation Consumer空闲 agent 的轮次预留与排队
dsh-tool-goal / dsh-command-goal模型工具 / 人类命令目标变更的两个入口
dsh-schedule会话日志内（无服务键）三个会话作用域工具；到期经 follow-up 队列

17.9 settings 与 credentials：配置与凭据

settings 家族解析用户可编辑的配置：ctx.settings 上插件注册命名空间 schema， 读值按「schema 默认 → 注册方组合的 base → 用户文档小节」分层解析；没有挂 provider 时 消费方照常只解析 entry config，所以每个组合有没有 settings 都能工作。 dsh-settings-file 把文档存在本地文件并观察外部编辑。 credentials 家族的教义是三句话：配置携带引用、绝不携带值（CredentialRef 是 branded 的，resolve(ref) 在每个操作开头解析、从不跨操作缓存——换密钥下一个 请求就生效）；describe 不返回值（配置 UI 安全）；空值即缺席。 dsh-credentials-local 把进程环境叠在 $DSH_HOME/.credentials.yaml 之上， .env 层兜底；只读来源遮蔽引用时 set/unset 刻意拒绝。

包ctx 键 / 角色扩展点
dsh-settingsctx.settings · Definitionregister(ns, schema, …)；settings/updated / settings/document-updated
dsh-settings-file注册于 ctx.settings本地文件 provider（外部编辑热发布）
dsh-credentialsctx.credentials · Definitionresolve / describe / set / unset；credentials/updated
dsh-credentials-local注册于 ctx.credentialsenv + .credentials.yaml + .env 分层 provider

17.10 attachment 与 code-runtime：字节与程序

attachment 家族处理持久二进制：ctx.attachments 校验并原子提交不可变的 图片字节，返回可序列化的 ImageAttachmentRef——消费者从不把浏览器路径、 object URL 或 base64 塞进会话事件；未发送的草稿图片留在浏览器侧，字节只有在用户提交提示 或 provider adapter 提交结构化输出时才进入持久存储。 dsh-attachment-local 把内容寻址的私有存储放在 DSH_HOME 之下。 code-runtime 家族是 Code Mode 的地基：ctx.codeRuntime 定义「执行一个模型写的程序、 对 host 提供的 async 绑定求值、捕获打印与返回值」的运行时，dsh-code-runtime-worker-thread 是 worker 线程后端；Consumer 是工具注册表自己的 Code Mode（tools: { mode: code }） ——run_code 工具与按加载运行时语言生成的 SDK。第 15 章你已见过它的一个侧面： 子调用结果的持久日志副本经 tools/code-dispatch-log 接受 spill 上限。

包ctx 键 / 角色扩展点
dsh-attachmentctx.attachments · DefinitionvalidateImage / saveImage / readImage
dsh-attachment-local注册于 ctx.attachmentsDSH_HOME 下内容寻址存储
dsh-code-runtimectx.codeRuntime · Definition注册运行时后端（语言、隔离、预算）
dsh-code-runtime-worker-thread注册于 ctx.codeRuntimeworker 线程执行

17.11 extensions 与 hooks：自省与桥接

extensions 家族让agent 检查并修改自己的运行时：dsh-tool-cordis 在 ctx.tools 上注册模型可见的运行时检查与动态包工具——检视已加载插件与服务 API、 定义并运行模型写的动态包、再撤回它们；dsh-cordis-host-runner 提供 ctx.dynamicCordisRunner（定义注册表 + node:vm 沙箱 + 请求-运行往返）， dsh-cordis-client-runner 是浏览器半边，dsh-ui-cordis 提供操作面板与只读 define 卡。这是「demo:cordis 让 agent 修改自己的运行时」背后的机制。hooks 家族面向外来生态： 它把 Claude Code / Codex 风格的外部 shell hook（hooks.json）忠实映射到 dsh 的 typed 拦截点上——dsh-hook-protocol 是共享的 wire 协议库， dsh-hooks-claude-code 与 dsh-hooks-codex 各自拥有方言的事件映射。 记住立场：dsh 的原生扩展面就是那些类型化拦截点，「原生 hook」不过是挂在上面的普通 Cordis 插件。

dsh-tool-cordis注册于 ctx.tools运行时检查 + 动态包定义/运行/撤回工具
dsh-cordis-host-runnerctx.dynamicCordisRunner（host）定义注册表 + node:vm 沙箱
dsh-cordis-client-runner / dsh-ui-cordis浏览器半边浏览器插件求值 + 面板 UI

17.12 本章回顾

  • 知识与外部信息：skill（ctx.skills 目录 + skill 工具）、web（ctx.web search/fetch 一条 seam、多 provider、显式选择策略）、lsp（四操作、无 JSON-RPC 逃生口）、mcp-client（mcp__server__tool 注册到 ctx.tools）。
  • 编排与续跑：workflow（ctx.workflowEngine + worker 线程 + workflow 工具）、ralph（固定 fresh-agent 循环，工作区即长期记忆）、jobs（ctx.jobs owner 圈定 + job_* 工具 + 注入/唤醒双车道通知）、goal（ctx.goals 事件溯源、activation 进程本地）、schedule（会话日志内提醒，无外部通知通道）。
  • 配置与凭据：settings（命名空间分层解析 + 文件 provider）、credentials（引用不携值、按操作 resolve、空值即缺席）。
  • 数据与执行：attachment（不可变图片字节 + ImageAttachmentRef）、code-runtime（ctx.codeRuntime + Code Mode 的 run_code 与生成 SDK）。
  • 自省与桥接：extensions（ctx.dynamicCordisRunner、模型检查/挂载自己的插件）、hooks（外部 shell-hook 协议桥接到 typed 拦截点）。
  • 共同句式：providers 注册能力不是工具；模型面的名字、schema、提示与展示归 Consumer 工具包独有；状态要么进会话日志、要么留在侧车，从不进模型历史。
常见坑
  • 给 web/lsp 的 provider 起工具名——providers 注册能力；模型可见名归 tool-web/tool-lsp。
  • 指望 web 自动在多个可用 provider 里挑一个——未配置 id 且多个可用时抛 WEB_PROVIDER_AMBIGUOUS，选择必须显式。
  • 把 worker 线程当安全边界——workflow 与 code-runtime 的线程只隔离事件循环，不是沙箱。
  • 以为 schedule 会推送通知——它是会话内提醒，只在有 live root agent 时投递。
  • 把凭据值写进配置——配置只带 CredentialRef；值由 provider 解析，空值视为未配置。
  • 给 ralph 加「Ralph 模式」或改 agent-loop——它是普通插件上的固定策略 workflow。
  • 绕过 ctx.attachments 直接把 base64/URL 塞进会话事件——持久引用只能是 ImageAttachmentRef。
