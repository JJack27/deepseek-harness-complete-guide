Capability Seam 模式：三角色方法论

前 10 章你见过的每一个能力——ctx.llm、ctx.tools、ctx.systemPrompt——背后都是同一个结构。 本章把这个结构命名清楚：capability seam，一个可替换能力的完整切口，由 Service Definition、Service Provider、Consumer 三个角色合起来构成。掌握了这个模式， 你就能回答 dsh 里最重要的工程问题：加一个能力要设计哪几块？换一个实现要动哪几块？答案是三块和一块。

学习目标
  • 能说出三角色各自的职责与边界，以及为什么 Service Definition 必须是 Cordis Service 子类而不是 TypeScript interface
  • 能以 dsh-shell 家族为范本，指出每个包扮演哪个角色
  • 能解释「换一个 provider 就换一个产品形态」的连锁机制——执行世界为什么是成组搬迁的
  • 会查 docs/capability-seams.md 这张脚本生成的全图，定位任意 ctx.* 服务的 owner、implementations 和 consumers
  • 拿到一个新能力需求时，能按三角色清单完成设计而不是只写一个插件

11.1 什么是 capability seam

dsh 的仓库说明里有一条反复出现的约定：A capability seam comprises Service Definition / Service Provider / Consumer roles. It is complete, never one role. 一个 capability seam 是一个可替换能力的完整切口：沿这条缝切下去，能力可以被整体换掉， 而切口的两侧都不知道对方的具体实现。

docs/glossary.md 的 capability-seam 条目给出了精确定义，三个角色是：

  • Service Definition——一个 Cordis Service 子类，拥有自己的 ctx.<key> 服务键和全部词汇类型（vocabulary types）。它可以是抽象类 （如 ShellExecutor），也可以是具体注册表（如 web 能力的 registry）， 但绝不是 TypeScript interface。interface 没有声明合并、没有 ctx.shell 这个键、没有生命周期——它挂不到 Cordis 的服务图上。
  • Service Provider——实现者。子类化抽象 Service 或向注册表注册，把「怎么做」填进去。 一个 seam 可以有一个 provider，也可以有一组并列的 provider。
  • Consumer——使用者。通过 inject 拿到 ctx.<key>， 只面对 Definition 的词汇编程。最常见的 Consumer 是模型可见工具（如 dsh-tool-bash）， 但也可以是别的插件。

两个容易忽略的细则。第一，角色通常分包，但不强制：当两个角色会一起演进时， 一个包可以兼任多角色——dsh-llm 同时拥有 LLM 能力的 Service Definition（ctx.llm） 和它的 Consumer（流式调用逻辑）；但只占一个角色不构成 seam，seam 这个词永远指完整切口。 第二，词汇类型归 Definition 所有：request、spec、result、事件名这些跨包共享的类型 定义在 Definition 包里，provider 和 consumer 都 import 它，谁也不自己另写一份。

为什么不是 interface

Cordis 的服务发现靠声明合并：包里写 declare module '@deepseek-ai/cordis' { interface Context { shell: ShellExecutor } }，ctx.shell 这个键才存在。TypeScript interface 表达不了「我注册了一个服务键」，也表达不了 effect 作用域与 dispose。所以 Definition 一定是 Service 的子类——它既是类型，也是运行时对象。

11.2 三角色关系图

把依赖方向画出来，模式的核心一目了然：两侧都指向中间，两侧互不相识。 Provider 子类化 Definition 的抽象服务；Consumer 注入 Definition 的 ctx.<key>。 从 Provider 到 Consumer 没有任何一条边——这正是「可替换」的来源。

图里那条红色虚线是审查 PR 时最值得盯的一条边。如果你发现 tool-bash 直接 import 了 dsh-bash-local，或者 bash-local 反过来 import 了某个工具包， seam 就裂了——换 provider 的自由立刻消失。

11.3 范本：dsh-shell 家族

仓库自己指定的范本是 packages/shell/。packages/shell/shell/README.md 开头的角色表：

包角色职责
@deepseek-ai/dsh-shellService Definition抽象 ShellExecutor + 词汇类型（ShellExecRequest / ShellExecSpec / ShellRunResult）
@deepseek-ai/dsh-bash-localProvider本机子进程实现
@deepseek-ai/dsh-bash-sandboxProvider沿用 bash-local 的机制，但每次 spawn 前经 ctx.sandbox 包装约束
@deepseek-ai/dsh-pwsh-localProviderWindows PowerShell 家族的本机实现
@deepseek-ai/dsh-tool-bashConsumer模型可见的 bash 工具，建在 ctx.shell 上
@deepseek-ai/dsh-tool-pwshConsumer模型可见的 pwsh 工具

读这个范本时注意三处「Definition 拥有什么」的细节，它们示范了词汇归谁所有：

  • 能力事实 sandboxMode。基类上它默认 undefined（「这个执行器不沙箱化」）； bash-sandbox 挂载时报告约束模式。tool-bash 在注册时读这个事实， 决定要不要给模型暴露 sandbox_permissions 升级参数——探测能力，不 import provider。 一个容器化或远端执行器以同样方式接入，工具层一行不改。
  • SHELL_SETTINGS_NAMESPACE（值为 bash）由 Definition 导出， 因为它命名的是能力而不是某个实现。host 恰好组装一个 ctx.shell provider ——Windows 层把 POSIX 行换成 pwsh 行，同时挂两个会在重复服务注册上失败——所以各家 provider 都注册这同一个命名空间而永不冲突，一份 settings.yaml 跨平台仍然可解析。
  • 渲染契约 parseExitStatus。[exit code: N] / [killed by signal: X] 标记的解析函数放在 Definition 包里， 让 tool-bash 和 tool-pwsh 两个 Consumer 永远不会在标记格式上漂移。
关键点

Definition 拥有的不只是抽象方法：能力事实、设置命名空间、跨实现共享的解析契约、事件词汇，全都归它。 判断一个类型该放哪个包，问一句「它是能力的一部分，还是某个实现的一部分」就够了。

11.4 换一个 provider，搬走整个执行世界

单个 seam 的可替换性已经很有用，但 dsh 真正的产品级威力来自成组的 seam 共享同一个执行世界。 回顾 docs/capability-seams.md 里的两条边：fs-e2b 与 subprocess-e2b 都注入 ctx.e2b——它们不是两个孤立的 provider，而是同一个远端 Linux 世界的两张本地面孔。

谁在消费 ctx.subprocess？bash 执行器（bash-local、bash-sandbox）、 PTY 后端（terminal-bash）、LSP 宿主（lsp-stdio）、三个进程外子代理后端 （subagent-acp、subagent-codex、subagent-claude-code）。 谁在消费 ctx.fs？文件工具 tool-fs。这意味着：把 fs-local 换成 fs-e2b、把 subprocess-local 换成 subprocess-e2b，Bash、终端、LSP、文件读写就一起搬进了远端沙箱—— 没有一个工具包需要改代码，也没有任何 provider 分叉出「E2B 专用版工具」。

11.5 扩展插件依赖 Definition，从不 import provider

这条规则不仅适用于工具包，也适用于所有想搭在能力之上的扩展插件。想给 bash 结果做审计？ 监听 seam 的事件、注入 seam 的服务，别去 import dsh-bash-local。 想在每组 provider 之上加行为？写成对 Definition 的消费，让所有 provider 免费获得。

更进一步：dsh-agent-loop 本身也是可换的。在 docs/capability-seams.md 的表里，ctx.agentLoop 的角色是 bundle——「唯一的具体循环插件； 扩展包依赖 dsh-agent 的事件和服务，而不是依赖这个包」。turn/step 循环是产品 API 脊柱的一部分 （改它要更新 docs/architecture.md），但从插件体系的角度看，它只是组装时的一个选择： 扩展从不直接耦合循环实现，而是挂在 agent/pre-step、tools/* 这些文档化的扩展点上。第 7 章你学的所有拦截点，就是这种解耦的受益面。

由此得到一张依赖方向的速查表：

写这种代码可以依赖禁止依赖
新 providerDefinition 包（类型 + 基类）其他 provider、Consumer 包
新 Consumer（工具、桥接）Definition 包的 ctx.<key> 与词汇任何具体 provider
能力之上的扩展插件seam 的事件与服务（如 fs/* 事件闸门）seam 的具体实现包
循环行为扩展dsh-agent 事件与服务、文档化扩展点dsh-agent-loop 包本身

11.6 查图：docs/capability-seams.md 全景

你不需要背下 150 个包的依赖关系——仓库已经替你生成了全图。 docs/capability-seams.md 由 scripts/gen-doc-graphs.ts 生成 （本地跑 pnpm run gen-doc-graphs 重新生成），文件头写着 do not edit by hand。 当前快照收录 56 个 ctx.* 服务，其中 26 个标记为 seam， 其余是 core（脊柱服务，如 ctx.sessions、ctx.tools）或 bundle（组装点，如 ctx.agentLoop）。

表格的每一行长这样（以 ctx.fs 为例），七列的读法：

列含义ctx.fs 行的内容
ctx key服务键与一句话职责ctx.fs Filesystem provider seam
Roleseam / core / bundleseam
OwnerDefinition 所在包fs（packages/fs/fs）
Implementations已知 provider 包fs-local、fs-sandbox、fs-e2b
Direct consumers直接消费服务的包tool-fs
Companion plugins不走服务注入、通过事件闸门参与的伴生插件fs-observation-policy
Note这一行的设计要点fs-sandbox 按共享沙箱模式围栏变更；观测策略经 fs/* 事件闸门参与

三种典型查法：

  • 「这个 ctx.foo 是谁家的？」——按 ctx key 列扫。 Owner 列直接给出 Definition 包路径；表上方还有一张 mermaid 图， pkg_* --> svc_* 边是「谁实现/注入谁」，svc_* --> pkg_* 边是「谁消费谁」。
  • 「给这个能力加实现要动哪些包？」——看 Owner 与 Implementations。 你只写一个新 provider 包，注册到同一个服务键上；Owner 与所有 Consumer 都不用动。
  • 「这个插件事先没注入服务，凭什么参与？」——查 Companion plugins 列与图里的 虚线边（svc_fs -. event gate .-> pkg_fs_observation_policy）。 伴生插件走事件闸门而非方法注入，这是第 13 章的主角。

注意这张表的生成是带完整性守卫的：角色分类写在生成脚本里，新服务如果漏了 implementation/consumer 归类，doc-sync 门禁会失败。所以它是可以当真话引用的活文档， 不是手维护、随时过期的那种 README。

11.7 实战清单：加一个能力 = 设计全三角色

把模式收拢成可执行的清单。假设需求是「给 dsh 加一个截图能力」，按三角色逐项设计：

  1. Definition 包 dsh-screenshot：一个 Cordis Service 子类 （ctx.screenshot），词汇类型（request / spec / result），以及任何跨实现共享的事实与 错误码。想清楚它是抽象类（单 provider，像 ShellExecutor）还是命名注册表 （多 provider 并存，像 ctx.web 的 search/fetch、ctx.subagents 的七种后端）。
  2. 至少一个 provider（如 screenshot-local），子类化或注册实现； 部署差异化的参数全部进它的 Config（由 cordis.yml 校验），不写死 DEFAULT_*。
  3. 至少一个 Consumer（如 tool-screenshot），注入 inject: ['tools', 'screenshot', 'systemPrompt']，只依赖词汇类型编程； 渲染意图（generic / terminal / diff / locations） 在设计时一次定好。
  4. 检查事件面：有模型可见的输入就要有 SessionEvent（model-visible ⟺ logged， 第 4 章的不变量）；有伴生策略就考虑事件闸门而不是再立一个服务。
  5. 回填全图：让 gen-doc-graphs 把新服务收录进 docs/capability-seams.md，同 PR 更新组 README 的包/ctx 键表。

这份清单的每一项都对应仓库里一条硬约定：seam 完整性、Config 可配置、misconfiguration fails loud、 文档随代码走。第 24 章会把这份清单再走一遍 cookbook 级的实操。

11.8 本章回顾

  • capability seam = 可替换能力的完整切口：Service Definition（Cordis Service 子类，拥有 ctx.<key> 与词汇类型）+ Provider + Consumer，缺一不成 seam。
  • 依赖方向：两侧都指向 Definition，Provider 与 Consumer 互不 import；探测能力用能力事实（如 sandboxMode），不用类型引用。
  • dsh-shell 是范本：shell（Definition）/ bash-local、bash-sandbox、pwsh-local（Provider）/ tool-bash、tool-pwsh（Consumer）。
  • fs 与 subprocess 共享一个执行世界：换 fs-e2b + subprocess-e2b，Bash、PTY、LSP、文件工具一起搬进远端沙箱。
  • 扩展插件依赖 Definition 与事件，不依赖具体 provider；连 dsh-agent-loop 也是可换的 bundle 角色。
  • docs/capability-seams.md 是脚本生成的活图（56 个服务、26 个 seam），查 owner / implementations / consumers / companion 四列即可定位任何能力的结构。
  • 加能力 = 同时设计三角色 + 事件面 + 回填全图。
常见坑
  • 把 seam 当成「接口」：用 TypeScript interface 写 Definition，ctx.<key> 根本不存在，声明合并挂不上。
  • Consumer import 具体 provider（或反过来）——seam 裂开，换实现自由消失；探测 provider 特性请用能力事实。
  • 词汇类型放错包：request/result 放在 provider 里，第二个 provider 出现时就得抄一份。
  • 只写一个插件就宣称「加了一个能力」——一个角色不是 seam；至少把三角色的边界想清楚、写进组 README。
  • 手改 docs/capability-seams.md——它是生成物，改 scripts/gen-doc-graphs.ts 再重新生成。
