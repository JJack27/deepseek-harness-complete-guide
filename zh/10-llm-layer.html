LLM 能力层：adapter seam 与流式词汇

前两章的尽头都是同一个调用：ctx.llm.stream(request)。 这一章讲它背后的世界 —— packages/llm/ 如何定义一套与供应商无关的 消息和流式词汇、adapter 如何像插头一样换进换出、流式的 chunk 怎么变成日志里的 assistant/message，以及换一家模型供应商到底要动多少代码（答案：一个新 adapter 插件）。

学习目标
  • 说出 ctx.llm 的双重身份：adapter 注册表 + 统一的流式调用 API
  • 复述消息词汇：Message、content blocks、StreamChunk 协议与 BlockAssembler
  • 描述一次流式回复如何经 llm/stream → assistant/chunk* → assistant/message 进日志
  • 说出 llm 组五个包的分工：llm / llm-deepseek / llm-pi-ai / llm-retry / token-meter
  • 解释 ctx.agentDefaultModel 与 prepareCall() / request/header 的关系

10.1 ctx.llm：一个 adapter seam

packages/llm/llm 提供的 LlmRuntime 服务挂在 ctx.llm 上。 它是第 11 章要正式命名的 capability seam 在 LLM 领域的实例： 一个供应商中立的消息与流式词汇（所有包共说的语言），加上一个 adapter 注册表（可替换的实现）。

核心注册 API 只有一个： 

const handle = ctx.llm.registerAdapter(['deepseek-official'], adapter)
// all-or-nothing：一个 provider 路由同时只能有一个 adapter（重名抛 DUPLICATE_ADAPTER）
// handle.dispose() 注销；handle.replace(providers) 原子换路由，无空窗

请求通过 GenerateOptions.provider 选择 adapter；model 由 adapter 自己解释 （目录是建议性的，未列出的模型 id 也原样通过）。配套的查询面： listProviders() / listModels(provider) / resolveModelInfo(provider, model)（拿精确模型的上下文窗口、输出默认、 reasoning 档位）—— 它们是给选择器 UI 用的发现面，不是路由白名单。

换模型供应商 = 写一个新 adapter 插件（继承 LlmAdapter，实现 stream()，可选实现元数据方法），注册几条 provider 路由，完毕。 loop、session、工具、UI 一行不改 —— 这正是第 3 章组装与第 11 章 seam 的兑现处。

10.2 消息与流式词汇

docs/subsystems/llm-streaming.md 是这层的字典。三层词汇从粗到细：

  • Message：带稳定 MessageId、角色（system/user/assistant）、 内容块数组的不可变值。模型产出的 assistant 消息在 source 里携带 provider、model 与可选的 adapter 私有 replayState。 构造函数（createUserMessage / createAssistantMessage / createToolResultMessage） 产出深冻结的值 —— 消息从诞生起就是不可变的。
  • content blocks：消息内容是类型化块的数组 —— text、 reasoning（思考，区别于可见文本）、tool-call（带 CallId、 名字、原始 JSON 参数串）、tool-result（嵌套内容 + isError）。 块联合来自可合并扩展的 ContentBlockMap —— 新模态（图像等）只有在 adapter/UI/压缩/回放路径都支持时才进核心表。
  • StreamChunk 原始流协议：adapter 吐的不是消息，是 block-start / text-delta / reasoning-delta / tool-call-delta / block-end / usage / finish 七种原始块（usage 先于 finish）。每个流只有一个终结 finish； 操作性失败以 {kind:'error'|'aborted', failure} 的 finish 收场， 不跨流 API 抛异常 —— 这是服务边界的一贯约定。

把 chunk 拼回消息的是 BlockAssembler —— 全仓库唯一一份拼装实现， agent loop 和它共享。这个「原始 chunk 协议 + 共享拼装器」的设计意味着： 任何新 adapter 只要会说 chunk 语言，UI 的逐字渲染、日志的 chunk 保真、 消息的定稿就全部自动工作。

10.3 流式如何进日志

把第 7 章的调用链放大到 LLM 层（agent.ts 的 step()）：

三个要点：

  • 双轨消费：loop 一边把每个 chunk 以 assistant/chunk 落日志 （保住流式与 UI 回放的保真度），一边喂给 BlockAssembler 攒块。 只有流正常走到 finish，才组装出一条 assistant/message 事件 —— 它是唯一参与 deriveMessages() 的 assistant 表面。
  • 失败不产生 message：终结 finish 是 error/aborted 时，先经 agent/request-error waterfall（第 7 章：默认保留原错误，返回 {kind:'retry'} 则同一步内重发）。失败尝试的 chunk 留在日志里， 但永远不会被组装成 message，模型历史不受污染。哪怕一次 max-tokens 截断的空内容回复， 也会有一条 message 事件（记录 usage 和空的 chunk 引用列表）。
  • llm/stream 是 waterfall：缓存、日志、路由类插件包在这里； 监听器必须调 next()。请求对象由 loop 深冻结并打上 sessionId 标记（markAgentLoopRequest()）， 第 7 章的 invariant 就是在这个口上校验「请求 ⟺ 日志推导」一致的。

10.4 llm 组的五个包

包角色要点
dsh-llm 词汇 + 服务 Message / StreamChunk / BlockAssembler / HarnessError 家族；ctx.llm 注册表与流式 API
dsh-llm-deepseek DeepSeek 官方 adapter 独占 deepseek-official 路由；直连 fetch + SSE（eventsource-parser 解帧）； 凭据经 ctx.credentials 读 apiKeyEnv（默认 DEEPSEEK_API_KEY）， baseURL 默认读 DEEPSEEK_BASE_URL 再退公网地址； thinking/reasoningEffort、maxTokens（默认 256000）、空闲读超时等都是配置
dsh-llm-pi-ai 多供应商 adapter 经 @earendil-works/pi-ai 把任意 provider/profile（含 OpenAI 兼容网关、自建端点） 变成配置声明 —— 路由名刻意与官方区分（如 pi-ai 的 deepseek），可与官方 adapter 并存
dsh-llm-retry 重试执行器 不包 ctx.llm.stream()；挂 agent/request-error 按各 provider 的 retryPolicy 退避重试，等待前后落 llm/retry / llm/retry-started durable 事件
dsh-token-meter token 计量 ctx.tokenMeter 从日志逐会话折叠用量（4 字符/token 的固定启发式）， 供压缩等压力敏感插件共享；可选挂出 tokenUsage / contextPressure / contextBreakdown 投影

「重试不包 stream、计量从日志折叠」这两处设计都体现同一条原则： 所有跨边界的可观测事实都以日志为准，进程内的包装只做策略。 另外注意配对关系：llm-retry 消费 adapter 注册时携带的 retryPolicy； token-meter 复用 provider 上报的 usage（assistant/message 里的 usage 字段）， 只在无法对齐时退回启发式估算。

10.5 请求配置：从默认模型到 request/header

一个 agent 的 provider/model 从哪来？入口点位（如 dsh --profile headless、 Host 侧的 ApiProxy）在创建没有会话本地选择的 Agent 时，读 packages/core/agent-default-model 提供的 ctx.agentDefaultModel： 插件配置要求 {provider, model}， currentSelection() 返回当前选择（设置提供方可在其上分层用户选择）， saveSelection() 保存完整用户选择。它不校验目录成员 —— 「这个模型可用吗」由真正开请求的一方诊断。

选定后，配置怎么变成一次请求？第 7 章已经见过 buildRequest() 的骨架，这里补 LLM 侧细节：

  1. agent/request waterfall 提议 LlmCallConfig （provider/model/reasoningEffort/temperature/maxTokens/stop —— 会话级状态，不是随手改的旋钮）。
  2. ctx.llm.prepareCall(config) 做一次精确模型查询：校验显式 effort、 物化 adapter 默认值（哪些字段是默认给的会记在 adapterDefaults 标记里）， 并把当次的 adapter 注册与不可变 retryPolicy 绑成一个一次性 PreparedLlmCall —— 之后 HMR 换 adapter 也不会把 A 家的能力查询和 B 家的请求拼在一起。
  3. loop 把生效配置以 request/header 事件落日志（首条 reason 为 initial/resume，之后仅在实际变化时落 change）， 供应商/模型/上下文窗口变化再落一条 request/context。 下一轮提议会略去被标记为 adapter 默认的字段 —— 换路由后各字段重新解析，不会被旧默认值污染。

于是「模型当时被怎样调用」与「模型当时看到什么」一样，全部可从日志重建。 顺带一提测试通道：真实 API 的 e2e 测试读 DEEPSEEK_API_KEY （可选 DEEPSEEK_BASE_URL），没有 key 时自动跳过 —— 凭据永远不进配置文件， 走 ctx.credentials 的引用式解析。

本章的关键直觉

LLM 层把「供应商差异」压进 adapter 一个点，把「流式事实」压进 chunk/message 两种事件， 把「调用配置」压进 request/header 一条日志。三样都做完，剩下的系统就可以对 「哪个模型、哪家供应商」完全无感。

10.6 本章回顾

  • ctx.llm = 供应商中立词汇 + adapter 注册表；registerAdapter(providers, adapter) 一个 provider 路由一个 adapter，换供应商就是换插件。
  • 词汇三层：Message（不可变、带 id/角色/source）→ content blocks（text/reasoning/tool-call/tool-result，可合并扩展）→ StreamChunk 原始流协议（七种块，唯一 finish 终结，失败也走 finish 不抛异常）。
  • BlockAssembler 是唯一拼装器；chunk 双轨消费：落 assistant/chunk 保真 + 攒块；流终结才落一条 assistant/message，deriveMessages 只认 message。
  • llm 组分工：llm（词汇/服务）、llm-deepseek（deepseek-official 路由）、llm-pi-ai（多供应商）、llm-retry（挂 agent/request-error，落 llm/retry 事件）、token-meter（从日志折叠用量）。
  • ctx.agentDefaultModel 供入口点位读部署默认；prepareCall() 绑定精确模型默认与 retryPolicy；生效配置以 request/header 落日志，adapter 默认字段带标记、换路由重新解析。
  • e2e 测试读 DEEPSEEK_API_KEY / DEEPSEEK_BASE_URL，无 key 自跳过；凭据走 ctx.credentials 引用。
常见误区
  • 以为 adapter 失败会抛异常穿透 —— 不会：一切失败规范化为流的终结 finish（error/aborted），消费者丢弃未完成的块。
  • 把 listModels() 当路由白名单 —— 目录是建议性的发现面，未列出的模型 id 原样通过。
  • 在 llm/stream 监听器里改请求或忘调 next() —— 请求是深冻结的（loop 请求还被 invariant 校验），忘调 next() 短路整条链。
  • 以为重试是包在 stream 外面的重发循环 —— llm-retry 挂 agent/request-error，每个 adapter 调用始终是一次供应商尝试。
  • 以为 request/header 每个 step 都落一条 —— 只在首条（initial/resume）与实际变化（change）时落；采样配置是会话级状态，不是每步旋钮。
