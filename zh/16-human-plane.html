人类协作面：commands、permission、approval、ask-user

上一章的 /compact 已经剧透了本章的核心区分：dsh 里人机交互分属两个平面。 命令平面上的斜杠命令经 ctx.commands 分发，不经模型轮次直接执行； 消息平面上一切要到达模型的内容都必须作为 SessionEvent 落日志。本章走完 interaction 家族的全部服务——命令注册表、one-shot 审批瀑布、permission presets、 结构化提问——再连同 plan-mode、todo、feedback 三个状态插件，把「人如何驾驭一个正在跑的 agent」这件事的完整机制讲清楚。

学习目标
  • 能用命令平面/消息平面的二分法判断任意一种交互「走哪条路、写不写日志、进不进模型历史」
  • 能描述 ctx.commands 的注册与分发契约，包括 command/run/command/done 事件对与 agent 作用域遮蔽
  • 能解释 one-shot 审批瀑布：结果词汇、fail-closed、tools/pre-execute 的 ask 决策如何路由到 ctx.approval
  • 能说出 permission-presets 打包了哪两个机制旋钮、custom 为何只能派生不能选中
  • 能区分 plan-mode 的 logged state 与强制执行：计划模式是软引导，sandbox 与 approval 独立执法
  • 能指出 todo 与 feedback 的两种归宿：会话日志事件 vs Host 侧 sidecar，以及为何都不进模型对话

16.1 两个平面：命令 vs 消息

dsh 的交互服务全部组装在现有契约之上，不改循环。packages/interaction/ 组 README 的第一句就点明了范围：这些是「人类与运行中 agent 协作」的服务与插件—— questions、approvals、permission presets、commands。把它们摆上第 4 章的事件溯源底座， 就得到一条贯穿本章的判断轴：

  • 命令平面：人类输入斜杠命令，ctx.commands.execute(agent, line, signal) 解析并直接运行处理器。不经模型轮次——没有请求、没有 token； 结果由 UI 适配器直接渲染，绝不进入模型历史。但命令生命周期本身是审计对象： 每次已解析的调用在该 agent 的会话上追加 log-only 的 command/run（先铸 commandId）与 command/done（结算时）事件对，没有 turn 包裹它们。
  • 消息平面：任何要发给模型的内容——直接提示、steering、注入的上下文—— 都以表面事件落日志（model-visible ⟺ logged），经第 7 章的 turn/step 循环进入请求。

命令平面「绕过模型但仍在日志里」不是矛盾：日志是审计与回放的唯一权威， 而模型历史是它的一个投影（deriveMessages() 只取表面事件）。命令处理器若确实要 触发模型工作，必须显式使用接收方的 Agent（如 /plan [message] 会经 agent.steer() 提交消息）——那时它就切换到了消息平面，并自己拥有 resulting message 的契约。注册表从不隐式把 rawInput 提交给 agent。

这张二分图也解释了各表面的差异：Web 客户端提供命令适配器；headless、ACP 自动化与 JSON-RPC 不提供——所以 /compact、/feedback 这类命令在那里不存在， 自动压缩照常工作。docs/architecture.md 的「Where new behavior goes」表里对应的一行是： Add a human command → register on ctx.commands; it dispatches without a model turn。

16.2 ctx.commands：命令注册表

dsh-commands 拥有 ctx.commands。注册一个命令就是 register(definition)：小写命令名（字母、数字、_、-）、 描述、可选输入提示、可选 recordInput 策略与可中止的处理器。 recordInput 默认为 true；当一个命令的权威领域事件自己携带载荷时把它设为 false， command/run 就会省略 args 而不是把输入重复记两遍—— /feedback 就是这么做的（文本只存在于 feedback/record 事件里）。

作用域规则沿用第 11 章见过的 host+per-scope 分层：普通 context 的注册是全局的； 挂在 agent.ctx 之下的命令生产者声明自己的 commands 注入、 创建精确的 agent 作用域定义，并遮蔽同名全局定义。同层重名在注册时失败。 注册与移除通知所有 commands/change 观察者，让活动适配器刷新发现列表。 parseCommand() 只认「第 0 字节是斜杠 + 小写名 + 空白或结尾」，名字之后的 每个字节都是 rawInput——命令特定的语法归各命令自己解析。

分发的结算契约：处理器返回 success 或 error 加可选 UI 文本； 成功时还可返回 sourceEventSeq 指向同会话中更早的一条非命令事件， 当那条领域事件拥有更丰富的展示时（如 /compact 指向 compaction/summary）。 生命周期不变量要求这个引用是先前的非命令事件。未知命令或非法语法返回 undefined，不产生任何日志（admission miss 不记账）；随船适配器对未知斜杠输入 直接拒绝，而不是把它变成发给模型的提示。

16.3 user-approval：one-shot 审批瀑布

dsh-user-approval 定义通道中立的 one-shot 审批 seam （ctx.approval）。一次 approval.request(req) 返回四种结局之一： allowed-once、rejected、cancelled、unavailable—— 注意词汇里只有 once：没有 allow-always、没有记忆规则、没有撤销存储， 一次授权只覆盖被请求的那一个动作。应答者缺席或失败时fail closed。 每个请求必须属于一个打开的 agent turn；服务追加成对的 approval/asked 与 approval/decided 审计记录（log-only），模型看到的只是最终的请求方工具结果。

应答者是 approval/request 瀑布监听器——第 2 章的瀑布语义在这里是硬约束： 要么返回一个结局为本 agent 作答，要么调用 next() 委托， 静默返回会掐断整条链。agent 作用域的监听器只收到该 agent 的请求；每个部署只组装一个 终端应答者，因为兄弟监听器的顺序不是策略优先级机制。ACP 自动化桥为它拥有的会话 提供机器决策的 one-shot 应答者。

与工具管道的接驳点在第 8 章：tools/pre-execute 决策联合包含 {kind:'ask', reason?}——注册表把它路由给 ctx.approval； seam 未挂载时降级为 deny（注册表对 approval 是机会主义消费 ctx.get('approval')，无静态注入，部署没有它也保持 ask→deny 语义）。 沙箱化的 bash 工具在升级重试时也走这个 seam。会话级策略只有两档： ApprovalPolicy 为 ask 或 never，有效值是最后一条 approval/policy 事件（回退到配置），setApprovalPolicy() 是写路径； never 在交互分发之前就拒绝。首次请求与每次有效策略变化会向模型追加一条 简短的运行时上下文快照（例如 never 下明确告诉模型不要再请求沙箱升级）。

为什么只有 one-shot

「记住我的选择」需要授权存储、失效与撤销语义——那是另一个尚未存在的领域。 one-shot 让审计语义保持最小：每次危险动作对应一次明确的决定， approval/asked/approval/decided 成对可回放。 要减少打扰，用 16.4 的 preset 切换整组策略，而不是让单次授权泛化。

16.4 permission-presets：面向用户的开关组合

sandbox/mode 与 approval/policy 是两个独立的机制旋钮； dsh-permission-presets（ctx.permissionPresets）把它们打包成 用户能理解的预设。每个配置的预设名捆绑一组值，随船默认是 workspace-write（workspace-write + ask）和 danger-full-access（danger-full-access + never）。 UI 适配器可以把表渲染成一个选择器，而沙箱执行与审批继续消费各自的旋钮—— preset 是展示与用户意图层，不是新的执行机制。

set(session, name) 先追加 log-only 的 permissionPresets/preset 事件 记录用户的选择，再在有效值变化时调用各旋钮的 setter——选择事件在前，保住了 「预设共享同一捆绑时的用户意图」；净零选择什么都不追加。current(events) 优先返回仍然匹配的已记录选择，否则第一个匹配的表项，都不匹配时返回 custom： custom 只能派生、不能被选中——用户可以切换离开一个 不再匹配的旋钮组合，但不能以它为目标持久化。名为 custom 的表项在加载时抛错。

会话创建时固定（pin）三件事：permissionPresets/preset、sandbox/mode、 approval/policy 落进该会话，之后的默认值变化不再改动既有会话； 恢复的 seed（包括显式空 seed）保留其有效权限。该服务要求一个受限的 ctx.shell 执行器与 ctx.approval——组合不匹配任何预设且未给 defaultPreset 时加载失败。两个可选子件随注册表激活：会话投影单元 （把三个全值旋钮事件折叠成选择视图）与 /permissionPresets 命令 （裸调用报告当前预设与表，带参切换）。

16.5 user-questions 与 tool-ask-user：模型向用户提问

到目前为止是人类发起（命令）与人类批准（审批）；dsh-user-questions 补上反方向：模型暂停工作、向人类要一个决定。Service Definition ctx.userQuestions 只有两个动词：UI 侧 registerProvider(provider) （一个 context 只允许一个活跃 provider，重复注册抛 DUPLICATE_PROVIDER）， 与 ask(request)（等待活跃 provider 的回答）。词汇是问题表单的形状： questions: [{ id, question, detail?, header?, options?, multiSelect? }]， 回答是 { answers: [{ id, selected, custom? }] }——单选时 custom 覆盖 selected，多选时补充它。循环不变：一个工具调用 await 一个 promise， 工具结果照常回到 agent 循环；等待期间不消耗任何 token。

Consumer 包 dsh-tool-ask-user 把它暴露为模型可见的 ask_user_question 工具：接受同样的 questions 数组（推荐选项放第一位并在 label 后加 (Recommended)），调用 ctx.userQuestions.ask()， 返回紧凑 JSON。它不渲染 UI、不知道输入怎么收集——只翻译参数与结果。

两处边界设计值得记下。其一，运行时拥有的子代理不能问用户： 请求带 agent 时，ask() 通过活跃 AgentRegistry 认证 确切的运行时根身份；被另一个 live agent 拥有的子代理被拒（工具侧表现为 DELEGATED_CALLER 错误，指示把未决问题写进子代理的最终结果）—— durable lineage 不是权威：一个带历史委派深度的会话被恢复为新的运行时根后可以正常提问。 这与第 14 章「lineage 是数据、不是可见性」一脉相承。其二， presentation intent：问题的 intent 字段声明这是一个已知种类的决定 （如 plan-review），认识的 UI 可以把它渲染成评审卡片，不认识的 UI 渲染通用选项表， 两种情况下调用者读到同样的回答字段。

16.6 plan-mode：logged state，不是特权模式

dsh-plan-mode 是双平面协作的最佳样本。它的持久状态是一条 log-only、 全值替换的 plan/mode（{ active: boolean }）SessionEvent： foldPlanMode(events) 返回最后记录值或 false，所以 resume、fork、 compaction 都直接从会话日志恢复计划状态，UI 通过 session/event 观察翻转。 计划模式是记录在日志里的状态，不是进程的特权模式——不存在「进入 plan mode 后运行时获得特殊权限」这回事。

对模型，激活的计划模式渲染配置的 section 文本到系统提示（prompt order 50）； 对人类，它经 ctx.commands 注册 /plan [message]（裸调用选择计划模式； 非 off 的非空参数先选择模式、再经 agent.steer() 把消息作为 普通日志 user 消息提交——这是命令处理器显式切换到消息平面的例子）与 /plan off （直接退出，不发模型输入）。退出评审走始终注册的 exit_plan_mode 工具： 只有激活状态下可执行，且必须经 ctx.userQuestions 拿到用户的确切批准 （问题带 plan-review intent，Approve 是批准标签）； 用户关闭评审转而说话时，模型被告知留在计划模式等待消息。 工具 schema 跨状态稳定，模式切换不改工具目录。

最容易误解的一点：计划模式是软引导。它引导模型先探索设计再交计划， 但不强制任何限制——sandbox 模式与审批策略独立执法、不读写计划状态。需要硬约束的部署 应配置 sandbox 与 approval（16.3、16.4），而不是指望 section 文本。 会话投影方面，挂载 ctx.sessionProjections 时它注册 plan 单元， 折叠 command/run（名为 plan）与 plan/mode 两种事件， view 派生 { active, pending }——pending 是纯回放量， 主机重启、其他标签页、冷读都能从日志单独恢复它。

16.7 todo 与 feedback：计划的两种归宿

dsh-tool-todo 注册模型可见的 todo_write 工具，设计极度克制： 整表替换是唯一操作——模型每次调用发送完整任务列表 （{ content, status }，status 为 pending/in_progress/completed）， 没有部分更新、没有逐项编辑。每次调用经 agent.session.append('todo/write', { todos }) 追加一条全量快照事件；当前列表就是最新那条（回放时 last-write-wins）。 列表属于唯一调用它的 agent 会话——没有 subagent/共享/swarm 作用域， 非 agent 调用者直接被拒。allowParallelInProgress 是必填配置：并发活动任务是否 合法是部署的选择，不是固定规则；但 durable-log 不变量不跟随它收紧（并行时期写的日志 必须仍能在收紧后回放）。挂载投影注册表时，todos 单元在每条 turn/start 清空——standing plan 只活到下一个 turn 开始，turn/end 保留完成的清单。

feedback 家族是「记录人类反馈」的两个刻意分离的契约。命令侧： dsh-command-feedback 的 recordFeedback(session, text) 追加一条 log-only 的 feedback/record 事件，/feedback <text> 命令只是 这个写路径的人类入口（因此 recordInput: false，命令配对事件不重复记录文本）。 反馈是触发无关的：别的 UI、hook、host 集成可以直接调用 producer。文本不做任何解析、 截断或合并；日志是追加式的，没有撤回。dsh-session-telemetry-otel 可选地观察 这个事件来释放 feedback-gated 的遥测前缀。消息侧：dsh-message-feedback （ctx.messageFeedback）是可编辑messageFeedback.list/put/delete Remote 契约，带 ifVersion compare-and-set 与按消息的版本冲突语义—— 它不是 Session 事件、不是投影、不触发遥测移交。

关键点

四种人类输入、四种归宿：斜杠命令 → 命令平面直接执行 + log-only 生命周期； 审批/提问 → 工具调用内的 one-shot 决定，审计对 log-only，模型只见工具结果； 计划 → log-only 的 plan/mode 状态 + 系统提示软引导； 反馈 → log-only 的 feedback/record 或 Host sidecar。 没有一种把 UI 交互本身塞进模型历史。

16.8 本章回顾

  • 双平面：命令平面经 ctx.commands 分发，不经模型轮次、结果不进模型历史，但记录 log-only 的 command/run/command/done；消息平面一切模型可见内容都以表面事件落日志。
  • 命令注册表：全局注册 + agent.ctx 作用域遮蔽，同层重名失败；recordInput: false 让权威领域事件独占载荷；未知斜杠输入被随船适配器拒绝而非变成提示。
  • 审批是 one-shot：allowed-once | rejected | cancelled | unavailable，授权只覆盖被请求的动作；应答者瀑布要么作答要么 next()；缺席/失败 fail closed；tools/pre-execute 的 ask 决策路由到 ctx.approval，未挂载则降级 deny。
  • permission-presets 打包 sandbox/mode + approval/policy（默认 workspace-write/danger-full-access）；custom 只能派生；会话创建时 pin 三事件。
  • ctx.userQuestions 单 provider；ask_user_question 是 Consumer；被 live 父代理拥有的子代理被拒（DELEGATED_CALLER），durable lineage 不是权威；intent（如 plan-review）只改展示不改回答字段。
  • plan-mode 是 logged state：plan/mode 全值替换事件 + 系统提示软引导 + exit_plan_mode 经确切批准退出；强制限制由 sandbox 与 approval 独立执行。
  • todo_write 整表替换、单 owner、todo/write 全量快照事件、投影在 turn/start 清空；feedback 分两路：feedback/record log-only 事件（命令可触发但触发无关）与 ctx.messageFeedback sidecar（带 CAS 的 Host Remote）。
常见坑
  • 以为斜杠命令的结果会进入模型上下文——不会；命令处理器要触发模型工作必须显式使用 Agent 并拥有 resulting message 契约。
  • 在审批瀑布监听器里返回 undefined 而不调 next()——整条链被掐断；瀑布监听器必须委托。
  • 期待 allow-always 或「记住我的选择」——词汇里只有 allowed-once；减少打扰用 preset 切策略。
  • 以为没挂 approval seam 时 ask 会放行或报错给用户——它降级为 deny，fail closed 是刻意的。
  • 把 plan mode 当强制边界——它是软引导；硬约束属于 sandbox/approval，两者不读写计划状态。
  • 给 todo_write 设计部分更新 API——整表替换是唯一操作，扩展 item 形状（id、嵌套）会在校验中 fail loud。
  • 把 message-feedback 当 Session 事件或投影——它是 storage-domain sidecar，与不可变的 feedback/record 事件是两个契约。
