委派与子代理

一个 agent 忙不过来时，dsh 的答案是委派：把任务交给子代理（subagent）， 各自拥有独立会话与上下文。ctx.subagents 是全仓最热闹的一条 seam—— 与 bash 只许一个 executor 不同，它是一个多 provider 注册表： 进程内分叉、全新进程内子代理、进程外 ACP、真正的 Codex 与 Claude Code、进程外完整 dsh， 七种后端并存于同一个契约之下。本章讲清 provider 谱系、三个模型面工具族、 记在 SessionHeader 里的血统（lineage）与深度上限，以及「每轮换新代理」的 Ralph 循环。

学习目标
  • 能解释 ctx.subagents 为什么是命名注册表（多 provider 共存）而非单服务 seam，并列出七种 provider 的差异
  • 能区分 fork 与 spawn 的 seed 边界，说出 in-process-driver 承担了哪些共享机制
  • 能按职责拆分 tool-subagent / tool-subagent-control / tool-subagent-report 三个工具族
  • 能说明 parentSession + delegationDepth 如何构成血统，以及「血统是数据不是可见性」的含义
  • 能描述 Ralph 循环的策略：全新子代理 + 有界结构化 handoff + 共享工作区当长期记忆

14.1 ctx.subagents：一个接口，多种后端

docs/subsystems/subagent.md 开篇就点出这条 seam 的特殊性：它允许多个 provider 实现在同一上下文里按名共存（ctx.subagents 注册表），而 bash 只允许一个 executor。 注册表的形态学的是 LLM 适配器注册表（第 10 章 ctx.llm），不是单服务的 bash executor。 Service Definition 是 dsh-subagent：它拥有 provider 注册、共享的请求/结果契约、 持久 descriptor，以及（可选启用的）continuable 子代理编排。

provider 侧的核心契约是 start(request): Promise<SubagentRun>—— 所有权转移的边界。fulfill 之前 provider 拥有启动过程，任何失败都必须取消、回滚、 静默掉未发布的资源；fulfill 之后调用方拥有 run，必须在所有路径上 dispose()。 SubagentRun.result resolve 成 { output, structured?, stopReason }： 子代理层面的失败以非 completed 的 reason resolve，只有 seam 表达不了的基础设施故障才 reject。

provider 用静态 capabilities 广告四个启动期能力——outputSchema（强制结构化最终结果）、 depthLimit（强制 maxDepth）、toolFilter（子代理工具限制）、 persona（子代理人格）。服务在子代理创建之前校验请求与能力， 缺能力就响亮拒绝（UNSUPPORTED_CAPABILITY），绝不「先收下再装没看见」。

14.2 provider 谱系：七种后端

provider（注册名）子代理跑在哪看得到父会话吗
subagent-spawn-in-process（spawn）当前进程内全新 Agent看不到：空对话起步，但继承 cwd、血统与模型
subagent-fork-in-process（fork）当前进程内看到已完成的轮（seed 是父日志截至最后一个 turn/end 的连续前缀）
subagent-acp（acp）全新子进程，作为 ACP 客户端驱动任意 Agent Client Protocol 代理看不到
subagent-codex（codex）子进程里的 codex app-server --stdio，每次一个临时线程看不到
subagent-claude-code（claude-code）官方 Claude Agent SDK 起的 claude 可执行文件看不到
subagent-dsh-sdk子进程里的完整 dsh 运行时（dsh-jsonrpc-agent bin），经 TypeScript SDK 走 stdio JSON-RPC看不到
另有一个不出现在注册表里的共享件：subagent-in-process-driver——spawn 与 fork 共用的运行驱动（下一节）。

fork 的 seed 边界是这条家族里最精巧的一处。父代理发起委派时，它当前的 tool-calling 轮还没结束：日志里有 assistant 的工具调用，却没有配对的工具结果，也没有 turn/end。 直接照抄原始日志会给子代理一份不平衡的非法会话。fork 因此只取「截至最后一个 turn/end 的连续前缀」——子代理看到所有已完成的轮、完全看不到进行中的轮； 父代理一个轮都没完成时 seed 为空，fork 退化为 spawn。seed 只转移对话历史： 子代理仍拿到全新的扁平注册 scope，不继承父代理的工具限制或权限。

两个进程内 provider 的其余机制全部收在 subagent-in-process-driver 的 startInProcessRun 里：深度校验 → ctx.agents.create（带必需的取消信号） → 未发布 setup 窗口里装 persona / 工具过滤 / 结构化输出运行时 → 发布子代理 → child.followup(prompt) + child.whenIdle() 驱动一个任务 → 读子代理自己的输出（最后一条非空 assistant 消息，或累计 assistant 文本）。 深度检查也在驱动内部：父深度 + 1 写进子代理 header（下一节）。

三个进程外后端（acp、codex、claude-code）都经 ctx.subprocess spawn 子进程 （第 12 章的底座），工作目录取委派父会话的 cwd——绝不取服务器进程自己的 cwd， 因为一个服务器进程服务多个工作区的会话。dsh-sdk 后端则让子代理是一个 完整的对等 harness：自己的 cordis.yml 组合、会话持久化、模型路由与工具； 它与 ACP 后端的差别在线缆与子代理契约——ACP 驱动「任意 ACP 代理」，SDK 驱动「特指 harness 运行时」。

委派出去的权限边界

两条进程内委派路径都在委派边界上固定子代理的权限范围：快照父会话的显式沙箱 覆盖，并把子代理的审批策略钉在 'never'（只要审批能力在组合里）——被委派的子代理 只在继承的沙箱范围内行动，任何 ask（例如 sandbox_permissions 升级）都被确定性拒绝， 而不是等一个没人在看的提示。这些值以 source: 'delegation' 的 sandbox/mode / approval/policy 事件写进子代理自己的日志—— 子代理的有效策略凭自己的日志即可重建。子代理还会收到一条 subagent:delegation 运行时上下文陈述：范围已固定，需要更大权限时在回复里说明限制，而不是重试。

14.3 工具族：发起、控制、报告

模型面由三个包分担，方向各不相同：

包方向工具与要点
tool-subagent父 → 子（发起）每个插件实例把一个 provider 绑到一个工具名（默认 subagent）；模型拿不到 provider 选择器，要暴露第二种传输就再挂一个改名实例。前台调用等 run.result 并总在返回前 run.dispose()；backgroundMode 选 one-shot（后台时注册普通 Task，返回 jobId）或 continuable（默认后台，返回持久 childId）。maxDepth 默认 3（0 禁止委派）。
tool-subagent-control父 → 子（续话）全局注册一次的 send_message / interrupt_agent / list_agents（列表工具经可分离的 ./list-agents 插件）。消息成为子代理的下一个 FIFO 轮（Agent.followup()），不能重定向进行中的轮；interrupt_agent 只停当前轮（keepInbox），排队的消息留着、已发布的后代继续跑。
tool-subagent-report子 → 父（报告）只在 continuable 子代理 scope 内注册的 report 工具——经 registerContinuableSetup 贡献安装，根会话、一次性子代理、远端 provider、兄弟 scope 都看不到它。它不收收件人参数：exec.agent 就是发送者凭证，服务从子代理持久的 parentSession 推导唯一收件人。scope 内注册刻意活过子代理的 toolFilter——委派白名单删不掉唯一的回程通道。

continuable 子代理的世界里还有一个「结算通知」：当子代理的驻留（Activation）结束， 编排管理器会在父代理自己的轮流里告诉它「子代理做完了它要做的全部」——附上停止原因与最终 assistant 内容。这条通知无条件投递：不取决于子代理有没有调过 report， 因为最需要交代收场的结局（token 耗尽、模型失败、取消、拆除）恰恰是子代理没来得及选择的时候。

14.4 血统：parentSession 与 delegationDepth

子代理不是无根的：本地 run 在发布子 agent/会话时，把 request.parent.session.id 记进子会话 header 的 parentSession 字段；进程内驱动把父深度 + 1 写进子会话 header 的 delegationDepth。这两个字段是 durable 的——随会话持久化， 冷恢复后依然成立。

深度语义有三条要记牢。第一，持久 header 权威且单调：运行时选项可以加深计数、 永远不能调浅——恢复的子代理不能被重新计为顶层。第二，上限在每次 start 时检查： 工具在 cap 处仍然可见（模型看得到工具存在），但被拒的派生以错误 tool result 返回； maxDepth 设 0 即禁止委派。进程外 provider 可以配 'provider-managed' ——预算属于子代理那侧的 harness，父侧不发 cap。第三，血统是数据，不是可见性： inheritsParentContext 只描述子代理是否看得到父会话完成的对话历史 （fork 看到、spawn 与进程外 provider 看不到），不表示继承工具、服务或权限； parentSession 也不给兄弟之间任何互相可见性——它服务的是投递授权（谁可以向这个子代理发消息）、 报告路由（report 送给谁）与 list_agents 的目录遍历。

14.5 continuable 子代理与 Activation

一次性（one-shot）委派是「问一次、拿一个结果」；continuable 子代理是持久对话对象： 一个持久 Session，加至多一个进程本地的 Activation——后者不是请求、 不是 Task、不是结果边界，只是「重建出的子 Agent 的一次驻留纪元」。Agent 收件箱是唯一的轮队列： 每条续话（send_message、唤醒式 report、结算通知）都经 Agent.followup() 成为下一个 FIFO 轮，绝不转向进行中的轮。驻留中的子代理直接收件（唤醒等待中的 Activation）； 不在驻留中的子代理从持久 Session 冷恢复——重建输入是日志里的 subagent/descriptor 事件（记录 provider 名、生命周期模式、创建标签、模型路由等）， 冷恢复不再经过任何 provider。

编排管理器从 Agent 静默与拥有的子代理集合推导三个内部驻留态：running（有活动轮或未醒收件工作）、 waiting（静默但仍拥有未 dispose 的子代理）、settled（全部子代理处置完毕，于是 dispose 掉 AgentHandle、移除 Activation）。拆除自顶向下传播取消、自底向上（child-first）释放句柄—— 一个父代理要等它启动的每个子代理真正处置完才算静默，失控的递归树因此有一个确定的收口。

14.6 Ralph 循环：每轮换一个全新的代理

委派谱系解决「并行分工」，Ralph 循环解决另一类问题：长目标的迭代执行。 dsh-tool-ralph（workflow 组）提供模型面的 ralph({ objective, maxRounds? }) 工具： 一个固定的前台工作流，把一个不可变目标交给一串全新的子代理。 它演示了「专门的编排策略 = 普通插件」——没有给 agent-loop 加任何 Ralph 模式， 一切建在 ctx.workflowEngine 与 ctx.subagents 两个 seam 上 （workflow 引擎的完整故事留到第 17 章）。

循环的规则：

  • 每轮经配置的 subagentProvider（默认 spawn）启动一个子代理；该 provider 必须支持结构化输出、且报告 inheritsParentContext: false——每轮都是干净的头脑。
  • 每个子代理只收到：不可变目标、当前轮次与上限、「共享工作区即权限」指令、上一轮的结构化 handoff 报告。父会话对话与更早的子代理会话一概不做 seed——工作区就是长期记忆。
  • 报告是结构化的：status: continue | complete | blocked，加非空摘要、证据、下一步与阻塞说明；序列化后受 maxHandoffChars（默认 16384 字符）封顶。无效、缺失或超限的报告让工作流失败，而不是被截断或误判为轮数耗尽。
  • 终局结果 complete / blocked / budget-limited 连同最后一轮有界报告与轮数返回；渲染明确标注这是工作代理的自述，不是独立认证。轮数上限默认 256（部署配置兼作调用覆盖的天花板）。
  • 普通子代理失败产生错误（点名失败轮次、保留上一份成功 handoff），Ralph 不重试该轮；取消同样是错误，partial output 永远不算成功。

把 Ralph 放在本章末尾，因为它把本章所有主题串成了一句话：委派的单位是会话， 记忆的单位是工作区，传递的单位是有界的结构化报告。每轮全新的子代理意味着上下文永不膨胀 （第 15 章的主题在这里提前有了答案）；handoff 有界意味着轮间状态可控； 血统与深度照常记录——Ralph 的子代理们是父代理直接派生的 depth-1 兄弟序列，不是越来越深的链。

14.7 本章回顾

  • ctx.subagents 是多 provider 注册表 seam（学 ctx.llm，不是单服务 bash）：spawn / fork / acp / codex / claude-code / dsh-sdk 六个注册名 + 共享的 in-process-driver。
  • provider 契约以 start() 为所有权转移边界：fulfill 前 provider 负责回滚，fulfill 后调用方必须 dispose()；能力四项在启动前校验，缺则响亮拒绝。
  • fork 的 seed 是截至最后一个 turn/end 的连续前缀——子代理永远拿到平衡的会话；seed 只给历史，不给工具限制或权限。
  • 工具三族：tool-subagent（per-provider 发起，one-shot/continuable 两种后台策略）、tool-subagent-control（send_message / interrupt_agent / list_agents）、tool-subagent-report（子域 report 回程，活过 toolFilter）。
  • 血统 = SessionHeader.parentSession + delegationDepth（权威、单调、持久）；深度上限防递归失控；血统是数据不是可见性。
  • 委派边界固定子代理权限：审批钉 'never'、沙箱覆盖快照成事件写进子日志，子代理收到 subagent:delegation 陈述。
  • continuable 子代理 = 持久 Session + 进程本地 Activation；收件箱是唯一 FIFO，结算通知无条件投递。
  • Ralph 循环 = 全新子代理序列 + 有界结构化 handoff + 工作区当长期记忆，全部建在两个既有 seam 上。
常见坑
  • 以为子代理像 bash 一样只能挂一个实现——ctx.subagents 是命名注册表，多个 provider 并存，工具实例逐个绑定。
  • 期待 send_message 能打断子代理当前的轮——它只排队为下一个 FIFO 轮；要停当前轮用 interrupt_agent，且它不处置子代理。
  • 把 parentSession 当可见性——血统只服务投递授权与目录；兄弟子代理互相看不见，fork 之外谁也看不见父会话。
  • 以为 toolFilter 是权限边界——它是可见性/组合限制；子代理的权限边界在委派时由 delegated policy 固定。
  • 给 fork 子代理配 continuable 模式——出厂组合都把 fork 绑在 one-shot 上：子域 report 工具会破坏 KV cache 需要的字节级前缀。
  • 把 Ralph 的 complete 当独立认证——那是最后一轮工作代理的自述；渲染器会明确标注这一点。
  • 指望 ACP 子代理出现在 list_agents 里——ACP run 没有本地子会话，不在 trace 可枚举的目录中。
