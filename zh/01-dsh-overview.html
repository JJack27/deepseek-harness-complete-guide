dsh 是什么：产品与仓库全景

在你写下一行 dsh 相关代码之前，先建立两张地图：一张是「一个只会说话的模型怎么变成能干活的助手」的分层地图， 一张是「代码都住在仓库哪个角落」的物理地图。本章两张都给你，后面的每一章都在这两张地图上放大局部。

学习目标
  • 能说清 LLM、agent harness、前端 UI、操作系统四层各自的职责边界
  • 能指出一条 shell 命令「能不能执行」由哪一层决定、为什么
  • 能列出 dsh 的四种产品形态（Web、headless、ACP、JSON-RPC SDK）分别给谁用
  • 能在仓库里按目录定位：bash 工具在哪、core 脊柱是什么、vendor/ 里放着什么
  • 能避免把 developer preview 阶段的接口当成稳定契约

1.1 一个只会说话的模型，怎么变成能干活的助手

先把起点说清楚：你直接调用 DeepSeek 的模型 API 时，得到的是什么？你发过去一串消息， 它返回一串文字——准确说，是一个 token 一个 token 地生成文本。仅此而已。它没有手： 不能启动一个进程，不能读写你的文件，不能上网抓页面。而且每次调用都是独立的： 这次聊完，下次它什么都不记得。

所谓 LLM agent，就是把这样一个「只会说话的大脑」变成能干活的助手，公式是：

agent = 模型 + 工具调用循环

循环大致长这样：模型看完当前对话，说「请帮我执行 bash 命令 ls -la」； 外面有个程序真的去执行这条命令，把输出塞回对话里；模型看完输出，决定下一步； 如此往复，直到模型认为任务完成。注意分工：模型只负责决定做什么， 真正动手的是外面那个程序。这个「外面那个程序」就是 agent harness（脚手架、马具—— 套在模型身上让它能拉车的那套装备）。DeepSeek Harness（命令名 dsh）就是这样一个 harness。

把循环拆开，harness 要管的远不止「执行命令」这一件事：

  • 循环驱动——什么时候再调一次模型、工具还要不要再跑、什么时候算任务结束；
  • 工具执行与守卫——真的跑命令，但套上超时、沙箱、输出截断这些护栏；
  • 权限——这条命令涉及危险操作时，放行、拒绝、还是先问用户；
  • 会话持久化——把发生过的每件事记成日志，进程重启后还能恢复现场；
  • prompt 装配——把系统提示、工具清单、对话历史组装成每次模型请求；
  • 多端 UI——同一套循环，既要给浏览器用，也要给终端、自动化协议用。

这份清单就是全书的目录预告：dsh 把每一项都做成了一组可替换的插件。本书后面会逐个走进去。

1.2 四层分工：谁管什么

把一次「你让 agent 跑测试」的旅程画成图，一共四层。从上往下：你在前端 UI 打字； agent harness（dsh）组织一切；它向下的两只手，一只伸向LLM API 拿模型的下一个决定， 另一只伸向操作系统真正执行进程、读写文件。

逐层记住三句话，后面读任何 dsh 代码都不迷路：

  • LLM API 层不知道工具、会话、权限的存在。它收消息、吐 token。你在这一层能做的只有换模型、调参数。
  • agent harness 层（dsh）是本书的主角。工具执行管道、权限、日志、prompt 装配全在这里。
  • 前端 UI 层消费 harness 投影出来的会话状态，把它画成界面。UI 换掉不影响决策逻辑；反过来 UI 也不替 harness 做任何安全决定。

操作系统层不神秘：harness 通过子进程、文件系统调用去用它，中间隔着沙箱和策略（第 12 章细讲）。

1.3 dsh 的产品形态：同一副骨架，四种外壳

dsh 不是一个单一程序，而是同一棵插件树的不同「出口」。你最先接触的四种形态：

形态命令 / 入口给谁用
Web 应用 npx @deepseek-ai/dsh web 人。默认起在 http://127.0.0.1:3080，浏览器里聊
一次性任务 dsh --profile headless "任务" 脚本 / CI。跑一个全新会话，打印最终答案就退出，全程不起服务
ACP 服务器 packages/acp/ 自动化客户端（编辑器等）。只走 Agent Client Protocol，没有人类界面
JSON-RPC SDK packages/sdk/（TS）+ python/（Python） 把 dsh 当子进程驱动的程序。Python 侧有两个发行版：deepseek-harness-sdk 和 deepseek-harness-runtime-bin

换形态换的是「外壳」——前端、入口、进程形态；不换的是底下那棵插件树的核心层（模型适配、工具、持久化）。 「树怎么长出来」正是第 3 章的主题，这里先埋个钩子。

developer preview：地板会动

dsh 目前处于 developer preview：迭代很快，官方明确说「会有兼容性破坏性变更」。 读写它的代码时，别把任何接口当成永久契约；反过来，这也是仓库敢大刀阔斧重构的原因—— 你在贡献指南里会看到「宁可改对地基，也不留兼容垫片」的立场。

1.4 仓库地图

克隆仓库后先看根目录。最重要的一个事实：这是一个 pnpm monorepo， packages/ 下按能力分成 49 个分组、200 多个 @deepseek-ai/dsh-* 包（数字持续增长，记「按能力分组、每个包很小」这个原则即可，别背数字）。 everything is a plugin——每个包都是插件树上的一块积木。

逐个说清每个目录的角色：

目录里面是什么
packages/ 全部 @deepseek-ai/dsh-* 工作区包，按能力分组：core、api、typert、llm、shell、subprocess、terminal、fs、lsp、skill、web、compaction、context、subagent、bundle、workflow、todo、plan、preset、guard、extensions、hooks、session、session-query、settings、credentials、storage、workspace、sdk、acp、interaction、boot、host、client、examples、test-support、util、attachment、code-runtime、feedback、goal、jobs、mcp、runtime-diagnostics、sandbox、schedule、spill、e2b……
vendor/ vendored 的 Cordis 框架源码：钉住的上游副本，重命名为 @deepseek-ai/cordis（第 2 章主角）
apps/ cli/（dsh 命令本体）和 web/（浏览器前端应用）
examples/ 可运行的 cordis.yml 叶子示例（agent-spine + CLI/ACP/JSON-RPC 演示）
docs/ 架构文档（architecture.md、cordis-primer.md）、生成目录、cookbook
python/ Python SDK 和打包的运行时：deepseek-harness-sdk 与 deepseek-harness-runtime-bin
native/ @deepseek-ai/node-addon-landlock-run：Linux Landlock 沙箱的 Node 原生模块
scripts/ 仓库质量门禁脚本和生成器（pnpm run hygiene、doc-sync 背后就是它们）
website/ 文档网站的 VitePress 源码
关键认知：按能力分组

packages/ 不是按「前端 / 后端」分组的，是按能力：shell 组管命令执行、fs 组管文件、 web 组管搜索抓取、subagent 组管委派、session 组管持久化……每组里通常还有更细的角色分工 （接口、实现、模型可见工具），第 11 章专门讲。现在你只需要记住：想找某个功能，先找它的能力组。

1.5 上手第一课：bash 工具住在哪

用一个具体问题练手：「模型看到并调用的 bash 工具，代码在哪？」 新手的直觉是去 packages/core/ 翻——毕竟那是「核心」。但按能力分组的原则， bash 属于 shell 能力，所以它住在 packages/shell/： 

# packages/shell/ 下的分工（bash 相关部分）
packages/shell/shell/          # shell 能力接口（Service Definition）：executor seam
packages/shell/shell-local/    # 本地实现（Provider）：真的在本机起进程
packages/shell/tool-bash/      # 模型可见的 bash 工具（Consumer）← 找的就是它
packages/shell/tool-pwsh/      # Windows 上的 PowerShell 孪生兄弟

模型可见的工具（tool-bash）、执行命令的本地实现（shell-local）、 两者之间的接口（shell）是三个不同的包。这个「接口 / 实现 / 使用者」的三分法 是 dsh 的核心设计之一，第 11 章会展开成完整的 capability seam 模型。

那 core/ 是什么？是脊柱——所有能力都要挂在上面的一组基础服务：

core 包管什么服务入口
core/session追加式会话事件日志与内存存储ctx.sessions
core/system-promptprompt 段落与工具 schema 的装配ctx.systemPrompt
core/tools带作用域的工具注册表 + 守卫执行管道ctx.tools
core/agentAgent 接口与在线注册表、agent/* 事件ctx.agents
core/agent-loop实现该接口的默认驱动循环ctx.agentLoop
core/scope按 agent 划定注册作用域的原语库，无 ctx key

注意最后一列——ctx.tools、ctx.sessions 这些名字。它们是插件之间互相找服务的钥匙， 也是下一章的主角。甚至循环本身（agent-loop）也只是挂上去的一个插件，可以被换掉。

1.6 本章回顾

  • 裸 LLM API 只会生成 token；agent = 模型 + 工具调用循环，循环驱动、工具执行与守卫、权限、持久化、prompt 装配、多端 UI 都是 harness 的活。
  • 四层分工：LLM API（生成）↔ agent harness（dsh，决策与执行）↔ 前端 UI（渲染）↔ 操作系统（真正的进程/文件/网络）。「命令能不能执行」归 harness。
  • dsh 四种形态：Web（npx @deepseek-ai/dsh web，默认 127.0.0.1:3080）、headless 一次性任务、ACP 自动化服务器、TS + Python 的 JSON-RPC SDK。developer preview，会有破坏性变更。
  • 仓库是 pnpm monorepo：packages/ 按能力分组（49 组、200+ 包）、vendor/ 是钉住的 Cordis、apps/ 是 cli + web、python/、native/、examples/、docs/、scripts/、website/。
  • bash 工具在 packages/shell/tool-bash（能力组），不在 core；core/ 是脊柱：session、system-prompt、tools、agent、agent-loop、scope。
常见误区
  • 以为模型「执行」了命令——模型只是请求执行，动手和把关的都是 harness。
  • 以为 dsh 是一个大程序——它是一棵启动时组装出来的插件树，第 3 章会看到组装过程。
  • 在 packages/core/ 里找 bash 工具——core 是脊柱，具体能力住在各自的能力组（packages/shell/）。
  • 以为权限决策在 UI 层——UI 只渲染，换掉 UI 不改变任何决策逻辑。
  • 把 developer preview 阶段的任何接口当稳定契约——升级时可以整个换掉。
