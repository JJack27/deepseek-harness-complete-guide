质量门禁与仓库约定

一个「everything is a plugin」的仓库，靠什么让几十个包的插件不打架？答案分两层： 一层是可执行的门禁——run-gates.ts 调度的几十个验证命令加 lefthook 钩子； 另一层是写在 AGENTS.md 里的硬约定——每一条都在回答「为什么这么写才不会烂」。 本章把这两层摊开：先给你命令地图与「按证据面选检查」的本地哲学，再逐条讲透二十条约定。 读完你就有了在这个仓库里判断「这么做行不行」的内化标准。

学习目标
  • 默写常用命令地图：clean / test / test:coverage / test:e2e / test:snapshot[:record] / typecheck / lint / duplication / build / hygiene / doc-sync / website:build 与 dsh --profile headless。
  • 按「证据面 → 检查」为一次改动选出最小检查集，而不是默认全量套件。
  • 说出 lefthook 三个钩子各查什么、刻意不查什么，以及 run-gates.ts 的 CI lane 划分。
  • 逐条复述 AGENTS.md 的二十条硬约定，并为每条讲出「为什么」。
  • 区分 test 与 test:coverage：后者才是 CI 覆盖率门禁。

23.1 命令地图

AGENTS.md 的 Commands 一节是命令的唯一权威入口；package.json 拥有脚本清单， scripts/run-gates.ts 拥有门禁聚合。日常用到的命令如下：

23.2 本地检查哲学：按证据面选检查

这个仓库对本地检查的态度只有一句话：匹配证据面，绝不默认全量。AGENTS.md 「Run relevant checks locally」一节列出五组对应关系——行为改动跑聚焦测试；模型或用户输出 跑快照；文档跑 doc-sync；发布路径跑 build/hygiene 加构建产物 smoke；provider 行为跑 e2e。为提交或推送重复跑一遍已经绿的检查被视为错误，而不是稳妥。穷尽覆盖与平台矩阵 （Node 22.19 / 24 / 26、Linux / Windows）是 CI 的职责；本地只有三种情况才值得排练全量： 明确要求、诊断 CI、或一个不可拆分的仓库级改动。

23.3 门禁家族：run-gates、CI lane 与 Git 钩子

scripts/run-gates.ts 是门禁的调度器：它以有向依赖图组织几十个 gate，在 有界并发下跑进程并汇总诊断。它的 Mode 清单就是 CI 的 lane 划分——ci-primary （ci-linux-primary 额外加 web 浏览器快照）、ci-static、 ci-coverage、ci-snapshot、ci-artifacts、 ci-consumers、三个 Windows lane（blocking / complete / observational）、 node-compat，加上本地可选的 check-all 与文档聚合 doc-sync。一条 lane 内部，artifact 消费者等待同 lane 的一次 build，而不是各建各的。

doc-sync 的叶子清单能让你感受这个仓库把「文档正确」做成了多少条可执行断言： cordis/client/tool/config/persistence 目录再生成比对、export JSDoc 校验、文档图、scoped events、 Markdown 换行与链接、公开仓库链接、文档引用、包路径、配置来源属主、README 的 model-experience 与 limitations 章节、Agent Note 的分类/格式/冻结校验、type-equiv（文档里贴的类型与源码逐字一致）、 翻译 prompt 与配对、文档预算、VitePress 站点构建。任何一个改了，门禁都会红。

Git 侧由 lefthook 提供三个快速检查点。pre-commit：校验暂存的翻译配对记录、用 项目无关的 .oxlintrc.staged.json 档案校验暂存文件并带一次有界重试地应用 Oxlint 修复、在输入文件变化时重新生成 THIRD_PARTY_NOTICES.md、检查暂存 diff 的空白错误 （git diff --cached --check——这就是「文件恰好一个尾随换行」的执行者）、跑 vendor manifest 守卫。pre-merge-commit：做同一套配对检查。pre-push：跑 pnpm run typecheck。注意钩子刻意不跑测试、快照、文档检查、构建 或 hygiene——那些归贡献者按证据面选择，归 CI 穷尽。

宿主沙箱失败的重试规则

当必需的 gh、pnpm、build、test 或生成器命令因为 agent 沙箱挡了 凭证、网络、IPC、文件监听或嵌套 sandbox-exec 而失败时，先原样用 最窄的宿主升级重试，再诊断认证或项目故障。要拿得出沙箱证据；绝不绕过真实的测试失败或被测的 产品沙箱。

23.4 运行时契约：五条关于 Cordis 与事件的约定

1）注册即效应。every contribution 经 ctx.effect() / ctx.on()， 注册表的 register() 返回 disposer。为什么：Cordis 的 fiber 生命周期是插件卸载/HMR 的基础，凡是不走 effect 的注册就是卸不掉的泄漏；第 3 章的 HMR-safety 测试正是对这条约定的验证。

2）运行时不变量断言拥有的关系。检查权威事件流或可变数据，而不是服务或方法 存在性、插件元数据、effect、固定的纯例子。为什么：「服务还在」证明不了「关系还对」——存在性检查 会在注册了却从不写日志的实现上绿灯通过。若无合理关系可断言，一个解释过的空伴随（empty companion） 就是正确答案，不要为了凑断言造伪证。

3）typed events 用 declaration merging。事件接口靠声明合并扩展 merge-extensible maps；事件 JSDoc 要 @mode，payload 要 @param，不在 payload 里的 scoped key 要标 @dshScopeScan unsupported。SessionEventMap 成员默认 required-on-read： 不认识该事件类型的构建拒绝读日志，除非事件带 ignorable: true；只有结构性格式变化才 bump SESSION_FORMAT_VERSION。为什么：这是「日志可重建运行时」的类型级保险，未知事件 在静默丢弃与拒绝加载之间，仓库选择了拒绝。

4）判别标签上 switch。封闭 union 以 assertNever 收尾；可扩展 union 穿过一个写明注释的 default。为什么：判别标签让穷尽性检查由编译器执行——给封闭 union 加 一个成员，所有忘记处理的 switch 立刻红；漏掉 assertNever 就把这层保险拆了。

5）waterfall 监听器必须调 next()。不调 next() 而直接 return 就是短路整条链。为什么：waterfall 的语义是层层委托（如权限审批的链式放行），忘了委托的 监听器会把下游所有监听器无声地藏起来——这是最难排查的一类「权限突然全拒绝」。

23.5 模型可见性与扩展点：三条结构性约定

6）model-visible ⟺ logged。凡到达模型请求的东西必须能从会话日志重建；新增一个 模型可见输入必须新增一个会话事件。为什么：会话日志是可回放、可审计、可做快照金标准的唯一事实源 （第 4 章）；从 llm-replay 到 ACP 快照，整条测试体系都站在这个等价关系上。绕过日志 塞进请求的内容，回放时会消失，快照会漂移。

7）插件不改 loop。新行为落在文档化的扩展点上；要改 agent-loop 本体 就必须同步更新 docs/architecture.md。为什么：loop 是所有插件共享的调度核，直接在里面塞私有逻辑 等于给所有人埋雷；扩展点是插件之间互不踩踏的合同。

8）capability seam 三角色齐全。一个能力面由 Service Definition / Service Provider / Consumer 三角色构成，齐全才算 seam，只有角色演化节奏确实不同才拆开。为什么：缺 Provider 的 「能力」没法换实现，缺 Consumer 的「能力」没人用，缺 Definition 的两端各自理解协议——三角色是 第 11 章可替换性的最小完备集。

23.6 包边界与配置：六条工程约定

9）优先维护良好的依赖而非手滚。当依赖真能删掉自有代码与测试时用它——这有政策 文档（.agents/notes/implemented/process/2026-07-26-dependencies-over-hand-rolling.md）背书。 为什么：「我们自己写更快」的直觉常忽略维护与测试的长期账单；但反过来，为省三行代码引入一个依赖 同样亏，所以判据是「真正删掉 owned code 与 tests」。

10）包边界显式 > 隐式。默认值是 owning 实现里一个显式的 resolve(request): Spec 步骤，绝不是 run() 里藏着的 ?? default ——dsh-shell 的 request/spec 拆分是模板。为什么：藏在执行路径里的默认值在审查与配置 面上都不可见，策略漂移无声发生；显式 resolve 让「谁拥有默认」一处可查。

11）插件里不许硬编码 tunables。部署可变的选项是经过校验的 Config 字段， 可从 cordis.yml 改；DEFAULT_* 常量或测试钩子不算可配置。协议常数、外部规范与安全 不量保持固定。为什么：一个写死的超时在别的部署里就是故障；而「安全不变量」如果做成可配置，就 不再是不变量。

12）配置错误大声失败。能自证时在加载期失败，否则在最早可解析点；绝不静默跳过 缺失的引用。为什么：静默跳过把错误推迟到运行中最贵的时刻，还伪装成正常；fail loud 让坏配置在 --dump-config 或启动时就爆。

15）source plane 与 artifact plane 永不混合。静态门禁与测试经 tsconfig paths 把 workspace 导入解析到 src，在干净树上通过；消费构建 lib/ 的门禁显式声明该依赖。为什么：混用会装出第二份模块单例、让陈旧产物混进源码验证，两边各自证明的 东西就都不可信了（22.7 节）。

16）每包一个聚合 compiler face。唯一例外是 api/remotes（Host 与 Client 两份 tsconfig，因 Host Typert 图与 Client /remote 声明的先后依赖而拆）。仓库级 程序要从 tsconfig.host.json 或 tsconfig.client.json 起种，绝不用根 solution。 为什么：两侧在相同键下 declaration-merge 出不同的 Context，压进一个 ts.Program 会撞合并冲突——这是两聚合架构（第 3 章）的编译面映照。

23.7 类型与代码纪律：六条小而硬的规矩

13）跨边界 id 用 branded 类型。Branded<B>（来自 dsh-brand），绝不裸 string。为什么：session id、turn id、goal id 在运行时 都是字符串，但把它们混着传是真实发生过的一类 bug；branded 类型把这类错误从运行时提前到编译时， 且零运行时开销。

14）类型化同进程边界信任 TypeScript。静态接口已要求的值，不额外加运行时校验、 回退行为或敌意输入测试；校验只发生在 parser/config、排队、模型/工具 JSON、durable/文件、worker、 进程与 wire 边界。为什么：为类型已保证的东西写防御代码，等于宣称自己的类型系统不可信——这些代码 无法被测试有意义地触发，只会腐烂。边界清单就是「不信任恰好开始的地方」。

17）空 catch 要点名吞了什么、为什么别的到不了；try 只包一条 语句。为什么：空 catch 是「这里出过错，然后有人把它按住了」的化石——不说清楚，下一个读者 无法判断吞掉的是预期分支还是新故障；try 缩小到一条语句让「吞了什么」在语法上无处 可藏。

18）平行值保持对称。未解释的不对称通常是漏掉一次提取的信号。为什么：成对出现 的值（两个 provider、两个方向、请求与响应）一旦不对称，要么是 bug，要么是没写下来的设计决策； 约定逼你二选一：改对称，或把理由写出来。

19）测试描述行为，不描述正确性。行为过时就连测试一起改，并在 PR 里说明为什么。 为什么：把测试当「正确性的碑文」会导致实现改进被旧断言锁死；测试的寿命应该等于它描述的行为的 寿命。

20）TODO 标记按紧急度：FIXME（应阻塞新发布）< TODO（尽快修） < XXX（也许哪天修）。文件以恰好一个尾随换行结束，git diff --cached --check 在 pre-commit 把关。为什么：扫描代码的人要能一眼分出发布阻塞与 someday-maybe； 换行约定则是给 diff 与工具链一个确定的文件终界。

把二十条读成一句话

Cordis 层：注册可撤销、不变量断言关系、事件可合并、union 可穷尽、waterfall 必须委托。可见性层： 模型可见必被日志记录、行为上扩展点而不是 loop、seam 三角色齐全。边界层：依赖优先但看删除量、 默认值显式 resolve、tunables 进 Config、配置 fail loud、源码面与产物面不混、每包一个聚合 face。 纪律层：id 要 branded、同进程信任 TS、空 catch 要交代、平行值要对称、测试随行为改、TODO 分级、 文件一个尾随换行。

23.8 本章回顾

  • 命令地图就位：clean / test / test:coverage / test:e2e / test:snapshot[:record] / typecheck / lint / duplication / build / hygiene / doc-sync / website:build / dsh --profile headless。
  • 本地哲学：按证据面选最小检查集（行为→聚焦测试、模型/用户输出→快照、文档→doc-sync、发布路径→build+hygiene+smoke、provider→e2e）；CI 拥有穷尽覆盖与平台矩阵；覆盖率门禁是 test:coverage。
  • run-gates.ts 的 Mode 清单即 CI lane；doc-sync 把文档正确做成几十条可执行断言；lefthook 三钩子（pre-commit 空白/暂存 lint/vendor 守卫、pre-merge-commit 配对、pre-push typecheck）刻意不跑测试。
  • 运行时契约：注册即效应、不变量断言拥有的关系、typed events 声明合并 + required-on-read + ignorable: true 例外、switch + assertNever、waterfall 必调 next()。
  • 结构契约：model-visible ⟺ logged、插件不改 loop、seam 三角色齐全。
  • 边界与纪律：显式 resolve(request): Spec、tunables 进 Config、fail loud、branded id、同进程信任 TS、source/artifact 面分离、一个聚合 face、空 catch 交代、对称性、测试随行为改、TODO 分级 + 一个尾随换行。
常见误区
  • 提交前习惯性跑 pnpm run test 全量——按证据面选聚焦检查；重复跑绿检查是这个仓库明确反对的。
  • 把 pnpm run test 当覆盖率门禁——门禁是 test:coverage（per-file 100%）。
  • 在 run() 里用 ?? 给请求补默认值——默认值属于 owning 实现的显式 resolve(request): Spec。
  • 给同进程函数参数加运行时校验——信任 TS；校验留给 parser/config、模型/工具 JSON、durable/文件、worker、进程、wire 边界。
  • waterfall 监听器判断完直接 return——必须调 next()，否则整条链被短路。
  • 给封闭 union 的 switch 写 default 而不收 assertNever——编译器再也帮不了你。
  • 新模型可见输入只改请求组装——没有对应会话事件就违反 model-visible ⟺ logged，快照与回放会漂移。
