ACP、SDK 与 Python

Web UI 只是人类开车的方式之一。当驱动者是另一个程序——编排器、测试框架、另一个 agent harness——dsh 提供三条进程外的路：ACP 服务器、TypeScript SDK、Python SDK。三条路形态 不同，底座一致：都经 stdio 上的 JSON-RPC 驱动一个完整的 harness 进程，都不需要浏览器。 本章把它们并排讲清楚，并给出选择依据。

学习目标
  • 说出三条进程外驱动路径的共同底座与各自形态。
  • 描述 ACP 的 automation-only 定位、方法面与「已提交消息才上 wire」的取舍。
  • 分清 SDK 三个包的角色：protocol（wire 契约）、server（插件）、client（TS 客户端）。
  • 解释 Python 两个发行版的分工，以及「零配置」为什么是显式参数传递而非隐藏回退。
  • 按场景为调用方选路径：标准协议客户端、repo 相邻 TS 自动化、pip 安装即用。

21.1 三条进程外驱动路径

把第 19、20 章的浏览器半区整个拿掉，剩下的 host 进程依然是完整的 harness：agents、会话 日志、工具管道、全部能力面都在。于是「程序当客户端」只需要一件事——一条进程间协议。 dsh 提供三条：

  • ACP（packages/acp/acp）：实现外部的 Agent Client Protocol，JSON-RPC over stdio，给任何说这门标准协议的客户端用；仓库内的典型客户端是 dsh-subagent-acp（第 14 章）。
  • TypeScript SDK（packages/sdk/）：自家的 deepseek-harness 式协议——换行分隔 JSON-RPC 2.0 over stdio——的 TS 客户端 与服务端插件；示例 bin 是 dsh-jsonrpc-agent。
  • Python SDK（python/）：同一协议的 Python 客户端，加一个 捆绑了 runtime 二进制的发行版，pip 装完即用。

21.2 ACP：automation-only 的 Agent Client Protocol

packages/acp/acp（@deepseek-ai/dsh-acp）是 stdio 上的 automation-only ACP 服务器。定位要读准：它是传输适配器， 不是 UI 集成，也不是 capability seam——不提供编辑器导航、transcript 回放、命令、模式、 配置选择器、elicitation、推理展示、计划、标题或工具呈现；交互渲染和人类提问属于 Web host 与 client 模块（第 19 章）。插件 apply 在 stdin/stdout 上开一条 AgentSideConnection 驱动 ctx.agents；stdout 保留给协议帧， 诊断走 stderr。

方法面很小而克制：

方法行为
initialize协商支持版本，只宣告 baseline-only 提示能力；不宣告任何 session、编辑器、终端、文件系统或 MCP 能力。authenticate 是 no-op。
session/new创建全新 agent，主 cwd 取绝对路径；空的 additionalDirectories 与 mcpServers 可接受，非空拒绝。
session/prompt拼接文本块，把 baseline 资源链接渲染成括号文本引用；拒绝空输入；每会话一次一个在途请求；等整个 agent 空闲。正常静默报告 end_turn，显式取消或废弃的准入报告 cancelled。
session/cancel只取消被点名的 agent；未知 id 是 no-op。
session/update对每条已提交 assistant/message 的每个非空文本块发一个 agent_message_chunk；原始 delta 与非消息事件不上 wire。
session/request_permission为带工具调用 id 的一次性审批请求提供 allow/reject 选择；客户端可以自动作答。

「只发已提交消息」是刻意用 token 级延迟换干净的自动化结果：未提交的 provider 流块与 重试尝试不可能漏出半截文本；推理与工具活动留在会话日志里，供其他界面观察。模型视角一如既往 地干净（第 4 章的法则在这里同样成立）：session/prompt 的文本逐字并成一条用户 消息，协议元数据、客户端能力、权限选择、会话 id 永不进入模型请求；权限决定的产物只是 owning 工具的正常 tool 结果。生命周期上，断连与 Cordis 销毁共用一次 memoized 清理：先拒绝新会话与 prompt、结算在途 prompt，再只在这条连接精确拥有的 continuable 后代范围内 排干并并行销毁——其他前端共享的 Context 保留自己的森林，ACP-only 的插件重载不留孤儿 agent。可运行的组合是 pnpm run demo:acp（packages/examples/acp-demo 的 dsh-acp-demo bin：agent spine + JSONL 持久化 + 检查点策略 + ACP 传输， stdout 即协议）。

21.3 TS SDK：protocol、server、client

packages/sdk/ 三个包把「自家协议」拆成三层：

  • dsh-sdk-protocol —— 共享 wire 契约：JsonRpcLineTransport 把 JSON-RPC 2.0 装帧在调用方自有的字节流上（一行一帧、\n 结尾的紧凑 JSON； 有 id 有 method 是请求、只有 id 是响应、只有 method 是通知；坏 JSON 行忽略），加上两端 共用的命名请求/结果/通知类型。纯库，无插件。
  • dsh-sdk-jsonrpc-server（server）—— inject: ['agents'] 的 jsonrpc 插件：每 sessionId 取或建一个 agent，把每个持久的 会话事实作为 session.event 流出、每个整 agent 生命周期翻转作为 session.status 流出。shutdown 回复后销毁根 context 到静默再 退出 0。
  • dsh-sdk-client（client）—— TS 客户端，两层：DeepSeekHarness 是高层 owned-run API，HarnessClient 是低层协议客户端。与 Python SDK 是 设计孪生，差别在 launch spec 全显式（command/args）——捆绑 runtime 的发现留给 Python 发行版。

wire 的请求/通知面值得背下来。请求三个：initialize（cwd 绝对化后过 wire， 附 provider/model 路由与可选的正整数 maxTokens 输出上限——对根 agent 及其进程内 后代生效）、session/prompt（排队一条带 id 的用户消息，立即返回 { messageId } 入队回执）、shutdown。通知四个： session.event（runtime 里每个会话的事件，不过滤——按会话收敛是 客户端自己的事）、session.status（整 agent 的 running/idle 翻转）、 subagent.started、subagent.finished（仅进程内运行）。 messageId 标识的是排队的那条 UserMessage——不是 后来的助手消息、turn 结束或「该 prompt 的结果」。协议没有取消方法：放弃一个 turn 的办法是 关掉 runtime 进程。

高层 DeepSeekHarness 怎么在这片原语上造出「跑一次拿结果」： 

await using harness = new DeepSeekHarness({
  launch: { command: 'node', args: ['lib/bin.js', 'cordis.yml'] },
  provider: 'deepseek-official',
  model: 'deepseek-v4-flash',
})
const result = await harness.run('say hi')
console.log(result.finalResponse)

run() 拥有一个活动区间：提交 prompt，等它的 MessageId 出现在持久的 agent/inbox/spliced 回执里，然后一路收集到下一个整 agent idle；返回 RunResult（sessionId、finalResponse、events、 notifications）。finalResponse 是该区间内根会话最后一条已提交的 助手文本——不是因果上归属这个 prompt 的回复；转向消息、注入上下文和其他排队工作都可能在 idle 之前贡献内容。子进程懒启动、由实例持有跨 run() 复用，close() （或 await using）必调，内部走协议 shutdown → stdin-EOF → SIGTERM → SIGKILL 的梯子直到进程真的退出。示例 bin 是 packages/examples/jsonrpc-demo 提供的 dsh-jsonrpc-agent：只负责 启动外部 cordis.yml（$DSH_CORDIS_CONFIG 或位置参数，缺配置一行 usage 退出 1），不指定服务插件——组合里有 dsh-sdk-jsonrpc-server 才有东西可 serve。stdin EOF 与信号走同样的销毁；EOF 可能切断在途 turn，要有序收尾就用协议级 shutdown。

21.4 Python：两个发行版与捆绑 runtime

python/ 出两个发行版：deepseek-harness-sdk（模块 deepseek_harness，高层 turns API + 低层 JSON-RPC 客户端）与 deepseek-harness-runtime-bin（模块 deepseek_harness_runtime， 捆绑的 runtime 二进制与默认 agent 配置）。装前者会带上同版本的后者平台 wheel： 

from deepseek_harness import DeepSeekHarness

with DeepSeekHarness() as harness:
    result = harness.run("Say hi.")

未钉 channel 时，SDK 自动启动匹配的捆绑 runtime：默认发射单文件可执行 dsh-jsonrpc-agent-pkg-<platform>-<arch>（linux/macos × x64/arm64； 目标机不需要装 Node），并经 DSH_CORDIS_CONFIG 注入该包自带的默认组合—— stdio JSON-RPC 服务入口、agent 核心、预载的 DeepSeek 适配器、带显式语义检查点策略的 JSONL 持久化、本地 bash。另有一个 dev-only 的 node 载体（完整 deploy closure 跑在系统 Node 上）， 必须显式 DSH_RUNTIME_MODE=node 才会选中——生产部署永远不能悄悄 骑在源码构建上。想要自己的插件组合：保留配置里的 @deepseek-ai/dsh-sdk-jsonrpc-server 条目，把 cordis= 指到你的 cordis.yml。runtime 继承 DEEPSEEK_API_KEY、DEEPSEEK_BASE_URL 等 环境变量。

这里有一处设计必须读准：runtime 永远要求显式配置——没有 $DSH_CORDIS_CONFIG 或位置参数就大声退出，这是 runtime 的设计语义， deepseek-harness-runtime-bin 不软化它。「零配置」是 wrapper 侧一次显式、可见的 参数注入，不是 runtime 里的隐藏回退。高层 API 的语义与 TS 孪生一致： Session.run() 拥有从持久入队回执到下一个整 agent idle 的活动区间，返回 RunResult(session_id, final_response, finish_reason, events, notifications, session_root)；finish_reason 是区间内最后一条根会话 turn/end 的 kind（如 completed、 max-tokens、error），无 turn 结束则 None。 events 只含根会话事件——后代消息不能顶替根回答；notifications 与 on_notification 按 wire 顺序收到根会话加已发现后代的全部通知。低层 session_prompt() 同样只回 MessageId，活动边界自理。

21.5 怎么选

三条路不是三种品味，是三种处境：

处境选理由
客户端说标准 ACP（编排器、别的 harness、通用 agent 客户端）ACP标准协议面小而稳；automation-only 语义与外部驱动天然匹配；dsh 可以当别的 dsh 的子代理后端（dsh-subagent-acp，第 14 章）。
repo 相邻的 TypeScript 自动化、CI、自家工具TS SDKlaunch spec 全显式，类型直接来自 dsh-sdk-protocol；适合知道自己要启动哪个 runtime 的调用方。
Python 生态、脚本、 notebook、最快上手Python SDKpip 装完即用，捆绑 runtime 免 Node 安装；DeepSeekHarness().run() 三行见结果。

无论选哪条，三件事不变：stdout 是协议（部署不得组合 stdout logger）；「结果」是活动区间的 聚合而非因果归属（要因果，自己在事件流上定义区间）；取消靠关进程或 ACP 的显式 session/cancel，SDK wire 上没有 per-prompt 取消。

21.6 本章回顾

  • 三条进程外驱动路径（ACP、TS SDK、Python SDK）共同点：都经 stdio JSON-RPC 驱动完整 harness 子进程，都不需要浏览器。
  • ACP 是 automation-only 传输适配器：方法面 initialize/session/new|prompt|cancel/update/request_permission；只发已提交的 assistant 文本；权限选择不进模型请求；连接销毁只清自己精确拥有的 continuable 后代。
  • SDK 三包：protocol（换行分隔 JSON-RPC 2.0 wire 契约，纯库）、server（jsonrpc 插件，inject agents）、client（DeepSeekHarness/HarnessClient，launch 全显式）。
  • wire 语义：session/prompt 立即回 { messageId } 入队回执；通知是 session.event/session.status/subagent.started|finished；无取消方法，放弃 turn 靠关进程。
  • Python 两发行版：sdk 自动启动匹配捆绑 runtime 并经 DSH_CORDIS_CONFIG 注入默认组合；runtime 本身永远要求显式配置——零配置是 wrapper 的显式注入，不是隐藏回退。
常见坑
  • 把 ACP 当 UI 集成或 capability seam——它是 automation-only 传输适配器；编辑器导航、transcript、模式切换都不在面上。
  • 期待 ACP 流式 token——只有已提交 assistant/message 的文本块上 wire，原始 delta 不出。
  • 把 { messageId } 当「prompt 的回复 id」——它标识入队的 UserMessage；最终回复靠活动区间聚合。
  • 给 runtime 的组合加 stdout logger——stdout 是 JSON-RPC 通道，日志去 stderr。
  • 以为 Python 零配置是 runtime 的默认行为——runtime 无显式配置会大声退出；注入发生在 wrapper 的 start()。
  • 忘了 close()/await using——子进程由实例持有，不关就漏。
