Agent 抽象与 Scope 机制

上一章结束时会话已经能落盘了，但「谁在驱动会话」还没出场。本章认识 Agent——dsh 对「一个正在工作的 agent」的公共接口，以及让 「每个 agent 有自己的一套工具和提示词」成为可能的 scope 机制： 一个活 agent 就是它自己 scope 的 key，最具体的注册胜出（shadowing）。 这是 per-session 人格（persona）、agent preset、子代理组合的共同地基。 具体的驱动循环（turn/step）留给下一章。

学完本章你能够
  • 说出 Agent 接口的成员与 ctx.agents 注册表（get/list/roots/isOwnedBy）各自回答什么问题
  • 按「观察还是拦截」给 agent/* 事件分类，并指出哪些是 waterfall（必须调 next()）
  • 解释 create/resume 走 AgentFactory 接缝的意义：接口与驱动分离，loop 可整体替换
  • 描述 setup window 的时序：在发布前组装 agent 的 scoped 世界，失败整体回滚
  • 用 shadowing 规则（最具体的 scope 胜出）推导一个同名注册在多 agent 下谁生效
  • 区分「lineage 是数据」与「runtime 所有权」：parentSession 记在 header，父不自动看到子

6.1 Agent：接口与注册表

第 4 章的 Session 是「发生过什么」；Agent 是「正在做的那个主体」。 它是一个纯接口（packages/core/agent/src/runtime-types.ts）， 具体实现是 agent-loop 包的私有物——插件永远不 import agent-loop，只依赖这个接口。成员按用途分组：

成员用途
id / sessionagent 与会话共享同一个 id（SessionId）；session 是它驱动的活会话，日志是耐久真相
optionsprovider 路由与模型等 per-agent 选项（merge-extensible 的 AgentOptions）
inbox持久待办投影：next-turn 与 next-step 两条有序队列
statusidle ⇄ running（每次转迁发 agent/status；dispose 不是第三个状态）
ctxagent-scoped 上下文：通过它注册的贡献是 agent 局部的、随 dispose 展开 afterwards 拒绝注册（6.5 节主角）
send / followup / steer / inject投递输入的四种姿势：send 是统一原语（目标 + 是否唤醒），后三个是固定预设（追加一轮 / 就近一步的转向 / 不唤醒的上下文注入）
cancel / whenIdle / runMaintenance取消（首个原因获胜，可 keepInbox 保队列）/ 等静止 / 从真空闲跑一段非 turn 维护任务

注册表 ctx.agents（AgentRegistry）管「谁活着」： get(id) 查活 agent、list() 按注册序列出全部、 roots() 只列无运行时父的顶层 agent、isOwnedBy(id, owner) 判断「这个子是不是经某个确切父的 scoped 上下文创建的」——注意这是运行时关系， 与耐久谱系无关（6.7 节展开）。

创建 agent 的消费者拿到的是 AgentHandle（{ agent, dispose() }）。 dispose 是一种能力：在消费者里只有持有者能拆掉这个 agent； 另一个结构性 owner 是注册了工厂的 provider（它的 scoped agent 依赖它的服务 API， provider 卸载会停掉并排空它造的所有活 handle）。拆卸顺序固定： 停 loop → 等 exit → 注销 agent → 从 session store 移除会话 → 最后展开它的 scoped 世界。 经配置创建的 agent（loop 自己的启动项）由 loop fiber 拥有，从不需要 handle。

6.2 agent/* 事件：观察与拦截进行中的工作

所有 agent/* 事件都携带活 Agent（payload 里）， 并经 scope 过滤的分发（上一节 Scoped<Agent> this 载体；6.6 节讲它意味着什么）。 按用途分三组记：

分组事件模式一句话
生命周期（观察）agent/created / agent/disposedemit发布 / 离开注册表；created 的同步抛出可否决发布
agent/statusemitidle ⇄ running 转迁镜像
agent/inbox/inserted / claimed / discardedemit活收件箱的进出；被认领后又被拒的消息止步于此
agent/session-startemit会话生命周期开始（每会话一次，第一个 turn 前）——agent.inject() 播种上下文的标准时机
拦截（扩展点）agent/pre-stepwaterfall拒绝拟议的 step，或改写进入它的消息（调 next() 保留）
agent/requestwaterfall替换冻结的调用配置；不能改消息（模型可见内容走日志通道）
agent/request-errorwaterfall认领失败请求的恢复（返回 retry 而不调 next），或委托
停止边界agent/turn-stoppingserial（无 next）turn 即将闭合；反对的方式是数据——steer() 注入新转向，机器重读收件箱
错误通知agent/erroremitstep/turn 出错的现场报告（哪怕错误在 turn 里没有耐久位置）

和第 4 章的对照值得再念一遍：会话事件是耐久事实，agent 事件是活扩展点。 事实必须熬过重启所以落日志；进行中的工作（inbox 变化、请求改写、turn 停止） 只对当下有意义，所以走 Cordis 事件总线。挑选机制时的第一问永远是： 这个事实需要在 reload 后还存在吗？

三个 waterfall（agent/pre-step、agent/request、 agent/request-error）的监听器必须调 next() 委托下层—— 不调就是短路整条链，这是第 2 章学过的 Cordis waterfall 语义在 dsh 里最重要的三个落点。 agent/turn-stopping 刻意是 serial 且无 next()：它不是否决点， 而是「最后看一眼」点，反对靠数据（steer）不靠返回值。

6.3 create/resume：工厂接缝

AgentRegistry 自己不构造 agent。它持有最多一个 AgentFactory（createAgent + resume 两个方法）， 由驱动插件在构造时经 ctx.agents.setFactory() 注册—— 出厂实现来自 agent-loop。没有注册就调 create/resume 会得到一句直白的错误： 「no agent factory registered (load an agent-loop plugin)」。 

// 消费者视角：只认识 ctx.agents，不认识 agent-loop
const handle = await ctx.agents.create({
  sessionId,              // 共享身份：agent 和 session 同一个 id
  meta: { cwd, parentSession, delegationDepth, agentPreset, ... },
  seed,                   // 可选：fork 的平衡前缀
  agentOptions: { provider, model, maxTokens },
  setup,                  // 6.4 节主角
})
// resume 是持久化版：先走 ctx.sessionPersistence.prepare(id)
const resumed = await ctx.agents.resume({ resumeSessionId, agentOptions, setup })

这个接缝的意义是接口与驱动分离：ACP 桥、测试工具、任何消费者都编程于 ctx.agents，谁也不知道驱动是谁。想把整个 loop 换成另一种实现 （比如不做工具循环的特殊驱动），注册自己的 factory 即可，插件生态不动。 工厂内部的事务顺序（下一章细讲）：铸造 scoped 上下文 → await setup → 依次插入并公告 session 与 agent → 发 agent/session-start → 启动 loop。 每一步都被回滚覆盖：已经公告过的创建会配上配对的 disposed 通知。

注册表还提供发起者（initiator）作用域：进程内异步链上的因果归属。 withInitiator(agent, fn) 把 agent 带进 fn 的整个返回生命周期， currentInitiator() 读它（可选形式，给日志/追踪/指标用）、 requireInitiator() 强制要求、withoutInitiator(fn) 显式清除 （给懒共享定时器、队列泵这种「别继承第一个碰巧初始化它的 agent」的场景）。 注意契约：initiator 的存在既不是活性证明也不是授权—— 只是同进程的因果标注；主体与 owner 永远显式传递。

6.4 setup window：发布前组装 scoped 世界

CreateAgentOptions.setup / ResumeAgentOptions.setup 是一个回调，签名是 (agentCtx: Context) => commit | Promise<commit | void> | void。 它是最重要的组装窗口，时序契约一句话：工厂铸造出 agentCtx 之后、 插入或公告 session 与 agent 之前 await 它。后果是观察者永远看不到 半配置的世界：通过 agentCtx 注册的一切（scoped 工具、prompt section / 变量、restrict()、监听器、await 的子插件）在 session/created、agent/created、agent/session-start 和第一次 prompt 组装之前全部就位。

  • setup 只组装，从不驱动：回调拿到完整 scoped 上下文（可信同进程代码）， 这是契约而非运行时限制——创建 resolve 之后才能驱动 agent。
  • setup 可以返回一个同步的 AgentSetupCommit，其 commit() 在所有 setup await 落定后、发布前一刻被调用——让可变的配置在确切的发布边界重新校验。
  • setup 抛错、commit 抛错、owner dispose，都会整体回滚： 两个 id（session 与 agent）都不发布。
  • resume 的 setup 同构：先加载持久化，再铸造 agentCtx、await setup， 期间重建的 session 与 agent 都未发布。

preset 系统就长在这个窗口上：ctx.agentPresets.mount(agentCtx, id) 的唯一受支持调用点就是工厂的 setup(agentCtx) 钩子——只有在那里 join 才能保证「组合失败 → 整个创建回滚」而不是留下半组装的会话（第 3 章组装、 第 14 章子代理都会回到这里）。

6.5 Scope 机制：agent 就是自己 scope 的 key

「通过 agentCtx 注册的东西是 agent 局部的」这句话的机制在 packages/core/scope。先记三个身份事实：

  • 它是一个库，不是 Cordis 服务——没有 ctx key，模块图里坐在 session 与 system-prompt 之下，好让它们用得起而不成环。
  • ScopeKey 是不透明的对象身份（type ScopeKey = object， 按同一性比较）。原语从不检查对象内容。
  • 出货的 loop 里，活 Agent 对象就是自己的 scope key： agent-loop/src/agent.ts 里 this.scope = createScope(loopCtx, this)， 然后 this.ctx = this.scope.ctx.extend({ agent: this })—— 你读到的 agent.ctx 就是这个带 scope 标签、又带 ctx.agent DX 访问器的上下文。

createScope(ctx, key, options?) 铸造一个 scope： 它在 ctx 下挂一个共享空插件（拥有全部注册的生命周期）， 把 key 写进派生上下文的标签位（scopeOf(ctx) 可读回）， 返回 { ctx, rawDispose, dispose }——rawDispose 保留 Cordis 确切 disposer 身份（给有序组合 effect 嵌套用），dispose() 是共享的静止拆卸边界。

一对方向相反的能力由同一条父链（bindScopeParent，防环）驱动：

  • 注册视图沿链向下继承：子 scope 看得见祖先的层 （ScopedLayers.chainLayers——这是下一节 shadowing 的基础）。
  • 事件准入沿链向上放行：scopeTarget(base, key) 造出路由载体， 未打标签的监听器全局放行，打了标签的监听器只有「匹配 key 或其祖先」才收到—— 祖先 scope 的监听器能收到所有后代 scope 的事件， 事件沿链上流，永不下流。这就是为什么一个常驻组合 （比如某个 preset 的 standing mount）能观察它下面组装的每个 agent。

6.6 Shadowing：最具体的 scope 胜出

现在看注册表这侧。scope 感知的注册表（ctx.tools、 ctx.systemPrompt……）用 ScopedLayers<L> 存两层： 一个急切构造的全局层，加每 scope 惰性创建的覆盖层。 读取用 merge()： 

// ScopedLayers.merge 的效果（示意）
merged = new Map(全局层的命名项)
for (layer of 沿父链由远到近的 scope 层)
  for ([name, value] of layer) merged.set(name, value)
// 同名时后写覆盖先写 → 链上最近的 scope 拥有最终发言权

规则就一句：最具体的 scope 胜出。同名注册在 agent 层出现， 就遮蔽（shadow）全局层的那一个——被遮蔽的注册没有卸载： 它还在全局层里，其他 agent 照常解析到它；只有这个 agent 的视图里， 自己层上的同名项盖住了它。注册与拆卸对称：经 ctx.effect() 拥有， undo 之后若整个层空了，层本身被回收。

这是 per-session 人格的底层机制。dsh-persona 插件 注册一段 deployment:persona prompt section——与 system-prompt 自己无条件注册的那一段同名。全局挂载会撞名失败（部署人格已有 owner）， 它被设计成只能在 agent scope 里挂载：preset 组合时， 该 agent 的视图里 persona 插件的文案遮蔽部署文案。可选 complete: true 甚至在组装完成后把该 agent 的系统提示词恢复成只剩这一段。 遮蔽改变的是视图，不是世界——同一个进程里别的 agent 一无所知。

scope 链还能更长：preset 的 standing mount 在进程里挂一次 （在 roster 服务自己的 fiber 下），每个点名它的会话把自己的 agent scope key 父子链接到 mount 的 key 上。于是该 agent 的视图解析顺序是 agent → preset → global：mount 层上的工具与 prompt section 对所有加入的 agent 生效且实例只有一份（插件按 Session/Agent 键控自己的状态）， 而 sibling preset 的监听器对它保持「聋」。

6.7 lineage 是数据，不是可见性

最后一组容易混淆的概念：会话的谱系（lineage）与运行时的可见性 / 所有权。 第 4 章见过 SessionHeader 的谱系字段：parentSession（从谁 fork/resume）、 seedLength（继承前缀多长）、origin: 'subagent'、 delegationDepth（递归预算，持久化就是为了熬过重启）。要点是：

谱系是数据，记在 header 里，供 UI 展示、递归预算、fork 导航用。 它不创造任何运行时可见性——父不自动看到子：父 agent 不会因为 header 里写着 parentSession 就收到子的事件或读到子的日志。

运行时的关系另有其人，两者刻意独立：

  • runtime 所有权：注册表 entry 上的 owner 字段—— 「这个子 agent 是经哪个确切父 agent 的 scoped 上下文创建的」 （isOwnedBy(id, owner) 查询）。resume 出来的 fork 没有 runtime 父， 仍然是 root——耐久谱系不影响这个运行时关系，反之亦然。
  • 事件可见性：scope 链的向上放行（6.5 节）。谁想观察子， 就在合适的祖先 scope 上挂监听器（preset 的 standing mount 观察它下面所有 agent 就是这么来的）；或显式传引用。没有「因为我是父亲所以自动收到」的隐式通道。
  • initiator 归属：进程内异步链上的因果标注 （currentInitiator()），第 14 章子代理会看到它怎么用于归因。

把三者分开的价值在边界上显形：重启之后 runtime owner 和 initiator 都没了， 只剩 header 里的谱系数据；跨进程 / 跨 wire 时（第 20 章 Typert RPC）， 连 Agent 对象都不再是同一个，只有 id 与谱系可传。 「数据归日志，关系归运行时」，这条线贯穿 dsh 的所有边界设计。

6.8 本章回顾

  • Agent 是公共接口（id/session/inbox/status/ctx + send 族 + cancel/whenIdle/runMaintenance），实现是 agent-loop 的私有物；ctx.agents 管活注册表，AgentHandle.dispose 是能力，拆卸顺序：停 loop → 注销 → 移会话 → 展开 scoped 世界。
  • agent/* 事件分三组：生命周期观察（emit）、拦截扩展点（pre-step / request / request-error 三个 waterfall，必须调 next()）、turn-stopping（serial，反对靠 steer 数据）+ agent/error 通知。会话事件是耐久事实，agent 事件是活扩展点。
  • create/resume 走 AgentFactory 接缝：loop 经 setFactory 注册，消费者只依赖 ctx.agents——接口与驱动分离，loop 可整体替换。
  • setup window 在发布前组装 scoped 世界：agentCtx 铸造后、双公告前 await；一切注册就位于第一个事件与首次 prompt 组装之前；失败整体回滚；可选 commit 在发布边界重校验。
  • scope 是库不是服务：ScopeKey 是不透明对象身份，活 Agent 对象就是自己的 key；agent.ctx = 带标签的 scoped 上下文。
  • shadowing：ScopedLayers 的全局层 + scope 覆盖层，merge 时沿父链由远到近、最近胜出；被遮蔽的注册不卸载。persona 插件靠它实现 per-session 人格（只能 scoped 挂载，全局挂载撞名失败）；preset standing mount 让视图解析变成 agent → preset → global。
  • 谱系是数据不是可见性：parentSession/delegationDepth 记在 header 供预算与导航；runtime owner（isOwnedBy）、scope 链的事件放行、initiator 归属是三个独立的运行时关系，父不自动看到子。
常见误区
  • 插件直接 import agent-loop 拿驱动。扩展件只依赖 agent（接口层）；需要发起者时用 ctx.agents.currentInitiator()。
  • 在 waterfall 监听器里不调 next() 就返回。pre-step / request / request-error 的链会当场短路，下层全部失效。
  • 以为 persona 插件能全局挂载然后按会话开关。同名注册相撞会大声失败——它被设计成只能在 agent scope（preset 组合）里挂载。
  • 把 header 里的 parentSession 当运行时父子关系用。谱系是数据：重启后仍在、但既不给事件可见性也不给拆卸权；runtime 所有权用 isOwnedBy 查。
  • 在 setup 里驱动 agent。setup 只组装、从不驱动；创建 resolve 之前任何 send/followup 都是误用。
