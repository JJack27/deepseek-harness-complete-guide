执行世界：shell、subprocess、terminal、sandbox

上一章你学会了 seam 方法论；本章进入它最重的应用现场。执行世界（execution world） 指模型命令实际发生的地方——进程、文件系统、终端共同构成的一个连贯环境。 dsh 用一组互相咬合的 seam 把它组织起来：ctx.shell 执行命令、ctx.subprocess 生成进程树、ctx.terminals 持久 PTY、ctx.sandbox 约束进程、 ctx.e2b 把整个世界搬到云端。读完本章，三种部署路线（本机直跑 / 本机沙箱 / E2B 云沙箱） 在你眼里会是同一张图的三种 provider 选择。

学习目标
  • 能画出执行世界的分层：模型工具 → shell / terminals seam → provider → subprocess / sandbox 底座
  • 能讲清 ShellExecutor 的词汇与 request/spec split，以及为什么默认值解析必须是显式的 resolve() 步骤
  • 能描述 ctx.subprocess 的进程树语义（tree-scoped 终止、stdio 三种处置、环境擦洗）与 PTY 原语
  • 能解释 ctx.sandbox.confine(argv, policy) 的包装模型、三种模式只管文件效果、fail-closed 语义，以及 sandbox-policy 为什么是共享 home
  • 能区分一次性 bash 与持久 terminal 会话，并说出 E2B 与 pwsh 家族在图中的位置

12.1 全景：一个执行世界，三条路线

先看整张图，再逐层拆解。模型可见的工具在最上层——它们全都是第 11 章定义的 Consumer。 中间是 seam 层：一次性命令走 ctx.shell，持久会话走 ctx.terminals， 两者脚下是同一个 ctx.subprocess 进程底座；沙箱不是第四个平行世界， 而是 provider 在 spawn 之前插入的一道包装（ctx.sandbox + ctx.sandboxPolicy）。 最下层是三条可切换的路线。

dsh-sandbox README 有一条容易被误读的边界：same-world confinement only。 bwrap/Landlock/Seatbelt/ACL 后端与宿主共享文件系统和内核，它们只是把 spawn 的 argv 包一层约束； 容器、微虚拟机、远端执行器不是这个 seam 的 backend——它们替换的是整个 ctx.shell / ctx.fs 的 provider（环境一致的组）。记住这条，后面的 confine 模型就不会想偏。

12.2 ctx.shell：执行 seam 与 request/spec split

ShellExecutor（ctx.shell）定义了「一个 bash 后端做什么」——跑前台命令、启动后台进程 ——而不说怎么做。它的 API 很小：

成员语义
run(spec)前台执行，命令结束时 resolve。只有基础设施失败才 reject（不可用的工作目录、缺 shell、预中止信号）；非零退出、超时击杀、中止击杀都以带说明的 ShellRunResult resolve。
start(spec)后台执行，立即返回无 Task 的 ShellProcess 句柄，不设超时；调用方可把它适配进 ctx.jobs。
sandboxMode能力事实：SANDBOXING 执行器报告其约束默认模式；基类为 undefined（「不沙箱化」）。
ShellProcess.readOutput()增量读取——连续读取不会重复投递；因缓冲上限丢数据的读取标记 lossy 并指向完整 spill 文件。
ShellProcess.kill()杀整个进程组；已结束返回 false。

「非零退出不是错误」这一条值得停下来体会：模型写了一条会失败的命令，这是结果而不是事故。 tool-bash 因此只在 spawn 错误与中止时产生 isError，退出码留给模型自己解释 （工具的 tool:bash prompt section 正是提醒模型检查 [exit code: N] 标记）。

词汇上，ShellExecRequest（command、workdir?、timeoutMs?、stdoutMaxBytes?、signal?、stdin?、env?、dshEnv?、sandboxPolicy?） 在执行前被解析成 ShellExecSpec（全部必填或显式可空）。这就是 AGENTS.md 点名的 request/spec split 模板：

request/spec split

显式 > 隐式 at package boundaries：默认值解析是 owning 实现里一个显式的 resolve(request): Spec 步骤，绝不能藏在 run() 里的 ?? default。 dsh-shell 是这个约定的范本：sandboxPolicy 在 request 上可选、在 spec 上必填可空—— 解析完成后，执行器拿到的 spec 是完全显式的，没有「没传就偷偷用某个默认」的暗道。 部署差异化的选择（超时、输出上限）由 provider 的 Config 供给，从 cordis.yml 校验进来。

本机 provider dsh-bash-local 的行为轮廓（细节在第 8 章工具管道之外，这里看执行器侧）：

  • 每次调用 spawn 一个全新的非登录 bash -c，无 rc 文件、无 shell 状态——需要目录就传 workdir，别指望 cd 留存。
  • 配置预算：默认前台超时 timeoutMs: 120000、上限 maxTimeoutMs: 600000、每流内存上限 maxOutputBytes: 64000（溢出 spill 到磁盘）、graceMs: 3000 击杀宽限。
  • 超时/取消分类：只有执行器自己的超时报 timedOut，上游取消报 aborted，命令自己收信号则两者皆非。
  • 模型友好的终端环境：NO_COLOR=1 TERM=dumb PAGER=cat GIT_PAGER=cat，防分页器与 ANSI 颜色弄脏结果。

12.3 ctx.subprocess：进程树底座

dsh-subprocess README 的第一句就是定位：subprocess seam 是「一个执行世界的进程那一半」。 抽象 SubprocessRuntime 暴露可执行文件查找、普通受管 spawn、以及唯一的终端原语 spawnTerminal。它的直接 consumer 名单解释了「底座」二字：bash 执行器两家、PTY 后端 terminal-bash、LSP 宿主 lsp-stdio，还有三个进程外子代理后端（acp、codex、claude-code） ——所有要起进程的能力都从这一条缝走。

契约要点（packages/subprocess/subprocess/README.md）：

  • spec 完全显式——argv、cwd、每流 stdio 处置、grace 全部由调用方给出； argv 永不被 shell 解释，想要 shell 的消费者自己传 ['bash', '-c', command]。 工作目录与可执行路径属于 provider 的执行世界：resolveExecutable 在那个世界里解析 PATH。
  • stdio 三种处置：'pipe' 把原始流交给调用者自己做协议框架 （LSP 的 JSON-RPC、ACP 的 ndjson）；'inherit' 直通父进程描述符；collect 模式 { maxBytes, spill? } 保留有界尾部、可选全量 spill 文件。collect 读取以全流字节偏移为准、 永不消费——多个独立读者不会互相抢增量；偏移滑出内存尾部的读取标记 lossy 并指向 spill。
  • 终止是树作用域的（所有平台）：POSIX detached 进程组 + 直接子进程回退； Windows 走 taskkill /T。唯一的终止动词 terminate() 按 SIGTERM → grace → SIGKILL 升级；waitForExit() 观察整棵树的存活， 让消费方的拆除阶梯在真正的静默上收尾。管理者只反应，不分类原因——期限、阶梯、原因归类都归调用方。
  • 环境擦洗单源：scrubbedParentEnv() / SENSITIVE_ENV_PATTERN 是唯一共享的擦洗定义——环境里的凭据形名称与 DSH_* 名被丢弃，显式 env 在擦洗后合并。 服务 dispose 时终止所有仍在运行的受管进程并等待退出。

本地实现 dsh-subprocess-local（LocalSubprocessRuntime）有一个反直觉的特点： 它没有任何 config。每种处置、上限、终端尺寸、grace、目录都来自调用它的能力 seam （bash-local、lsp-stdio、terminal-bash）。PTY 由 node-pty 分配，配合平台进程检查； spill 文件是 0600 权限、藏在 0700 的每进程私有目录里。这也是 request/spec 哲学的延续：部署差异归上层能力的 Config，底座只做机制。

12.4 ctx.sandbox：spawn 前的约束包装

沙箱 seam 的契约可以压成一行：ctx.sandbox.confine(argv, policy) 返回「改跑这个」的 argv——消费者把自己正要 spawn 的确切 argv 交给 provider，拿回一个包装后的 argv 直接去 spawn， 外加后端的执行完备度（enforcement）、拒绝方言签名（denialSignatures） 与结构化 runner 失败证据。没有可用后端时它抛异常而不是放行未约束的执行——fail closed。

三条硬事实：

  • 模式词汇只覆盖文件效果：read-only（默认，禁止一切写入，仅 /dev/null 例外）、 workspace-write（只许写 workspaceRoot 与临时区）、danger-full-access（不约束，不询问 provider）。 网络与进程可见性刻意不在词汇里——模式不假装覆盖后端不强制的东西。
  • 平台后端在 sandbox-local 里选型：Linux 优先探测可用的 bwrap，否则 Landlock 启动器； macOS 用 Seatbelt（sandbox-exec，allow-default + (deny file-write*) 加写白名单）； Windows 用 ACL restricted-token runner 链（dsh-sandbox-windows-acl，WRITE_RESTRICTED 令牌 + 按 workspace 派生的 SID）。 老内核 ABI 只覆盖部分访问类时如实上报 enforcement: 'partial'。 Landlock 启动器的源码记录处在 native/landlock-run/——npm 包 @deepseek-ai/node-addon-landlock-run（self-restrict-then-exec 启动器 + 功能探针 + CLI 参数词汇）， harness 与它同仓同锁文件，契约变更和消费方更新一起落地。
  • sandbox-policy 是唯一的策略 home。部署默认 mode（默认 read-only） 与回退 workspaceRoot（默认 process.cwd()）都在这里； ctx.sandboxPolicy.resolve({ session, mode }) 为每次调用解析出完整策略—— 显式批准 > 会话最后一次 sandbox/mode 事件（effectiveSandboxMode fold）> 部署默认； 会话不可变的 SessionHeader.cwd 经文件系统语义规范化后成为 workspaceRoot。 bash、fs、terminal 三个强制家族都读这同一份解析，谁也不能把 bash 和 fs 围到不同的根。 切换本身就是一个 log-only 的 sandbox/mode 事件——重启后靠重放恢复，两个会话互不可见对方状态。

沙箱拒绝的呈现路径也值得走一遍：受限命令失败时，stderr 带的是所选后端自己的拒绝方言 （bwrap 的 EROFS、Landlock 的 EACCES、Seatbelt 的 EPERM），执行器对照签名保守分类为 ShellRunResult.sandbox.denied: true——拒绝是结果事实，不是异常。 工具层把它渲染成 [sandbox: file access denied under <mode> mode]， 并在组合支持升级时附上提示：同一 turn 内可以用 sandbox_permissions（严格更宽的模式） + justification 重试一次，批准问题走 ctx.approval 询问用户。 后端完全不可用时抛 SANDBOX_UNAVAILABLE（附平台安装指引），绝不静默降级。

12.5 ctx.terminals：持久 PTY 会话

一次性 bash 每次都是全新的 bash -c，但有些工作需要持久的终端状态： 导出的环境变量、激活的 virtualenv、跑在前台的服务。ctx.terminals（dsh-terminal） 是 owner-scoped 的持久 PTY seam：铸造不透明 session id、经命名 backend 创建会话、 把每个操作围栏到确切的存活 Agent。dsh-terminal-bash 是本地 backend， 建在 ctx.subprocess.spawnTerminal 上——PTY 分配、环境擦洗、前台进程组、信号、 完整终端会话清理都归 subprocess provider，所以同一个 PTY backend 既配本机也配远端执行世界。

与一次性 bash 的对照：

tool-bash（一次性）tool-terminal（持久会话）
状态每次全新 bash -c，无留存cwd、导出变量、前台进程跨调用留存
进程形态受管进程树，普通管道真 PTY（spawnTerminal 原语），UTF-8 文本 I/O
工具面bash（+ 后台 job 适配）terminal_open / send / read / signal / close / list 六个工具
归属后台进程注册进 ctx.jobs，按 job 控制每个操作要求确切的发起 Agent——模型学到了别人的 id 也不能操作
就绪无需就绪概念私有 PS1 标记 + 前台 stdin-wait 事实 + 静默回退 + 绝对超时

家族里还有一个变体 dsh-tool-bash-persistent：模型可见的 bash(command) 工具， 但背后是每个 Agent 一条 owner-scoped 的 ctx.terminals shell——命令共享同一个 shell， cwd、导出变量、激活环境、函数、后台 job 都跨调用留存。它演示了「工具契约」与「执行面」的解耦： 同名 bash 工具，可以站在一次性 seam 上，也可以站在持久会话上。

12.6 E2B、pwsh 家族与 shell-env

E2B 是第三条路线（POC 定位）。dsh-e2b 拥有 ctx.e2b—— 一个 E2B 沙箱的共享生命周期 owner：构造即开沙箱（pin e2b@2.29.1），建好 cwd （默认 /home/user/workspace，必须绝对 POSIX 路径）与私有的 cwd/.dsh-e2b 状态目录， timeoutMs（默认五分钟）控制沙箱寿命、到期即删。fs-e2b 与 subprocess-e2b 注入它、await 同一个 SDK 句柄，于是文件工具与 bash/PTY/LSP 消费者落进同一个远端 Linux 世界—— 这是第 11 章「换 provider 搬走执行世界」的实例化。注意它的边界（README 明言）：Cordis 服务、 会话状态、session 日志、LLM 请求都留在宿主进程；沙箱状态是易失的，不做宿主同步。

pwsh 家族是 Windows 的对称设计。dsh-pwsh-local 逐条镜像 bash-local： 每次全新 pwsh -NoLogo -NoProfile -NonInteractive -Command <command>，命令串作为 单个 argv 元素传给 -Command（由 PowerShell 自己解析，没有中间 shell，也就没有转义层）； UTF-8 输出编码先行 pin 住；Windows 树终止走 taskkill，强杀结算为 exit 1 无信号。 dsh-pwsh-sandbox 镜像 bash-sandbox，约束实质是平台中立的：Windows 上解析到 ACL runner 链， Linux/macOS 上照旧 bwrap/Landlock/Seatbelt。dsh-tool-pwsh 则与 tool-bash 逐调用对齐 （前台/后台、DSH_* 环境、拒绝渲染与升级面）。

shell-env 补上受管环境的最后一块：它拥有 ctx.shellEnv 注册表—— 每次模型 shell 调用都会新采集一份可信的 DSH_* 快照（内建事实 DSH_HOME、DSH_SHELL=1、DSH_SESSION_ID，以及持久层定位到 JSONL 时的 DSH_SESSION_JSONL）。快照走专用通道 ShellExecRequest.dshEnv， 本地执行器先抹掉继承的全部 DSH_* 再合并快照——嵌套 harness、 并发的父子 agent 都无法把过期身份漏进子进程；process.env 永不被修改。 其他插件用 effect 作用域注册自己的受管事实，重名或未声明的运行时键都 fail loud。

12.7 本章回顾

  • 执行世界 = 进程 + 文件系统 + 终端构成的连贯环境；三条路线（本机 / 本机沙箱 / E2B）只是 provider 选择。
  • ctx.shell：run/start/sandboxMode；只有基础设施失败才 reject；request → 显式 resolve() → spec 是全仓模板。
  • ctx.subprocess：argv 永不被 shell 解释；stdio pipe/inherit/collect；树作用域终止（SIGTERM→grace→SIGKILL、taskkill /T）；scrubbedParentEnv 单源擦洗；本地实现零 config。
  • ctx.sandbox.confine(argv, policy) 返回改跑的 argv；三模式只管文件效果；fail closed 抛 SANDBOX_UNAVAILABLE；Landlock 启动器源码在 native/landlock-run/。
  • ctx.sandboxPolicy 是唯一策略 home：sandbox/mode 事件 + 会话不可变 cwd，三个强制家族共享同一份解析。
  • ctx.terminals 持久 PTY：owner 围栏、六工具、就绪推断；terminal-bash 站在 spawnTerminal 上，随执行世界一起搬迁。
  • E2B（ctx.e2b + fs-e2b + subprocess-e2b）是云端执行世界的 POC；pwsh 家族是 bash 的逐调用镜像；shell-env 管住 DSH_* 受管环境。
常见坑
  • 把非零退出码当 isError——只有基础设施失败（spawn 错误、中止）才是错误；退出码是模型要解释的结果。
  • 期待 cd 或导出变量在一次 bash 调用后留存——每次都是全新 bash -c；要状态就用 workdir、env 或持久 terminal。
  • 在 run() 里藏 ?? default——默认值解析必须走 owning 实现的显式 resolve(request): Spec。
  • 以为沙箱模式管网络/进程——词汇只覆盖文件效果；容器与微虚拟机不是 sandbox backend，是整组 provider 替换。
  • 绕过 ctx.subprocess 自己 spawn——进程树终止、环境擦洗、spill、dispose 清理全都随之丢失。
  • 期望 E2B 同步宿主工作区——远端 cwd 只是一个空目录，上传/回写都不在 POC 范围内。
