Cordis 心智模型：Context、插件、服务、事件

第 1 章说 dsh 是「一棵插件树」。本章讲这棵树生长的土壤：Cordis 插件框架。 Context、插件、服务、事件、效应——五个概念吃透，全书后面任何一章的代码你都能直接读懂。 这是全书最重要的基础章，值得慢读。

学习目标
  • 能说出 Cordis 在 dsh 里的位置，以及「一切皆插件、没有特权核心」意味着什么
  • 能把 Context（ctx）解释成「服务仓库」，并按 key（如 ctx.tools）找到服务
  • 能读懂两种插件写法：函数插件和 Service 子类，以及 inject 如何表达加载顺序
  • 能解释「注册即效应」：为什么一切贡献走 ctx.effect() / ctx.on()，卸载如何自动退场
  • 能区分四种事件分发模式，并准确描述 waterfall 的 next() 语义与短路后果

2.1 Cordis：dsh 脚下的地板

dsh 没有从零发明插件系统。它站在 Cordis 上——一个开源插件框架， 设计思想写在论文《A Programming Paradigm for Spatiotemporal Composability》里（现在读不读都行）。 你可以把 Cordis 理解为「dsh 的操作系统内核替代品」：它不管进程和内存，它管插件怎么挂载、 怎么找到彼此、怎么通话、怎么退场。

一个对本书很重要的事实：Cordis 的源码不在 node_modules 里，而在仓库的 vendor/ 目录。

  • vendor/ 是钉住的上游源码副本（pinned）：每份都记录着上游 commit， 可以审计、可以打补丁、版本钉死，不跟 npm 上的版本漂移。
  • 所有 vendored 包被改名为 @deepseek-ai/ 作用域：cordis → @deepseek-ai/cordis。这样发布 dsh 时等于连这层框架一起发布，也不会在 npm 上冒名占用上游包名。
  • 每个 harness 包都把 @deepseek-ai/cordis 声明为 peerDependency： 整棵树共享同一个 Cordis 实例。
  • 想更新 vendored 代码，走 vendor/README.md 里写明的同步流程，重新套用（或撤销）记录在案的本地修改。

在这套地板上，dsh 立了一条贯穿全仓库的宪法：everything is a plugin。 模型适配器是插件，工具注册表是插件，会话日志是插件，连 agent loop 本身也是插件—— 全都可以在配置层替换。这意味着没有特权核心可打补丁： 你扩展 dsh 的方式不是 fork 一份核心代码，而是把自己的插件挂到其他插件旁边。 「怎么挂」是第 3 章的主题；本章先讲挂上去之后，插件之间如何共存。

2.2 Context：一张共享的服务桌子

每个插件被 Cordis 挂载时，都会拿到一个 ctx（Context 实例）。 把它想成一张大家共用的桌子：Context 是服务的仓库。一个服务在桌上占一个稳定的 key，别的插件通过 key 取用，而不是 import 某个具体实现类。

你已经见过几个 key 了（第 1 章的表格里那一列）：

  • ctx.tools —— 工具注册表与执行管道（core/tools）
  • ctx.sessions —— 会话事件日志（core/session）
  • ctx.systemPrompt —— prompt 装配（core/system-prompt）
  • ctx.llm —— 模型适配器接口（llm/llm）
  • ctx.agents / ctx.agentLoop —— 在线 agent 注册表 / 默认循环

「按 key 找服务」带来一个关键性质：接口与实现分离。调用方（比如 bash 工具） 只依赖 ctx.shell 这个名字和它的 TypeScript 类型；至于背后是本地实现还是沙箱实现， 由配置决定。换实现不用改一行调用方代码——这就是第 1 章说的「一切皆可替换」落到实处的机制。

那「一个服务」在代码里长什么样？它是 Cordis Service 的子类，构造时把自己的 key 报给 Cordis。看真实代码——工具注册表（节选自 packages/core/tools/src/index.ts）： 

// packages/core/tools/src/index.ts（节选、简化）
export class ToolRuntime extends Service {
  static inject = ['systemPrompt']   // 我需要 systemPrompt 服务才能激活

  constructor(ctx: Context, config: Config = {}) {
    super(ctx, 'tools')              // <-- 在 ctx 桌上占的 key 就是这个
    …
  }
}

super(ctx, 'tools') 的第二个参数，就是这个世界里最重要的一个字符串： 它决定了别的插件从 ctx.tools 取到的就是这实例。

那 ctx.tools 的 TypeScript 类型从哪来？不是 dsh 手工维护一张中央注册表， 而是用声明合并（declaration merging）：工具包在自己的文件里向 Cordis 的 Context 接口「合并」进一个成员—— 

// packages/core/tools/src/index.ts（节选）
declare module '@deepseek-ai/cordis' {
  interface Context {
    tools: ToolRuntime      // 从此 ctx.tools 有类型
  }
}

每个服务包都这样贡献自己的 key；合并出来的 Context 接口就是整张桌子的「菜单」。 事件类型也用同样的机制扩展（见 2.5 节）。

Service Definition：接口与实现分离的名字

本书后续会把「声明某个 key 上该有什么接口」的代码叫 Service Definition（服务定义）， 把「真正实现这个接口的插件」叫 Service Provider（服务提供者）。dsh 的规范是一句话： 扩展插件依赖 Service Definition，绝不依赖具体 Provider。 这就是为什么 dsh-agent-loop 可以被整体换掉而 UI、工具插件毫发无伤。

2.3 插件长什么样：函数，或 Service 子类

Cordis 里的插件只有两种写法，dsh 两种都用。

写法一：函数插件。一个带 name、inject、apply 三件套的模块。 真实例子——bash 工具（packages/shell/tool-bash/src/index.ts）：

// packages/shell/tool-bash/src/index.ts（节选）
export const name = 'tool-bash'
export const inject = ['tools', 'shell', 'systemPrompt', 'shellEnv']

export function apply(ctx: Context, config: Config = {}): void {
  // 在 ctx.tools 上注册 bash 工具；调用 ctx.shell 执行命令
}

apply(ctx) 在插件挂载时被调用，ctx 就是它的入场券。 适合「往别人的服务上注册点东西」的插件——dsh 里大多数能力插件都是这种。

写法二：Service 子类插件。像上面的 ToolRuntime 那样继承 Service，Cordis 把它的生命周期（构造、启动、停用）挂进当前 context。 适合「自己就是一个服务、要在桌上占个 key」的插件。

两种写法共用的关键字段是 inject：

inject：用服务需求表达加载顺序

inject 声明「我要这些服务」。Cordis 会等这些服务都存在了才激活这个插件。 于是加载顺序不再靠手工排序，而是靠依赖关系自然涌现： tool-bash 声明需要 tools 和 shell， 所以无论配置里两行谁先谁后，它都不会在服务缺席时启动。谁等谁，代码自己说了算。

回头看第 1 章那张 core 表格，现在能读出第二层含义：core/agent-loop 依赖 ctx.agents 声明的接口，但它只是一个插件——把它从配置里换掉，换上一个你自己写的循环， 其余插件照常工作。「一切皆插件」不是口号，是 inject 撑起来的事实。

2.4 注册即效应：一切贡献都可退场

插件在 apply（或构造）里做的事，统称「贡献」：注册一个工具、加一段 prompt、 订阅一个事件、装一个模型适配器。dsh 的铁律是：注册即效应（registrations are effects）—— 一切贡献必须走 ctx.effect() 或 ctx.on()，并且拿到处置器（disposer）。

  • ctx.effect(setup) 接收一个 generator 函数，你在里面 yield 出清理动作； 它返回一个 disposer，调用即撤销整套注册。
  • ctx.on(event, listener) 订阅事件，返回值就是退订函数。
  • 注册表风格的 API（比如往 ctx.tools 注册工具）返回的也是 disposer—— 「注册的返回值就是注销函数」是通用约定。

真实代码（简化自 ToolRuntime.presentAs，packages/core/tools/src/index.ts）： 

const dispose = ctx.effect(function* () {
  yield this.layers.effect(ctx, layer => {
    layer.mode = mode
    return () => { layer.mode = undefined }   // 清理：还原
  })
  yield ctx.systemPrompt.section(this.sdkSection()) // 返回值同样是退场函数
})
// dispose() 一调，上面两件事按相反顺序全部撤销

为什么把「注册」抬到「效应」的高度？因为可逆性：

  • 插件卸载时，它做过的所有注册自动、按序退场——树始终保持一致；
  • 热更新（HMR）靠它：换一版插件 = 卸旧挂新，不用重启进程；
  • 测试靠它：每个用例挂自己的小树，结束拆掉，互不污染。

反过来的推论同样重要：绕过 ctx.effect() 直接改全局状态，等于在树上留下一处 卸载时无人打扫的脏东西。dsh 的代码评审会把这当成缺陷，而不是风格问题。 如果卸载顺序重要，把相关的几件事放进同一个 effect 里， 让清理按你 yield 的反序解开。

2.5 事件：插件之间的通话方式

服务方法适合「直接使唤」：ctx.shell.run(...) 就是跑一条命令。 但很多场合你需要的是旁观或拦截——工具要执行了，我想检查一眼、改一下、甚至否决它。 这就是事件的领地：ctx.on() 订阅，四种方式分发。

四种分发模式是理解 dsh 事件系统的钥匙（来自 docs/cordis-primer.md）：

模式等待监听器？顺序有返回值？典型用途
emit否按注册顺序无纯观察：工具跑完了、注册表变了
waterfall否按注册顺序有包裹与拦截：改写请求、否决调用（洋葱模型）
parallel是并行无扇出通知：广播给互不依赖的观察者
serial是按注册顺序有有序处理且要结果

注意两件事。第一，分发模式是事件公共契约的一部分：同一个事件只能用属于它的那一种方式分发， dsh 要求新事件的 JSDoc 用 @mode 标注，生成的目录会据此核对声明与分发点是否一致。 第二，事件名里的类型也是声明合并出来的——和 Context 接口同一招，只是这次合并的是 Events 接口： 

// packages/core/tools/src/index.ts（节选、简化）
declare module '@deepseek-ai/cordis' {
  interface Events {
    /** Allow, deny, or ask before dispatch. …
     *  @mode waterfall */
    'tools/pre-execute'(exec: ToolExecution,
                      next: () => Promise<PreToolDecision>): Promise<PreToolDecision>
    /** Observe the frozen final outcome. …
     *  @mode emit */
    'tools/result'(exec: readonly ToolExecution,
                  result: readonly ToolExecutionResult): undefined
  }
}

读这段真实声明能学到三件事：tools/pre-execute 是 waterfall（有 next、有返回值）， 用于「放行 / 拒绝 / 先问人」的决策；tools/result 是 emit（无返回值），用于观察最终结果； 每个事件的 JSDoc 写明契约，@mode 让工具可以机器核对。

2.6 waterfall：洋葱、包裹与短路

四种模式里最值得吃透的是 ctx.waterfall()——dsh 的拦截层全部建在它上面： agent/pre-step、agent/request、llm/stream、 tools/pre-execute、tools/execute、tools/post-execute 全是 waterfall （对照：agent/turn-stopping 是 serial，没有 next）。

语义一句话：waterfall 是 around 中间件。监听器收到 (…args, next)：

  • 调 next()：把（可能改写过的）请求交给下一层；next() 的返回值是下层的结果；
  • 不调 next() 就返回：整条链在此短路——后面的监听器和真正的执行都不会发生， 你的返回值成为最终结果。

用伪代码把两种结局写出来：

// 协作型监听器：改一改，然后放行
ctx.on('tools/execute', async (exec, next) => {
  exec.timeoutMs = 30_000                    // 包裹：改写共享请求
  return await next()                        // 必须放行，结果从这层返回
})

// 决策型监听器：我拥有这个决定，到此为止
ctx.on('tools/pre-execute', async (exec, next) => {
  if (exec.name === 'bash' && isDangerous(exec.args)) {
    return { kind: 'deny' }               // 不调 next()：短路即否决
  }
  return await next()                        // 其余放行
})

什么时候短路是对的、什么时候是事故？判据一句话：

  • 单决策事件里，短路是设计。一个策略监听器拥有决策权时（拒绝一条危险命令）， 不调 next() 就是它的表达方式。
  • 只标注或观察的监听器必须调 next()。忘调 next() 的包裹层不是「跳过自己」， 而是「掐死后面所有人」——后面的监听器和真正的执行全部静默消失，这是 dsh 文档里反复强调的事故模式。
  • 另外两个小知识：结果值沿 next() 的返回值往回传；监听器也可以整体替换下层结果， 下游看到的将是替换后的值。prepend: true 只在该监听器必须先于普通注册运行时使用。

2.7 三个事件域：先见森林

dsh 的事件按「事实属于谁」分三个域。现在只需要认识这三个名字和选域的直觉， 每个域后面都有整章展开：session events 第 4 章、agent events 第 6/7 章、 capability events 第 8/11 章。

事件域例子本质什么时候选它
session events user/message、assistant/message、tool/call、turn/* 持久事实，追加进会话日志并通过 session/event 广播 这个事实必须活过重启、要能被回放
agent events agent/pre-step、agent/request、agent/turn-stopping 携带一个活的 Agent：收件箱、步骤、状态、请求、校验、续跑 想观察或拦截进行中的工作
capability events tools/*、fs/*、telemetry/* 能力 seam 上的策略与适配器挂点 想给某个能力加策略而不碰 agent loop

选域的直觉：事实要留痕 → session；盯着正在跑的活 → agent；给能力加政策 → capability。 dsh 的架构文档说「事件就是扩展点，选对域是大多数改动的第一个决策」——这句话你会在第 24 章实践时反复体会到。

补一句：模型可见 ⟺ 已记录

dsh 还有一条和事件域相关的铁律，先记住结论（第 4 章展开）：凡是到达模型请求的内容， 都必须能从会话日志重建。想新增一种模型可见的输入，就必须新增一个 session event—— 「模型看见的」和「日志里记的」永远一一对应。

2.8 本章回顾

  • Cordis 是 dsh 脚下的插件框架，vendored 于 vendor/（钉住的上游源码副本，rescope 成 @deepseek-ai/cordis，所有 harness 包以它为 peerDependency）；同步走 vendor/README.md 的流程。
  • 一切皆插件：模型适配器、工具注册表、会话日志、agent loop 本身都是插件，都能在配置层替换；没有特权核心可打补丁。
  • Context 是服务仓库：服务按 key 上桌（ctx.tools、ctx.llm、ctx.sessions…），插件按 key 取用；服务是 Service 子类，接口（Service Definition）与实现分离；类型靠声明合并。
  • 插件两种写法：函数插件（name + inject + apply）或 Service 子类；inject 声明服务依赖，加载顺序由依赖关系表达。
  • 注册即效应：一切贡献走 ctx.effect() / ctx.on()，注册返回 disposer；插件卸载时注册自动按序退场。
  • 事件四种分发模式（emit / waterfall / parallel / serial），模式是事件契约的一部分（@mode 标注）；waterfall 监听器必须调 next()，不调即短路整条链——单决策事件里短路是设计，观察型监听器忘了调是事故。
  • 三个事件域：session（持久事实）、agent（进行中的工作）、capability（能力上的策略）。
常见误区
  • 为了用某个服务去 import 它的实现类——按 key 从 ctx 取；依赖 Service Definition，不依赖 Provider。
  • waterfall 监听器忘了调 next()——不是「跳过自己」，是掐死后面所有层和真正的执行。
  • 期待 emit 事件有返回值——emit 只观察、无返回值；要包裹与拦截找 waterfall。
  • 把 ctx.effect() 当可选的风格偏好——绕过它直接改全局状态会留下卸载时无人清理的脏东西，这是缺陷。
  • 想改行为就去改 agent-loop——先找对应域的事件挂上去；改循环本身要更新架构文档，是最后手段。
  • 以为 vendor/ 是从 npm 装的普通依赖——它是钉住的源码副本，有自己的同步流程和本地修改日志。
