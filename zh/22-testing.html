测试体系：五条 vitest 通道与回放

前面二十一章你读了 dsh 的运行时；本章读它的「证明义务」。这个仓库把测试分成五条 vitest 通道——unit、e2e、snapshot、web、web-stress/perf——每条通道只回答一类证据问题， 谁需要密钥、谁在 CI 里跑、谁产出提交进仓库的金标准，都有明确分工。读懂这套体系， 你才知道自己的改动「要补什么测试」，以及为什么包测试永远不能替代组装后的应用转录。

学习目标
  • 说出五条 vitest 通道各自的入口命令、include 模式与证据面。
  • 解释 test:coverage（而非 test）为何是 CI 覆盖率门禁，以及 per-file 100% 的含义。
  • 区分 DSH_SNAPSHOT 的 replay / record / refresh 三种模式各自需要什么、写不写金标准。
  • 描述 llm-replay 如何把持久化会话日志变成无密钥回放脚本，包括按 (turn, step) 分组与按首调顺序绑定子会话。
  • 复述 docs/testing.md 的核心政策：同一 PR 内用真实可运行 example 补 keyless 快照、fixture 在 macOS/Linux 可回放、修 fixture 而不是修 normalizer。

22.1 五条通道：一张矩阵

仓库根目录下每个通道一份独立 vitest 配置：vitest.config.ts（unit）、 vitest.e2e.config.ts（真实 API）、vitest.snapshot.config.ts（金标准回放）、 vitest.web.config.ts（浏览器）以及 vitest.web-stress.config.ts 与 vitest.web.perf.config.ts（压力与性能）。它们不是按「快慢」分层，而是按 证据面分层：unit 证明包内行为，e2e 证明真实 provider 行为，snapshot 证明 组装后的完整转录，web 证明浏览器里的真实渲染，stress/perf 证明 Web 界面在负载下的表现。

注意矩阵里一个容易忽略的细节：e2e 的「无则自跳过」不是降级运行，而是整段 suite 直接 skip——无密钥的 CI 与无密钥的贡献者永远看到绿色，但这不是成本信号。真正的 provider 证据只来自带密钥的那次运行。反过来，snapshot 的 replay 是完整证据：它 会真实组装 ACP/headless example、真实跑完进程与协议，只是把模型响应换成录好的脚本。

22.2 unit 通道与覆盖率门禁

vitest.config.ts 的 include 列表划定了 unit 通道的疆域： 

const testIncludes = [
  'packages/*/*/tests/**/*.spec.{ts,tsx}',
  'apps/*/tests/**/*.spec.ts',
  'examples/*/tests/**/*.spec.ts',
  'scripts/**/*.spec.ts',
]

测试与被测代码住在一起（tests 留在它们考察的代码区域旁）。配置里有两个 vitest project： thread-safe 与 process-bound——后者收纳那些依赖进程全局状态或 时敏进程 I/O、无法在聚合门禁竞争下被 worker 线程可靠隔离的 suite（如 packages/session/session-persistence-jsonl/tests/jsonl.spec.ts、 packages/boot/app-boot/tests/app-boot.spec.ts），两边都用 forks 池跑 Node 稳定性。 所有 suite 都加载 scripts/test-invariants.ts 这个 setup 文件。

docs/testing.md 给 unit 通道定了三条写作纪律。其一，每个注册表都要有一条 HMR-safety 测试：dispose 掉贡献它的 fiber，断言清理干净——这是第 3 章「注册即效应」 在测试侧的映照。其二，优先写边界情形、错误路径、事件顺序、并发竞争。其三，契约回归要 有永久测试，范例是 packages/core/agent-loop/tests/contract-regressions.spec.ts。

覆盖率：门禁是 test:coverage，不是 test

CI 的覆盖率门禁是 pnpm run test:coverage（vitest run --coverage）：对 packages/*/*/src 按文件执行 statements / branches / functions / lines 全 100%。按文件而不是按总量，是为了让一个覆盖 良好的大文件补贴不了一个裸奔的小文件。配置里的每一处豁免（types-only 文件、bin/worker 薄入口、GUI 债务清单、Windows-only 源码等）都是显式列出并带理由注释的；比如没有真实 pwsh 的主机上，pwsh-local 的 executor suite 自跳过，配置随之豁免该文件， 而 CI 的 runner 带 pwsh，仍然执行完整门槛。

还有一条解读纪律：一条未覆盖的行，往往是门禁在正确地标记死代码该删， 而不是缺一条测试该补。行覆盖是必要条件，永不充分——它证明行跑过，不证明功能按发布形态 工作。后面三条通道补的就是这个「充分」的一半。

22.3 e2e：真实 API 与 with-key 政策

vitest.e2e.config.ts 只收 **/*.e2e.ts，且范围刻意收窄： packages/*/*/tests、apps/cli/tests（只有 cli，不是 apps/*—— apps/web 的 e2e 归 web 通道）、examples/*/tests。它花真金白银的 token，所以 配置处处体现这一点：120 秒 testTimeout、retry 2（共享内部密钥会撞并发配额，瞬时抖动重试）、 DSH_E2E_MAX_WORKERS（默认 4）限制并行文件数，且不做覆盖率——覆盖率归 unit 通道所有。

docs/testing.md 的 with-key 政策标题就叫「inference is cheap here」：不要省真实 API 测试。 无密钥测试只证明管道通；只有带密钥的运行才证明 agent 对真实模型工作。要覆盖写文件的 prompt、多轮对话、工具使用、中途取消。价值最高的是smoke 测试：启动真实 example、发一条 prompt、然后检查世界。它们专杀「unit 全绿、产品坏了」这一类故障—— mock 抓不到它，事后剖析记录在 docs/postmortem/0001-acp-default-export-drops-inject.md （一个 default export 悄悄丢掉了 inject）。

e2e 通道还有两条写作铁律。验证世界，而不是自证：断言要在 agent 外部重新跑 命令、重新读文件；对 agent 自身输出做关键字探测会让一个作弊的 agent 通过。没被碰过的文件 必须断言字节相同。e2e 测试拥有自己的资源：在测试里创建 harness，afterEach 里 dispose（失败、重试、超时也要）；共享 fixture 放在普通的 tests/harness.ts， 绝不放进另一个 *.e2e.ts——import 一个 spec 会重新注册它的 describe，把真实 API 调用翻倍。

真实实现优于 mock

只 mock 昂贵或非确定的边界——LLM adapter、网络、时钟；边界下游的一切保持真实。手搓的替身 只能证明桥在搬字节，不能证明发布的工具如断言那样工作。桥接工具调用测试用脚本化 mock 模型 配真实工具与执行器：makeBridgeHarness({ withBash: true }) 插上 dsh-bash-local 与 dsh-tool-bash，然后真的跑一遍 echo。

22.4 snapshot：record / refresh / replay

snapshot 通道的配置文件 vitest.snapshot.config.ts 收 scripts/**/*.snapshot.ts、apps/cli/tests/**/*.snapshot.ts、 examples/*/tests/**/*.snapshot.ts（DSH_EXAMPLE_MODE=lib 时再加 apps/web/tests）。它用 DSH_SNAPSHOT 环境变量切换三种模式：

模式命令密钥行为
replay（默认） pnpm run test:snapshot 免密 从已提交的金标准 fixture 回放模型响应，跑完整组装路径，比对组装后的请求、规范化协议/转录输出与重持久化的日志。从不写已提交的期望输出。
record pnpm run test:snapshot:record 需要 DEEPSEEK_API_KEY 真实调用 API，重跑场景，把模型响应与期望输出写回 fixture 与 expected 文件（配置注释原话：只有 record 从环境或根 .env 读密钥；replay/refresh 永不加载 .env）。模型转录变化时用它重录。
refresh pnpm run test:snapshot:refresh 免密 回放已提交的脚本但更新当前期望输出——回放输入仍然有效、只是输出侧需要刷新时用。每一条 JSONL 与 expected 的 diff 都要人工审。
试一试 —— 快照的 record / replay 两种模式
切换模式。

并行策略也按模式区分：replay 不写金标准且每个场景自持可变运行时状态，所以文件级并行，用 DSH_SNAPSHOT_MAX_CONCURRENCY（默认 5）限制文件内并发，值 1 可在受限机器上恢复 完全串行；record 与 refresh 保持串行——record 每个场景都在花真实 API 配额，refresh 的写回 会从磁盘上已有的 fixture 收割易变值，并发写手会毁掉金标准。

金标准的分布有明确归属：ACP 自动化场景在 examples/<name>/tests/snapshots/ （examples/acp-agent 是主场）；examples/headless-agent 拥有内部 canonical-event JSONL 快照与回放 fixture；apps/cli 单独拥有产品级 dsh --profile headless 验收；完成的交互式终端旅程用 apps/cli/tests/snapshots/ 下的 JSONL 驱动场景；浏览器渲染的 Web GUI 旅程在 apps/web/tests/snapshots/。还有一个著名的精细设计：只有一个 ACP 场景 （text-turn）钉住完整 system-prompt/tool-schema 内容，其余 fixture 把它 token 化，这样一次编辑只搅动一行。

22.5 llm-replay：会话日志就是 fixture

packages/test-support/llm-replay（包名 @deepseek-ai/dsh-llm-replay）是 replay 模式的发动机。它的核心洞见是： fixture 就是持久化的会话日志本身——<scenario>/session.jsonl。 第 4 章你学过 assistant/chunk 事件携带每一个 StreamChunk；把它们按 (turn, step) 分组，就能重建 agent-loop 每一次 stream() 调用的 chunk 序列。录制因此就是「把真实 agent 跑一遍，收割 .jsonl」——这个插件自己不录制。 

// ACP / headless snapshot 套件经 Loader 挂载它，顶替真实 LLM adapter
- id: llm-replay
  name: '@deepseek-ai/dsh-llm-replay'
  config:
    providers:
      - id: deepseek-official
        name: DeepSeek
        models:
          - id: deepseek-v4-flash
            contextWindow: 128000
  # file / overrideFile / childFiles 默认取 $DSH_SNAPSHOT_FILE 等
  # 环境变量，由 snapshot harness 按场景注入

日志推导覆盖不了两种失败形态：任何 chunk 之前就纯抛错（比如 HTTP 401，日志里只有 turn/end {error}）与取消/挂起（是时序问题，不是 chunk 内容）。需要它们的场景 提供可选 sidecar <scenario>/replay.override.json：要么整体替换派生脚本 （裸 ReplayEntry[]），要么按 0 基调用索引打补丁（{ patches: [{ at, entry }] }，at 等于派生长度时在注入的一次瞬态 throw 后追加重试尝试）。 sidecar 文档、每个 patch、每条 entry、每个 chunk 判别标签在文件加载时全部校验——misconfiguration fails loud 在这里同样是铁律。

嵌套 agent 是第二个精巧点。父 agent 委派进程内 subagent 的场景会录出多份日志： session.jsonl（父）加 session.1.jsonl、session.2.jsonl…… 每个 agent 是同一 context 上自己的 Session。live session id 每次运行都是新随机值， 永远不等于录制的，所以 replay 按首调顺序绑定：脚本按 header 的 createdAt 排序（父先——它必须先流式输出才能委派），第一个发起任意调用的 live session 认领第一份脚本，下一个新 session 认领下一份，各自推进自己的游标。live session 多于 录制脚本则 fail loud。

编程入口是 installLlmReplay(ctx, config)，返回 ReplayHandle： dispose() 保 HMR 安全，assertConsumed() 在 teardown 时断言每份录制 脚本都绑到了 live session、每个绑定游标都耗尽——把「场景悄悄少驱动了几次模型调用」变成一条 清晰诊断。Web 浏览器 e2e 通道不走 Loader，直接安装它以保留这个 teardown 消费句柄。

22.6 测试基建六件套

除了 llm-replay，packages/test-support/ 下还有五个支撑包。它们是 test-tier 基建，不是产品 API：

包角色
llm-replay 从录制会话日志重建模型流的无密钥回放插件（22.5 节）。
llm-mock-server 可脚本化的 OpenAI 兼容 HTTP/SSE 服务器， exercising 真实 LLM adapter、agent loop 与恢复策略而无需 provider 密钥。--sequence 是 FIFO 行为表：connection_reset、partial_disconnect、stall、rate_limit、success、tool_call_success……用 pnpm run mock:llm 起服务，把发布的 DeepSeek adapter 指过去（DEEPSEEK_BASE_URL）。
acp-snapshot ACP 快照套件工具箱，四层可分别 import：launchAcpTestAgent（进程启动器）、runScenario（场景 harness）、规范化纯函数组（stdout/会话日志/cwd token 化/system-prompt 与 tool-schema 清洗）、defineAcpSnapshotSuite（从一个场景表注册整棵 describe/it 树的工厂）。
agent-loop-testkit mountAgentLoopTestDependencies(ctx) 按依赖顺序装上 LLM、session、system-prompt、tool、agent 服务；adapter、可选插件、AgentLoop 本体、Context teardown 仍归调用者，让场景特定的顺序保持可见。
client-runtime jsdom 槽位测试运行时：真实 Cordis Context、生产 SlotRegistry 与 web-react 渲染器，配上实现相同对外面的 typed double。生产面一变，测试台在编译期就断——而不是悄悄漂移。
loader-smoke 经 Cordis Loader 启动 app 与 cordis.yml 的共享子进程 harness：resolveExampleLaunch 在本地 src 模式（tsx）与 CI lib 模式（纯 Node + package exports）间选择；runLoaderSmoke 拥有隔离 cwd、DSH homes、deadline 与清理；runFixtureTurn 驱动一个任务并返回最终回答与 usage。

这套基建的存在理由写在 acp-snapshot 的 README 第一段：所有比对/守卫机制集中在一个包里、 处在 per-file 覆盖率门禁之下，而不是每个 example 抍一份。一个消费方的 *.snapshot.ts 通常就是「一张场景表 + 一次工厂调用」。

22.7 核心政策：快照为什么不可替代

docs/testing.md 的「When a snapshot test is required」一节是整个体系的宪法： 每个非平凡的模型可见、协议可见或人类可见的行为变化，必须在同一个 PR 里通过某个 真实可运行 example 的快照套件加/更新一个 keyless 场景。包测试、e2e 断言、 mock/仅测试组合、PR 说明——都不能替代组装后的应用转录；需要时先扩展 harness。AGENTS.md 把同一条列为仓库级约定，并补上两条：fixture 必须在 macOS/Linux 可回放（修 fixture， 而不是修 normalizer）；新的 capability seam、生命周期变体或转录面，在计划阶段就点名每一层 覆盖，并先验证 harness 能表达它再动手实现。

为什么包测试不够？回到 postmortem 0001 那类故障：一个 default export 丢掉 inject， 单元层的组合可以全绿，产品在真实 Loader 组合下才断。所以政策还要求「测真实入口路径」： 产品可见插件必须有非 unit 的真实组合测试，手搭的 ctx.plugin(...) suite 不算数—— 要 boot 测试专用的 cordis.yml，穿过 Loader 与 app/进程。「真实入口路径」还指 发布产物：一个包的 bin 在纯 node 下跑构建好的 lib/bin.js，暴露 tsx 会掩盖的故障（settle 竞争、模块解析、被吞的加载失败）；构建产物 smoke 要保持绿色 （packages/examples/*/tests/built-bin.e2e.ts 等），并断言真正缺配置时非零退出。

解析面同样有纪律：测试解析只走 source plane——每份 vitest 配置都把 vite-tsconfig-paths 指向 tsconfig.base.json，裸 workspace 导入解析到 src，绝不经 package exports 落到构建的 lib/（那里陈旧的产物会 装出第二份模块单例）。构建产物只在显式声明的场合被消费：lib 模式子进程与 built smoke。

测试子进程的启动模式（test subprocess launch modes）

CI 与带构建的测试通道把每个 example 或 Cordis 配置子进程从构建好的 lib/ 经 共享的双模式 launcher 跑——不要为这些子进程手写 --import tsx。不加载 Cordis 的协议/操作系统 fixture 用可擦除的 .ts 直接跑 Node，不带 tsx 也不用根 paths 映射。只有被测对象就是源码路径解析时才可选 src，且要在测试里写明这条契约。 AGENTS.md 的一句话总结：配置子进程在纯 Node 下跑构建的 lib/；源码回归用声明 的 launcher。

22.8 本章回顾

  • 五条通道按证据面分工：unit（包级行为）、e2e（真实 provider）、snapshot（组装后转录）、web（Chromium 渲染）、stress/perf（负载）。
  • test:coverage 才是 CI 覆盖率门禁：packages/*/*/src per-file 100%；未覆盖行常是死代码该删。
  • e2e 无密钥自跳过不是成本信号；smoke 测试（起真实 example、发一条 prompt、查世界）专杀「unit 全绿产品坏了」。
  • DSH_SNAPSHOT：replay 免密回放且不写金标准（CI 默认）；record 需密钥重录 fixture；refresh 免密刷新期望输出；diff 必须逐条人工审。
  • llm-replay 的 fixture 就是 session.jsonl：assistant/chunk 按 (turn, step) 分组重建流；override sidecar 补纯抛错/取消；子会话按首调顺序绑定；assertConsumed() 兜底。
  • 宪法条款：非平凡的模型/用户可见变化必须同一 PR 内通过真实可运行 example 补 keyless 快照；fixture 在 macOS/Linux 可回放，修 fixture 不修 normalizer。
  • 测试解析只走 source plane；配置子进程用构建的 lib/ 加共享双模式 launcher，别手写 --import tsx。
常见误区
  • 以为 pnpm run test 绿了就满足覆盖率——门禁是 test:coverage，per-file 100%。
  • 把 e2e 的 self-skip 当成「e2e 免密也可跑」——跳过的 suite 不产生任何 provider 证据。
  • 改了模型可见行为后用包测试或 PR 说明交差——宪法要求同一 PR 内的 keyless 快照场景。
  • 快照 diff 不合预期就去改 normalizer——先修 fixture；normalizer 是共享纯函数，改它影响所有场景。
  • 给 example 子进程手写 --import tsx——用共享双模式 launcher，CI 从构建的 lib/ 跑。
  • 在 *.e2e.ts 之间互相 import 共享 fixture——import 一个 spec 会重复注册 describe 并翻倍真实 API 调用；共享代码放 tests/harness.ts。
