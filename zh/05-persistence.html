持久化：JSONL/SQLite 后端与版本化

上一章的 SessionEvent 日志是活真相，活在进程内存里。本章讲它怎么变得 durable（耐崩溃）：一个抽象的持久化接缝（ctx.sessionPersistence）、 两个可互换的后端（JSONL 与 SQLite）、两层版本化与「拒绝式」加载策略、 崩溃恢复，以及从同一条日志派生出来的投影、标题与遥测。读完本章， 你能回答「dsh 把我的会话存到哪了、以什么格式存、版本变了怎么办」。

学完本章你能够
  • 描述持久化接缝的职责边界：write-behind 批量写、revision 令牌、prepare/load/inspect/readFrom 各自解决什么
  • 说出两个后端的物理形态：JSONL 每会话一个 transcript 文件、SQLite 的三张表与一行一事件
  • 区分两层版本化：SessionHeader.version（当前 0）盖事件词汇，SQLite SCHEMA_VERSION（当前 15）盖表结构，且都是拒绝而非迁移
  • 解释崩溃恢复为什么「收口孤儿 turn」而不是截断日志
  • 列出从日志派生的状态（投影缓存冷读梯、标题、遥测）与非会话数据（ctx.storage hub）的去向

5.1 内存日志是活真相，持久化是接缝

先把上一章的分工再钉一次：SessionStore（ctx.sessions） 故意不实现任何持久化。落盘是插件的事——持久化插件订阅 session/event（同步通知，插件把事件拷进自己的缓冲，不阻塞生产者）， 并在 session/flush 检查点排空。抽象服务是 ctx.sessionPersistence（包 packages/session/session-persistence）， 它是一个标准 capability seam：Service Definition 声明接口，两个 Service Provider 实现它，若干 Consumer 使用它——同样的 SessionEvent 词汇， 没有第二种持久化事件类型要同步。

接口面（都在 session-persistence/src/index.ts）按使用场景记：

  • locate(meta)：同步解析一个会话的工件位置，不读不建不冲刷。JSONL 返回 transcript 绝对路径；SQLite 返回 undefined（所有会话共享一个库）。
  • create(meta) / append(id, events)：登记头元数据 / 持久一批连续事件。append 只在耐久完成后 resolve。
  • prepare(id)：resume 用的——取出一个未发布的 SessionPreparation（上一章 4.8 节那个），提交修复、预留独占。
  • load(id) / inspect(id)：加载平衡过的逻辑视图（提交冷恢复）/ 只读检查不写恢复。
  • readFrom(id, fromSeq)：从某个 seq 读存储后缀——给「从水位续读」的读模型用。
  • list() / listSnapshots()：轻量列举，只读头元数据、不解析全日志。

协调器与 write-behind 批量写

两个后端不各自发明缓冲逻辑：session-persistence/src/coordinator.ts 提供共享的缓冲、序列化、修复、销毁编排（第三方后端也可以直接实现接缝）。 批量写策略在 write-behind.ts：

  • 第一个待写事件启动一个固定的批量窗口（默认 200ms， writeBatchMaxDelayMs 可配）；窗口内后续事件加入同一批， 不重置截止时间。
  • 窗口到期触发一次耐久批量写；写入期间到达的事件获得自己的新窗口，形成后续批次。
  • session/flush 取消等待、排空到静止（quiescence）——所以循环在认领下一个普通 turn 前拿它当顺序与错误观察检查点。
  • 后台写失败时事件保留并暂停自动重试；新事件重启窗口，显式 flush 立即重试并把失败通过 agent/error 与日志上报——绝不会作为会话事件写进已关闭的 turn。

revision（revision.ts，SessionPersistenceRevision） 是后端自有表示的不透明令牌：它同时标识「哪个存储源」和「该源的第几版」， 随 append 或修复性 load 在事务中改变。派生状态的消费者在加载完整日志前先比较 这个廉价令牌——相等就不必重读。调用方只做相等比较，不解释它的内部结构。

5.2 JSONL 后端：每会话一个 transcript 文件

packages/session/session-persistence-jsonl 把每个会话存成一个 append-only 的逻辑 JSONL 日志。磁盘布局： 

<root>/
  --<normalized-cwd>--/        # 可读的项目目录（无 cwd 时 _no-cwd/）
    <encoded-session-id>/      # 会话自有目录
      session.jsonl.zstd       # 默认：校验和的 zstd 帧序列
      session.jsonl            # 仅当 compression: 'none'

逻辑内容三件事值得记：

  • 第一行是 SessionHeader（打上 { type: 'session', ... } 标签），之后每行一条存储记录，seq 跨整个解码后的日志保持连续（events[i].seq === i）。assistant/chunk 一条不丢。
  • packed chunk row：默认开启（packChunks: true）时， 连续 ≥3 条同 block 的 assistant/chunk 增量打包成一行 （text-chunks / reasoning-chunks / tool-call-chunks， 无斜杠的裸标签，不会与事件类型混淆），用 seq0/time0 + 逐成员 dt 精确重建每条成员的 seq/time——实测能把逻辑日志缩小约 60%。读取对布局无感： 打包、未打包、混合的文件加载结果完全相同。这正是上一章「持久层可自选编码， 但 load 必须返回精确事件」契约的实例。
  • 物理编码：默认是「校验和 Zstandard 帧的串接」——头行一帧， 之后每个耐久批量一帧。compression: 'none' 保留原始换行文本。 一个 root 只属于一种编码，混用后缀会被拒绝而不是被忽略。

配置上有一个刻意的「无默认」：root 必填。给 process.cwd() 当默认值 会让文件随进程 cwd 漂移（bash 调用、子进程都会改 cwd），把会话散落各处。 这是「显式优于隐式」规约的教科书案例。

5.3 SQLite 后端：一行一事件

packages/session/session-persistence-sqlite 用 Node 内置的 node:sqlite（DatabaseSync），DDL 在 src/schema.ts，三张表： 

CREATE TABLE persistence_state (   # store 身份：单例行 + 随机 store_id
  singleton INTEGER PRIMARY KEY CHECK (singleton = 1),
  store_id  TEXT NOT NULL) STRICT;

CREATE TABLE sessions (              # 会话元数据表 = SessionHeader
  id TEXT PRIMARY KEY, version INTEGER NOT NULL, created_at INTEGER NOT NULL,
  cwd TEXT, parent_session TEXT, seed_length INTEGER, origin TEXT,
  delegation_depth INTEGER, agent_preset TEXT,
  incarnation TEXT NOT NULL,          # 物化时分配的稳定身份
  revision   INTEGER NOT NULL) STRICT;   # 单调日志变更令牌

CREATE TABLE events (                # 事件表：一条 SessionEvent 一行
  session_id TEXT NOT NULL REFERENCES sessions(id) ON DELETE CASCADE,
  seq INTEGER NOT NULL, type TEXT NOT NULL, time INTEGER NOT NULL,
  data TEXT NOT NULL,               # 事件 data 的 JSON 文本
  source_event_seqs TEXT,       # JSON 编码的 number[]，或 NULL
  surface_op TEXT,                # JSON 编码的 SurfaceOp，或 NULL
  ignorable  INTEGER,              # 带标记时为 1
  PRIMARY KEY (session_id, seq)) STRICT;

行字段 (session_id, seq, type, time, data, source_event_seqs, surface_op) 与事件 1:1 映射，包括可选的 surface 元数据——所以「没有第二套持久化 schema 要维护」。几个行为细节：

  • 惰性物化：sessions 行只在第一次 append 时写入。 建了但从没写过事件的会话在 list() 里不存在——废弃会话不留痕迹， 与 JSONL 的「第一次 append 才有文件」对称。
  • journal 模式：默认 wal；回滚日志模式（delete/ truncate/persist）为 WAL 共享内存文件不可用的文件系统（网络挂载）保留。 memory/off 被排除——静默丢弃日志耐久性与本后端的承诺矛盾。
  • locate() 返回 undefined（共享一个库，没有 per-session 工件）； 因此它也不支持原始工件读取（supportsRawArtifacts === false）， 而 JSONL 的 readRaw 能逐字节回放它写下的文本。
  • revision 的 SQLite 形态：sessions 行里的 revision 列， 每个变更事务单调 +1；store_id 让不同后端实例的 revision 永不撞车。

5.4 两层版本化：拒绝，不迁移

dsh 的版本策略只有一句话：读不了的日志必须被拒绝，绝不悄悄猜。 落到实现是两层各自把关：

会话格式层SQLite 结构层
版本住在哪SessionHeader.version，创建时从 SESSION_FORMAT_VERSION 盖章PRAGMA user_version（SCHEMA_VERSION）+ PRAGMA application_id
当前值0（预发布期钉死：无兼容承诺）15（单调递增；application id 0x44534850）
盖住什么事件词汇与信封的结构语义（header 形态、信封、核心事件语义、surface 机制）表结构布局（三张表怎么长）
不匹配时抛 SessionFormatUnsupportedError，文案区分方向：版本更高 =「由更新的 harness 写的——升级 harness」；更低 =「本构建没有升级路径」拒绝打开数据库；user_version 为 0 但非空、或版本非当前，一律拒绝，绝不在原地迁移
什么不碰它新增普通事件类型不 bump——词汇增长由 ignorable 标记覆盖（上一章）会话自己的 version 存在 sessions 行里，与本层正交

注意区分「拒绝格式不支持」（SessionFormatUnsupportedError：日志没坏， 只是这个构建读不了）与「损坏」（SessionPersistenceCorruptionError： 已提交前缀里的数据真坏了）。方向感知的拒绝文案是产品级细节：用户该看到 「升级 harness」，永远不该看到「文件损坏」。JSONL 后端甚至从原始头行 就能给出方向判断——在任何结构校验之前；SQLite 则先用 SCHEMA_VERSION pragma 把整库结构挡在门外。仓库 AGENTS.md 的预发布立场说得直白： 没有外部消费者时，优先正确的地基——拒绝旧格式、自由重命名、同步更新所有引用。

5.5 崩溃恢复：收口孤儿 turn

上一章 4.8 节讲了修复语义（interruptedTurnClosers： 悬空调用补 error 结果、补边界、turn/end { interrupted }、已有事件不动）， 这里补上持久化层的执行时机与边界判定：

  • 只对冷会话修复。对仍活着的会话 id，load(id) 等内存里的 权威快照耐久化后返回它；活会话的开着的 turn 直接拒绝，不会收到合成的 中断边界。
  • 撕裂尾 vs 半截 turn：写了一半的物理记录（JSONL 的断帧、 SQLite 的不可解析行或 seq 空洞）是「从未提交」的撕裂尾，丢弃； 而完整写入的半截 turn 是已提交事实，收口保留。 SQLite 的 scanRows 用「最后一个 turn/end」做分界： 界前的洞是已提交区的损坏（抛错），界后的洞是可容忍的撕裂尾（截掉）。
  • inspect 不落盘修复：冷检视在内存里补合成闭合，物理撕裂尾原样不动； load / prepare 才把修复提交回存储（此时 revision 也会变）。
  • prepare 的缓存复用：协调器把冷的未发布会话留在有界 LRU 里 （默认 5 个），重复的历史读取和随后的 resume 共享一次「读取、解压、验证、冻结、构造」。

5.6 派生状态：投影、标题、遥测

会话日志落了盘，一大类「读模型」就可以从它派生——日志在先，缓存在后， 缓存永远可以扔掉重推。这一节认识三个家族（都在 packages/session/ 下）。

投影与冷读梯（session-projection / session-projection-cache）

ctx.sessionProjections 是一个「框架驱动、领域计算」的注册表： 每个领域注册一个投影单元 { key, schema, init, apply, view, stateVersion }—— 三个纯同步函数加声明。框架订阅一次 session/event，让每个已提交事件 流过每个单元的 apply；snapshot(session) 给出所有单元在同一个 asOfSeq 上的一致快照。两条性能纪律是契约的一部分： 不关心该事件的 apply 必须返回同一个 state 引用（引用相等即免下游工作）； 状态事件必须携带整值而非增量（last-wins、自描述）。

挂上 session-projection-cache 后，每个会话的投影检查点持久化到 storage-domain（见 5.7），冷读走梯子而绝不加载完整日志： 

缓存行（(key → ver, seq, val)，零 I/O）
  → restoreFloor（锚定在最低可用水位下方一个事件）
  → 持久层 readFrom(id, floor)（只读后缀）
  → restore 折叠 → 回写刷新行（fail-soft）

会话列表因此永远不解析完整日志：cachedSnapshot(meta) 直接从 存储记录读整值；ver 对不上就丢弃重推（不迁移）；记录绑定日志生命周期身份 （createdAt/cwd），换了底层存储的残留缓存会被识别并丢弃。 写入有两个强制点（turn/end、会话 dispose）加两个节流配置 （writeEveryEvents、writeIntervalMs，两个都必填—— 刷写节奏是部署决策，没有普适默认值）。

标题（session-title 家族）

会话列表要给人看的一行标题。策略是「先给个能用的，再异步换更好的」： 第一条人类提示词的前几个词（限字节数、控制序列清除、不切断 code point） 立即成为回退标题；可选的 provider（如 session-title-llm、 session-title-first-prompt-llm、session-title-all-prompts-llm 按摘要范围区分）稍后用模型生成更好的。每个被接受的修订都是一条 log-only 的 session/title 会话事件，foldSessionTitle() 取最新—— 标题也是事件溯源的，fork 继承父的标题事件。用户手动改名（rename） 写 user 来源的标题事件并钉住会话：之后的人类消息不再触发自动改名， 显式 refresh 才解钉。自动标题绝不延迟主响应：provider 只在循环自己发出的请求 且路由与已记录的 request/header 精确匹配时才跑，完成后追加独立的 log-only 事件（不开 turn）。

遥测（session-telemetry / session-telemetry-otel）

SessionTelemetryCoordinator 把会话记录交给实现 SessionTelemetrySink（emit/flush/shutdown） 的后端——session-telemetry-otel 是 OTel 实现。捕获两种模式： live（挂 session/created / session/event / session/flush / session/disposed / agent/error） 或 on-demand（显式 captureSession() 回放日志前缀）。 出站前过一道 sessionTelemetry/record redact waterfall—— 本包不自带任何规则，导出多干净取决于部署挂了什么规则；redact 只作用于出站副本， 规范日志永不改写。两个值得记的取舍：每个 (turn, step) 只出首条 assistant/chunk（流已开始的信号），所以线上 seq 有洞是常态不是丢失； 接收端按 (session.id, event.seq) 去重。resume 不回填上个进程没送达的记录 （at-most-once），feedback 门控的共享策略（full/feedback-only/disabled） 由部署披露。

5.7 非会话数据：storage hub 与 DSH_HOME

不是所有耐久数据都是会话日志。工作区偏好、用户反馈记录这类「应用数据」走另一个 家族（packages/storage/）：

  • storage/——hub，接缝 ctx.storage：把具名后端与类型化数据形态接起来；
  • storage-json/（后端 json，JSON 文件）与 storage-sqlite/（后端 sqlite）——两个可换后端；
  • storage-domain/——ctx.storageDomain：类型化的领域记录存储 （DomainSpec/Domain、domain/changed 事件）， 消费者拿领域形态而不是裸后端。

使用方包括 workspace（工作区数据，json 后端落在存储根的 workspace.json 旁）、message-feedback（反馈记录）、 以及 5.6 节的投影缓存（session_projcache 领域）。 与会话日志的区别一句话：它们不是事件流，是按领域的记录存储， 不需要 append-only、seq、投影这些机制，所以值得一条独立接缝。

这些文件的家由 packages/util/home-paths 决定： $DSH_HOME 环境变量覆盖默认值，默认是 ~/.dsh（DSH_HOME_DIR_NAME）。投影缓存、preset 根等 用户级数据都在这个屋檐下按部署配置分目录。

5.8 本章回顾

  • 持久化是插件接缝不是 store 职责：ctx.sessionPersistence 声明 locate/create/append/prepare/load/inspect/readFrom/list(listSnapshots)，两个后端实现同一契约，没有第二种持久化事件类型。
  • 协调器做 write-behind：首个事件起固定批量窗口（默认 200ms，不重置）、后续事件并批；session/flush 排空到静止；失败保留重试；revision 是后端自有的不透明变更令牌。
  • JSONL 后端：每会话一个 transcript（默认 zstd 帧串接），头行是 SessionHeader，packed chunk row 是无损编码（读取布局无感）；root 刻意无默认。
  • SQLite 后端：三张表（store 身份、sessions 元数据、events 一行一事件，1:1 映射含 surface 列），惰性物化，默认 WAL。
  • 两层版本化都是拒绝式：会话层 SESSION_FORMAT_VERSION = 0 盖事件词汇（不匹配抛 SessionFormatUnsupportedError，文案区分新旧方向）；SQLite 层 SCHEMA_VERSION = 15 + application id 0x44534850 盖表结构。不迁移。
  • 崩溃恢复收口不截断：完整写入的孤儿 turn 补合成 tool/result（TOOL_NOT_STARTED / TOOL_OUTCOME_UNKNOWN）、step/end、turn/end { interrupted }；撕裂物理尾丢弃；只对冷会话修复。
  • 派生状态从日志推出：投影注册表（apply 同引用、整值事件）+ 投影缓存冷读梯（缓存行 → readFrom 后缀 → 折叠回写，列表永不加载完整日志）；标题是 session/title 事件（回退 + 可选 LLM provider，用户改名钉住）；遥测 redact waterfall 后交给 sink，按 (session.id, seq) 去重。
  • 非会话数据走 ctx.storage hub（json/sqlite 后端 + storage-domain 类型化形态），家在 $DSH_HOME（默认 ~/.dsh）。
常见误区
  • 以为 append() 落盘后才算提交。提交在 push 进内存日志那一刻；持久化是异步批量。要耐久屏障就显式 flush。
  • 把两层版本混为一谈。SessionHeader.version 版本化事件词汇，SQLite SCHEMA_VERSION 版本化表结构；互不代理。
  • 期望旧日志自动迁移到新格式。dsh 的策略是拒绝式版本化：读不了就抛方向明确的错误，迁移路径留给未来的升级链。
  • 以为崩溃恢复会丢掉半个 turn 的工作。收口不截断——已完整写入的事件全部保留，只有撕裂的物理尾被丢弃。
  • 把投影缓存当权威。缓存行「可能旧（seq 说明旧多少）但不会错」，日志才是权威；ver 不匹配直接丢弃重推。
