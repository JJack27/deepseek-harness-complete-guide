文件系统能力：fs seam 与观测策略

模型改文件的每一笔都经过同一条缝：ctx.fs。它是执行世界的文件那一半—— 十二个存储原语、三个可替换 provider（本机 / 沙箱 / E2B）、一组挂在事件闸门上的观测策略， 以及一个四层分明的工具栈。本章除了讲清 seam 本身，还要回答一个更微妙的问题： 「先读后写」这类策略为什么不做成服务，而做成 fs/* 事件上的伴生插件。 读完你能顺着一次 edit 调用，从工具 schema 一路讲到 provider 的原子提交。

学习目标
  • 能列出 FileSystem 的原语分组（解析身份 / 执行世界坐标 / 读取 / 原子变更）并说出版本守卫为什么是可选的
  • 能对比三个 provider：fs-local、fs-sandbox（只围写、读放行）、fs-e2b（远端世界）
  • 能解释 fs/* 三个事件的分工，以及 fs-observation-policy 如何用「单槽决策 + 不调 next()」实现先读后写
  • 能说明 tool-fs 与 tool-fs-search 为什么一个走 ctx.fs、一个走 ctx.subprocess 里的 ripgrep
  • 能描述 str_replace_editor 的编辑模型：view/create/str_replace/insert、唯一字面匹配、无 replace_all

13.1 ctx.fs：十二个原语与可选版本守卫

FileSystem（ctx.fs，包 dsh-fs）定义「一个执行世界里的存储原语」， 不说怎么做。后端子类化它、实现十二个原语。按职责分组记最快：

分组原语要点
身份解析resolve(path, opts?)把路径解析成稳定的 FsTarget（不透明 targetKey + displayPath）；同一文件经不同路径到达必须得到同一 targetKey。opts.cwd 是相对路径的基（调用方传会话工作区）。
执行世界坐标processPath / fileUrl / contains给出「这个世界里的子进程能打开的规范绝对路径」「这个世界的 file: URI」「父子包含判定」——消费者永远不解析 targetKey。
元数据stat / lstat / listDirstat 只回元数据不回内容；lstat 不跟随最后的符号链接（消费者可先拒掉仓库自带的 symlink）；listDir 一层、稳定名序、绝不读内容。
读取readText / streamText / readBytes文本读负责 UTF-8 解码与二进制/NUL 拒绝（FS_NOT_TEXT）；流式读跨块解码留在 provider；readBytes 的 maxBytes 必填——已知或发现的超限直接 FS_TOO_LARGE，绝不无界缓冲。
原子变更writeText / editText原子创建/替换与字面编辑；expected 守卫可选——省略即无条件，提供则按 createIfAbsent / replaceIfVersion / { version } 做 CAS。变更总在后端的每目标锁内，无条件也只是去掉版本前置条件，不去掉原子性。

这个包同时拥有 fs/* 策略事件词汇——这一点放到 13.3 展开。整条 seam 的姿态被 README 概括为「fsspec 风格的存储原语，比字节级 cat/open 高半级」： 单独挂上 ctx.fs，它就是一个完整、无约束的存储缝；策略是后来叠上去的一层。

为什么版本守卫是可选的

因为「无策略的裸 provider」是合法形态。守卫参数的缺席不是「忘了」， 而是契约的一部分：省略 = 无条件创建或覆盖。策略插件（13.3）的职责恰恰是把守卫填进来—— 它把「这个 agent 观察到什么版本」转换成 provider 的 CAS 前置条件。 分层由此成立：provider 管原子性与一致性，策略管授权逻辑。

13.2 三个 provider：local、sandbox、e2b

fs-local（LocalFileSystem）是本机实现，也是另外两家的基座：

  • 身份：targetKey 是文件的 realpath——两条路径经符号链接到达同一文件即同一身份，写入落在链接目标上（保留链接）。版本是 dev:ino:size:mtimeNs:ctimeNs 派生的不透明令牌。
  • 原子写：在目标旁的私有 staging 目录里以 wx（0o600）独占建临时文件，fsync 后发布；已有文件的 mode 被保留，Windows 上替换走 ReplaceFileW 保住原 DACL。createIfAbsent 用硬链接做「原子不替换发布」——初始探测之后并发出现的文件被保留并以 FS_NOT_OBSERVED 拒绝。
  • 字面编辑：同一原语上的原子读-改-写，按目标串行；LF 规范化匹配、按文件主流 CRLF/LF 风格写回；空 oldString、零匹配（FS_EDIT_NOT_FOUND）、无 replace_all 的多匹配（FS_AMBIGUOUS_EDIT）都拒绝。

fs-sandbox（SandboxedFileSystem）继承 local 的全部机制， 只在 writeText/editText 上加一道每调用模式围栏： read-only 拒绝一切变更（结构化 FS_SANDBOX_DENIED）；workspace-write 只允许目标规范化后落在可写根内——工作区根加平台临时区，与 Seatbelt 配置文件同一个 writableRoots 函数派生，fs 围栏与 bash runner 因此不会漂移； danger-full-access 直接放行。读永远放行——所有模式都允许读。 它加载时替换 fs-local 即完成切换，模型工具一行不改。

fs-e2b 把同一份契约落在第 12 章的远端世界：相对路径按 ctx.e2b.cwd 解析、 GNU realpath -mz 供规范身份、写经 staging 目录 + 同文件系统原子 rename 发布。 它不复制、不挂载、不同步宿主工作区——给 cwd 一个宿主路径只会造出同名远端目录。

威胁模型：策略围栏，不是内核边界

fs-sandbox README 特意声明：这道围栏是可信代码里的一次检查，检查对象是模型控制的路径。 操作本身（open、rename）是 seam 自己的，只有目标路径不可信，所以「规范化再判包含」就是完整答案； 写前原地再规范化收窄了残留 TOCTOU。对抗性代码的内核级隔离是 ctx.shell 沙箱路线的职责 （第 12 章）——两家用同一份 sandboxPolicy，但机制与威胁模型不同。

13.3 观测策略：挂在 fs/* 事件闸门上

「谁在读写什么、写之前读过没有」是产品策略，不是存储原语。dsh 的解法是 四层栈：工具/执行器（tool-fs）→ 策略（fs-observation-policy） → provider 契约（dsh-fs）→ provider（fs-local 等）。 策略层没有服务：它不注册 ctx.fsPolicy，工具也不注入它—— 它只注册 fs/* 事件的三个监听器，而事件词汇归 Definition 所有。

三个事件（由 dsh-fs 声明、tool-fs 派发、策略插件倾听）：

事件形态fs-observation-policy 的监听器做什么
fs/write-intent单槽决策 waterfall未观察/观察到缺席 → { kind: 'createIfAbsent' }；观察到存在 → { kind: 'replaceIfVersion', version }。完全决策，不调 next()。
fs/edit-intent单槽决策 waterfall未观察 → FS_NOT_OBSERVED；观察到缺席 → FS_NOT_FOUND；观察到存在 → { version } 作为 CAS 基准。同样不调 next()。
fs/observedfire-and-forget 记录记下 { kind: 'present', version } 或 { kind: 'absent' }——同步、只做副作用的 WeakMap.set。

观测状态是「先前观察记录」：owner 到目标的弱映射，三态（未观察 / 确认缺席 / 存在于某版本）。 成功的读或变更记录「存在」；read 或 str_replace_editor 的 view/str_replace/insert 碰到元数据 miss 先记「缺席」再返回 FS_NOT_FOUND。策略自身不做任何文件 I/O—— 它只把观察状态换算成 provider 守卫：存在就供版本，缺席就只放行 createIfAbsent， 编辑没有版本基准就直接 FS_NOT_FOUND。窗口化的读观察的是整个文件的版本， 所以之后的定向编辑只在文件未变期间被允许。

「单槽、先注册先得」是刻意的：fs/write-intent/fs/edit-intent 槽位恰容纳一个决策者， 本插件占位是默认部署约定而非事件强制的硬性不变量。它不是可组合的授权链—— 分层权限、审计、沙箱拦截属于 tools/execute 管道（第 8 章）。 而事件闸门换来的最大红利是优雅装卸：策略只经事件影响世界，移除它不会让 tool-fs 在服务注入边界上坏掉——工具落回裸 provider（无条件写/编辑、无观测状态）， 再装回来策略重新叠上。装了 tool-fs 的部署预期同时装上它， 于是默认行为是先读后写。

13.4 工具家族：tool-fs 与 tool-fs-search

tool-fs 是模型面的读写层：read / read_image / write / edit 四个工具加上执行器本身。它拥有工具名、schema、参数校验、prompt section、 读窗口化（readLimit 默认 2000 行、每行 readMaxLineLength 2000 字符、 readMaxBytes 51200 字节）与结果格式化。每次调用的执行序列（README 标了 stat 次数）：

  • read：resolve（传会话 cwd）→ 一次 stat（类型、大小路由、版本）→ readText/streamText → 组行窗口 → ctx.emit('fs/observed')。
  • write：resolve → ctx.waterfall('fs/write-intent', …) 拿可选守卫 → writeText(target, content, intent) → fs/observed。（0 stat。）
  • edit：resolve → ctx.waterfall('fs/edit-intent', …) → editText(target, edit, intent) → fs/observed。（0 stat。）
  • read_image：只在挂了持久 ctx.attachments 且当前路由模型声明图片输入时注册；经有界 readBytes 读 PNG/JPEG/WebP/GIF，经 attachments.saveImage 提交，返回图片块。

工具把 exec（工具执行上下文）作为不透明 actor 随每次派发传递—— 事件里只有 dsh-fs 词汇加不透明 actor，没有模型面概念，也没有 agent/session 归属结构。 挂了围栏 provider（ctx.fs.sandboxMode 报告约束）时，write/edit 同样广告 sandbox_permissions + justification 升级面，机制与第 12 章 bash 完全同构。

tool-fs-search 是刻意的例外：glob / grep 两个发现工具不走 ctx.fs 原语，而是把打包的 @vscode/ripgrep 二进制经 ctx.subprocess spawn（--no-config 前置，防宿主 RIPGREP_CONFIG_PATH 注入 --pre；模型控制的值都是普通 argv 元素，无 shell 层故无引号问题）。 理由写在 README 里：本地工作区发现天然是进程化的 rg 工作流， 把搜索放上 ctx.fs 会逼每个文件系统后端长出搜索 API。 注意它注入 subprocess 而不注入 fs——远端执行世界下的搜索需要工作区同置（co-located）才对模型有意义。

13.5 str_replace_editor：模型改文件的主力编辑器

dsh-tool-str-replace-editor 提供独立的 str_replace_editor 工具—— 可以与持久 bash、一次性 bash、沙箱 bash 或其他终端面自由组合。它的 schema 是四个命令：

命令行为
view文件视图用一基行号并原样保留 tab——显示出来的文本就是合法的字面替换输入；目录视图省略隐藏、依赖与 Python 缓存条目，向下两级。
create建新文件。
str_replace替换一段字面文本：要求恰好一次唯一匹配，零次或多次匹配都报错，且错误只用公开的 old_str 词汇表述。没有 replace_all 参数。
insert沿选定的零基插入边界插入，不添加隐式行尾换行。

编辑模型的取向很清楚：精确优于宽松。没有正则、没有 replace-all、 编辑区外的 tab 原样保留、匹配以显示文本为准——这些约束共同保证「模型看到什么就能替换什么」， 一次 view 的输出就是下一次 str_replace 的合法输入。 元数据 miss 会先记「确认缺席」再返回 FS_NOT_FOUND，所以外部删除过的路径可以用 create 经挂载策略的守卫式建文件恢复；但缺席不授权 str_replace 或 insert。

它不是旁路：每一次变更都走 fs/write-intent 或 fs/edit-intent， 解析当前会话沙箱策略，把强制执行委托给挂载的文件系统与策略插件。 换句话说，str_replace_editor 是「编辑模型」的拥有者，而原子性、版本守卫、沙箱围栏 全部来自 13.1–13.3 的那台机器——这正是 seam 分层的收益：编辑器换掉，策略照常工作； provider 换掉，编辑器照常工作。

13.6 本章回顾

  • ctx.fs 十二原语分五组：身份解析、执行世界坐标、元数据、读取、原子变更；版本守卫可选——省略即无条件，原子性永在。
  • 三个 provider：fs-local（realpath 身份、staging + 原子发布、DACL 保留）、fs-sandbox（只围写、读放行、FS_SANDBOX_DENIED、与 Seatbelt 共享 writableRoots）、fs-e2b（远端世界、无宿主同步）。
  • 策略不是服务：fs-observation-policy 只挂 fs/* 事件闸门——两个单槽决策 waterfall（不调 next()）+ 一个 fire-and-forget 记录事件；装卸优雅，工具永不在注入边界坏掉。
  • 观测状态 = 先前观察记录；窗口化读观察整文件版本；「先读后写」由观察记录换算成 provider CAS 守卫。
  • tool-fs 是工具兼执行器（read/write/edit/read_image + 窗口化 + fs/* 派发）；tool-fs-search 刻意绕开 ctx.fs，用打包 ripgrep 经 ctx.subprocess。
  • str_replace_editor：view/create/str_replace/insert，唯一字面匹配、无 replace-all、tab 保留，变更全部经 fs/* 闸门。
常见坑
  • 给 ctx.fs 加搜索方法——搜索是 rg 工作流，放进 provider 契约会逼每个后端实现一遍。
  • 把观测策略当授权链往 fs/* 上再叠一层决策者——槽是单槽、先注册先得；分层拦截属于 tools/execute。
  • 期望观测状态跨会话存活——WeakMap 是进程内弱引用，resume 后要重新 read。
  • 以为 fs-sandbox 围住了读——所有模式读放行，围栏只在 writeText/editText 上。
  • 给 str_replace_editor 找 replace_all——故意没有；多匹配是错误，模型应换更长的锚文本。
  • 以为 readBytes 会截断——maxBytes 必填，超限直接 FS_TOO_LARGE，从不无界缓冲。
