System Prompt 装配

模型每个 step 看到的 system 区块和运行时上下文，不是一段写死的字符串， 而是每次都现拼的：插件们把 section、动态上下文、变量、工具 schema 注册进 ctx.systemPrompt，agent loop 在认领输入后调用装配，得到这一轮的完整输入。 这一章讲清装配的全部零件、scoped 注册如何做出 per-agent 人格， 以及 context 组插件贡献的模型可见内容为什么全都走「可从日志重建」的路径。

学习目标
  • 说出 ctx.systemPrompt 的四类注册物：section、context、variable、tools provider
  • 复述 assemble() 的合并规则：scoped 遮蔽、order 排序、toolOrder 校验、waterfall、complete section
  • 区分「system section」与「runtime context」两条不同的模型可见通道（后者落 durable 日志）
  • 用 scoped section 遮蔽 deployment:persona 实现一个 per-agent 人格
  • 说出 context 组四个插件分别贡献什么、以什么事件落日志

9.1 注册表：四类输入

packages/core/system-prompt/ 的 SystemPrompt 服务（ctx.systemPrompt） 是一个「有序 prompt 输入」的注册表。能注册的东西恰好四类，每类都返回效应 disposer， 都支持 scoped 注册（经 agent.ctx 注册就只对该 agent 生效）：

API是什么进入哪条通道
section({name, order, text, complete?}) system 区块的一段；text 是静态字符串或每次装配时求值的函数；可引用 {{variable}} system prompt 本体
context({name, order, text}) 动态运行时上下文（时间、环境、位置这类「此刻事实」） runtime-context 快照 → durable user-role 消息
variable(name, provider) 一个 {{name}} 变量的求值器（如 cwd、provider、model） section/context 文本的插值
tools(provider) 工具 schema 提供者（第 8 章的注册表就挂在这里） 请求的 tools 字段

两个内建 section 值得记住：order -100 是 harness 身份 （You are an AI agent powered by DeepSeek Harness.，可用配置 includeHarnessIdentity: false 关掉）；order 0 是部署人格槽位 deployment:persona（由 persona 配置填充）。约定俗成的编号带： 负数区在人格之前，工具自述用 100–199。另外 suppressRuntimeContext() 可以在某个 scope 关掉全部动态上下文贡献，而不需要动拥有这些事实的服务。

9.2 装配：每个 step 现拼一次

回忆第 7 章：preStep() 认领输入后立刻调用 ctx.systemPrompt.assemble({scope, signal})。装配按固定顺序发生：

  1. 合并 scope 链：变量按「最具体的 scope 获胜」取值；section / context 里 scoped 同名条目遮蔽全局条目；工具提供者全局与链上的都参与。
  2. 排序：section 与 context 各自按 order 升序；工具 schema 按 toolOrder 配置排（必须恰含一次 <unlisted-tools> 占位； 未配置则字典序），配置了不存在的工具名会在装配时抛错。
  3. waterfall：system-prompt/assemble 是一个专家 waterfall， 监听器可以整体改写装配结果，返回值权威 —— 唯一的例外是 complete: true 的 section： 装配结束后它会被恢复为唯一的 prompt section（同时存在两个 complete section 会让装配失败）。
  4. 渲染：renderPrompt(assembly) 做严格插值 —— {{name}} 引用必须已注册且有值，畸形或未知的引用直接抛错； 渲染为空的 section 被丢弃，其余用空行连接。工具 schema 则进入请求的 tools 字段。

为什么 contexts 不进 system prompt？ 因为 system prompt 是每轮都一样（或由配置变化驱动）的 「身份与规则」，而 runtime context 是「此刻事实」：时间在走、tmux 窗口在动。把它做成 durable 的 user-role 消息，日志就能忠实记录「模型当时知道什么」，快照之间的替换关系 （「此快照取代早先的运行时上下文快照」）也写在消息文本里。这是第 4 章不变量的又一次应用： 模型可见的输入必须可从日志重建 —— section 走 request/header 里的 system， context 走 user/message，各得其所。

9.3 scoped section 与 per-agent 人格

注册表是 scoped 的，这直接给出 per-agent 人格的做法：在某个 agent 的 agent.ctx 里注册一个同名 section deployment:persona， 它就遮蔽部署层的人格槽位，只对这个 agent 生效。persona 类的 preset 包用的正是这套： 同名遮蔽而不是追加，所以一个 agent 永远只有一个人格 section，不会出现两段人格互相打架。 packages/core/system-prompt/src/index.ts 特意导出了 PERSONA_SECTION 常量，让「部署侧」和「遮蔽侧」引用同一个名字 —— 两侧各写一个魔法字符串是最容易错位的地方，共享常量让替换天然成立。 

// 在某个 agent 的 agent.ctx 里（伪代码示意遮蔽机制）
agent.ctx.systemPrompt.section({
  name: PERSONA_SECTION,        // 'deployment:persona'：同名遮蔽部署人格
  order: PERSONA_ORDER,         // 0：人格槽位不变
  text: '你是只读审查员，绝不修改文件。当前目录 {{cwd}}。',
})

同样的机制也覆盖变量与工具：scoped 变量遮蔽全局变量，第 8 章的 scoped 工具遮蔽全局工具。 第 6 章的 shadowing 心智模型在 prompt 侧不需要任何新概念。

9.4 context 组：模型可见内容的四个真实来源

packages/context/ 组的四个插件是「给模型添加上下文」的官方实现。 逐一过一遍，重点看每个插件的内容如何落日志：

  • dsh-agent-instructions（AGENTS.md 指令链）：加载 $DSH_HOME/AGENTS.md 与从项目根到 cwd 每一级目录的指令文件 （AGENTS.md/CLAUDE.md 等候选，逐字节相同者去重）。基线在会话第一个合格的 agent/pre-step 处合成，折进进入批次 —— 紧跟用户直接 prompt 落成 durable 的 user-role 消息（<system-reminder> 框架）； 之后它观察成功的 read/write/edit 工具结果，发现新目录的指令文件就往 inbox 排 增/改/删通知，同样以带来源的 user/message 落日志。
  • dsh-time-context（时间上下文，opt-in）：在 agent/pre-step 链首追加监听；到期时给返回的批次追加一条带来源的 UserMessage（source: {kind:'plugin', plugin:'time-context', form:'snapshot', …}）， agent-loop 在 step/start 之后、请求推导之前落盘。浏览器时区来自当前 turn 的 user-rpc 消息来源；默认组合不加载它（Schedule Web overlay 才挂）。
  • dsh-tmux-context（tmux 位置，opt-in）：每个 turn 的第一步， 经 ctx.shell 跑一条只读探测命令确认自己真的跑在 tmux pane 里（光有 $TMUX_PANE 不算 —— 环境变量会被继承），命中才在进入批次前部插入一条 source {kind:'plugin', plugin:'tmux-context'} 的 UserMessage， 同样在 step/start 后落日志。
  • dsh-session-reference（跨会话引用）：提供 ctx.sessionReferenceResolver；prepare() 把被 @ 提及的其他会话 投影成有界只读快照，返回一条带识别来源的 UserMessage。agent 空闲时经一次性 agent/pre-step 包装并入进入批次；运行中则 inject() 紧跟 steer()，两条消息一起等下一次认领。快照固定在捕获时刻 —— 源会话后续变化不影响目标日志重放。

四个插件，四种入口（pre-step 折入批次、pre-step 追加、pre-step 前插、inject+steer）， 但殊途同归：没有任何一个把文字悄悄塞进 system prompt。模型可见内容全部以 带来源的 durable user 消息存在，日志既记得「模型看到了什么」，也记得「是谁给的」。 如果你要写第五个上下文插件，照这个模式做 —— 这不是风格建议，是 「新的模型可见输入需要新的会话事件」这条仓库级规则的直接推论。

与第 7 章的衔接

装配发生在 preStep() 里、agent/pre-step waterfall之前， 装配结果（PromptAssembly）随后跟着 enter 决策进入 step()： sections 渲染成请求的 system，contexts 由 RuntimeContextProjection 投影成 进入批次里的上下文消息。也就是说：每个 step 都重新装配一次 —— 工具注册变化、变量取值变化，下一个 step 立刻生效。

9.5 本章回顾

  • ctx.systemPrompt 收四类注册：section（system 本体）、context（动态快照）、variable（{{}} 插值）、tools provider（工具 schema）。
  • assemble()：scope 链合并（scoped 遮蔽全局）→ order / toolOrder 排序与校验 → system-prompt/assemble waterfall → complete section 恢复；renderPrompt 做严格插值、丢空段。
  • sections 与工具 schema 进请求本体；contexts 走另一条通道 —— durable user-role 快照消息，带「取代旧快照」声明。
  • per-agent 人格 = 在 agent.ctx 注册同名 deployment:persona section 遮蔽部署槽位；共享常量 PERSONA_SECTION 保证两侧同名。
  • context 组四插件：agent-instructions（AGENTS.md 链）、time-context、tmux-context、session-reference —— 内容全走带来源的 durable user/message，可从日志重建。
  • 装配在每个 step 的 pre-step 之前发生，每步现拼，注册变化下一步即生效。
常见误区
  • 以为 runtime context 会拼进 system prompt —— 它是独立的 durable user 消息通道；把「此刻事实」塞进 system 会破坏日志的可重建性。
  • 给每个 agent 各写一段人格但忘了同名遮蔽 —— 会得到两段人格叠加；正确做法是同名 deployment:persona 遮蔽。
  • 在 section 里写 {{var}} 却不注册变量 —— 渲染时直接抛错（严格插值，不静默留空）。
  • 配置 toolOrder 漏掉 <unlisted-tools> 或写了不存在的工具名 —— 装配时失败，不会静默忽略。
  • 写上下文插件时直接改 system prompt 或绕过日志注入 —— 违反 model-visible ⟺ logged；照 context 组的模式走 pre-step / inject 落 user/message。
