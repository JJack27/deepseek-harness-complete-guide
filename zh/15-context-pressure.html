上下文压力管理：compaction、spill、context 插件

第 7 章的 turn/step 循环假设每个请求都装得下全部历史——但上下文窗口是有限的， 而一次 bash 输出、一次网页抓取就能瞬间塞满它。dsh 用三道闸回答这个问题： spill 在结果产生时就外置超大输出，pruner 在压力触发时修剪工具结果， compaction 在仍然超压时把旧历史摘要成 checkpoint。本章逐个拆开这三道闸， 并补上压力视角下的最后一环：排队等准入的 agent.inject() 注入。

学习目标
  • 能画出三道闸的触发时机与代价排序：spill（结果产生时）、pruner（压力触发后、选区之前）、compaction（摘要替换）
  • 能解释 compaction 的表面契约——为什么唯一的表面变更是带 surfaceOp: replace 的 user/message，而 compaction/* 事件全部 log-only
  • 能配置 dsh-compaction-basic 的阈值与保留策略（thresholdRatio / retainRatio / modelPolicies），并说明摘要调用如何复用 KV 缓存
  • 能区分 pruner 的「修剪」与 spill 的「外置」：一个改写表面节点，一个把全文移出上下文只留 locator
  • 能说出 /compact 是人类命令而非模型工具，以及 agent.inject() 的排队与准入语义

15.1 问题：窗口有限，工具结果瞬间塞满

上下文窗口是模型一次请求能看到的全部：系统提示、工具 schema、路由信息、assistant 完成、 工具结果、缓冲中的上下文和 steering。第 9 章你看到系统提示怎么装配；第 8 章你看到工具结果 怎么落进 tool/result 表面事件。把它们放在一起就出现一个工程问题： 历史是单调增长的，而窗口不是。一次不带限制的 grep -r、 一次抓取完整网页、一份巨大的测试输出，都可以在一个 step 之内把后续请求挤爆。

dsh 的答案不是给 agent-loop 加分支，而是三个各自独立的插件家族，挂在现有的扩展点上：

  • packages/spill/——spill：在工具结果产生时（tools/post-execute） 把超大纯文本结果外置到 storage，模型上下文里只留有界预览加 locator（定位符）。
  • packages/compaction/compaction-tool-result-pruner/——pruner： 压力触发之后、选择摘要区间之前，把超预算的 tool/result 表面节点改写成 「开头 + 省略标记 + 结尾」。
  • packages/compaction/（其余三包）——compaction： 把较旧的历史区间摘要成一个 checkpoint 消息，替换掉被遮蔽的区间。

三者的分工边界写进了组 README 的角色表：测量（这次请求到底多大）属于 LLM 家族的 ctx.tokenMeter，不属于任何一个闸门；spill 只管存储与定位（不管保留策略、不管取回 API）； compaction 只管「何时算太大」与「怎么摘要」的契约，具体策略由后端实现。这是第 11 章 capability seam 方法论的一次成组应用。

15.2 三道闸：时机与代价

把三个家族放进同一个工具结果的生命周期里，顺序就清楚了。 闸 1（spill）是预防闸：它在 tools/post-execute 拦截最终结果， 超过 maxInlineBytes 的纯文本在进入上下文之前就被外置——大输出根本不会进窗口。 闸 2（pruner）和闸 3（compaction）是响应闸：只有当 ctx.tokenMeter 报告的压力越过阈值（或 provider 确认了窗口溢出），pruner 才先修剪超预算的工具结果， 重新测量；仍超压时 compaction 才做摘要替换。

这个排序也是代价经济学：spill 和 pruner 都不调用模型——一个换存储， 一个做纯文本切片；compaction 要付一次辅助 llm.stream() 调用，还要使被替换区间的 KV 缓存失效。所以仓库把它们排成「越贵越靠后」：pruner 修剪后如果重新测量已经低于压力， compaction-basic 会直接跳过摘要。反过来，有些情况三道闸都无能为力：compaction 的 README 明说， 单个不可分割的巨大单元（非工具节点、不可修剪的工具单元）以及系统提示/工具 schema 本身超窗， 都不在表面压缩的契约内——那是装配层（第 9 章）要控制的事。

15.3 compaction seam：ctx.compaction 的契约

packages/compaction/compaction/ 是 Service Definition 包： CompactionEngine（ctx.compaction）定义压缩做什么—— 判断历史何时过大、把较旧区间摘要成单个表面节点——而不说怎么做。三个操作全部抽象：

成员语义
compactIfNeeded(agent, trigger, signal)自动压缩入口，trigger 是 pressure 或 context-overflow；返回 CompactionResult，无安全区间时返回 null
compactNow(agent, signal)显式压缩：即使低于自动压力也摘要一个有用的平衡区间；同步预约空闲轮次准入，以 turn: null 记录独立 bracket
compactRegion(start, end, agent, signal?)强制摘要表面位置区间 [start, end]（闭区间 seq）；注意是表面位置区间而非数值 seq 区间——一次 replace 之后表面顺序不再跟随 seq 顺序

契约里最值得背下来的是表面契约。第 4 章讲过 SurfaceEventType 是封闭联合：只有 user/message、assistant/message、tool/result 能携带 surfaceOp，所以 compaction/* 事件不可能出现在表面上。 一次成功的压缩是这样五步：

  1. 追加 compaction/start（log-only）——取得锁；
  2. 摘要选中的区间；
  3. 追加 compaction/summary（log-only），携带摘要、区间、被遮蔽的 seq、token 计数与 provider/model 调用信封；
  4. 追加一条 user/message，source 为 compactCheckpointSource(compactionId)、携带 surfaceOp: { op: 'replace', start, end }——这是整个操作唯一的表面变更；
  5. 追加 compaction/end（log-only）——释放锁。

于是 deriveMessages() 渲染出的模型历史是：checkpoint 摘要（user 角色、 以 <compacted-summary> 标签框住）加上保留的近期节点；被遮蔽的原始事件 仍留在追加式日志里，回放是确定性的。锁本身就是日志记录：一个没有配对的 compaction/start 就是 busy 信号，崩溃后留下的是可检测的孤儿锁， 而不是一个谎称压缩已完成的 compaction/end。

还有两处第 11 章方法论的变体值得注意。其一，Definition 导出 toolPairingBalancedBefore/After(session, seq) 边界助手：安全切边不能穿过 未应答的 assistant 工具调用，这个「配对平衡」的校验逻辑归 Definition 所有， 供所有后端复用。其二，这个 Definition 一反「只依赖 cordis」的惯例， 依赖了 dsh-session 和 dsh-llm——因为它的动词定义在 Session 上、输出是 ContentBlock 词汇，绕不开这两个包。 这个偏差是刻意的，记录在 compaction capability-seam Agent Note 里。

为什么唯一表面变更是那条 user/message

因为模型可见 ⟺ 已日志（第 4 章不变量）。摘要要让模型看到，就必须以表面事件的形式存在； 而锁、账本、调用信封这些实现细节模型不需要看到，所以全部 log-only。 compactCheckpointSource(compactionId) 把 checkpoint 与它的 compaction/* 事务关联起来，isCompactCheckpointSource() 让客户端程序在不知道后端身份的前提下认出这个标记。

15.4 compaction-basic：压力、保留与摘要后端

dsh-compaction-basic 是基础后端（Service Provider）：它需要 ctx.llm、ctx.tokenMeter 和 ctx.sessions， 拥有完整的压缩策略。压力测量委托给单例 ctx.tokenMeter——它在同一个已消费日志 版本上给「最新规范日志信封 + 当前表面」定价，所以 step 边界的压力已经包含 系统提示、工具、路由、assistant 完成、工具结果、缓冲上下文和 steering 的实际消耗。 阈值不是绝对 token 数，而是按当前路由的模型窗口解析： floor(routedContextWindow × thresholdRatio)。这解释了为什么同一份 compact 插件能安全服务不同容量的模型。

触发路径有两条：默认 auto: true 时，串行的 agent/pre-step 监听器在请求推导之前检查压力；provider 确认的窗口溢出则从 agent/request-error 进入，走独立的溢出恢复路径（先修剪，再做一次最大的 平衡头部缩减）。保留策略压缩「最旧的完整表面单元」并保留近期尾部， 切边走 Definition 的配对平衡助手；失控 turn 内部的旧 step 不受 turn 边界保护。

摘要本身是一次直接的一击 ctx.llm.stream() 调用，不是 loop step （所以逐调用拦截发生在 llm/stream，而不是 agent/request）。 它逐字重放会话自己的系统提示、工具 schema 和被遮蔽区间的消息——包括图片引用—— 再把压缩指令作为最后一条 user 消息追加。由于前缀与上次路由请求逐字节一致， provider 的暖前缀缓存被复用，只有末尾指令和摘要是未缓存的。 调用带 GenerateOptions.purpose: 'compaction'（DeepSeek adapter 会发送 x-deepseek-harness-compact: 1 归因头，不动模型可见体）；只有返回文本进入 checkpoint，推理与工具调用被排除——否则会泄漏私有推理或制造孤儿调用。

Config 键默认含义
thresholdRatio0.8在 floor(路由窗口 × 比例) 处压缩
retainRatio0.16按路由窗口比例保留近期表面（与 retainTokens 互斥）
retainTokens—绝对 token 预算保留近期表面，必须低于解析出的阈值
summarizationProvider / summarizationModel''成对设置摘要模型；留空则回退到最新日志请求目标、再到 agent 目标
maxTokens8192摘要调用的生成上限
compactionRetries1压力仍超阈值时的额外尝试次数
maxOverflowRetries1窗口溢出后的最大重试次数（0 只关闭恢复）
modelPolicies[]对精确 { provider, model } 对的部分策略覆盖
autotrue注册 step 边界压力与溢出恢复监听器；false 为纯手动

所有键都是可选的、在插件加载时校验（未知键、重复目标、互斥保留形式、 retainRatio 不低于 thresholdRatio 都会加载失败）——这是 「misconfiguration fails loud」与「无写死调参」两条仓库约定的标准体现。想换摘要实现， 子类化 BasicCompactionEngine 并覆写受保护的 summarize()—— 这是唯一的子类钩子，压力、保留、事件账本都留在基类。

15.5 compaction-tool-result-pruner：无模型修剪

dsh-compaction-tool-result-pruner 注册 ctx.toolResultPruner， 是 compaction-basic 的可选伴生插件，不是后端也不是模型工具。 compact-basic 通过可选的 ctx.get('toolResultPruner') 读取它， 所以两个包可以独立组装——加载顺序上把它放在 compact-basic 之前作为兄弟插件即可启用。

它做的事情纯语法、零模型调用：pruneSession(session) 扫描当前表面的一个稳定快照， 把每个超预算的 tool/result 替换成一条新追加的 tool/result， 携带 surfaceOp: { op: 'replace', start: 原seq, end: 原seq } 与 sourceEventSeqs: [原seq]。替换结果完整复制原事件数据、只改 content： 保留 head、固定的省略标记 [... tool result middle pruned ...]、保留 tail。 原始事件保留在追加式日志里，供持久化、回放和精确日志检查。

三个配置键都是 Unicode 码点数：thresholdChars（默认 8192）、 headChars（默认 4096）、tailChars（默认 1024）， 约束 head + 标记 + tail ≤ threshold，保证第二次扫描不再产生替换。 两个要点防止误解：其一，低于压力的 step 检查从不修剪——pruner 只在压力或溢出 触发合格之后、区间选择之前运行，修剪完 compact-basic 重新测量，若已安全就跳过摘要； 其二，字符预算不是 token 预算——「修剪是否解除了请求压力」的裁决权仍在 ctx.tokenMeter。

15.6 command-compact：/compact 是人类命令

组 README 的「已知限制」第一条写得直白：Human command, not a model tool。 dsh 没有模型可见的 compact 工具——触发压缩的模型侧入口不存在， 自动压力与人类命令是仅有的两个入口。dsh-command-compact 在 ctx.commands 上注册一个全局命令：无参数的 /compact 调用 ctx.compaction.compactNow(agent, signal)，即使低于自动压力也摘要一个有用的平衡区间， 然后报告被替换的历史条目数与估算 token。带任何参数返回用法错误；无可压缩历史返回 No compactable history yet.。

注意命令执行时发生了什么：没有模型轮次。斜杠输入与直接结果不进入模型请求 （也不消耗 token），但每次已解析的调用都会在该 agent 的会话上记录 log-only 的 command/run / command/done 事件对—— command/done.sourceEventSeq 指向事务的 compaction/summary 事件， 让展示层能把命令生命周期折叠到对应 checkpoint 上，而不必解析结果文本。 ManualCompactionError 的封闭错误码（busy | changed | summary | commit | persistence）被翻译成稳定的直接错误文案。

为什么不让模型自己压缩？因为入口的所有者是人类的控制面： 命令平面不经模型轮次直接分发，这正是下一章的主角。这里先记下伏笔： /compact 的「不经模型、仍写日志」是命令平面的标准形态。

15.7 spill：外置而非裁剪

pruner 的策略是「保头保尾砍中间」——对日志类输出足够，但有些结果的价值恰恰在全文： 模型之后可能要用 grep 在里面搜索、用 read 分段读。 spill 家族回答这个问题：把全文移出上下文，留下 locator。 三个包的角色表：

包角色职责
dsh-spillService Definitionctx.spillStore 抽象服务 + 词汇类型（SaveTextSpill / SpillRef / branded 的 SpillLocator）
dsh-spill-localService Provider会话作用域的私有本地文件存储
dsh-spill-policyConsumertools/post-execute 转换器，决定何时外置并组装通知

seam 只拥有存储：saveText(input) 逐字持久化 input.content， 返回 SpillRef（locator、写入字节数、取回提示），真正的存储失败会 reject。 它没有保留策略（那是 util 家族的 dsh-output-retention）、 没有工具结果替换（那是 spill-policy）、没有取回/搜索 API—— 后端的 retrievalHint 告诉模型拿到 locator 该做什么。 SpillLocator 是 branded 类型，对模型渲染为不透明字符串： spill-local 返回本地路径，未来的远端后端可以返回 URI、数据库键或命令令牌， policy 与工具消费者一行不改。

dsh-spill-local 的存储布局是安全设计的范本：文件落在 <root>/session-<hash>/<random>-<safeName>—— root 缺省时是 OS 临时目录下懒创建的 0700 私有目录（可预测且全局可读的 root 会让其他本地用户读到外置输出或植入符号链接）；session-<hash> 是 sha256(sessionId) 前缀，让同一会话的外置文件成组、将来可按会话清理； 文件名带不可预测的十六进制前缀，写入用独占 + 仅属主（open(path, 'wx', 0o600)）， 任何已存在的路径（包括植入的符号链接）都会失败。

dsh-spill-policy 是唯一的 Consumer：一个 tools/post-execute 转换器。它只做四件事——让工具先跑（next() 委托）、只在结果是纯文本且超过 maxInlineBytes 时动作、把全文经 ctx.spillStore 外置、 用「有界 head/tail 预览 + 通知」替换模型可见结果，整体不超过预算： 

<retained head/tail preview>

(Omitted N bytes. Full formatted result stored at: /…/session-…/…-web_fetch.txt.
Use read with offset/limit, or grep this path to search within it.)

豁免清单同样重要：嵌套执行（exec.parent 存在）、被接受的值替换、 read 工具的结果（避免 read → spill → 再 read 的循环）、 非 accept 决策、含任何非文本 block 的结果——全部原样放行。 一切是 best-effort：没有会话 owner、没挂 backend、saveText 被拒， 都记一条警告并保留内联结果——外置失败绝不把成功调用变成 isError 或藏起结果。 另外它还有第二条臂：监听 tools/code-dispatch-log，给 Code Mode run_code 子调用结果的持久日志副本施加同一上限 （第 17 章会再遇到 Code Mode）。

关键点

阈值是策略不是常数：maxInlineBytes 是加载时校验的 Config 键， 单位 UTF-8 字节；不设置就整体禁用（插件什么都不注册）。 替换结果的字节数永远不超过上限——通知本身的字节成本从预算里预留，预览收缩来凑， 所以外置从不增加字节。

15.8 context 组：注入排队，等待准入

压力管理的最后一环是「往窗口里加东西的人」。packages/context/ 组是 一批不定义工具、只添加模型可见请求上下文的产品插件： agent-instructions（工作区指令链，默认随 agent spine 演示 bundle 组装、可经 bundle 配置禁用）、time-context（当前时间与经过时间）、 tmux-context（tmux 位置上下文）、session-reference （其他会话的有界快照，ctx.sessionReferenceResolver）。 第 9 章你从装配角度看过它们；压力视角下的问题是：这些内容何时进入请求？

答案是 agent.inject(message) 的排队语义：它把非唤醒的 next-step 上下文排进收件箱。运行中的 driver 在最近的下一个 pre-step 边界 认领它；空闲的 driver 把它挂起，直到 followup() 或 steer() 唤醒。 它甚至可能错过一个请求——如果那个请求的 pre-step 已经认领了自己的批次。 docs/architecture.md 的「Where new behavior goes」表把这总结成一行： Add model-visible context → call agent.inject(); it lands in the next admitted request。注入的内容以 user/message 事件落日志， 所以第 4 章的 model-visible ⟺ logged 不变量对它照常成立—— 本章你已经见过证据：一次手动的 /compact 期间，空闲注入的上下文可以落在 compaction/start 与 compaction/end 之间，且位置式替换让它 在 checkpoint 之后仍然可见。

压力视角还有两个交叉点。第一，ctx.tokenMeter 的定价包含缓冲上下文与 steering——排着队的注入已经被计入压力，不会免费。第二，压缩会重置上下文插件： agent-instructions 的作用域在它的上下文事件离开可见表面后被重新武装， 下一个进入的 pre-step 重组当前基线；skill 目录（第 17 章）同理，在被压缩遮蔽后由下一次 完整观察重建。三道闸收窄窗口，context 插件在新的空间里重建必要的上下文—— 这两股力量的配合才是完整的压力管理。

15.9 本章回顾

  • 三道闸按时机分工：spill 在 tools/post-execute 预防（外置超大纯文本，留预览 + locator）；pruner 在压力/溢出合格后修剪超预算 tool/result；compaction 在仍超压时摘要替换。
  • 代价排序：spill 与 pruner 零模型调用，compaction 付一次辅助 llm.stream() 调用并使被替换区间缓存失效；pruner 修剪后若低于压力则跳过摘要。
  • compaction 表面契约：compaction/start → compaction/summary → user/message（surfaceOp replace，唯一表面变更）→ compaction/end；锁是日志 bracket，孤儿 start 即 busy。
  • compaction-basic 策略全在 Config：thresholdRatio（默认 0.8，按路由窗口解析）、retainRatio/retainTokens、modelPolicies、auto；摘要逐字重放前缀以复用 KV 缓存。
  • pruner 替换保留原始事件；字符预算不是 token 预算，裁决权在 ctx.tokenMeter；低于压力从不修剪。
  • 没有模型可见的 compact 工具：/compact 是 ctx.commands 上的人类命令，不经模型轮次，但记录 log-only 的 command/run/command/done。
  • spill seam 只管存储：saveText → SpillRef（branded SpillLocator + retrievalHint）；策略（maxInlineBytes，缺省即禁用）与文件布局（0700 root、sha256 会话前缀、独占 0600 写入）分属 spill-policy 与 spill-local。
  • agent.inject() 排队非唤醒上下文，落在下一个被准入的请求；注入计入 tokenMeter 压力，压缩后由上下文插件重建目录与指令基线。
常见坑
  • 以为有模型可见的 compact 工具——没有；入口只有自动压力/溢出与人类的 /compact 命令。
  • 把 pruner 和 spill 混为一谈：pruner 改写表面节点（head + 标记 + tail，原始事件在日志里），spill 把全文移出上下文、留下可取回的 locator。
  • 以为 compaction/* 事件会出现在表面上——封闭联合只允许 user/message / assistant/message / tool/result 携带 surfaceOp。
  • 把阈值当 token 数硬编码：compaction 阈值按路由模型的窗口容量解析比例，pruner 阈值是字符数；策略全部走 Config 并在加载时校验。
  • 期望压缩能解决一切溢出：不可分割单元、系统提示/工具 schema 超窗不在表面压缩契约内。
  • 给 spill-policy 的豁免清单漏项：嵌套执行、read 结果、非文本 block、非 accept 决策都原样放行——尤其 read 是为了防外置循环。
  • 以为注入立即生效：agent.inject() 排队等下一个被准入的请求，空闲时要等 followup()/steer() 唤醒。
