Agent Loop：Turn/Step 生命周期

前六章你认识了插件、事件、会话日志和 Agent 接口，但一直有一个黑盒： 消息进了 inbox 之后，到底是谁、按什么顺序、把「模型请求 → 工具调用 → 再请求」 这台机器转起来的？这一章打开这个黑盒。读完你会知道一个 turn 从开门到关门 发生的每一件事、哪些事件进日志、哪些只在进程里活着，以及你能在哪些点拦截它。

学习目标
  • 说出 ctx.agentLoop、ReactLoopAgent 与第 6 章 Agent 接口的关系
  • 区分 driver（外层循环）、turn（一次被准入的输入排空）、step（一次模型请求 + 它的工具）三层
  • 按顺序复述一个完整 turn 的全部事件与扩展点
  • 分清 durable 会话事件与 live 进程内事件，以及哪些 waterfall 必须调 next()
  • 解释 inbox 的 followup / steer / inject 三种投递与并行工具调度、取消恢复的行为

7.1 唯一的驱动：ReactLoopAgent 与 ctx.agentLoop

第 6 章说过，Agent 是所有插件（UI、hooks、编排器）编程面对的表面： ctx.agents.get(id) 拿到它，往上调 followup()、往下等 whenIdle()。但 Agent 只是一个接口 —— 谁来实现「把消息变成模型请求、 把模型回复变成工具调用、再把工具结果变成下一个请求」这个循环？

答案在 packages/core/agent-loop/。它有两个角色：

  • AgentLoop 服务（ctx.agentLoop）：插在 packages/core/agent-loop/src/index.ts，是一个 AgentFactory —— 负责按配置创建/恢复 agent、发布进 ctx.agents / ctx.sessions 注册表、 并拥有有序拆除。它声明 static inject = ['agents', 'sessions', 'llm', 'tools', 'systemPrompt']， 也就是说一个 agent loop 天然站在这五个服务的交汇点上。
  • ReactLoopAgent（src/agent.ts）：真正实现 Agent 接口的驱动器。它的模块文档一句话讲清了自己： 「驱动排队轮次与步骤边界输入的默认 Agent 驱动；每个请求都从会话日志推导」 （Default Agent driver over queued turns and step-boundary input. Every request is derived from the session log.）。它是 Agent 接口在仓库里的唯一具体驱动， 而且是包内私有实现 —— 循环之外没有任何代码依赖这个类，大家都只依赖接口。

「每个请求都从会话日志推导」值得停一秒。这不是风格偏好，而是第 4 章那条不变量的落点： 每个步骤里，模型历史不是内存里攒出来的数组，而是调用 session.deriveMessages() 从日志事件流投影出来的。 你在本章末尾会看到 packages/core/agent-loop/src/invariant.ts 甚至在 llm/stream 上挂了运行时断言：请求里的 messages 必须和日志推导结果逐字节一致。

ReactLoopAgent 内部维护一个三态的 Phase： idle（没有活动）、running（一个 driver 正在跑 turn，带 turn/step 计数与 AbortController）、maintenance（跑一个非 turn 的维护任务）。状态切换会对外广播 agent/status（idle / running），这就是 UI 里那个小状态灯的来源。

7.2 三层词汇：driver、turn、step

先把词表立起来。从外到内三层：

  • driver（外层循环，有的系统叫 round）：一个被唤醒的驱动器会连续拉起 turn， 直到没有欠账也没有排队输入才回到 idle。诚实说明：dsh 源码里没有叫 round 的实体 —— 外层就是 kick() 里的 while (await this.turn()) {} 循环；持久化编号也只到 turn/step 两级。把这一层记成「策略迭代层」即可：它决定要不要再开一个 turn。
  • turn（轮次）：一次「把被准入的输入排空」的完整过程，包含零或多个 step。 docs/architecture.md 的定义原文是：turn 在认领它的第一条输入之前打开， 在没有欠账（nothing is owed）时关闭。每个 turn 有单调递增的编号，日志里以 turn/start 和 turn/end 一对事件框住，turn/end 携带结束原因 TurnEndReason：completed / max-tokens / blocked / aborted / error。
  • step（步骤）：一次模型请求加上它调用的全部工具。日志里以 step/start 和 step/end 框住，编号在 turn 内从 1 递增。 工具结果「欠」一次回应、或有新输入插队，都会催生下一个 step。

一个 turn 也可以零个 step：输入被 agent/pre-step 拒绝、或第一批被改写为空时， turn 照样开门和关门（下面 7.3 讲为什么这不是浪费）。反过来，一个 turn 里 step 的数量没有静态上限， 只由「有没有欠账」决定。

7.3 一个完整 turn 的生命周期

下面这段流程照 docs/architecture.md「Turn flow」一节展开，每一步我都标了 agent.ts 里对应的代码位置。你可以把这一节当成排查问题时的检查清单。

把流程走一遍，重点看四个门：

开门（turn()）。 driver 先落 turn/start，编号取上一个 turn + 1（恢复会话时从日志里 findLast(turn/start) 找回，所以编号跨进程持续）。 然后进入循环：每个候选 step 先经过 preStep() —— 它做三件事： this.inbox.claim(target, turn) 认领下一步输入加一条排队消息； 调 ctx.systemPrompt.assemble() 装配 prompt section 与工具 schema（第 9 章展开）； 最后把认领结果交给 agent/pre-step waterfall。

准入门（agent/pre-step）。 这是「模型本轮看什么」的权威决策点。默认决定是 enter(messages)； 监听器可以改写这批消息，也可以返回 reject。两种结局值得记住：

  • reject → turn 以 {kind:'blocked'} 关闭，一个 step 都不花；
  • 第一个 enter 被改写为空 → turn 以 {kind:'completed'} 关闭，同样不花 step。 代码注释写得很直白：被移除的唤醒消息或改写为空的 enter 决定仍拥有这个 turn 边界， 但它不花任何模型调用。

注意「不花 step」不等于「不留痕迹」：turn/start 和 turn/end 都已落日志， 这次尝试永远可查。这正是第 4 章「durable 边界事件框住一切」的用意。

step 内部（step() 与 buildRequest()）。 准入通过后：落 step/start，把 enter 的每条消息以 user/message 追加进日志 （包括上一 step 工具捎带的 context 与插件注入的上下文）；然后用 session.deriveMessages() 从日志推导模型历史； buildRequest() 先让 agent/request waterfall 提议请求配置 （provider/model/采样参数），经 ctx.llm.prepareCall() 绑定 adapter， 并在配置变化时落 request/header 与 request/context 事件（第 10 章展开）。 随后请求进入 llm/stream：流里每个 chunk 立刻以 assistant/chunk 落日志并喂给 BlockAssembler；流正常结束时组装出一条 assistant/message 事件 （携带 usage 和它引用的 chunk 序列 sourceEventSeqs）。

如果 assistant 消息里有 tool-call 块，就轮到 executeToolCalls() （7.6）：每个调用先落 tool/call（先记再执行），穿过第 8 章的执行管道， 以 tool/result 收尾。工具结果天然欠一次模型回应 —— 除非某个结果标记了 concludesTurn —— 所以 loop 再认领、再开下一个 step。assistant 消息没有工具调用、 或撞上 max-tokens（该原因在 turn 内是「粘性的」：后续正常完成的 step 不能把它降级）， step 就以对应原因结束。

关门。 step 结束后若「没有欠账、next-step inbox 也空」，先广播 agent/turn-stopping —— 这是一个串行、没有 next() 的终局检查点（比如收尾插件在这里做最后动作）—— 然后落 turn/end。无论中间发生什么，turn/end 在 finally 里追加， 崩溃、取消、错误都会得到一个带原因的关門事件。

7.4 两类事件：durable 与 live

把 7.3 的流程按「是否进日志」切成两半，你会得到一张值得背下来的表。 durable 事件是会话日志的一部分，重放、恢复、fork、transcript 全靠它们； live 事件只在本进程内广播，用于协调与拦截，进程一死就没了。

类别事件说明
durable turn/start、turn/end、step/start、step/end 边界框；turn/end 带 TurnEndReason
durable user/message、assistant/chunk、assistant/message 对话表面；chunk 服务回放，message 服务推导
durable tool/call、tool/result 工具调用对；先记再执行
durable request/header、request/context（以及 llm-retry 的 llm/retry 等） 请求配置与环境的可重建快照
live agent/status、agent/error、agent/inbox/inserted|claimed|discarded 状态与队列协调信号
live · waterfall agent/pre-step、agent/request、agent/request-error、llm/stream、tools/pre-execute、tools/execute、tools/post-execute 可拦截可改写；监听器必须调 next() 委托下游，否则短路整条链
live · serial agent/turn-stopping 串行广播，没有 next()；只做观察/收尾，不能改写决定
不变量的运行时证据

packages/core/agent-loop/src/invariant.ts 在 llm/stream 最前面挂了一条断言： loop 构建的请求必须被冻结、携带活的 sessionId，且 request.messages 必须与 session.deriveMessages() 的结果完全一致、 请求头与日志折叠出的 request/header 一致。任何插件在半路塞给模型一个日志里不存在的东西， 都会在这里被抓住 —— 「model-visible ⟺ logged」不只是文档口号，它是被执行的检查。

7.5 inbox：所有输入的唯一入口

UI 的聊天框、命令系统、hooks、子代理、压缩插件 —— 所有想跟 agent 说话的人， 走的都是同一个收件箱。ReactLoopAgent 构造函数里创建 new Inbox(session, {...})，并把插入/丢弃/认领即时映射成 agent/inbox/inserted / agent/inbox/discarded / agent/inbox/claimed 三个 live 事件。 统一入口的语义在 send(message, target, wakeup) 上：

方法target唤醒语义
followup(msg)next-turn是新的一句话，等下一个 turn 处理
steer(msg)next-step是插队指令，尽快在下一个 step 进入模型视野
inject(msg)next-step否注入上下文，排队等下一次被准入的请求

关键差别在 wakeup：有的消息会立刻唤醒 driver（followup/steer）， 有的不会（inject）。docs/architecture.md 的扩展表里那句 「Add model-facing context → call agent.inject(); it lands in the next admitted request」 说的是：注入的内容静静躺在 next-step 队列里，直到某条消息唤醒 driver、 或当前 turn 的下一个 step 来认领它。一个空闲的 agent 被 inject() 之后仍然是空闲的。

取消与唤醒的交互有一个精细点（源码注释称为 wake latch）：唤醒类输入如果撞上正在取消的活动， 会被改派到 next-turn 并在活动收敛到 idle 后重放；而一个已经 idle 的 agent 收到的唤醒总会开自己的 turn 边界。你不需要背细节，只需要知道：唤醒不会丢， 顶多晚到。

7.6 工具调用的调度：并行池与屏障

一个 step 的 assistant 消息可以带多个 tool-call 块。src/tool-calls.ts 的 executeToolCalls() 负责调度它们，规则只有三条：

  • 先分类。 每个调用经 ctx.tools.executionMode(exec) 分类： 只有工具定义的 isConcurrencySafe(args) 恰好返回 true 才是 parallel；未声明、抛异常、返回非 true，统统按 exclusive 处理 —— 失败保守。
  • 排他是屏障。 一个 exclusive 调用单独成组，形成顺序屏障；parallel 调用组成 有上限的滚动池（maxParallelToolCalls，默认 10，可经 agent-loop 的 settings 在运行中调整）。池里「dispatch 可重叠，策略与结果保持模型顺序」： pre-execute 串行按序，工具体并发跑，结果按模型给出的顺序提交落盘。
  • 启动前重新分类。 每个调用启动前重查当前注册表（工具可能中途被注册/注销）， 后来变成 exclusive 的调用会等当前池排空、单独成屏障。

取消的语义同样为重放服务：abort 后，已启动的调用照常排空并提交结果； 未启动的调用补一对合成的 tool/call + tool/result （错误码 ABORTED_BEFORE_DISPATCH），保证日志里每个 call 都有 result， 重放不缺角。

7.7 取消、维护与错误恢复：agent handle

docs/subsystems/core.md「The agent handle」一节把对外的生命周期方法讲得很清楚， 这里挑 loop 视角最相关的四个：

  • cancel(cause, options?)：默认清空 inbox 并中止活动；传 {keepInbox:true} 保留排队工作。第一个原因获胜；没有活动时是 no-op。取消不是硬杀 —— 它沿 AbortSignal 协作传播到 step、流、每个工具（第 8 章的工具取消契约同源）。
  • whenIdle()：等整个 agent 达到静止（当前 driver 与后续接替者都跑完）。拆除流程 （dispose）就是「一次 cancel({kind:'disposed'}) + whenIdle()」。
  • runMaintenance(job)：从真正的 idle 出发跑一个非 turn 维护任务（比如压缩的收尾）； 期间到达的唤醒输入留在 inbox，任务结束再重放，对外状态保持 idle。
  • 错误恢复：结构化失败。LlmError 保留自己的 code/facts， 其他异常被 errorChain() 摊平为 UNKNOWN code 文本；失败经 agent/error 上报后由 driver 边界容纳，turn/end 记 {kind:'error', error}。流内失败先走 agent/request-error waterfall： 默认保留原错误；返回 {kind:'retry'} 则在同一步内重发请求 （llm-retry 插件会在等待前后落 llm/retry 与 llm/retry-started 事件； 失败尝试的 chunk 留在日志里，但永远不会被组装成 message，所以不会污染模型历史）。
本章的关键直觉

agent loop 是一台「日志优先」的状态机：先落事件，再做动作；一切模型输入从日志推导， 一切边界（turn/step/工具调用）都有 durable 框架。你以后写任何插件，只要问一句 「我的行为落在日志的哪一格、拦截在 live 的哪一点」，就不会迷路。

7.8 本章回顾

  • ctx.agentLoop（AgentLoop 服务）创建/恢复 agent；ReactLoopAgent 是 Agent 接口的唯一具体驱动，包内私有、每个请求从会话日志推导。
  • 三层词汇：driver 外层循环（书中称 round，源码无此命名）> turn（零或多个 step 的排空过程）> step（一次模型请求 + 它的工具）。
  • 完整 turn：turn/start → claim → 装配 → agent/pre-step（reject | enter）→ step/start → user/message → derive → agent/request → llm/stream → assistant/chunk* → assistant/message → tool/call* → tools 管道 → tool/result* → step/end → （欠账则下一个 step）→ agent/turn-stopping → turn/end。
  • reject 或首个 enter 为空 → 无 step 关门（blocked/completed），但日志记录尝试；turn/end 永远落盘并携带原因。
  • durable：turn/*、step/*、user/message、assistant/*、tool/*、request/*；live：agent/*、llm/stream、tools/*。waterfall 监听器必须调 next()；agent/turn-stopping 串行无 next()。
  • inbox 统一入口：followup（next-turn，唤醒）、steer（next-step，唤醒）、inject（next-step，不唤醒）。
  • 工具调度：isConcurrencySafe 严格判定 parallel；exclusive 成屏障；池有上限；结果按模型顺序提交；abort 为未启动调用补合成结果。
  • handle：cancel/keepInbox、whenIdle、runMaintenance；错误结构化，retry 在同一步内重发。
常见误区
  • 以为「turn 没有执行就等于没有发生」—— 无 step 的 turn 也留下 turn/start + turn/end，这正是审计需要的。
  • 在 waterfall 监听器里忘记调 next() —— 你不是「加了个钩子」，你是掐断了整条链（第 2 章语义在这是硬规则）。
  • 把 inject() 当成「立刻给模型发消息」—— 它不唤醒 agent，只排队等下一次准入。
  • 以为并行工具的「结果顺序」等于「完成顺序」—— 调度可以重叠，提交永远按模型顺序。
  • 以为重试会新开一个编号的 turn —— 按 agent.ts 与 llm-retry 测试，retry 动作在同一个 step 内重发请求。
