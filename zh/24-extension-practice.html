扩展实战：从 cookbook 写一个插件

前二十三章你读懂了 dsh；本章你动手改它。我们以「给 dsh 加一个新能力」为主线，把 docs/cookbook/ 走三遍：加一个包、加一个工具、加一个 LLM 适配器——每遍都摘真实代码骨架、 标注出处、点出会咬人的契约。最后看 out-of-tree 插件如何用一份 insert overlay 叠在已发布的 组合之上，连仓库都不用进。这一章结束时，你应该有信心提交自己的第一个扩展 PR。

学习目标
  • 按 docs/cookbook/adding-a-package.md 的清单建一个 @deepseek-ai/dsh-<name> 包并通过约束门禁。
  • 用 defineTool 写一个满足 execute() 契约与渲染意图纪律的模型可见工具。
  • 写一个满足协议义务（usage 先于 finish、两条错误路径、exec.signal）的 LlmAdapter。
  • 解释 cordis.yml 的 !!js 边界与 bare 插件的 dependencies 要求，并用 insert overlay 叠加 out-of-tree 能力。
  • 为每种扩展点名它的验证义务（同一 PR 的 keyless 快照、examples 的双 smoke）。

24.1 实战主线：先选扩展点，再写代码

extension-cookbook.md 的「feature → mechanism map」是每个扩展的入口：仓库里每个产品特性 都映射到某个文档化扩展点上的一条监听器——这是微内核主张的可检验形态，没有任何一行 改 loop。动手前先在这张表里找到你的位置：想加模型工具就走 ctx.tools， 想改提示词就走 ctx.systemPrompt.section()，想接新供应商就走 ctx.llm.registerAdapter，想让插件自带一张设置卡就走 ctx.settings 的命名空间 schema（设置面是插件自有的，2026-08 起配套指南 docs/cookbook/adding-a-settings-card.md，第 17 章 17.9 节）。选错扩展点， 后面所有代码都在还债。

本章三遍实战对应三条最常见的路径：加一个包（新能力需要新 home 时）、 加一个工具（模型可见的新能力）与 加一个 LLM 适配器（新供应商）。 每遍都以同一条收尾：验证义务。examples/AGENTS.md 要求每个 example 配双 smoke——keyless 的 「经真实 Loader 启动 cordis.yml、驱动、断言输出与干净退出」（专抓 hand-mounted 测试漏掉的 Loader 导出错误，postmortem 0001 的教训），和带密钥的「发真实 prompt、验证外部世界而非模型 自述」。

24.2 第一遍：加一个包

docs/cookbook/adding-a-package.md 给出逐文件清单（它以 bash 与 adapter 包为模板校验，漂移了 要先修文档）： 

packages/<group>/<pkg>/
  package.json     # 从 packages/core/tools 拷贝，改 name/description/deps
  tsconfig.json    # extends ../../../tsconfig.base.json，rootDir src，
                   # outDir lib/types，references 指向 vendor 与各 dsh 依赖
  src/index.ts     # service 默认导出或插件（name/inject/apply/Config）
  README.md        # 服务 API、事件、扩展点、设计说明
                   # + 门禁要求的 Model Experience 与 Known Limitations 段落

package.json 的不变量由 pnpm run constraints（scripts/check-workspace-constraints.ts） 执行：private: true、version 与根 package.json 一致、type: module、 main: lib/index.js、types: lib/types/index.d.ts、 exports["."] 的 types/default 指向同一对文件；@deepseek-ai/cordis 必须同时出现在 peerDependencies 和 devDependencies（同版本区间）；每个 dsh peer 依赖都在 devDependencies 里有镜像；@deepseek-ai/schemastery 属于 dependencies （它是运行时校验器）；files 清单精确列出 lib/index.js、 lib/invariant.js、lib/types/**/*.d.ts 与包特有的运行时产物——不发布 src、declaration map 或 JS map。包内相对导入在源码里写显式 .ts 后缀 （如 export * from './types.ts'），编译器在产物里改写为 .js。

注册进根配置只要动两处：往 tsconfig.host.json（Host 包）或 tsconfig.client.json（Client 包）的 references 加一行——普通包恰好属于一个聚合， 绝不两边都进（api/remotes 的拆分是仓库特例，新包不许模仿）；新 group 才需要动 tsconfig.base.json 的通配。其余（root workspaces、publint、tsdown、oxlint、 constraints）都被 glob 或 manifest 发现自动覆盖。

命名是设计的一部分：给稳定存在的职责命名，不命名第一个实现或「可能的将来」。单一引擎用 单数 ctx 键，注册表用复数；角色词要配得上行为——Registry 拥有一组可增删的命名 注册（含查找、重复/优先规则、生命周期），Runtime 跑活的工作并拥有调度与取消， Provider 供给一个能力定义的一种实现，Store 只拥有一份数据及其 CRUD/快照/订阅。README 以固定次序收尾：Model Experience（What the model sees → Verbatim text → Token effect → KV Cache effect）加 Known Limitations and Deferred Work——这两段由 doc-sync 的校验器把关。最后跑清单第五步： 

pnpm install        # 注册 workspace
pnpm run doc-sync
pnpm run constraints && pnpm run typecheck && pnpm run lint
pnpm run build && pnpm run hygiene

24.3 第二遍：加一个工具

工具参考 docs/cookbook/adding-a-tool.md（教程版在 docs/user/develop/basic/tool.md）。 最小形状——defineTool 是第一方工具的类型化助手（MCP 来源的工具则以裸 JSON-Schema ToolDefinition 直接进 ctx.tools.register()）： 

import { readFile } from 'node:fs/promises'
import type { Context } from '@deepseek-ai/cordis'
import { defineTool } from '@deepseek-ai/dsh-tools'

export const name = 'my-tool'
export const inject = ['tools']

export function apply(ctx: Context) {
  ctx.tools.register(defineTool({
    name: 'read_file',
    description: 'Read a file from disk.',   // 模型看到的内容
    parameters: {
      path: { type: 'string', required: true, description: 'Absolute path' },
      limit: { type: 'number' },                // 默认可选
    },
    output: {
      schema: { type: 'string' },
      render: (_args, value) => [{ type: 'text', text: value }],
    },
    async execute(args, exec) {
      // args 的类型由 schema 推导：{ path: string; limit?: number }
      return readFile(args.path, { encoding: 'utf8', signal: exec.signal })
    },
  }))
}

注册即效应：dispose 插件 fiber 就注销工具；schema 自动流入 system-prompt 组装。execute() 的 契约要点：参数已被校验——defineTool 在 execute 之前用统一 ParameterSchemaSpec 校验模型生成的 arguments（类型、必填、literal 约束、exact-one union、嵌套 值），DSL 表达不了的约束（非空字符串、正数、跨字段规则）才需要你手查；返回恰好一个 canonical JSON 值——output.schema 可有对象/数组/标量/null 根，注册表会 对返回值做快照、校验、冻结，再交给 output.render；不要在 body 里返回 content blocks、不要让调用方解析散文找 id；抛错或返回非法值都算 isError ——基础设施故障用 throw，非理想但成功的领域结果（如非零退出码）留在 canonical 值里由渲染层 解释；尊重 exec.signal；异步通知用 exec.agent.inject()（追加下次模型请求可见的持久上下文，不是唤醒信号）。

渲染意图是设计的一部分，事前决定

工具的 UI 卡片与模型结果分离，用纯投影声明：presentCall(args) 返回 pending 卡 （generic 默认 / terminal——你的调用就是一条 shell 命令 / diff——你的调用创建或修改文件，可带 locations 让编辑器跟随）； presentResult(args, { content, isError, meta }) 返回完成卡（还有 search 与 web 两种结果形态）。硬规矩：这些函数在直播流与会话日志回放时 都会跑，所以必须是 args（+结果）的纯函数——不许 I/O、不许读会话状态、不许时钟/随机。想要 文件旧内容或工作目录？停下——那属于持久化的 result metadata 或 UI 适配器。UI 专属的格式 （console 围栏、相对化路径）绝不进模型结果。没有 UI 呈现的工具自动落回通用卡。

长任务走后台：用 producer config 放开 run_in_background，然后经 ctx.jobs.start({ kind, label, owner: exec.agent, run }) 注册。成功的后台分支返回 类型化句柄（如 { kind: 'background', jobId }）；Native 渲染可以保留人类可读的 started background job bash-1，但 Code Mode 绝不能从这句散文里解析 jobId。 id 发布之后用任务自己的取消信号而不是 exec.signal——外层调用的取消只是不再等待， 杀掉已发布工作的是 job_kill、owner 销毁与服务 teardown。

部署策略不进工具本体：可扩展的 allow/deny/ask 用 tools/pre-execute（返回类型化 决策的 waterfall），不可撤销的最终拒绝用 ctx.tools.guard()，超时/重试/指标用 tools/execute 包住调度生命周期（只有 exec.signal 可替换），显式 变换结果用 tools/post-execute，观察不可变的最终结果用 tools/result。 而在 Code Mode 里，每个可见注册工具免费变成 await tools.<name>(args)——类型由 同一组 schema 生成的 ToolArgsMap/ToolOutputMap 提供。

24.4 第三遍：加一个 LLM 适配器

docs/cookbook/adding-an-llm-adapter.md 连接新模型供应商；参考实现是 packages/llm/llm-deepseek（直连 HTTP、eventsource-parser 分帧）与 packages/llm/llm-pi-ai（包装一个 LLM 库）。动手前先读 packages/llm/llm/src/types.ts 里 StreamChunk 的文档——两个适配器 都按它记录的协议约定校验过。形状： 

class MyAdapter extends LlmAdapter {
  async * stream(options: GenerateOptions): AsyncIterable<StreamChunk> { … }
}

export const name = 'llm-myprovider'
export const inject = ['llm']
export const Config = z.object({ apiKey: z.string(), … })

export function apply(ctx: Context, config: Config) {
  ctx.llm.registerAdapter(['my-provider'], new MyAdapter(…))
}

注册按效应走（HMR 安全）；一条 provider 路由一个适配器——重复注册 throw，多路由注册要么全成 要么全不成。options.provider 选适配器，options.model 是供应商模型 id，所以动态目录式适配器无需生命周期重配就能服务新模型。密钥走 cordis 原生路径：schemastery Config 加 env 回退，从 cordis.yml 经 !!js process.env.MY_KEY 喂入——代码里绝不读 临时密钥文件。

协议义务（两个实现验证过的契约）：usage 在 finish 之前发，finish 之后什么都不 发——稳妥做法是把 finish/usage 缓冲到供应商的流结束标记再冲刷；工具调用 arguments 端到端是裸 JSON 字符串，流式片段用 argumentsDelta，供应商若回解析好的 对象就在 block-end 重新序列化；block 的 index 按首次出现的流序分配， 同一块的每个 delta 复用；错误恰好两条正道——从 stream() throw（传输/协议失败， 用带稳定 code 的 LlmError）或以 finish {kind: 'error' | 'aborted'} 收流（供应商带内失败），按失败类别二选一并写进文档；尊重 options.signal； 无法兑现的 GenerateOptions 字段要 throw LlmError(..., 'UNSUPPORTED') 而不是静默丢弃；供应商需要响应 id/签名等原生元数据时，把最小无损 JSON 投影作为 finish.replayState 发出，重建历史时校验它——绝不只凭 provider/model 名字推断原生 重放。模型元数据走 provider 中立的能力面：实现 resolveModel()，推理力度是有序的 opaque id，由适配器映射到供应商请求。实现结构上把 wire 类型、请求序列化、传输解析、chunk 翻译 与适配器类分作不同职责。

24.5 Out-of-tree：insert overlay 与第三方边界

不是所有扩展都要进仓库。examples/web-schedule/cordis.yml 是最小可运行的 out-of-tree 叠加——整个文件只有一段 insert： 

# Opt-in Schedule patch over the shipped Web composition.
# The owner observes only roots published after this overlay loads.
- insert:
    - id: time-context
      name: '@deepseek-ai/dsh-time-context'

    - id: schedule
      name: '@deepseek-ai/dsh-schedule'

它是发布 Web 组合（dsh-base + dsh-web-app 的 bundle 层）之上的一份 patch overlay：insert 把 这些行追加到同一 include 层的尾部，加载顺序决定可见性——owner 只观察 overlay 加载之后发布的 根。dsh web --patch <path> 即可启用。对照 examples/web-cordis/cordis.yml 能看到另一种 patch：不带 insert 的行直接替换目标行（同 id）的整个 config——它在 webserver 行上钉死 127.0.0.1:3081，再用 insert 加进 cordis 自检工具。

cordis.yml 的两条安全边界来自根 AGENTS.md：!!js（绝不 !js）只允许 出现在插件 config 与条目 disabled 下，其余元数据保持字面量——所以 条件式组合也用 overlay 表达；Raw/Web cordis.yml 里的 bare 插件必须出现在其 resolver manifest 的 dependencies 里，verify-cordis-config 强制检查。第三方能力的样板 是 examples/mcp-memory/：三份默认关闭的参考配置（memorix、mcp-reference-memory、 engram），每份一个 insert，把 @deepseek-ai/dsh-mcp-client 指向各自的 stdio 命令 ——DSH 解析 overlay、起子进程、发现 MCP 工具、以 mcp__<serverName>__<tool> 暴露；DSH 不下载服务器、不建库、不管账号。stdio 桥接在拉起子进程前刻意剥掉名字里通常带凭证的 环境变量与全部 DSH_* 变量。

示例的边界

examples/AGENTS.md：examples 是可运行组合，不是构建目标；可复用逻辑要抽进 packages/（那里有 per-file 覆盖与 README 门禁），examples 只留 cordis.yml 接线、demo 产物与 e2e/snapshot 场景； app 包的 bin 拥有启动胶水。每个 example 都有 keyless 与 with-key 两个 smoke。

24.6 每一遍的终点：验证义务

三遍 cookbook 的「Verification」小节都指回同一份 docs/testing.md（第 22 章）。映射到本章的三种 扩展：新包——包级行为进 unit + 覆盖率门禁，产品可见插件必须有非 unit 的真实 组合测试（手搭 ctx.plugin(...) 不算数，要 boot 测试专用 cordis.yml 穿过 Loader）； 新工具或改工具——模型可见与 UI 可见的 shipped 变化都要组装后的覆盖（同 PR 的 keyless 快照场景，UI 卡片变化进 web 快照），渲染回放要能在 macOS/Linux 重放；新 适配器——testing.md 拥有适配器覆盖、真实供应商检查与发布入口要求：协议义务逐条有 测试，真实 provider 行为跑 e2e，发布入口跑 built smoke。若 harness 还表达不了你要的场景， 政策要求先扩展 harness 再实现——这也是 acp-snapshot 把比对机制集中成一个包的原因。

24.7 本章回顾

  • 先在 feature → mechanism map 里选扩展点，再写代码；没有一行路通向 agent-loop。
  • 加包：清单五件套（package.json/tsconfig/src/README/注册），constraints 门禁的不变量，命名配角色，README 以 Model Experience + Known Limitations 收尾。
  • 加工具：defineTool 的 execute() 契约（参数已校验、一个 canonical JSON 值、throw 即 isError、尊重 signal）；渲染意图事前决定且是 args 的纯函数；后台走 ctx.jobs.start 返回类型化句柄；策略上扩展点不进本体。
  • 加适配器：ctx.llm.registerAdapter 按路由注册；usage 先于 finish、arguments 是裸 JSON 字符串、错误只有 throw 与 finish {kind} 两条路、不支持的选项 throw UNSUPPORTED、原生重放态走 finish.replayState。
  • Out-of-tree：insert overlay 叠加在发布组合之上（web-schedule 是最小样板）；不带 insert 的行替换目标行整个 config；!!js 只在 config 与 disabled 下；bare 插件必须在 resolver manifest 的 dependencies。
  • 每一遍的终点都是验证义务：同 PR 的 keyless 快照 + examples 双 smoke + 真实组合测试。
常见误区
  • 在 execute() 里手写参数校验——defineTool 已按 schema 校验，只补 DSL 表达不了的约束。
  • 在 presentCall 里想读文件旧内容或工作目录——那是持久化 result metadata 或 UI 适配器的职责，presenter 必须纯。
  • 让 Code Mode 从渲染散文里解析 jobId——后台分支返回类型化句柄，散文只给人看。
  • 把部署策略（超时、权限）写进工具本体——分别上 tools/execute 与 tools/pre-execute。
  • 适配器把 finish 之后的尾部 usage 直接丢弃或乱序发——缓冲到流结束标记再冲刷。
  • 供应商回解析好的参数对象就直接塞给流——arguments 端到端是裸 JSON 字符串，在 block-end 重新序列化。
  • 在 cordis.yml 的插件 id/name 等元数据上写 !!js——只允许 config 与 disabled。
  • 新包同时挂进 Host 与 Client 聚合——普通包恰好属于一个；api/remotes 的拆分不许模仿。
