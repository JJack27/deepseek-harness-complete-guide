组装一个运行时：boot、profiles、bundles、补丁层

你敲下 dsh web、回车、浏览器打开——中间那几秒钟，一棵插件树从零长了出来。 本章追踪这棵树的生长过程：profile 决定叠哪些层，bundle 是每层的发行格式， 补丁按 id 一层层改写行。读完这章，你能解释你机器上任何一个 dsh 进程里跑着的每一行插件。

学习目标
  • 能把「一条 dsh 命令启动」拆成：选 profile → 按 dsh.profile 叠 bundle 层 → 套补丁层 → Loader 挂载
  • 能说出 profile 目录（$DSH_HOME/profiles/<name>/）里每个文件的角色
  • 能解释 bundle 是什么、dsh-base 为什么是每个 profile 的第一层
  • 能按正确的层序（bundle → profile 补丁 → home 补丁 → --patch）预测一行的最终 config
  • 能用 --dump-config 亲眼检查组合结果，并写出自己的第一条 cordis.patch.yml

3.1 启动即组装

先纠正一个容易带入的想象：dsh 不是「一个编译好的大程序，启动时把功能都加载进来」。 准确的说法来自架构文档的第一句：运行中的 dsh，是启动时从有序层组装出的一棵插件树。 树上每一行是一个插件——第 2 章讲的那种，带 inject、在 ctx 桌上占 key、 通过事件通话的插件。

把 dsh web 拆成步骤：

  1. 选 profile：launcher（apps/cli）解析自己的标志，确定要启动 web 这个 profile；
  2. 解析层列表：读 profile 的 dsh.profile，得到一份有序的 bundle 名单；
  3. 组合 entry list：从空列表出发，每个 bundle 贡献一批插件行，再套上你的补丁层；
  4. 挂载：Cordis Loader 依 inject 依赖关系挂载这些行（第 2 章的机制）；
  5. 断言：启动 glue（packages/boot/app-boot）核对每个启用的行都真的激活了——谁没挂上，报错点名。

本章的主角是第 2、3 步：层从哪来、按什么顺序叠、谁覆盖谁。第 4、5 步在第 18 章（CLI 与 boot）展开。

3.2 profile：Harness home 里的命名组合

profile 是一份命名组合，存在 Harness home 里。Harness home 由环境变量 $DSH_HOME 指定，默认是 ~/.dsh。每个 profile 住一个目录： 

~/.dsh/                       # Harness home（$DSH_HOME，默认 ~/.dsh）
├── cordis.patch.yml         # home 级补丁层（所有 profile 之上、你的机器全局）
└── profiles/
    └── web/                 # 一个 profile = 一个目录
        ├── package.json     # dsh.profile（bundle 顺序表）+ out-of-tree 插件依赖
        └── cordis.patch.yml # 这个 profile 自己的补丁层

profile 目录里的 package.json 有两个作用：

  • dsh.profile 字段：一份有序的 bundle 名单，顺序就是层的顺序；
  • dependencies：装你自己（out-of-tree）插件的地方，由 dsh plugin 命令帮你管理。

web 和 headless 这两个名字随产品发行模板，首次使用自动初始化； 其他名字不会凭空存在——必须先用 dsh plugin --profile <name> <pnpm 参数> 创建并装插件， 直接启动一个不存在的 profile 会当场报错（失败即大声，见 3.6 节）。

「一次性」与「常驻」都从这出发

第 1 章的两种形态在这里对上了：dsh web 启动 web profile（常驻浏览器应用）， dsh --profile headless "任务" 启动 headless profile（一次性 runner，跑完即退）。 它们不是两个程序，是两份不同的层叠方案。

3.3 bundle：可安装的层

bundle 是一种发行格式：一个 npm 包，里面装着一批 Cordis 配置行和这些行要挂的代码。 关键在于「发行格式」三个字——bundle 插入的行不是特权，它们和平常的行一样， 会被它上面的层按 id 改写。这正是架构文档强调的性质： 「bundle 插入的一切，保持可被上层补丁修改」。

一个包如何声明自己是 bundle？在 package.json 的 dsh 字段里指向补丁文件：

// packages/bundle/base/package.json（示意）
{
  "name": "@deepseek-ai/dsh-base",
  "dsh": {
    "bundle": { "patch": "./cordis.patch.yml" }
  }
}

产品随发行三个 bundle，角色各异：

bundle角色
@deepseek-ai/dsh-base 每个 profile 的第一层（78 行左右）：模型适配器（llm-deepseek）、默认模型选择（agent-default-model）、工具（含 tool-bash）、持久化（session-persistence-jsonl）、沙箱与审批策略（bash-sandbox 等）、settings、credentials、遥测。一个 profile 无论多定制，都从这层开始往上叠。
@deepseek-ai/dsh-web-app 在 base 之上加浏览器应用：Web 服务器、API gateway、workspace、浏览器插件全家桶、coding persona（system-prompt 的 persona 在这层设置，不在 base）。
@deepseek-ai/dsh-headless 在 base 之上加一次性 runner：禁用 HMR、挂 Code Mode worker，不挂任何 Host、HTTP 服务器或浏览器插件。

为什么把 persona 放 web-app 而不放 base？因为 base 的行要被所有模式共用，而 persona 是「模式相关」的值—— dsh 的分层纪律：模式相关的值住在模式 bundle 里，base 保持中性。这条纪律马上会在补丁语义里看到代价与回报。

3.4 层序：从空列表到最终树

所有层都往同一个空 entry list上叠，顺序固定：

  1. profile 列出的各 bundle，按 dsh.profile.bundles 的书写顺序（如 base → web-app）；
  2. profile 自己的 cordis.patch.yml；
  3. home 级的 $DSH_HOME/cordis.patch.yml；
  4. 命令行 --patch overlay（如果有）。

「补丁」能做两件事，也只有这两件事：

  • 按 id 替换一行的整份 config——注意是整行替换，不做深合并。 你想保留的字段必须原样重述，漏掉的字段就没了。这不是偷懒，是刻意的：整行替换让每一行的最终样子 可以只看「最后一个碰它的层」就知道，不用在脑子里做多层合并算术。
  • insert 插入新行——新插件（你自己写的或第三方装的）从这里进树。

真实例子（packages/bundle/web-app/cordis.patch.yml，节选）——web-app 作为后一层， 改写 base 里已有的行、并插入自己的新行： 

# packages/bundle/web-app/cordis.patch.yml（节选）
- id: system-prompt          # 替换 base 里这一行的整份 config
  config:
    persona: >-
      You are a coding agent powered by the {{model}} model.
      Your working directory is {{cwd}}.

- id: hmr                     # 也可以只是禁用这一行
  disabled: true

- insert:                        # 插入 web 才需要的新行
  - id: storage
    name: '@deepseek-ai/dsh-storage'
  …
试一试 —— 补丁层怎么叠加

预测一行最终 config 的方法

从下往上扫层序，找到最后一个碰这个 id 的层：如果它替换了 config，最终 config 就是它写的 那份（它没重述的字段统统回落到插件代码里的默认值，而不是更低层写的值）；没人碰，就用 bundle 插入时的原始值。 「last write wins」按行生效，不同行可以来自不同层。

3.5 亲眼看：dump 出你的树

不必靠脑内模拟。这个命令把组合结果原样打印出来，不启动任何东西：

dsh --profile web --dump-config

它用与真正启动同一套解析与补丁算法离线组合（所以打印的和你启动的必然一致）， !!js 表达式按原样保留。架构文档接着的那句话是本章的钥匙： 「打印出来的任何一行，都能被你自己的补丁替换。」

动手写你的第一条补丁。在 ~/.dsh/profiles/web/cordis.patch.yml 里（示意）：

# ~/.dsh/profiles/web/cordis.patch.yml（示意）
- id: agent-default-model     # base 里这行原本是 deepseek-v4-flash
  config:
    provider: deepseek-official
    model: deepseek-v4-pro       # 整行替换：两个字段都重述了

- insert:                        # 再挂一个自己的插件
  - id: my-weather
    name: '@your-scope/dsh-my-weather'

保存后再跑一次 --dump-config，diff 前后输出：你会看到 agent-default-model 那行变了、my-weather 出现了。改运行中的产品，不需要 fork 任何代码——这就是第 2 章 「没有特权核心可打补丁」落在你手上的体验。

3.6 失败即大声，改了即生效

组装机制这么灵活，出错怎么办？dsh 的立场是一条贯穿全仓库的原则：misconfiguration fails loud—— 配置错误大声失败。加载期能自我证明的错误，在加载期就报出来；boot 的启动 glue 会把挂了一半的树 整个拆掉再拒绝启动，而不是带着残缺继续跑。落到本章机制上：

  • profile 名单里列了一个没有 bundle 声明的包 → 解析时失败点名；
  • cordis.patch.yml 是空文件或只有注释 → 直接抛错（它解析成「什么都不是」而不是空列表； 想禁用这一层，请写 []）；
  • 补丁指向一个树里不存在的 id → stderr 警告（提醒你可能拼错了 id）；
  • 行声明了但没激活（依赖的服务一直缺席）→ 启动断言报出每个没挂上的插件名。

还有对开发体验至关重要的一条：每次 profile 启动都会盯着你补丁文件的变化（HMR watch）。 保存 cordis.patch.yml，树就地按同一套层序重组；如果新内容读不得、解析不了， 上一个好树继续运行，失败广播出来——不会因为一次手滑把正在跑的会话弄崩。

一个体现「大声」价值真实案例：base 的补丁用平台表达式门控两套 shell—— tool-bash/bash-sandbox 带 disabled: !!js process.platform === 'win32'（bash 没有 Windows 运行器）， 它们的孪生行 tool-pwsh/pwsh-sandbox 反之。想在自己机器上恢复 bash， 你得补全整份配方（同时禁用 pwsh 两行、启用 bash 两行）；只做一半， 两个执行器族会注册同一个 bash 服务——加载当场失败并告诉你为什么。 静默成功一半、留下半残的树，才是这类系统最坏的结果。

3.7 本章回顾

  • 运行中的 dsh = 启动时从有序层组装出的插件树：选 profile → 按 dsh.profile 叠 bundle → 套补丁 → Loader 按 inject 依赖挂载 → 启动断言。
  • profile 是 Harness home（$DSH_HOME，默认 ~/.dsh）里的命名组合：profiles/<name>/ 下 package.json（dsh.profile bundle 顺序表 + 插件依赖）和 cordis.patch.yml。web、headless 是随产品发行的模板，首次使用自动初始化；其他 profile 用 dsh plugin 创建。
  • bundle = Cordis 配置行 + 所挂代码的发行格式，package.json 的 dsh.bundle 字段指向补丁文件；它插入的行仍可被上层改写。
  • dsh-base 是每个 profile 的第一层：模型适配器、默认模型、工具、持久化、沙箱与审批策略、settings、credentials、遥测。dsh-web-app 加浏览器应用；dsh-headless 加一次性 runner、无服务器。
  • 层序：空 entry list → 各 bundle（profile 列出的顺序）→ profile 补丁 → home 级补丁 → --patch overlay。补丁按 id 定位，整行替换（不深合并，保留字段要重述）或 insert 新行；同一行后写的层赢。
  • dsh --profile web --dump-config 用与启动同一套算法离线打印组合结果；打印出的任何一行都能被你的补丁替换。补丁文件有 HMR 盯着：改了即重组，坏了保留上一个好树。
  • 失败即大声：无 bundle 声明、空/纯注释补丁文件、半份 shell 恢复配方……都在加载期报错，不留静默残缺。
常见误区
  • 以为补丁会深合并——id 补丁替换整行 config，保留的字段必须原样重述。
  • 改产品行为去编辑 packages/bundle/base/cordis.patch.yml——那是发行物；你的改写属于 profile / home 补丁层，用层序赢它。
  • 直接启动一个没创建过的 profile 名字——只有 web、headless 自动初始化，其余要先 dsh plugin。
  • 以为 --dump-config 会启动服务——它纯离线组合打印，一个进程都不起。
  • 补丁 id 拼错后不看 stderr——命中不了任何行的补丁是警告不是报错，树照常启动，静默缺少你以为的改写。
  • 想禁用一层补丁就把 cordis.patch.yml 清空——空文件/纯注释会抛错；写 [] 才是显式禁用。
