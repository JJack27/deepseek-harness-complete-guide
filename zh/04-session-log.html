Session Log：事件溯源的真相源

这是全书最重的一章。dsh 对「一次 agent 对话是什么」的全部回答，都压缩在 packages/core/session 这一个包里：一条 append-only 的 SessionEvent 日志。模型看到的历史、UI 显示的转录、崩溃后的恢复、 从中间分叉的新会话、遥测导出——全部是同一条事件流的投影。读完本章， 你应该能把「dsh 为什么这样存对话」讲给任何人听。

学完本章你能够
  • 解释事件溯源取向：dsh 不存「对话的当前状态」，只追加「发生过的事实」，以及为什么这让 fork/resume/转录/遥测全部从同一条流推导
  • 读懂一条 SessionEvent 的信封字段与完整事件词汇表，包括插件如何用 declaration merging 扩展 SessionEventMap
  • 描述 deriveMessages() 的投影规则，尤其是 assistant/chunk 与 assistant/message 的分工
  • 把「model-visible ⟺ logged」不变量应用到一个新需求上：判断该加会话事件还是该走别的通道
  • 说出 SessionHeader、session/end-seed、fork() 边界和 repair.ts 各自解决什么问题

4.1 不存状态，只存事实

想象你要记录一次 agent 对话。最直觉的做法是维护一个「当前状态」： 一个消息数组，模型每回复一次就往里 push 一条，需要改历史时就地修改。 这个做法的问题不在写，而在读——状态只能回答「现在是什么」， 回答不了「怎么变成这样的」。你想从第 3 轮分叉重试、想回放当时的流式输出、 想统计每一步的 token 消耗、想在崩溃后恢复现场，每一种需求都要求你 额外记录一份「演化过程」，于是真相散落成好几份互相竞争的副本。

dsh 的选择反过来：只追加发生过的事实，不存任何当前状态。 一次对话就是一个 Session，它的全部内容是一条只增不改的 SessionEvent 日志（append-only log）。用户发了一条消息，是一个事实； 模型吐了一个流式分片，是一个事实；一次工具调用和它的结果、一个 turn 的开始与结束， 都是事实。任何「当前状态」——最典型的就是模型历史——都是从这条日志推导出来的投影， 推导函数是纯的，随时可以重跑。

这就是「会话真相只有一份」的含义：

  • resume（进程重启后继续会话）：把持久化的事件流重新灌回内存，投影照旧成立；
  • fork（从某个历史时刻分叉出新会话）：取事件流的一个稳定前缀做种子；
  • 转录（UI 回放）：按事件顺序渲染，连打字机般的流式过程都能逐 token 重放；
  • 遥测：消费同一条流的投影；
  • 持久化：把流原样落盘，没有第二种序列化格式要维护。

载体是 ctx.sessions（SessionStore，一个 Cordis 服务）： 它持有当前进程内所有活会话的注册表；每个 Session 对象内部是一条 SessionEvent[] 日志加上几个投影缓存。注意分工——内存日志是活真相， 落盘是插件的事：持久化插件订阅 session/event 广播、 在 session/flush 检查点排空缓冲。整条持久化接缝是下一章的主角。

源码位置

packages/core/session/src/index.ts（Session 类与 SessionStore）、types.ts（事件词汇与信封类型）、 surface.ts（surface 投影）、repair.ts（崩溃修复）、 preparation.ts（发布前准备）。文档在 docs/subsystems/session.md 与 docs/architecture.md 的 Session log 一节。

4.2 SessionEvent：一条日志长什么样

每条事件是一个可判别联合（discriminated union over type）的成员， 信封字段固定： 

type SessionEvent<T extends SessionEventType = SessionEventType> = {
  type: T            // 事件类型，switch 的判别标签
  seq: number        // 会话内单调序号，恒等于它之前的事件数
  time: number       // Unix epoch 毫秒
  data: SessionEventMap[T]  // 类型化载荷，纯 JSON
  ignorable?: true   // 读者不认识 type 时可安全跳过的标记
}

两个契约值得刻在脑子里：

  • seq = log.length 连续性契约。事件序号从 0 开始严格连续， 事件在日志里的下标就是它自己的 seq。这条契约是整个系统的地基： 持久化后端可以逐行落盘、崩溃后可以判断「截断到哪」，都靠它。 连 assistant/chunk 这种高频事件也不允许被过滤掉—— 一旦丢弃，seq 就出现空洞。
  • 载荷必须是无损 JSON。Session.append() 在入口就做一次 递归校验加快照：BigInt、函数、undefined、循环引用、Date、 Map 这类值当场抛错，坏事件永远进不了日志， 而不是等到落盘时才失败。通过校验的数据被深冻结（deep freeze）—— 事件一旦入日志，任何代码都无法改写既成事实。

核心事件词汇

SessionEventMap 声明了全部事件类型的载荷。核心成员（你在任何会话里 都会反复见到的）：

事件类型载荷要点角色
turn/start / turn/end{ turn }；end 附带 TurnEndReasonturn 边界。一个 turn 是「零或多个 step」的外壳
step/start / step/end{ turn, step }step 边界。一个 step = 一次模型调用 + 它请求的工具执行
user/message完整的 UserMessage进入模型可见表面的用户侧消息：人类提问、agent.inject() 注入的上下文、goal 续轮，source 区分三者
assistant/chunk{ turn, step, chunk }原始流式分片，逐 token 回放保真
assistant/message{ turn, step, message, usage? }组装完成的 assistant 消息，推导历史用它；usage 与消息同行
tool/call{ turn, step, callId, name, arguments }模型请求的工具调用，arguments 是模型原样的未解析 JSON 字符串
tool/result{ turn, step, message, error?, meta? }工具调用的模型可见结果；meta 是工具私有的展示数据（必须可 JSON 序列化）
request/header{ header: EpochHeader, reason }下一次请求的完整信封：调用配置 + 渲染后的 system prompt + 工具 schema。log-only
request/context解析到的路由与容量元数据log-only，路由或容量变化时才记录
session/end-seed空载荷构造种子结束的边界标记（见 4.6）

「step 里模型到底看到了什么配置」由 request/header 回答： 每个循环实例的第一个请求记一张完整快照（reason: 'initial' 或 'resume'），之后配置变了再记一张（'change'）。 最新一张快照就能重建请求信封——每次对话请求都是日志的纯函数， 这是 reconstructability 的另一半（4.5 节）。

词汇是可合并扩展的

SessionEventMap 不是封闭枚举。插件通过 declaration merging 声明自己的事件类型——比如 compaction 接缝加的 compaction/start / compaction/end，agent 包加的 agent/inbox/spliced： 

// 某插件内：向会话词汇表合并一个新事件类型
declare module '@deepseek-ai/dsh-session/types' {
  interface SessionEventMap {
    'my-plugin/notice': { text: string }
  }
}

合并之后，session.append('my-plugin/notice', { text }) 就是类型安全的。 这些插件事件默认是 log-only：它们是可回放的事实记录， 不携带 surface 元数据、不进模型历史。

扩展性立刻引出一个读者问题：一个旧版 dsh 读到新版插件写的事件怎么办？ 答案是默认 required-on-read：遇到不认识的 type 且信封上 没有 ignorable: true 标记，读取方必须拒绝重建会话，而不是静默丢事件—— 一个不认识的必需事件可能改变整条日志其余部分的读法。写方只有在事件 「纯粹是信息性的、丢了也不影响重建」时才标 ignorable。 这个默认值的取向值得体会：忘打标记的后果是拒绝（麻烦但不伤数据）， 而不是静默恢复出一个被掏空的会话（伤数据）。 本仓库构建里全部已知类型由生成器产出到 known-event-types.ts 的 KNOWN_SESSION_EVENT_TYPES 集合， 持久化读取路径用它做这份判定。

4.3 追加路径：append、广播与不变量

Session.append(type, data, ...opts) 是日志唯一的人口。它做的事， 按顺序：

  1. 对 data 与 surface 元数据各做一次无损 JSON 校验 + 快照，不过就抛——日志入口即校验入口；
  2. 构造事件对象（seq = log.length、time = Date.now()）并深冻结；
  3. 校验 surface 转换合法性（4.4 节）；
  4. 解析 session/event 监听器快照；
  5. push 进日志——此刻追加已提交；
  6. 逐个调用监听器，每个监听器的失败只记日志、不影响返回值，也不挡住后续监听器。

注意提交与通知的顺序：事件先入日志，监听器后跑。追加是同步的、 热路径上不碰 I/O——持久化插件在自己的缓冲里异步攒批（下一章展开）。 观察者挂了也不能让已提交的事实消失，这就是「contained observer」语义。

日志事件与 Cordis 事件的边界在这里最容易混淆，值得单独说清： SessionEvent 是日志条目，不是 Cordis 事件。 一条日志事件抵达监听器，走的是唯一的 Cordis emit 通道 session/event， 载荷是 (session, event)。围绕会话生命周期的 Cordis 事件一共四个：

Cordis 事件模式语义
session/createdemit会话发布完成。同步抛出可以否决发布并回滚
session/disposedemit已发布的会话离开 store（含发布回滚的配对通知）
session/eventemit提交后、即发即忘的追加流。持久化、遥测、投影都挂在这里
session/flushparallel被 await 的持久性检查点：所有监听器并行跑完并等待，无 waterfall 否决

图 4-1 是本章的心智图。特别留意右下角：模型历史和遥测、UI 回放地位相同， 都只是这条流的消费者。不存在一份「权威消息数组」让别的数据去同步。

4.4 deriveMessages()：从日志投影模型历史

session.deriveMessages() 是把事件日志折叠成 Message[]（模型请求 的 messages 字段）的纯投影。它不直接扫全部事件，而是沿着一条由 surface 元数据维护的有序表面（surface）走：只有三种 「消息生产事件」（SurfaceEventType）能上表面—— user/message、assistant/message、tool/result—— 而它们每次 append 时都必须声明 surfaceOp（怎么加入表面）， 编译器在调用点强制非表面类型（如 turn/start、assistant/chunk） 传不了这个参数。 

// 表面事件的追加必须声明 surfaceOp；普通路径是 append
session.append('user/message', message, {
  surfaceOp: 'append',
  sourceEventSeqs: [],  // 可选：引用哪些更早的事件
})

surfaceOp 有两种：

  • 'append'：加到表面尾部。用户消息、assistant 消息、工具结果的常规路径。
  • { op: 'replace', start, end }：把表面上 start 到 end （闭区间）的节点遮蔽掉，用本事件顶替。这是 compaction（上下文压缩） 的机制：摘要事件替换被摘要的那段历史，推导历史里旧节点就此消失， 但原始事件仍留在日志里——人类转录读的是 append 起源的原始事件， 模型读的是压缩后的表面，两不相扰。

逐节点的投影规则（deriveEventMessage，公开的纯函数，外部重建方与 核心用同一套规则，不可能各推各的）：

  • user/message → 一条 user 消息，content 原样投影（人类提问、注入上下文、goal 续轮一律如此，source 区分来源）；
  • assistant/message → 一条 assistant 消息；空 content 的 assistant/message 被跳过——max-tokens 截断、没产出内容的 step 仍会记一条 assistant/message 来承载 usage 与 provider/model，但空内容不该进模型转录；
  • tool/result → 一条 user 角色消息，内含 tool-result block；
  • 其余一切（turn/*、step/*、插件 log-only 事件）是结构性记录，不投影成消息。

chunk 与 message 的分工（常考细节）

一个 step 的模型输出在日志里出现两次：流式期间每个分片一条 assistant/chunk，流结束后一条组装好的 assistant/message。 分工是：

  • assistant/chunk：回放保真与计量。UI 重放打字机效果、 逐 token 时间戳靠它；token 计量也优先读每 step 的 usage 类型 chunk， 失败的请求没有 assistant 消息，它的 usage chunk 就是唯一的计量记录。
  • assistant/message：推导权威。deriveMessages() 只认它。原始 chunk 在推导中被跳过——组装消息才是权威副本。 它可以带 sourceEventSeqs 反向引用构成它的那些 chunk。

所以「删掉 chunk 省空间」听起来诱人，却直接违反 seq 连续性契约—— 持久层只能换编码（JSONL 后端的 packed chunk row 就是这种编码，见下一章）， 不能删事件。投影本身有缓存：每个表面节点只投影一次，之后的调用只处理新节点， 是 O(新节点)；一次 replace 改写表面会让缓存整体重建 （replaceGeneration 代数控制）。返回的数组每次是新快照， 里面的 Message 对象与日志共享且深冻结——想通过投影改历史， 在 JavaScript 层面就不可表示。

4.5 核心不变量：model-visible ⟺ logged

现在可以把全仓最重要的会话规则说完整了：

凡是进入模型请求的内容，必须能从会话日志重建（model-visible means logged）。 一条运行时不变量（invariant 插件）会断言它。因此： 新增一种模型可见输入，必然意味着新增一个会话事件—— 扩展 SessionEventMap，并让消费路径从日志渲染。

这条规则把「能不能被恢复」从祈祷变成了机械检查。想想它覆盖的面：

  • 消息历史：deriveMessages() 只从日志推导（4.4 节）。
  • 请求信封：system prompt、工具 schema、调用配置由 request/header 快照承载，最新一张即可重建，请求是日志的纯函数。
  • 组合本身：agent 由哪个 preset 组装决定了模型看到的工具和 prompt， 所以 preset 切换要落一条 agent-preset/selected 会话事件—— 否则 resume 后重建出的组合和产生这段历史的组合不一致， 模型会面对一段自己「无法行动」的历史。
  • 注入上下文：agent.inject() 塞进下一次请求的文件变更通知、 skill 内容等，落地为 user/message 事件（source 标明来源）， 而不是请求时的旁路魔法。

反过来说，不需要在 resume 后重建的运行时细节——比如一次工具执行的 展示元数据之外的内部过程——不必也不应该发明事件。判断口诀： 「模型下次请求还能不能感知到它？」能，就必须可从日志重建；不能，就别污染词汇表。 仓库规约把这条写成硬约束（AGENTS.md：a new model-visible input requires a session event）， 第 23 章讲门禁时你还会遇到它。

一个推论值得单独点名：拦截点里改请求配置是允许的——agent/request waterfall 可以替换 LlmCallConfig——但改了之后这条 header 会被记进日志 （下一个 request/header 快照），下次请求从日志比对。可以改事实， 不可以绕过记账。

4.6 SessionHeader 与 session/end-seed

有意留在日志之外的一类信息：会话的创建元数据。 SessionHeader 是一个深冻结的小对象，经 session.header 读取：

字段含义
version磁盘格式版本，来自 SESSION_FORMAT_VERSION（当前为 0）。持久化后端加载时拒绝任何其他版本——不迁移
id / createdAt会话身份与创建时间
cwd创建时的绝对工作目录（必须是绝对路径；存储后端按它分目录）
parentSession种子谱系：这个会话从哪个会话 fork/resume 而来
seedLength通过种子继承的前缀长度，让 resume/fork 区分「父母的历史」与「自己的工作」
origin / delegationDepth子代理分类与委托深度（递归预算要熬过重启，所以持久化）
agentPreset组装本会话 agent 的 preset id（4.5 节讲过它为什么必须持久）

为什么放日志外？因为它们是存储关注点，不是可回放的对话状态： 不产生消息、不参与推导，也不该占用 seq。谱系字段是纯数据—— 「我是从谁分出来的」不带来任何运行时可见性，第 6 章讲 scope 时会回到这点。

session/end-seed：种子边界的持久投影

resume 或 fork 出来的会话，构造时带一个事件种子。种子事件与活写入在字节上 无法区分，于是 Session 的构造函数在种子末尾追加一条空载荷的 session/end-seed 事件，作为「这个生命周期从哪开始写」的 边界。三件事容易考倒人：

  • 它是 firstLiveSeq（内存对象上的字段）的持久投影： 手里拿对象读字段，手里只有磁盘字节读事件。
  • 读最后一条 session/end-seed，不要假设它在 firstLiveSeq 位置——一个会话被反复打开而中间没干活， 不会每次都补一条标记。
  • 构造函数是唯一合法写入者。插件自己 append 一条， 会把之前的活写入静默错认成种子历史。所以核心的不变量伴随件刻意不管它—— 写错属于「误用保留给作者的权限」。

4.7 fork：从任意稳定边界分叉

事件溯源的回报在这一节兑现。分叉一个会话不需要拷贝任何「状态」， 只需要取事件流的一个前缀做种子： 

// 从 source 的一个稳定前缀长出一个活子会话
const child = ctx.sessions.fork(source, boundary?, childSessionId?)

语义逐个参数说：

  • source：活 Session 对象或活 SessionId。 传一个已不在 store 里的对象会得到 SESSION_NOT_LIVE。
  • boundary：包含（inclusive）的源事件 seq； 省略表示「当前最后一条事件」。
  • childSessionId：可选子会话 id，省略由 store 分配。

子会话自动带上谱系元数据：parentSession、seedLength（= 种子长度）、 继承的 cwd。拒绝情形是类型化的（SessionForkError 携带错误码）：

错误码何时抛
SESSION_NOT_FOUND / SESSION_NOT_LIVE源 id 不在 store / 源对象不是 store 的活实例
SESSION_ALREADY_EXISTS请求的子 id 已被占用
INVALID_BOUNDARYboundary 不是非负安全整数，或指向不存在/不连续的 seq
OPEN_TURN选中的前缀结束在一个未闭合的 turn 里

OPEN_TURN 这条值得停下来想。选中的前缀允许停在 turn 之间的 某条独立 log-only 事件上（比如一条 turn/end 之后、下一条 turn/start 之前），但不允许停在开着的 turn 中间—— 那样种子就带着悬空的工具调用与未闭合的边界，恢复出的转录对 provider 不合法。 API 的选择是拒绝而不是悄悄裁剪：要分叉就明说一个稳定边界。 （工具中途委托给子代理的 dsh-subagent-fork-in-process 场景保留自己的 完成前缀裁剪，因为父 turn 通常还开着——那是另一个包的显式策略。）

4.8 崩溃修复与发布前准备

日志世界的最后一组机制处理两个边角：进程崩在 turn 中间怎么办， 以及一个从磁盘重建的会话在被发布前归谁管。

repair.ts：收口，而不是截断

进程崩溃时，磁盘上的日志可能停在半截：一个 turn/start 没等到它的 turn/end，assistant 消息里的工具调用没等到 tool/result。 dsh 的修复语义（interruptedTurnClosers(events)，纯函数、确定性）是：

  1. 扫日志，追踪开着的 turn、开着的 step、以及悬空的工具调用 （assistant 消息的 tool-call block 出现了、但没有配对的 tool/result）；
  2. 为每个悬空调用合成一条error 的 tool/result，错误码区分两种情况： TOOL_NOT_STARTED（还没记录为已开始，重试安全）与 TOOL_OUTCOME_UNKNOWN（已开始但结果未落盘，结果未知—— 合成文本明确告诫模型「先验证外部状态再决定是否重试」）；
  3. 补一条 step/end（如有开着的 step）、一条 turn/end，理由是 { kind: 'interrupted' }；
  4. 合成事件的 seq 接续日志，time 复用最后一条真实事件的时间戳。

关键取舍：崩溃前已落盘的事件一条不动。长任务的一个大 turn 可能装着巨量工具输出，截断等于销毁工作成果；收口只是补上边界，让恢复出的 转录对 provider 合法。顺带一提，interrupted 是唯一一个 循环永远不会发出的 TurnEndReason——它只属于崩溃恢复 （持久化后端在加载时调用这套修复，下一章见）。日志本身是平衡的（没有开着的 turn） 就什么都不补。

preparation.ts：发布前的所有权

从磁盘重建的会话在被挂进 store、对观察者发布之前，存在一个窗口： 它是「谁的东西」？SessionPreparation 回答这个问题—— 它包住一个确切的未发布 Session，实现 Disposable （using 语法可直接用）：发布成功或回滚时， [Symbol.dispose]() 恰好一次地释放提供方持有的状态 （可选的 release 回调决定是归还缓存还是丢弃）。 这让 resume 路径能把「读取、验证、冻结、构造会话」这套昂贵工作 在多次冷读与最终 resume 之间共享——细节属于持久化协调器，下一章展开。

4.9 本章回顾

  • dsh 只追加事实，不存状态：Session 是一条 append-only 的 SessionEvent 日志，fork/resume/转录/遥测/持久化全部是同一条流的投影，会话真相只有一份。
  • 事件信封是 type/seq/time/data（surface 事件另带 surfaceOp/sourceEventSeqs），seq = log.length 严格连续，载荷必须无损 JSON 且入日志即深冻结。
  • 词汇表由 SessionEventMap 声明、插件可 declaration-merge 扩展；未知事件默认 required-on-read，除非信封带 ignorable: true。
  • append 同步校验、push 即提交、再广播 session/event；持久化走 session/flush 检查点。
  • deriveMessages() 沿 surfaceOp 维护的有序表面投影模型历史；assistant/chunk 保回放与计量、不进推导，assistant/message 是推导权威；compaction 用 replace 遮蔽区间。
  • model-visible ⟺ logged：进入模型请求的一切必须可从日志重建，运行时不变量断言它；新模型可见输入必须新增会话事件。
  • SessionHeader（版本、cwd、谱系、preset）是日志外的存储元数据；session/end-seed 是种子边界的持久投影，构造函数是唯一合法写入者。
  • fork(source, boundary?, childSessionId?) 取稳定前缀做种子，拒绝停在开着的 turn（OPEN_TURN）。
  • 崩溃修复收口不截断：悬空工具调用补 error 结果（TOOL_NOT_STARTED / TOOL_OUTCOME_UNKNOWN），再补 step/end 与 turn/end { interrupted }；SessionPreparation 持有未发布会话直至发布或回滚。
常见误区
  • 把 SessionEvent 当 Cordis 事件理解。日志条目不是事件总线的成员；它只通过唯一的 session/event emit 抵达监听器。
  • 以为 assistant/chunk 参与模型历史推导。推导只认 assistant/message；chunk 服务于回放与 token 计量，但持久层一条都不能丢（seq 连续性）。
  • 想给模型塞新输入时走「请求时旁路」而不是新增事件。违反 model-visible ⟺ logged，运行时不变量会当场拒绝。
  • 给所有新事件打 ignorable: true 求省事。标记只属于丢了不影响重建的纯信息性记录；默认 required-on-read 是有意的安全取向。
  • 把 session/end-seed 当「会话开始」标记，或假设它总在 firstLiveSeq 处。它是种子结束的边界，读最后一条。
