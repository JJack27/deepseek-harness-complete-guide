贡献地图与专家导航

最后一章做两件事：把「在这个仓库里留下一次改动」需要的流程地图补齐——Agent Notes 决策 账本、双语文档契约、PR 标签与栈规则；然后把全书二十五章拼成一张导航图，让「我想改 X， 先读 Y」变成一次查表。读完这章，你就从「读懂 dsh 的人」变成「能在 dsh 里开工的人」。 这是收官章，图要慢慢看。

学习目标
  • 说出 Agent Note 的生命周期目录（proposed / implemented / rejected / archived）、六个 class 与「非平凡改动同 PR 必带 Note」的规则。
  • 解释 archived 树的冻结契约：永不编辑、不当现权威，由 verify-archived-agent-notes 执行。
  • 描述双语文档的配对结构（*.md + *.zh.md + *.i18n.yaml）与「一个事实一个家」的层级税。
  • 复述 PR 规则：一个 kind/*、全部 material area/*、原生 Issue Type、栈式 PR 的 --force-with-lease 纪律。
  • 用全书导航图把「我想改 X」定位到「先读 Y」的包、事件或注册表。

25.1 Agent Notes：决策的账本

.agents/notes/ 只住一种文档：记录一个影响代码库的决策——为什么这么定、 放弃了什么——这些代码和常规文档带不动的东西。路径本身就是元数据： {lifecycle}/{class}/yyyy-mm-dd-topic-title.md。生命周期四个目录： proposed/（实现前评审的提案）、implemented/（已发布的决策，且 随代码保持现势——代码挪了文件、改了默认值，同一改动里要把 Note 的事实更新）、 rejected/（被否决的提案，只在其理由仍能挡住一个有诱惑力的错误时保留，否则三元组 整体删除）、archived/（冻结的历史，见下）。class 是封闭集，由 scripts/agent-note-tree.ts 与分类门禁执行：feature / bug-fix / simplification / architecture / process / testing ——分界线是「architecture 管我们发布的源码，process 管围着代码的工具与流程」，而 refactor 被刻意排除（与 simplification 重叠）。

写作时机是一条硬规则：每个非平凡改动必须在同一个 PR 里新增或更新至少一条 Agent Note。非平凡指改了行为、架构、跨文件/包的契约、流程或工具、测试策略、盘上/线上/配置 格式，或任何维护者可能重开的决策。更新已拥有该决策的 Note 即可满足规则，不要造重复；纯机械/ 局部的编辑豁免。文件格式由 verify-agent-note-format（doc-sync 的一部分）执行：头两 行精确是 # Agent Note: <title> 与 Status: <status> （proposed / implemented / rejected — 一行理由，状态必须与所在目录一致）；正文以 ## Problem 开篇；implemented 骨架是 Problem → Decision → … → Alternatives considered → Consequences，且禁止出现 Proposal/Plan/Acceptance criteria 这类规格腔。 每条 Note 必须有 ## Alternatives considered：没记录「打败了什么」 的决策是在邀请重审——这正是 Agent Notes 存在要防止的失败。Note 之间的互链用相对 markdown 链接，绝不裸写编号，所以链接可被机械校验、搬目录也不死。

archived 是冻结的

一条 implemented Note 在决策已完整落地、理由 unlikely 再指导未来工作时归档：整个英/中/sidecar 三元组搬进 archived/{class}/，加一行 Archived: YYYY-MM-DD，此后 永不编辑、翻译、重排、更新、移动或删除，也不当作当前行为的权威。文档门禁跳过 归档源；活跃文档仍可有意引用它作为历史。执行者是 verify-archived-agent-notes：封闭 class 树、完整三元组、归档元数据、sidecar 哈希与 append-only 冻结清单。归档用校准过的 dsh-archive-agent-notes 工作流判断，不数字数不看年龄。

25.2 双语文档与 doc-sync

这个仓库的文档是英中双份平行：*.md 与 *.zh.md 逐节镜像，旁边一份 *.i18n.yaml sidecar 记录配对状态；配对契约由 docs/i18n/README.md 拥有， verify-translation-pairing 校验。日常双语工作按 docs/AGENTS.md 走：术语引导、单遍 active-agent 翻译重录 sidecar；只有显式用户调用才跑 dsh-translate-docs 技能。Git 侧还有配对 merge driver（pre-commit / pre-merge-commit 校验暂存记录）。

docs/AGENTS.md 的层级税只有一句：一个事实一个家。根 AGENTS.md 只放常备命令 （每条一到三行、链去它的家）；architecture.md 是有序地图；subsystems/ 一子系统一页类型参考； Agent Notes 放决策理由；postmortem/ 是唯一允许战史叙事的层；cookbook/ 放带编号验证步骤的 how-to；包 README 是每包契约（含 Model Experience）；生成参考（tool-catalog、config-catalog、 module-graph 等）从源码再生、新鲜度受门禁。写作规则里最常咬人的四条：文档写当前状态 不写变更史（避免「以前/现在/不再」，故事进 Note 或 postmortem）；一段一个 物理行（verify-md-wrap）；围栏 ts 块必须可编译（doc-typecheck），贴类型 用 ts type-equiv 并登记 manifest 防漂移；跨引用用相对 markdown 链接 （verify-md-links）。字数预算由 verify-doc-budgets 把守，红了先搬迁、再压缩、 实在不够才提 manifest 里的天花板。这一整套连同目录再生、JSDoc、Agent Note 校验，都聚合在 pnpm run doc-sync（第 23 章）。

文档网站是投影不是家：website/ 只拥有 VitePress 配置、呈现资产与发布清单 （website/docs.ts 把 docs/ 各层源映射进两个 locale 的路由树），Markdown 留在 所属层，投影写进被忽略的 website/.generated/——永不手编。改这个子树跑 pnpm docs:check。

25.3 PR 规则、标签与栈

AGENTS.md 对 PR 历史的要求是「刻意选择」：独立改动拆开提交；修 bug 优先在 引入它的 PR 里修，而不是向前传播。独立 PR 与官方栈评审后可以 merge-forward 或 rebase； 改写历史用 --force-with-lease，远端动了就中止，绝不裸 --force；进行中的 merge-forward 在拿更新的 base 前先保存自己的 checkpoint （依据 .agents/notes/implemented/process/2026-08-02-native-github-stacks-and-optional-rebases.md， 配套技能 dsh-merging-stacked-prs）。推送前按 dsh-pre-push-checks 技能选最小检查集 （第 23 章的证据面对应）；gh stack sync 之后立即验证，检查不过不合并。

标签税：每个 PR 恰好一个 kind/*（改动种类），所有实质涉及的 area/*， 加上原生 GitHub Issue Type——分类学由 .agents/notes/implemented/process/2026-08-08-unified-github-label-taxonomy.md 拥有。

先读 CONTRIBUTING.md：外部 PR 的当前状态

仓库根的 CONTRIBUTING.md 写明：DeepSeek Harness 仍处早期、活跃开发中，目前不接受外部 pull request。参与方式是生态式的——在 GitHub Discussions 报问题/投票；写让你兴奋的 插件并给 GitHub 项目挂 dsh-plugin topic；写博客与 how-to；回答社区问题。仓库的 立场是：官方仓库的包并不天然比社区包重要——这个仓库更像一个想法、一个官方展示、一个灵感来源。 所以上一节与本章的 PR 规则，对你意味着两层用法：在你的检出/fork 里按同一套纪律走完整流程 （最小检查集、同 PR 的 Note 与快照），以及用 out-of-tree 插件（第 24 章）参与生态。

25.4 全书导航图

二十五章叠成五层，下层是上层的地基：没有 Cordis 心智读不懂事件流，没有事件流读不懂 loop， 没有 loop 读不懂工具管道，没有 seam 读不懂执行世界的整体搬迁，没有前四部分读不懂测试与门禁 在保护什么。右边那张速查表把最常见的「我想改 X」映射到入口——注意每一行都指向 扩展点、事件或 seam，没有一行指向 agent-loop 本体。

把速查表读成一句话

行为上扩展点、数据上事件流、实现上 provider seam：想改的如果不是这三者之一，先回 docs/architecture.md 找到它属于谁——「找不到入口」几乎总是「读错了层」的症状。

25.5 毕业路线

读完全书，按这个顺序把知识压实成肌肉记忆：

步做什么为什么
1通读 docs/architecture.md把 25 章压回一份有序地图：组合、核心包、loop、seam、扩展点——改 packages/ 前的必读。
2读 docs/capability-seams.md三角色模式的一次集中复习，之后每个新能力都按它定位。
3通读 packages/core/agent-loop/src/agent.ts 全文亲眼看见第 6-7 章的 turn/step、inbox 准入与全部拦截点在代码里的样子。
4跑一遍 pnpm run test:snapshot无密钥走完整个组装转录回放；看它绿，感受金标准体系。
5提你的第一个 PR从第 24 章三遍实战里挑一个小改动（或一个新插件），按第 23 章选最小检查集，带 Note 与快照。若走外部路线：当前 CONTRIBUTING.md 不收外部 PR——那就 fork 里走完整流程，或以 dsh-plugin 生态参与。

最后一条提醒：你此刻读到的所有事实都以仓库为准。门禁清单会变、包会挪、事件会长—— 真正不变的是这本书教的定位方法：找到事实的家，读它，然后改它。

25.6 本章回顾

  • Agent Notes 是决策账本：proposed/implemented/rejected/archived × 六个 class；非平凡改动同 PR 必带；## Alternatives considered 强制；implemented 保持现势、archived 永久冻结不当权威。
  • 双语文档 = *.md + *.zh.md + *.i18n.yaml 配对；一个事实一个家；当前状态不写变更史；一段一个物理行；doc-sync 聚合全部文档门禁；只有显式调用才跑 dsh-translate-docs；website/ 只是投影。
  • PR：独立改动拆开、修引入 PR；一个 kind/* + 全部 material area/* + 原生 Issue Type；栈可 merge-forward/rebase，改写只用 --force-with-lease；推送前 dsh-pre-push-checks 选最小集。
  • CONTRIBUTING.md 当前不收外部 PR：参与方式是 Discussions、博客、与挂 dsh-plugin topic 的插件生态。
  • 导航口诀：行为上扩展点、数据上事件流、实现上 provider seam；改完按证据面选检查、同 PR 补 keyless 快照、带 Agent Note。
  • 毕业路线：architecture.md → capability-seams.md → agent.ts 全文 → test:snapshot → 第一个 PR。
常见误区
  • 把 archived Note 当现权威引用——它是冻结历史；当前行为查 implemented Note 与源码。
  • 非平凡 PR 不带 Agent Note——硬规则；更新已拥有的 Note 即可，别造重复。
  • 给 implemented Note 写「应该/迁移计划/验收清单」——规格腔被格式门禁拒绝，它只写已发布的事实。
  • 文档里写「以前/现在/不再」——变更史进 Note 与 postmortem，当前文档只写当前机制。
  • 栈式 PR 用裸 --force——只用 --force-with-lease，远端动了就中止。
  • 以为外部可以直接投 PR——先读 CONTRIBUTING.md；当前窗口是 Discussions 与 dsh-plugin 生态。
  • 改持久化格式时忘了 required-on-read 与 SESSION_FORMAT_VERSION 的结构变化规则——先回第 4 章与 SessionEventMap。
